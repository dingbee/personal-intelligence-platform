# UX-14.4 Phase 2 — Spreadsheet Artifact & Structured Export Discovery

**Status: design only.** No code, migrations, or UI changes were made to produce this document, per explicit instruction. Constraints held: no collaboration, no permissions, no workspace sharing, no schema changes unless required, reuse the Phase 1 artifact metadata foundation, solve structured formulas/tables first, design the export pipeline before implementing multiple formats.

Builds on `docs/ux-14.4-knowledge-artifact-architecture.md` (blueprint) and its Phase 1 implementation record (`ArtifactKind` registry, `detectArtifactKind`, `generation_metadata.artifactKind` tagging — all shipped in `4dd5af1`).

## 1. Audit: What Already Exists, Grounded in Code

- **Read-side spreadsheet handling already exists and is the right model to mirror.** `processing/extractors/spreadsheet.ts` reads uploaded workbooks with the already-installed `xlsx` (SheetJS) package. Critically: `formulaColumnIndexes()` reads a cell's formula directly off the raw `WorkSheet` object via `cell.f` — SheetJS's own convention for "this cell holds a formula string." Writing an artifact cell is the exact mirror of this: set `{ f: '<formula string>' }` on a `WorkSheet` before calling `XLSX.writeFile`. Same library, same field, both directions — no new formula representation to invent.
- **The "ask the model for JSON, parse it leniently" pattern already exists**, twice: `parseKnowledgeExtractionResponse.ts`'s `extractJsonArray()` (strips markdown fences, locates the outermost `[...]`, `JSON.parse`s it) backs `parseConceptsResponse`/`parseEntitiesResponse`, and the codebase comment references the same convention for flashcards. This is the established, low-risk way to get structured output from a capability that still runs through `runCapability`/`streamChatCompletion` (free-text streaming, no JSON response-format mode) — a spreadsheet-generation capability does not need new AI-runtime plumbing, it needs a new prompt template plus an object-shaped sibling of `extractJsonArray`.
- **The export precedent is `buildKnowledgeExportMarkdown()` + `knowledgeExportFilename()`** — pure, synchronous, client-side, no server round trip, no AI call. XLSX export should follow the identical shape: a pure function that takes an artifact payload and returns something downloadable, plus a filename builder, triggered from a button the same way Markdown export already is.
- **Phase 1's `generation_metadata.artifactKind` field is exactly where a `spreadsheet`/`formula` payload belongs too** — it's already a free-form JSONB field on `Note`, already read via `getArtifactKind()`, already proven safe to extend additively (Phase 1 added one key without a migration; this phase adds one more).
- **No structured-data generation capability exists yet.** `SheetAnalysis` (`processing/spreadsheet/types.ts`) is read-only analysis of an *uploaded* file — column stats, trends, anomalies. Nothing today asks the model to *produce* a new sheet's worth of cells from a conversation. This is the one genuinely new piece of AI-runtime surface this phase implies.

## 2. Spreadsheet Artifact Schema (no database change)

Stored inside the same `Note.generation_metadata` JSONB field Phase 1 already writes `artifactKind` into — **not** a new table, per the "no schema changes unless required" constraint and consistent with the original blueprint's own recommendation to defer a `payload`-bearing table until a real consumer needs one. This phase is that consumer's *design*, not yet the table itself, because the payload shape below hasn't been validated against real model output yet — locking a schema in before that would be exactly the premature architecture this initiative has consistently avoided.

```json
{
  "artifactKind": "spreadsheet",
  "artifactData": {
    "sheets": [
      {
        "name": "Occupancy Forecast",
        "columns": ["Month", "Available Rooms", "Sold Rooms", "Occupancy %"],
        "cells": [
          { "cell": "A2", "value": "January" },
          { "cell": "B2", "value": 744 },
          { "cell": "C2", "value": 520 },
          { "cell": "D2", "value": null, "formula": "C2/B2" }
        ]
      }
    ]
  }
}
```

- `value` is a plain literal (string/number/null) — matches `SheetAnalysis`'s own documented convention ("no Date objects, no functions, persisted verbatim into jsonb").
- `formula`, when present, is a bare formula string (no leading `=`) — written into the exported cell's `.f` field verbatim, exactly as SheetJS itself represents it on read. **Not evaluated client-side.** No formula engine is built or needed — Excel/Sheets/whatever opens the export computes it, the same way a human-typed `.xlsx` formula works today. This avoids the single biggest risk in this whole phase (a bug in a hand-rolled formula evaluator silently producing a wrong number in someone's revenue model) by simply not building one.
- `formula.ts`/`Formula Template` artifacts reuse the same `cells` shape but typically describe one representative row plus named `inputs` rather than a full sheet — deferred to its own pass once the Spreadsheet Model's shape is validated against real usage, per this document's own sequencing (§5).

## 3. The Spreadsheet Builder — Two Paths, Not One

The roadmap's own example ("Create a hotel occupancy forecast model" → a fully laid-out sheet with a real formula in `D2`) is **not** achievable by parsing prose after the fact — no amount of regex on "Occupancy = Rooms Sold / Available Rooms" reconstructs a cell grid. Two genuinely different mechanisms are needed, and conflating them would be the wrong abstraction:

**Path A — Deterministic table extraction (cheap, always-on).** When a response already contains a markdown table (the same `MARKDOWN_TABLE_PATTERN` `detectArtifactKind` already uses to classify `spreadsheet`), a pure parser converts it directly into the `cells` shape above — one cell per table cell, no formulas (prose tables don't carry per-cell formulas), `value` only. This is a natural sibling to `detectArtifactKind`, not a new subsystem: same file family (`src/modules/ai/artifacts/`), same "deterministic, not AI" rule. Covers the common case (the model already answered with a table) at zero marginal cost.

**Path B — A new capability for on-demand structured generation (the roadmap's actual example).** When a user explicitly asks for a spreadsheet/formula model — or picks "Spreadsheet Model" in Save As on a response that Path A couldn't structure — a new capability (`generate-spreadsheet-artifact`, registered the same way `generate-briefing` is) prompts the model to emit the schema in §2 as fenced JSON, parsed by a new `parseSpreadsheetArtifactResponse.ts` mirroring `extractJsonArray`'s exact convention (fence-stripping, brace-matching, `JSON.parse`, then field-by-field validation — reject/drop malformed cells rather than trusting the model's output verbatim, same defensiveness `parseConceptsResponse` already applies to `title`). This runs through the existing `runCapability`/`runWithFallback` path unchanged — **no new AI-runtime infrastructure**, just a new prompt template and a new parser, the same shape as every other capability this codebase already has.

Per this phase's own instruction ("solve structured formulas/tables first"), **Path A is the lower-risk, sequence-first piece** — it needs no new prompt template, no new capability registration, and directly upgrades every response that already contains a table (which the `spreadsheet` classification already fires on today). Path B is real, valuable, and explicitly the mechanism the roadmap's hero example needs, but it's a new AI-facing surface (a new prompt) and belongs in its own scoped, reviewed step rather than bundled into the same pass as Path A.

## 4. Export Pipeline

Format-agnostic dispatcher from day one, even though only XLSX ships first — so PDF/DOCX (Note/Briefing, per the original blueprint) and CSV slot in later without a redesign:

```
Artifact (Note + generation_metadata.artifactData)
        │
        ▼
exportArtifact(note, format: 'xlsx' | 'csv' | ...)
        │
        ├── 'xlsx' → buildSpreadsheetWorkbook(artifactData)  -- XLSX.utils.aoa_to_sheet / book_new,
        │            writing {v, f} per cell exactly as the read path already reads them
        │            → XLSX.writeFile — client-side, no server round trip
        │
        └── 'csv'  → (first sheet only; XLSX.utils.sheet_to_csv, already a one-liner once
                       the workbook above exists — effectively free once XLSX lands)
```

- **XLSX first**: zero new dependency (`xlsx` is already installed and already used for both read paths in this codebase), and it's the one format that can carry real formulas — `formula.trim() ? { f: formula } : { v: value }` per cell, direct mirror of `formulaColumnIndexes`'s read-side check.
- **CSV**: SheetJS gives this for free once a `WorkSheet` object exists (`sheet_to_csv`), so it costs almost nothing to add alongside XLSX rather than sequencing it separately — flattens formulas to their `value` field since CSV has no formula concept.
- **PDF/DOCX** (Note/Briefing export, from the original blueprint) are explicitly **not** designed here — no dependency exists for either, and they apply to a different artifact family (prose, not cells). Left as a separate, later design pass so this document doesn't scope-creep into two unrelated export problems.
- Entry point: a "Download" action on `NoteDetailPage` and `NoteCard`'s dropdown menu, gated on `getArtifactKind(note) === 'spreadsheet'` (and, once Formula Templates exist, `'formula'`) — same conditional-rendering pattern `ArtifactKindBadge` and the `NoteDetailPage` Knowledge Card block already established in Phase 1.

## 5. Recommended Sequencing (Phase 2 implementation, once authorized)

1. **Artifact payload schema on `generation_metadata`** (§2) — additive, no migration, land it alongside whichever consumer needs it first rather than speculatively.
2. **Path A: deterministic markdown-table → `cells` parser** — cheapest, no new AI surface, immediately useful for every response `detectArtifactKind` already classifies as `spreadsheet`.
3. **XLSX export button** wired to Path A's output — the first time a user can go from "NOVA answered with a table" to "a real spreadsheet file" with zero AI-runtime changes.
4. **CSV export** — near-free addition once (3) exists.
5. **Path B: `generate-spreadsheet-artifact` capability** — the on-demand formula-construction case (the roadmap's hero example). Sequenced last because it's the one genuinely new AI-facing surface in this phase, and should be reviewed as its own scoped step per this codebase's established discipline around prompt-template changes.
6. **Formula Template artifact kind** — once (5) exists and the `cells`/`formula` shape has been validated against real generated output, extract the "named inputs + one representative formula" variant.

## 6. On the Acceptance Harness Recommendation

Agreed on the reasoning: Phase 1 (Save As, badges, Knowledge Card rendering) was additive display/classification with no new state-changing user action; this phase's export step is the first place a user clicks something and gets a *file* — a genuinely different risk class from everything shipped in UX-14 so far, and boot-smoke-only verification (the pattern used since UX-14.2) is measurably weaker evidence for it.

Building the harness itself — a dedicated Supabase test project/branch, seed data, and Playwright flows against a real authenticated session — is a new-infrastructure decision with real cost and access implications (a new Supabase project or branch, credentials to manage, ongoing maintenance), not something to spin up unilaterally under a "Discovery" instruction whose explicit constraints were about spreadsheet/export design.

**Decision (recorded):** harness build is sequenced *after* Phase 2's implementation, not before or in parallel. Path A (deterministic table parsing) + XLSX/CSV export ship first under the same disclosed boot-smoke-only verification used since UX-14.2 — the harness lands before Path B (the `generate-spreadsheet-artifact` capability) or UX-14.5 collaboration, both of which carry materially higher risk (a new AI-facing prompt surface; a new authorization model) than a deterministic parser and a client-side file download.
