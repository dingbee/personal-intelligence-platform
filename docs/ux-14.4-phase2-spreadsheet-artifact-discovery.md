# UX-14.4 Phase 2 — Spreadsheet Artifact & Structured Export Discovery

**Status: design only.** No code, migrations, or UI changes were made to produce this document, per explicit instruction. Constraints held: no collaboration, no permissions, no workspace sharing, no schema changes unless required, reuse the Phase 1 artifact metadata foundation, solve structured formulas/tables first, design the export pipeline before implementing multiple formats.

Builds on `docs/ux-14.4-knowledge-artifact-architecture.md` (blueprint) and its Phase 1 implementation record (`ArtifactKind` registry, `detectArtifactKind`, `generation_metadata.artifactKind` tagging — all shipped in `4dd5af1`).

## 1. Audit: What Already Exists, Grounded in Code

- **Read-side spreadsheet handling already exists and is the right model to mirror.** `processing/extractors/spreadsheet.ts` reads uploaded workbooks with the already-installed `xlsx` (SheetJS) package. Critically: `formulaColumnIndexes()` reads a cell's formula directly off the raw `WorkSheet` object via `cell.f` — SheetJS's own convention for "this cell holds a formula string." Writing an artifact cell is the exact mirror of this: set `{ f: '<formula string>' }` on a `WorkSheet` before calling `XLSX.writeFile`. Same library, same field, both directions — no new formula representation to invent.
- **The "ask the model for JSON, parse it leniently" pattern already exists**, twice: `parseKnowledgeExtractionResponse.ts`'s `extractJsonArray()` (strips markdown fences, locates the outermost `[...]`, `JSON.parse`s it) backs `parseConceptsResponse`/`parseEntitiesResponse`, and the codebase comment references the same convention for flashcards. This is the established, low-risk way to get structured output from a capability that still runs through `runCapability`/`streamChatCompletion` (free-text streaming, no JSON response-format mode) — a spreadsheet-generation capability does not need new AI-runtime plumbing, it needs a new prompt template plus an object-shaped sibling of `extractJsonArray`.
- **The export precedent is `buildKnowledgeExportMarkdown()` + `knowledgeExportFilename()`** — pure, synchronous, client-side, no server round trip, no AI call. XLSX export should follow the identical shape: a pure function that takes an artifact payload and returns something downloadable, plus a filename builder, triggered from a button the same way Markdown export already is.
- **Phase 1's `generation_metadata.artifactKind` field is exactly where a `spreadsheet`/`formula` payload belongs too** — it's already a free-form JSONB field on `Note`, already read via `getArtifactKind()`, already proven safe to extend additively (Phase 1 added one key without a migration; this phase adds one more).
- **No structured-data generation capability exists yet.** `SheetAnalysis` (`processing/spreadsheet/types.ts`) is read-only analysis of an *uploaded* file — column stats, trends, anomalies. Nothing today asks the model to *produce* a new sheet's worth of cells from a conversation. This is the one genuinely new piece of AI-runtime surface this phase implies.

## 2. Spreadsheet Artifact Schema (no database change)

Stored inside the same `Note.generation_metadata` JSONB field Phase 1 already writes `artifactKind` into — **not** a new table, per the "no schema changes unless required" constraint and consistent with the original blueprint's own recommendation to defer a `payload`-bearing table until a real consumer needs one. This phase is that consumer's *design*, not yet the table itself, because the payload shape below hasn't been validated against real model output yet — locking a schema in before that would be exactly the premature architecture this initiative has consistently avoided.

```json
{
  "artifactKind": "spreadsheet",
  "artifactData": {
    "sheets": [
      {
        "name": "Occupancy Forecast",
        "columns": ["Month", "Available Rooms", "Sold Rooms", "Occupancy %"],
        "cells": [
          { "cell": "A2", "value": "January" },
          { "cell": "B2", "value": 744 },
          { "cell": "C2", "value": 520 },
          { "cell": "D2", "value": null, "formula": "C2/B2" }
        ]
      }
    ]
  }
}
```

- `value` is a plain literal (string/number/null) — matches `SheetAnalysis`'s own documented convention ("no Date objects, no functions, persisted verbatim into jsonb").
- `formula`, when present, is a bare formula string (no leading `=`) — written into the exported cell's `.f` field verbatim, exactly as SheetJS itself represents it on read. **Not evaluated client-side.** No formula engine is built or needed — Excel/Sheets/whatever opens the export computes it, the same way a human-typed `.xlsx` formula works today. This avoids the single biggest risk in this whole phase (a bug in a hand-rolled formula evaluator silently producing a wrong number in someone's revenue model) by simply not building one.
- `formula.ts`/`Formula Template` artifacts reuse the same `cells` shape but typically describe one representative row plus named `inputs` rather than a full sheet — deferred to its own pass once the Spreadsheet Model's shape is validated against real usage, per this document's own sequencing (§5).

## 3. The Spreadsheet Builder — Two Paths, Not One

The roadmap's own example ("Create a hotel occupancy forecast model" → a fully laid-out sheet with a real formula in `D2`) is **not** achievable by parsing prose after the fact — no amount of regex on "Occupancy = Rooms Sold / Available Rooms" reconstructs a cell grid. Two genuinely different mechanisms are needed, and conflating them would be the wrong abstraction:

**Path A — Deterministic table extraction (cheap, always-on).** When a response already contains a markdown table (the same `MARKDOWN_TABLE_PATTERN` `detectArtifactKind` already uses to classify `spreadsheet`), a pure parser converts it directly into the `cells` shape above — one cell per table cell, no formulas (prose tables don't carry per-cell formulas), `value` only. This is a natural sibling to `detectArtifactKind`, not a new subsystem: same file family (`src/modules/ai/artifacts/`), same "deterministic, not AI" rule. Covers the common case (the model already answered with a table) at zero marginal cost.

**Path B — A new capability for on-demand structured generation (the roadmap's actual example).** When a user explicitly asks for a spreadsheet/formula model — or picks "Spreadsheet Model" in Save As on a response that Path A couldn't structure — a new capability (`generate-spreadsheet-artifact`, registered the same way `generate-briefing` is) prompts the model to emit the schema in §2 as fenced JSON, parsed by a new `parseSpreadsheetArtifactResponse.ts` mirroring `extractJsonArray`'s exact convention (fence-stripping, brace-matching, `JSON.parse`, then field-by-field validation — reject/drop malformed cells rather than trusting the model's output verbatim, same defensiveness `parseConceptsResponse` already applies to `title`). This runs through the existing `runCapability`/`runWithFallback` path unchanged — **no new AI-runtime infrastructure**, just a new prompt template and a new parser, the same shape as every other capability this codebase already has.

Per this phase's own instruction ("solve structured formulas/tables first"), **Path A is the lower-risk, sequence-first piece** — it needs no new prompt template, no new capability registration, and directly upgrades every response that already contains a table (which the `spreadsheet` classification already fires on today). Path B is real, valuable, and explicitly the mechanism the roadmap's hero example needs, but it's a new AI-facing surface (a new prompt) and belongs in its own scoped, reviewed step rather than bundled into the same pass as Path A.

## 4. Export Pipeline

Format-agnostic dispatcher from day one, even though only XLSX ships first — so PDF/DOCX (Note/Briefing, per the original blueprint) and CSV slot in later without a redesign:

```
Artifact (Note + generation_metadata.artifactData)
        │
        ▼
exportArtifact(note, format: 'xlsx' | 'csv' | ...)
        │
        ├── 'xlsx' → buildSpreadsheetWorkbook(artifactData)  -- XLSX.utils.aoa_to_sheet / book_new,
        │            writing {v, f} per cell exactly as the read path already reads them
        │            → XLSX.writeFile — client-side, no server round trip
        │
        └── 'csv'  → (first sheet only; XLSX.utils.sheet_to_csv, already a one-liner once
                       the workbook above exists — effectively free once XLSX lands)
```

- **XLSX first**: zero new dependency (`xlsx` is already installed and already used for both read paths in this codebase), and it's the one format that can carry real formulas — `formula.trim() ? { f: formula } : { v: value }` per cell, direct mirror of `formulaColumnIndexes`'s read-side check.
- **CSV**: SheetJS gives this for free once a `WorkSheet` object exists (`sheet_to_csv`), so it costs almost nothing to add alongside XLSX rather than sequencing it separately — flattens formulas to their `value` field since CSV has no formula concept.
- **PDF/DOCX** (Note/Briefing export, from the original blueprint) are explicitly **not** designed here — no dependency exists for either, and they apply to a different artifact family (prose, not cells). Left as a separate, later design pass so this document doesn't scope-creep into two unrelated export problems.
- Entry point: a "Download" action on `NoteDetailPage` and `NoteCard`'s dropdown menu, gated on `getArtifactKind(note) === 'spreadsheet'` (and, once Formula Templates exist, `'formula'`) — same conditional-rendering pattern `ArtifactKindBadge` and the `NoteDetailPage` Knowledge Card block already established in Phase 1.

## 5. Recommended Sequencing (Phase 2 implementation, once authorized)

1. **Artifact payload schema on `generation_metadata`** (§2) — additive, no migration, land it alongside whichever consumer needs it first rather than speculatively.
2. **Path A: deterministic markdown-table → `cells` parser** — cheapest, no new AI surface, immediately useful for every response `detectArtifactKind` already classifies as `spreadsheet`.
3. **XLSX export button** wired to Path A's output — the first time a user can go from "NOVA answered with a table" to "a real spreadsheet file" with zero AI-runtime changes.
4. **CSV export** — near-free addition once (3) exists.
5. **Path B: `generate-spreadsheet-artifact` capability** — the on-demand formula-construction case (the roadmap's hero example). Sequenced last because it's the one genuinely new AI-facing surface in this phase, and should be reviewed as its own scoped step per this codebase's established discipline around prompt-template changes.
6. **Formula Template artifact kind** — once (5) exists and the `cells`/`formula` shape has been validated against real generated output, extract the "named inputs + one representative formula" variant.

## 6. On the Acceptance Harness Recommendation

Agreed on the reasoning: Phase 1 (Save As, badges, Knowledge Card rendering) was additive display/classification with no new state-changing user action; this phase's export step is the first place a user clicks something and gets a *file* — a genuinely different risk class from everything shipped in UX-14 so far, and boot-smoke-only verification (the pattern used since UX-14.2) is measurably weaker evidence for it.

Building the harness itself — a dedicated Supabase test project/branch, seed data, and Playwright flows against a real authenticated session — is a new-infrastructure decision with real cost and access implications (a new Supabase project or branch, credentials to manage, ongoing maintenance), not something to spin up unilaterally under a "Discovery" instruction whose explicit constraints were about spreadsheet/export design.

**Decision (recorded):** harness build is sequenced *after* Phase 2's implementation, not before or in parallel. Path A (deterministic table parsing) + XLSX/CSV export ship first under the same disclosed boot-smoke-only verification used since UX-14.2 — the harness lands before Path B (the `generate-spreadsheet-artifact` capability) or UX-14.5 collaboration, both of which carry materially higher risk (a new AI-facing prompt surface; a new authorization model) than a deterministic parser and a client-side file download.

## Implementation Record — Path A: Deterministic Spreadsheet Artifact Export (completed)

Scope, as authorized: markdown-table → cell parser, explicit formula cells preserved (never evaluated), XLSX export via existing dependencies, CSV export through the same dispatcher, a user download action, a basic preview. Constraints held: no new database tables, no collaboration/sharing, no AI spreadsheet generation, no formula calculation engine, no PDF/DOCX export, existing Note architecture unchanged.

**What was built** (`src/modules/ai/artifacts/spreadsheet/`):

- `types.ts` — `SpreadsheetCell`/`SpreadsheetSheet`/`SpreadsheetArtifactData`, the exact schema from this document's §2.
- `parseMarkdownTableToArtifact.ts` (+ tests) — deterministic, no AI call. Converts every markdown table in a response into a sheet of A1-addressed cells; a cell whose text starts with `=` becomes a `formula` (stripped of the leading `=`, never evaluated); everything else becomes a `value`, coerced to a number when the whole cell parses as one. Multiple tables become multiple sheets.
- `buildSpreadsheetWorkbook.ts` (+ tests) — pure, builds an in-memory SheetJS workbook from the schema. **A real finding, not assumed**: verified via an actual `XLSX.write`/`XLSX.read` round trip that SheetJS's writer silently *drops* a formula cell that has no cached `v` — a formula written as `{ f: formula }` alone vanishes on export. Fixed by writing `{ t: 'n', v: 0, f: formula }`: `v: 0` is an inert placeholder, not a computed result — every spreadsheet application recalculates it the instant the file opens, the same as any hand-built workbook with a stale cached value. This does not weaken the "never evaluate formulas" rule; it's what makes the formula survive the export at all, and is now covered by a test that performs the actual write/read round trip rather than only inspecting the pre-write object.
- `sheetToGrid.ts` (+ tests) — pure, lays cells into a dense 2D grid for preview; a formula cell renders as literal `"=formula"` text, same honesty rule as the exporter.
- `exportSpreadsheetArtifact.ts` (+ tests for the pure pieces) — format-agnostic dispatcher (`'xlsx' | 'csv'`), exactly as §4 specified. XLSX via `XLSX.write` + a new `downloadBinaryFile` (sibling to the existing `downloadTextFile`, for binary payloads); CSV via `XLSX.utils.sheet_to_csv` on the first sheet, near-free once the workbook builder exists.
- `buildArtifactGenerationMetadata.ts` (+ tests) — the one place that decides which artifact kinds get a structured `artifactData` payload; today only `spreadsheet` does. Shared by every note-creation call site.

**Where it's wired in:**

- `saveMessageToNote.ts` and `SaveConversationDialog.tsx` (Save As) both now call `buildArtifactGenerationMetadata`, replacing their direct `withArtifactKind` calls — a note tagged `spreadsheet` with a parseable table now carries `generation_metadata.artifactData` alongside `artifactKind`, with zero new call sites to keep in sync as future kinds get a payload builder.
- `NoteDetailPage.tsx` renders a new `SpreadsheetArtifactPanel` (preview table per sheet, reusing `SpreadsheetGridView`'s established styling, plus an Excel/CSV format picker and a Download button) whenever a note is tagged `spreadsheet` and has parsed `artifactData`. A note tagged `spreadsheet` with no parsed table (e.g. picked manually on prose) renders nothing extra — consistent with Phase 1's "no fabricated data" rule.

**A second real finding, caught before commit**: the first working version statically imported `SpreadsheetArtifactPanel` from `NoteDetailPage.tsx`, which pulled `xlsx` (a ~330KB dependency) into the main application bundle for every page load — confirmed by comparing `vite build` output before and after. `xlsx` was previously reachable only through `React.lazy()` boundaries (`PdfReaderView`/`SpreadsheetReaderView` in `ReaderPage.tsx`, and the extractor registry), so it had never been in the eager bundle before. Fixed by lazy-loading `SpreadsheetArtifactPanel` the same way, with a `Suspense` fallback — confirmed by rebuilding: the main bundle returned to its prior size and `xlsx` is a separate chunk again.

**Files changed:** 5 new files in `spreadsheet/` (+ their test files), `buildArtifactGenerationMetadata.ts` (+ test), `SpreadsheetArtifactPanel.tsx`, `downloadBinaryFile.ts`; 4 modified (`artifactMetadata.ts` gained `getArtifactData`/`withArtifactData`; `saveMessageToNote.ts`, `SaveConversationDialog.tsx`, `NoteDetailPage.tsx` wired in). Zero schema/migration changes.

**Verification.** `tsc -b`: clean. `vitest run`: 998/998 passing (up from 978 — 20 new tests, including the write/read round-trip test that caught the SheetJS finding above). `lint`/`build`: clean; bundle-size regression found and fixed before commit (verified via `vite build` output comparison, not assumed fixed). Browser: boot-smoke-tested (fresh dev server, zero console/page errors). **Not verified live**: the full authenticated flow (open a note tagged spreadsheet → see the preview → click Download → confirm the file opens correctly in Excel/Sheets with the formula intact) — same disclosed gap as every UX-14 milestone since UX-14.2. Per the recorded harness-sequencing decision above, this is expected to remain the case through Path A; the harness lands before Path B.

**Not built, per instruction:** no `generate-spreadsheet-artifact` capability (Path B), no formula evaluation of any kind, no PDF/DOCX export, no new database table, no sharing/collaboration surface.

**Recommendation:** per the recorded decision, build the Acceptance Harness next, before Path B — Path B introduces a new AI-facing prompt surface (real generation risk: a malformed or unsafe model response feeding into a downloadable file) that deserves a stronger verification floor than boot-smoke checks before it ships.

## Implementation Record — UX-14.4.5: Artifact Acceptance Harness (completed)

**Acceptance approach.** This is deliberately a lightweight, code-level acceptance path — not the live-authenticated-browser-against-a-Supabase-test-project harness floated (but not built) in this document's §6. That heavier harness remains undecided and unbuilt; conflating the two would misrepresent what's actually verified now, so this section is explicit about the distinction. What was built instead, per this milestone's own "use existing project testing conventions" and "avoid unnecessary infrastructure" instructions:

1. **A lifecycle integration test** (`spreadsheetArtifactLifecycle.test.ts`) that calls the real production functions, in the real order the app calls them, on one shared realistic fixture (a chat-response-shaped markdown table with a formula cell) — walking the exact chain this milestone specified: classification → metadata → (a `JSON.stringify`/`parse` round trip standing in for the `generation_metadata` jsonb column, since that's what actually proves data survives storage rather than reusing an in-memory reference) → preview → XLSX export → a real `XLSX.write`/`XLSX.read` round trip → CSV export → filenames. One test, one fixture, the whole pipeline — not six isolated unit tests that each assume the others' output shape is correct.
2. **A dedicated regression file** (`regressions.test.ts`) naming both prior discoveries explicitly: the SheetJS formula-drop platform trap (one test reproducing the raw trap, one confirming `buildSpreadsheetWorkbook` avoids it), and the eager-`xlsx`-import bundle regression (a source-inspection test asserting `NoteDetailPage.tsx` still lazy-loads `SpreadsheetArtifactPanel` rather than importing it statically — fast, runs on every `vitest run`, no build step required).
3. **A build-output verification script** (`scripts/verify-bundle-splitting.mjs`, run via `npm run verify:bundle`) — the one piece that can't be a vitest test, since it needs a real `vite build` to inspect. Checks actual `dist/assets` output: a separate `xlsx-*.js` chunk exists, and the main entry chunk stays under a byte ceiling set between this codebase's actual measured baseline (~955 KB) and the actual measured regression size (~1.40 MB) from Phase 2. Not wired into CI (no CI workflow exists in this repository) — it's a manual step, same tier as `tsc`/`vitest`/`lint`/`build` already are in this project's per-milestone verification checklist.

**Verification of the harness itself**, not just assumed working:
- The lifecycle and regression tests pass as part of the normal suite (see below).
- The bundle-splitting script was run against the real, current build (passed) and then verified to actually *fail* against a fabricated regressed build (a 1.27 MB oversized entry chunk with no `xlsx-*.js` sibling) — confirmed exit code 1 with the expected diagnostic message, then the fabricated files were discarded. This is the harness proving it catches the exact failure it exists to catch, not just a script that always prints "OK."
- The regression test's regex was independently confirmed to distinguish the current (lazy) `NoteDetailPage.tsx` from a reconstructed eager-import version of the same file.

**Verification coverage now in place for the spreadsheet artifact pipeline:**
- Classification → metadata → jsonb-round-trip → preview → XLSX export → formula preservation → CSV export, as one connected chain (lifecycle test).
- The two concrete bugs found during Phase 2, each with its own named regression test.
- A real `vite build` output check for the bundle-splitting regression specifically (script, run manually).

**Remaining limitations, stated plainly:**
- No live Supabase persistence is exercised — `createNote`'s actual insert path, RLS, and the real `notes` table are untouched by any of this; the jsonb round trip only proves the JSON *shape* survives serialization, not that Supabase stores/returns it identically.
- No real browser download is triggered or inspected — `downloadBinaryFile`/`downloadTextFile`'s `Blob`/`URL.createObjectURL`/anchor-click mechanics remain unverified beyond the boot-smoke check, same as every UX-14 milestone since UX-14.2.
- No real spreadsheet application (Excel, Google Sheets, LibreOffice) has opened an exported file — "the formula survives a SheetJS round trip" is not the same claim as "Excel recalculates it correctly," though it is the strongest verification available without that heavier, still-undecided live harness.
- `npm run verify:bundle` is manual, not automated in CI (none exists) — it protects against the *next* regression only if someone remembers to run it.

**Files changed:** `spreadsheetArtifactLifecycle.test.ts`, `regressions.test.ts` (both new, no production code changed), `scripts/verify-bundle-splitting.mjs` (new), `package.json` (`verify:bundle` script). Zero application code touched — this milestone is entirely additive test/verification infrastructure, matching its own scope: no new artifact types, no AI generation, no PDF/DOCX, no collaboration, no production database changes.

**Verification.** `tsc -b`: clean. `vitest run`: 1003/1003 passing (up from 998 — 5 new tests: 2 lifecycle, 3 regression). `lint`/`build`: clean. `npm run verify:bundle`: passes against the real build, confirmed to fail against a simulated regression. Browser: boot-smoke-tested (fresh dev server, zero console/page errors).

**Recommendation for Path B:** the harness now gives real, executable protection against the two specific classes of bug already found in this artifact pipeline (a SheetJS write/read platform trap, and an eager-import bundle regression) — but it does not close the disclosed live-verification gap (Supabase persistence, real browser download, a real spreadsheet app opening the file). Proceeding to Path B (`generate-spreadsheet-artifact`, a new AI-facing prompt surface) is reasonable given this milestone's scope, provided that gap stays disclosed rather than implied closed — Path B's own output should route through this same lifecycle test's assertions (classification/metadata/preview/export/formula-preservation) before it's considered done, extending the fixture to cover an AI-generated payload rather than only a parsed one.
