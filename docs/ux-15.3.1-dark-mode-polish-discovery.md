# UX-15.3.1 — Dark Mode Polish & Visual Consistency

Discovery, implementation, and verification record for the Platform Polish Sprint's first phase: "Complete dark theme audit across the platform. Remove remaining hard-coded light colors. Improve contrast, elevation, borders, icons, tables, markdown, dialogs, charts, and hover/focus states. Validate accessibility and visual consistency."

## Discovery: there was no working dark theme at all

`src/index.css` declared `color-scheme: light dark` on `html`, and a stale comment above the `@theme` block claimed "dark variants are applied via the `dark:` variant." Both were misleading. `grep -rl "dark:" src --include=*.tsx --include=*.ts` returned zero matches — no component anywhere used Tailwind's `dark:` variant. `color-scheme: light dark` only tells the browser to dark-style its own native widgets (scrollbars, form controls); it does nothing for the app's own CSS. So a user with an OS-level dark preference got a fully light-themed app with dark-styled scrollbars — the worst of both, not a working dark theme.

This reframed the phase from "polish an existing dark theme" to "build the first one, on an already-disciplined-for-neutrals but undisciplined-for-status-colors design-token architecture."

## What was already right

The project's semantic design-token convention (`--color-canvas`/`--color-surface`/`--color-border`/`--color-ink`/`--color-ink-muted`/`--color-accent`, referenced everywhere via `bg-[var(--color-x)]` bracket syntax rather than Tailwind's own color palette) was **100% consistent for neutrals** — a `grep` for raw `gray-*` classes across `src/**/*.tsx` returned zero hits. That discipline made the fix mechanism trivial for everything already using it: a single `@media (prefers-color-scheme: dark)` block re-declaring those custom properties at `:root` re-themes the entire app with zero component-level changes, because Tailwind v4's `@theme` block makes these both compile-time utility tokens *and* real runtime CSS custom properties — a later media-query override at `:root` is genuinely read at paint time by every `bg-[var(--color-x)]` reference.

Markdown renderer components (`CodeBlock`/`TableBlock`/`QuoteBlock`/`ListBlock`/`HeadingBlock`), `Dialog.tsx`, and `ErrorDistributionChart.tsx` were already 100% semantic-var based and needed no changes — they theme correctly from the CSS block alone.

## What was broken, and the fix for each

**1. Status colors (red/green/amber) never had the same discipline as neutrals.** ~140 call sites used raw Tailwind literals (`text-red-600`, `bg-amber-100`, etc.) — shades tuned for a white background only, by construction a dark-mode bug. Fix: ten new semantic tokens (`--color-danger`/`-strong`/`-bg`/`-border`, `--color-success`/`-strong`/`-bg`, `--color-warning`/`-strong`/`-bg`) with light defaults in `@theme` and dark overrides in the new media-query block; every raw literal replaced project-wide via scripted `sed`. A follow-up broader grep (`emerald`/`teal`/`cyan`/`sky`/`blue`/`indigo`/`violet`/`purple`/`fuchsia`/`pink`/`rose`/`orange`/`lime`/`slate`/`zinc`/`neutral`/`stone`) caught one item the first pass missed: `WorkspaceHealthPanel.tsx`'s `STATUS_DOT_CLASS.good: 'bg-emerald-500'`, fixed to `bg-[var(--color-success)]`.

**2. `GraphCanvas.tsx`'s six categorical node colors were fixed hex, and two failed contrast against the new dark surface.** Measured contrast of the light-tuned hex values against `--color-surface` dark (`#292524`): `document` (indigo `#4f46e5`) 2.41:1, `concept` (violet `#7c3aed`) 2.66:1 — both below the 3:1 WCAG non-text-contrast minimum for graphical objects; `tag` (rose) passed at only 3.23:1. Fix: six new `--graph-color-*` tokens, light defaults unchanged, dark overrides moved to each color's ~400-shade equivalent (measured 5.09–9.09:1 against the dark surface, all comfortably passing).

**3. Sixteen call sites paired a theme-flipping background with a hardcoded `text-white`.** The dominant pattern, `bg-[var(--color-ink)] text-white`, is used for every "active tab/selected pill" affordance in the app (`TagFilterBar`, `ExportCenterPage`, `KnowledgeExplorerPage`, `AiHealthPage`, `MemoryManagementPage`, `ImageReaderPage`, `WorkbookNav`, `ReaderPage` ×2, `PdfPageControls`). `--color-ink` flips from near-black to near-white (`#f5f5f4`) in dark mode — so every one of those pills would have rendered **white text on a near-white background** in dark mode, i.e. invisible. A second pattern, `bg-[var(--color-accent)] text-white` (`Button.tsx` primary variant, `MessageBubble.tsx`, `ContinueWorkingCard.tsx`, `SelectionHighlightButton.tsx`), didn't go fully invisible but measured only 2.98:1 against the dark-mode accent (`#818cf8`) — below the 4.5:1 AA text minimum. Fix: replaced all sixteen with `text-[var(--color-canvas)]` — `--color-canvas` is the literal inverse of `--color-ink`/`--color-accent`'s intended contrast partner in both themes (measured 6.02:1 light / 5.86:1 dark against accent, and by construction always the opposite of `--color-ink` since they're the two ends of the same token pair). `ImageLightbox.tsx`'s `text-white` was left untouched — it sits on a fixed `backdrop:bg-black/80` scrim, a deliberately theme-agnostic dark overlay (standard image-viewer convention), not a light-theme leak.

**4. Elevation (shadows) silently didn't reach the dark theme at all, even after adding a `--shadow-*` override block.** The `--shadow-soft`/`--shadow-raised`/etc. tokens are declared in `@theme`, and Tailwind v4 resolves `@theme` shadow values into each `shadow-*` utility's own `--tw-shadow` **at build time** — confirmed by inspecting the compiled `dist/assets/index-*.css`: it contains zero `var(--shadow-*)` references anywhere. A `:root`-level override of `--shadow-raised` in the dark media query is consequently inert; the generated `.shadow-raised` class never reads it. This is a different mechanism from the color tokens (which components reference directly and explicitly via `bg-[var(--color-x)]`, a real runtime `var()`) and is easy to miss without inspecting build output. Fix: override `--tw-shadow` directly on each utility class name (`.shadow-soft`, `.shadow-soft-lg`, `.shadow-raised`, `.shadow-inset`, `.shadow-floating`) inside the dark media query — same selector specificity as Tailwind's own generated rule, later in source/compiled order, so it wins the cascade. Verified directly in the compiled CSS that the dark rule is emitted after the base rule. Alpha values raised ~3x (e.g. `--shadow-raised`'s 0.05/0.12 → 0.35/0.5) since the same low alpha that reads as a soft shadow against a near-white canvas is functionally invisible against a near-black one — otherwise the neomorphic elevation system (Phase UX-3.5) would have silently collapsed in dark mode with zero visible symptom short of a side-by-side comparison.

**5. Border contrast measured 1.70:1 (canvas) / 1.48:1 (surface) at the naive "one shade darker than canvas" value.** Below the 3:1 non-text-contrast guideline for a UI boundary — cards, table rows, and dividers would have been barely distinguishable from their background. Fix: moved from Tailwind's stone-700 to stone-500 (`#78716c`), measured at 3.65:1 / 3.16:1 — still a muted divider, not a loud one, but now actually functions as a visible boundary.

## Accessibility validation (Phase 4)

Every dark-mode foreground/background pairing introduced or affected by this phase was checked against WCAG 2.1 contrast minimums (4.5:1 for text, 3:1 for non-text UI/graphical objects), computed via the standard relative-luminance formula:

| Pairing | Ratio | Minimum | Result |
|---|---|---|---|
| Ink text / canvas (body text) | 16.03 | 4.5 | Pass |
| Ink text / surface (card text) | 13.90 | 4.5 | Pass |
| Ink-muted text / canvas | 6.93 | 4.5 | Pass |
| Ink-muted text / surface | 6.01 | 4.5 | Pass |
| Accent text / canvas (links) | 5.86 | 4.5 | Pass |
| Canvas text on accent background (primary buttons) | 5.86 | 4.5 | Pass |
| Danger text / canvas | 6.32 | 4.5 | Pass |
| Danger text / danger-bg (banners) | 5.65 | 4.5 | Pass |
| Success text / canvas | 10.04 | 4.5 | Pass |
| Success text / success-bg | 8.83 | 4.5 | Pass |
| Warning text / canvas | 10.48 | 4.5 | Pass |
| Warning text / warning-bg | 8.29 | 4.5 | Pass |
| Border / canvas (non-text) | 3.65 | 3.0 | Pass |
| Border / surface (non-text) | 3.16 | 3.0 | Pass |
| Focus ring (accent) / canvas (non-text) | 5.86 | 3.0 | Pass |
| Graph node colors (×6) / surface | 5.09–9.09 | 3.0 | Pass (all six) |

Visual consistency was checked structurally rather than via a running browser (no browser tooling available in this environment): confirmed every remaining raw-color call site across `src/**/*.tsx` was converted (final sweep across all Tailwind color families beyond red/green/amber — emerald/teal/cyan/sky/blue/indigo/violet/purple/fuchsia/pink/rose/orange/lime/slate/zinc/neutral/stone — returned zero hits after the fixes above), and that every affected component still passes the existing test suite unchanged (a pure color-token substitution should not, and did not, change any test's behavioral assertions).

## Explicitly out of scope

- `buildInvitationEmail.ts`'s hardcoded hex colors — a static HTML email template. Email clients don't reliably support CSS custom properties or `prefers-color-scheme`, so hardcoded colors are the correct choice there, not a dark-mode bug.
- No manual light/dark toggle (Settings UI, `localStorage`, React context) was added. The mechanism is a single OS-level `prefers-color-scheme` media query, consistent with `color-scheme: light dark` already declaring automatic detection as the intended behavior, and because a manual toggle is new feature scope beyond "polish an existing/intended mechanism."
- No changes to `PackageVersion`/`PackageValidator`/`PackageExporter`/`PackageImporter`, Knowledge Exchange, AI orchestration/prompts, migrations, RLS, or Edge Functions — this phase is CSS tokens and `className` string substitutions only.
