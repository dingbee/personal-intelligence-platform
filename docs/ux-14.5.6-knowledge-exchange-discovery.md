# UX-14.5 Phase 6 — Knowledge Exchange: Architecture Discovery

**Status: discovery only. No schema changes, no migrations, no RLS changes, no UI implementation in this document or the commit that adds it.**

Objective per the brief: design NOVA PIP's Knowledge Exchange capability —
packaging, transferring, importing, and continuing intelligence across
people and workspaces — while preserving the collaboration architecture
Phases 1–5 already built and shipped to `main`. Every recommendation below
is grounded in the current codebase (31 migrations, `0001_init.sql`
through `0031_shared_knowledge_objects.sql`, plus the Phase 5 UI-layer
commit) and the prior UX-14.5 discovery sequence, not assumptions about
what a generic export/import feature looks like. Audit performed first;
architecture proposed second, per the brief's instruction.

A framing point that shapes everything below: **Phases 1–5 solved *live,
in-place* collaboration** — multiple accounts holding different roles
against the *same* row, inside one workspace, via RLS. **Knowledge
Exchange is a different problem** — moving intelligence *across* the
boundary RLS enforces, into a workspace or account the source data was
never RLS-visible to in the first place. No OR-clause, however cleverly
written, can express "let a stranger's account read my row" — that would
mean an RLS policy referencing `auth.uid()` values that aren't the row's
owner and aren't a workspace co-member, which is not a boundary this
schema, or Supabase RLS in general, is built to express safely. This is
the central architectural fact the rest of this document works from.

## 0. Audit summary — what already exists

Before proposing anything, here is what this codebase already has that
bears directly on Knowledge Exchange, confirmed by reading the actual
code, not inferred:

- **"Export Knowledge Package"** (Knowledge Actions v1, UX-13.x era)
  already exists and already uses the phrase "package." It is a **pure
  client-side markdown download** — `buildKnowledgeExportMarkdown()`
  (`src/modules/knowledge-intelligence/api/knowledgeExportMarkdown.ts`)
  renders one already-fetched `KnowledgeNodeEvidence` object (a single
  knowledge node's title/description, related nodes, and evidence items)
  into prose markdown with `#`/`##` headings, downloaded via
  `downloadTextFile()` (`src/shared/utils/downloadTextFile.ts`, a `Blob`
  + `URL.createObjectURL` + synthetic `<a download>` click — no server
  call, no storage write, no database row created). **There is no
  manifest, no frontmatter, no version field, no machine-readable
  structure at all** — it's read-only, human-facing prose, single-node
  scope only (no collection-level or multi-object export path exists).
  **There is no import counterpart anywhere in the codebase** — nothing
  reads this markdown back in. This is exactly Option D ("Intelligence
  packages — snapshot exchange") that `ux-14.5-knowledge-exchange-
  collaboration-discovery.md` §3 already named and explicitly deferred,
  describing it as extending "a feature direction that already exists."
  Phase 6 is that deferral coming due.
- **"Merge Notes"** (`src/modules/notes/api/mergeNotes.ts`) is the
  closest existing precedent for *combining* multiple knowledge objects
  into one, and it teaches a real lesson worth carrying forward: its own
  doc-comment records that collection membership used to be silently
  dropped on merge until that was fixed — union tags, union collection
  membership, then delete the originals. **Losing membership/provenance
  on a combine operation is a real, previously-hit bug class in this
  codebase**, not a hypothetical risk to design against.
- **"Generate Briefing"** (`src/modules/knowledge-intelligence/api/
  generateBriefing.ts`) shows the pattern for closing the loop back into
  the graph after producing new content: persist as a `Note`, then call
  `recordKnowledgeNodeSource` to link it back as evidence, then
  `indexNote` (search) and `linkKnownConceptsToSource` (re-scan for
  concept mentions) — i.e., a generated/imported object is not "done"
  until it's re-registered with every downstream system that expects to
  find it. This is the shape §5 and §7 below reuse.
- **Knowledge Collections** (`knowledge_collections` +
  polymorphic-membership rows in `knowledge_links` where
  `source_type='knowledge_collection'`) has **no export/snapshot
  capability today** — confirmed by grep, zero hits for "collection
  export" or "snapshot" anywhere in `src/`. `listCollectionItems()`
  already resolves a collection's cross-type membership into the same
  `EvidenceItem` shape node evidence uses — real, reusable
  infrastructure for building a package's manifest.
- **`resolveCanonicalNode`** (`src/modules/knowledge-intelligence/api/
  knowledgeNodeResolution.ts`) is this codebase's only existing identity/
  dedup mechanism: exact match on `normalizeTitle()`-normalized title,
  scoped to `(user_id, node_type)` — not fuzzy, not embedding-similarity.
  Its own code comment documents an **accepted, unenforced trade-off**:
  no hard DB uniqueness constraint backs the lookup (a race between two
  concurrent resolutions of a brand-new title could create duplicates),
  judged acceptable today only because extraction is single-user-
  triggered, not concurrent. **This safety margin does not survive
  multi-account import**, where two independent imports racing is a real
  scenario, not a theoretical one — flagged as a real design input for
  §4 below, not solved here.
- **Retrieval boundaries** (`retrieveContext.ts`, `retrieveGraphContext.ts`,
  `retrieveMemoryContext.ts`) all either rely entirely on RLS (the latter
  two, by their own code comments) or apply one explicit `workspace_id`
  filter (the first, for document-scoped chat). None of the three cache
  or duplicate embeddings client-side — every retrieval is a live RPC
  call (`match_document_chunks`/`match_messages`/`match_notes`) against
  the `embeddings`/`message_embeddings`/`note_embeddings` tables. This
  means **there is no existing "export the embeddings" pathway to reuse
  or extend** — embeddings are a derived index, not source content, and
  no code anywhere treats them as portable.
- **No `attachments` table exists** — confirmed by grep across `src/`
  and `supabase/migrations/`, zero hits. `documents` and `assets` are the
  only binary-content-bearing tables, and they are structurally distinct
  (`documents` → the ingestion/chunking/RAG pipeline; `assets` → uploaded
  or generated images with derivative rendition paths). There is no
  generic "attachment" abstraction to design Knowledge Exchange's
  binary-content story around; the design below treats `documents` and
  `assets` as the two binary-content object types directly.
- **The personal/shareable boundary Phases 1–5 already drew** is the
  direct precedent for §6 below. `docs/ux-14.5.3-intelligence-object-
  access-model.md` §3.3 states the governing rule explicitly: *"content
  that was true of the person before the workspace existed, or that NOVA
  inferred about the person rather than about the project, must never
  become visible to a teammate as a side effect of workspace
  membership."* That rule was written for *intra-workspace* sharing;
  Knowledge Exchange crosses an even harder boundary (a different
  *account*, possibly a stranger), so it applies at least as strongly,
  argued in full in §6.
- **One correction to the brief's own framing, found by checking the
  live migration rather than assuming**: the brief's §6 lists
  "objectives" alongside `ai_memory`/provider settings/preferences as
  something to confirm stays personal. **It does not, today.**
  `workspace_objectives` was explicitly *reclassified* into the
  shareable bucket by `0031_shared_knowledge_objects.sql` — it now
  follows the identical four-command RLS split every other shareable
  object uses, gated by workspace role, same as `notes`/`documents`.
  §6.2 below addresses this directly rather than silently going along
  with the brief's assumption.

## 1. Knowledge Package Model

Classification below is per-object, each justified against this
codebase's actual current RLS/data-model state (confirmed live in
Phases 1–5, not assumed), not a generic taxonomy. "Transferable" here
specifically means: a reasonable candidate to include, by default, when
a user chooses to export/share a given package scope (a note, a
collection, a document + its derivatives). It does **not** mean "the
underlying table's RLS is already extended" — as established above,
Knowledge Exchange is a copy operation across an RLS boundary, so a
table's current intra-workspace shareability (or lack of it) is a
*related* fact, not a *determining* one.

| Object | Classification | Justification |
|---|---|---|
| **Notes** | **Transferable** | The clearest case. A note is self-contained prose (`content` column, no binary dependency), already the app's "durable output" unit — `SaveConversationDialog`, `generateBriefing`, `mergeNotesIntoOne`, and highlight→note creation all convert *other* ephemeral or derived content *into* a note specifically because a note is this codebase's portable, human-readable unit of knowledge. Its own RLS (`0029_note_sharing.sql`) already extends to workspace roles, confirming the product's own judgment that a note is meant to travel beyond its creator. |
| **Documents** | **Transferable, with a caveat** | The uploaded file (`file_path` in the private `documents` storage bucket) plus its already-shareable metadata row is transferable in principle — it's exactly the "team knowledge" case §3.2 of the object-access-model doc names explicitly. The caveat: storage is a **separate, coarser boundary** (`ux-14.5-knowledge-exchange-collaboration-discovery.md` §1.4) — RLS on `storage.objects` is keyed to `(storage.foldername(name))[1] = auth.uid()::text`, a per-user folder prefix, not a per-object grant. Exporting a document's *file* (not just its metadata row) requires a storage-level copy, which nothing in this codebase does today (confirmed: no cross-user storage copy code anywhere in `src/modules/library` or `src/modules/assets`). This is real, separate implementation work, not a side effect of any table-RLS pattern — flagged as a dependency for §8's roadmap. |
| **Knowledge Collections** | **Transferable (as a container, recursively)** | A collection is thin identity/metadata (`knowledge_collections`) plus polymorphic membership rows in `knowledge_links`. It is the natural **package scope boundary** — "export this collection" is a coherent, bounded unit in a way "export my entire account" is not. Transferability of the collection *itself* is trivial (name + description); transferability of its *contents* recursively follows each member item's own classification in this table. |
| **Knowledge Nodes** | **Transferable, but never 1:1 — see §4** | A node (`knowledge_nodes`) is an AI-extracted concept/entity, not user-authored content. Its title/description/type is transferable, but a node's *identity* is meaningful only within the exporting account's `(user_id, node_type, title_normalized)` space (§0, `resolveCanonicalNode`) — there is no cross-account canonical identity today, and none should be invented as a side effect of Phase 6 (§4 recommends re-resolution on import, not identity preservation). |
| **Knowledge Links** | **Transferable only as edges between two already-transferred nodes** | A `knowledge_links` row is meaningless without both endpoints (`source_id`/`target_id`, polymorphic, not FK-enforced at the DB level per its own type comment). Include a link in a package only if both its endpoints are also in the package; otherwise it's a dangling reference to an object the recipient will never receive. This is a package-*construction* rule, detailed in §4. |
| **Assets** | **Transferable, with the same storage caveat as Documents** | Same reasoning and same caveat as Documents — `assets`' storage bucket has the identical per-user-folder RLS boundary (`0022_assets.sql`), and no cross-user asset-copy path exists today. |
| **Conversations** | **Optionally transferable, and the product's own precedent argues against making it a first-class package object** | A conversation is a live back-and-forth with an AI provider, tied to `provider_id`, streaming state, and (per `ChatPage.tsx`, Phase 5 §16.4) per-message `messages.user_id` attribution that has no meaning outside the exporting account. The existing product pattern — `SaveConversationDialog` — already treats "durably preserve part of a conversation" as *converting it into a note*, not exporting the conversation object itself. Recommend the same pattern for Knowledge Exchange: a conversation is optionally transferable **by first converting it to a note** (reusing `SaveConversationDialog`'s existing extraction, not a new conversation-serialization format), never as a raw `conversations`/`messages` export. |
| **Reading progress** | **Never transferable** | `reading_progress` (`document_id, user_id, chapter_index, scroll_fraction`) is pure UI-scroll-position state for one specific account's reading session. It has zero meaning to a recipient who is a different person with a different reading history, and per §0/Phase 4, this table was deliberately never extended even for intra-workspace sharing — the strongest possible existing precedent that this stays personal. |
| **Flashcards** | **Optionally transferable, contingent on the document also transferring** | A flashcard (`front`/`back`, `source_chunk_ids`) is real, reusable study content, not UI state — a legitimate candidate for inclusion when its parent document is also in the package. But `flashcards`' RLS was **never extended to workspace roles at all**, even intra-workspace (Phase 4 §15.6, "residual gap, not a security exclusion" — simply out of scope, not evaluated). Practically: exporting a flashcard makes sense only bundled with its source document (a flashcard without its source is a floating fact with no traceable origin), so this is scoped as "optional, document-attached," not a standalone package object. |
| **Highlights** | **Optionally transferable, same reasoning as Flashcards** | A highlight (`quote`, `note`, `chapter_index`) is user-curated content with real value to a recipient, same "residual gap" RLS status as flashcards (Phase 4 §15.6). Same recommendation: optional, always bundled with its source document, never standalone. |
| **Summaries (`chapter_summaries`)** | **Optionally transferable, same reasoning again** | Same table-status class as flashcards/highlights (Phase 4's residual gap). A chapter summary has real recipient value bundled with its document, none as a standalone floating object. |
| **Attachments** | **N/A — no such object exists** | Confirmed by exhaustive grep (§0): there is no `attachments` table or concept in this codebase. `documents` and `assets` are the only binary-content types, both already classified above. This row is included in the classification only to close it out explicitly, not left as a silent gap. |

### 1.1 Objects outside the brief's list that the audit surfaced as relevant

Two object types the brief's list omits are worth naming explicitly,
since a complete package design has to account for what happens to them,
even if the answer is "nothing travels":

- **`extraction_metadata`** (author/language/page-count/etc., derived
  during document processing) — should travel *with* its document as
  read-only descriptive metadata (it's cheap, has no privacy
  implications, and re-deriving it on import would mean literally
  re-running the extraction pipeline for no benefit). Not independently
  transferable — meaningless without its document.
- **`tags`** — user-authored labels (`tags` table, `user_id`-scoped
  identity + `note_tags`/`document_tags` join tables). A tag *name* is
  cheap to recreate (find-or-create by name in the importing account, the
  same pattern `DocumentTagEditor`/`NoteTagEditor` already use for
  ordinary tag creation) — recommend tags travel as plain string labels
  attached to their parent object, re-resolved to the importing account's
  own `tags` rows on import, never as a reference to the exporting
  account's `tags.id`. This is consistent with treating tags as a
  taxonomy convenience, not an identity-bearing object.

## 2. Package Semantics

### 2.1 The three options, evaluated against this codebase specifically

**Live references** (the package points at the source rows; a recipient
"sees" the exporter's live data) — **rejected**. This would require
either (a) extending RLS to grant a specific *other account* (not a
workspace co-member) read access to specific rows — a materially
different, and materially riskier, authorization primitive than anything
in this schema, since every existing OR-clause (Phases 2–4) only ever
extends access to accounts that are *members of the same workspace*, a
bounded, revocable, auditable relationship — cross-account row-level
grants to an open-ended stranger have no such natural revocation/
audit story here; or (b) a proxy/gateway layer re-checking permissions
per request, which is new infrastructure this app has never needed and
that "no speculative enterprise architecture" (per the brief's own
constraint) argues against building now. Live references also fail the
brief's own "offline use" criterion outright — nothing to reference
while offline.

**Immutable snapshots** (the package is a self-contained copy; import
creates brand-new, independently-owned rows) — **recommended**. This
requires *zero* RLS change, of any kind, to any table — the exporting
account reads its own already-fully-visible-to-it rows (ordinary,
existing queries, same authorization the export button click already
has), and the importing account creates brand-new rows under its own
`user_id`, going through the exact same insert path (and RLS check) any
ordinary "create a note"/"create a knowledge node" action already uses
today. This is precisely why Option D was flagged in the original
discovery as the lowest-blast-radius exchange model, and the audit above
confirms it — `buildKnowledgeExportMarkdown`/`downloadTextFile` already
prove the "read what I can already see, serialize it, hand it to the
user" half of this exact pattern works, cleanly, with zero backend
changes.

**Hybrid** (snapshot content + a live pointer back to the source, e.g.
for "check for updates") — **not recommended for this phase**, but worth
naming why precisely: it requires solving snapshot import *first*
(everything below) *and* a live cross-account reference mechanism (which
§2.1's live-reference rejection already ruled out as premature) *on top*
of it. A hybrid model is strictly a superset of the snapshot model's
complexity, not an alternative to it — if it's ever wanted, it's
"snapshot import, plus a later phase," not a different Phase 6.

### 2.2 Trade-off table, stated explicitly per the brief's four axes

| Axis | Snapshot (recommended) | Live reference | Hybrid |
|---|---|---|---|
| **Collaboration** | No live co-editing across the exchange boundary — a fork, not a shared document. Correct: cross-account collaboration on a *specific* object, if ever wanted, is a distinct, smaller-scoped feature (explicit per-object sharing, Option A from the original discovery), not something Knowledge Exchange should quietly also become. | Real-time shared state, but requires an authorization primitive this schema doesn't have and the brief says not to build. | Same ceiling as live reference, plus snapshot's own complexity. |
| **Offline use** | Works trivially — the package is a complete, standalone copy the moment it lands. | Fails outright — nothing to read without a live connection back to the source account. | Works for the snapshot half; the "check for updates" half doesn't. |
| **Provenance** | Clean and honest: `generation_metadata`/a new "imported from" field (§4.3) records where it came from, but the imported row is unambiguously the importing account's own content going forward — matches this codebase's existing `source_chunk_ids`/`creationMethod` provenance convention (`ux-14.5-knowledge-exchange-collaboration-discovery.md` §5) exactly, extended rather than reinvented. | Provenance and "current state" become the same question, which this schema's `user_id`-as-permanent-author convention was deliberately built to keep separate (Phase 3's §4.2 ownership-transfer reasoning applies with equal force here). | Same tension as live reference for the "live" half. |
| **Future versioning** | Cleanest possible starting point: a snapshot is a whole, versioned artifact by construction (each import is a discrete event) — later "re-import an update" is additive (a second import creating a new snapshot or an explicit merge action), never a retrofit of existing rows. | Versioning becomes entangled with live-sync semantics (whose edit wins, when) — a strictly harder problem, and one this schema has no answer to yet even *within* a single workspace (`ux-14.5-knowledge-exchange-collaboration-discovery.md` §5 flags editor-role version history as still undesigned). | Inherits live reference's harder versioning problem. |
| **Performance** | One-time read + one-time write, same cost class as any existing bulk create operation (`mergeNotesIntoOne` already does exactly this shape: read several rows, write several new rows). No new steady-state query load. | Requires either a live query fan-out to the source account on every access (steady-state load, new query patterns, cache-invalidation problems) or a sync mechanism (background jobs — infrastructure this app doesn't have, confirmed nowhere in `supabase/functions/`). | Same steady-state cost as live reference for the "live" half. |

### 2.3 Recommendation

**Immutable snapshot.** It is the only option that requires zero RLS
change, matches the one existing precedent this codebase already has
(Export Knowledge Package), and keeps every hard problem (cross-account
live access, concurrent-edit resolution) out of scope rather than
quietly reintroducing exactly the "speculative enterprise architecture"
the brief says to avoid.

## 3. Import Model

### 3.1 Ownership

An imported object is owned, unambiguously, by the importing account —
`user_id` (or `owner_id` for assets) is set to the importer, exactly as
every existing "create X" code path in this app already does (there is
no precedent anywhere in ~40 API modules for inserting a row with
someone else's `user_id`, and inventing one for import would be the
first). This directly follows from §2.3's snapshot recommendation: a
snapshot *is* a new, independently-owned copy by definition.

### 3.2 Workspace assignment

Recommend import always requires an **explicit** target — either "no
workspace" (personal) or a specific workspace the importer is a member
of — never inferred or defaulted from the package's *original*
workspace metadata (which the importer may not even be a member of, or
which may not exist in their account at all). This mirrors §7.4's
resolved ambiguity from the original discovery doc: `workspace_id` null
already has one settled meaning in this schema (personal/unfiled) and
import should not invent a second, conflicting interpretation of it.
Concretely: strip the source `workspace_id` entirely during package
construction (§4.3 — packages carry no workspace identity at all, only
content) and require the importer to pick a destination at import time,
using the exact same `useWorkspace()`/workspace-switcher UI pattern
every other "create in workspace X" flow already uses.

### 3.3 Metadata preservation

Preserve: title, content, tags (re-resolved per §1.1), creation
timestamp *of the original* (as a separate, clearly-labeled field —
never overwriting the new row's own `created_at`, which should reflect
when *this account* actually received it), and any `generation_metadata`/
`source_chunk_ids` the object already carries (these are already
namespaced JSONB/array fields specifically designed to be additive
per-object provenance, per `ux-14.5-knowledge-exchange-collaboration-
discovery.md` §5 — extending their existing shape, not inventing a new
one). Do not preserve: `workspace_id` (§3.2), `id` (§3.5), any
importing-account-specific state.

### 3.4 Provenance

Recommend one new, additive JSONB field the existing `generation_metadata`
convention already has room for — an `imported_from` block recording:
source account identifier (or, if the exporter chooses anonymity, simply
omitted — see §6.4's disclosure question), package identifier (§3.5),
original object id (for later duplicate-detection, §3.6, and for a
"this was imported" UI badge — a small, cheap addition mirroring
Phase 5's `SharingBadge` precedent), and import timestamp. This is a
direct, minimal extension of a field every relevant table already has
(`notes`, `chapter_summaries`, `flashcards`, `highlights`,
`knowledge_nodes` all already carry nullable `generation_metadata:
Record<string, unknown>`), not a new column, and not a new table.

### 3.5 Identifier strategy

**Never preserve the source `id` on import.** Every primary key in this
schema is a Postgres-generated UUID with no cross-table meaning beyond
its own row — reusing a source id on import would risk colliding with an
unrelated row that already exists (in the *same* database, across
accounts) with that id, and would incorrectly imply identity continuity
this document has already rejected (§2.1, §3.4's "original object id"
is recorded as a **reference**, in `generation_metadata`, specifically
so it's inert data rather than a foreign key with real consequences).
Every imported row gets a fresh id via the same `insert()` path every
other create operation already uses.

### 3.6 Duplicate detection and conflict handling

This is the sharpest open question the audit surfaces, and it should be
answered narrowly, not generically:

- **For Notes/Documents/Assets** (user-authored or uploaded content):
  no automatic dedup. Two notes with the same title are not the same
  note — this app has never treated title as an identity key for
  user-authored content (`notes` has no unique constraint on title
  anywhere), and inventing fuzzy-content-matching dedup for freeform
  prose is real, unscoped complexity with no existing precedent to build
  on. Recommend: always create a new row; if the importer later notices
  a duplicate, they delete it manually, the same way they'd handle any
  other accidental duplicate today.
- **For Knowledge Nodes** specifically: this is where real dedup logic
  already exists and should be reused, not reinvented — `resolveCanonicalNode`
  (§0). On import, run each imported node through the importing
  account's *own* `resolveCanonicalNode` exactly as if it had just been
  freshly extracted from a document, using `(source_type: 'import',
  source_id: <package id>)` as its provenance. If the importer's account
  already has a node with the same normalized title, the existing
  `reuse` branch applies automatically — the import becomes a new
  `knowledge_node_sources` provenance row on the importer's *existing*
  node, not a duplicate node. This gets Phase 6 real, tested dedup logic
  for free, for the one object type that actually needs it, with zero
  new code beyond calling an existing function at a new call site. The
  known race-condition caveat (§0) becomes real under concurrent import
  in a way it wasn't before — flagged as a genuine risk for the roadmap
  (§8), not silently accepted a second time without comment.
- **For Knowledge Links**: no independent conflict question — a link is
  only ever created alongside both its (now-resolved, possibly-deduped)
  endpoints, so "does this link already exist" reduces to "does an
  identical `(source_type, source_id, target_type, target_id)` tuple
  already exist," a cheap existence check before insert, not a
  duplicate-*detection* problem in its own right.

## 4. Intelligence Integrity

### 4.1 What must be rebuilt on import

- **Embeddings** (`embeddings`/`note_embeddings`/`message_embeddings`) —
  always regenerated, never copied. §0 already confirms no code anywhere
  treats embeddings as portable data, and packages should follow that
  same judgment deliberately: an embedding is a function of (content,
  model) — reusing a stale vector risks a silent mismatch if the
  importing account's default provider/model differs from the
  exporter's, and this app already has an established, working pipeline
  for producing correct embeddings from content
  (`SupabaseVectorStore.upsert`, called during ordinary note/document
  creation). Import should call that exact same pipeline, not a
  parallel one.
- **Knowledge node canonical identity** — per §3.6, always re-resolved
  through `resolveCanonicalNode`, never copied verbatim. An imported
  node's identity is only meaningful relative to the *importing*
  account's existing node space.
- **Search indexing** — `indexNote`-shaped calls (per the
  `generateBriefing` precedent, §0) must run for every imported
  searchable object, the same way they run for any freshly created one.
  An imported note that doesn't show up in Universal Search until some
  unrelated event happens to trigger indexing would be a real,
  user-visible bug.
- **Concept-mention linking** — `linkKnownConceptsToSource` (the same
  call `generateBriefing` and ordinary note-save already make) should
  run against imported note/document content, so imported knowledge
  participates in the importing account's existing concept graph the
  same way natively-created content does.

### 4.2 What can be reused as-is

- **The object's own content** (title, prose, quote text, front/back)
  — no transformation needed, it's the whole point of the export.
- **`generation_metadata`/`source_chunk_ids` structure** — these fields'
  *shape* travels unchanged; only their *scope* changes (source chunk
  ids reference chunks that only exist in the exporter's account and
  become meaningless post-import — recommend clearing `source_chunk_ids`
  on import specifically, since a stale chunk id pointing at nothing in
  the importer's account is worse than an honest null, while keeping
  `generation_metadata`'s descriptive fields like `creationMethod`
  intact).
- **`knowledge_links` edge *shape*** (source_type/target_type vocabulary)
  — the polymorphic link model itself needs no change; only which
  specific ids populate it changes, once both endpoints have been
  imported and assigned fresh ids (§3.5).
- **The existing evidence-resolution machinery** — `listCollectionItems`/
  `resolveSourceItems`/`EvidenceItem` (§0) are exactly the right tools
  for *building* a package's manifest in the first place (walking a
  collection's polymorphic membership into a flat, typed list of
  included objects) — this is real, existing infrastructure Phase 6
  implementation should call, not duplicate.

### 4.3 Collaboration and future agents

Imported content, once landed in a workspace, is subject to **exactly
the same Phase 1–5 RLS and role-gated UI** as any natively-created
object in that workspace — no special-casing. This is a direct
consequence of §3.1/§3.5: an imported note is, from the moment it's
inserted, indistinguishable at the database level from any other note
the importer created by hand. It gets a `SharingBadge`/`OwnershipLine`
(Phase 5) exactly like anything else, gets `canEdit`/`canDelete` gating
exactly like anything else, and needs zero Knowledge-Exchange-specific
collaboration code. This is a genuine architectural win worth stating
plainly: **because Phase 6 is a snapshot/copy model, it inherits Phase
1–5's entire collaboration and permission story for free**, the moment
import completes. The only Phase-6-specific work is getting a correct,
complete, properly-attributed row into the database in the first place
— everything downstream is already built.

For future agents specifically (§7 below expands this): an agent acting
on imported content should be bound by the same rule §4.3 of
`ux-14.5-knowledge-exchange-collaboration-discovery.md` already
established for AI acting on shared content — no distinct identity, no
elevated permission, scoped strictly to whatever role the invoking human
member holds. Nothing about import changes that; an imported note is
just a note.

## 5. Personal Intelligence Boundary

Confirming, per-item, using the same evidentiary standard Phases 1–5
established (read the actual RLS/migration, not just the object's name):

### 5.1 Confirmed personal — must never be included in any package, ever

- **`ai_memory`** — never touched by *any* workspace-sharing RLS
  extension across all of Phases 1–4 (confirmed: `0031_shared_knowledge_
  objects.sql`'s own header states this explicitly, §0). The rule from
  `ux-14.5.3-intelligence-object-access-model.md` §3.3 — "content that
  was true of the person before the workspace existed... must never
  become visible to a teammate as a side effect of workspace
  membership" — applies with *at least* equal force to Knowledge
  Exchange, since crossing an account boundary is a strictly stronger
  disclosure than crossing a role boundary within one workspace. No
  package, of any scope, should ever be able to include an `ai_memory`
  row, directly or indirectly (e.g. bundled as a knowledge node's
  "evidence" — package construction, §4.3, must explicitly exclude
  `ai_memory` from every evidence-resolution path it reuses from §4.2).
- **`provider_overrides`** — per-account runtime provider enable/disable
  state (`0014_provider_overrides.sql`'s own header: "runtime provider
  enable/disable, per account"). Meaningless to a recipient — it
  describes the *exporter's* provider configuration, not any content.
- **Confidence history** (`ai_memory.confidence`, added `0027_ai_memory_
  confidence.sql`) — inherits `ai_memory`'s boundary directly; it isn't
  a separate table, it's a column on the table already excluded above.
- **AI runtime state** (`ai_requests`) — per-account usage/cost/latency
  log, append-only by RLS design (§6 of the original discovery doc), and
  explicitly named in §3.1 of the object-access-model doc as "not
  naturally a teammate's business" even at the *workspace* level, let
  alone across accounts.
- **Preferences generally** — `reading_progress` (§1's "never
  transferable" already covers this) and any future per-account setting
  following this same shape.

### 5.2 The one correction to the brief's assumption

**`workspace_objectives`** is explicitly named in the brief's list
alongside these — but per §0's audit finding, it is **not** personal
today. `0031_shared_knowledge_objects.sql` deliberately reclassified it
into the shareable bucket, granting it the identical four-command
workspace-role RLS split every other shareable object gets. This is a
real product decision already made and shipped, not an oversight to
silently preserve.

Recommend: **`workspace_objectives` should be treated the same as
`notes`/`documents`** for Knowledge Exchange purposes — optionally
transferable, following the same package-construction rules as any
other workspace-shareable content — *not* folded into §5.1's
never-transferable bucket just because the brief's prompt listed it
alongside genuinely-personal items. Silently overriding a shipped,
deliberate architecture decision to match an outdated assumption would
be a worse outcome than flagging the discrepancy plainly, which is what
this section does.

### 5.3 Why this boundary is even more load-bearing for Exchange than for Collaboration

Phases 1-5's personal boundary had a natural backstop: even in the worst
case (a bug in the workspace-role gating), the "attacker" was a
workspace co-member the account owner had already, explicitly, chosen to
invite. Knowledge Exchange's package-construction step has no equivalent
backstop — a package is explicitly *built to leave the account*, headed
to a recipient who may be a stranger the account owner has never
interacted with inside the app at all. This means package construction
(§4.3, whatever code eventually builds a package's manifest) must
**allow-list** transferable object types explicitly (build the query
that says "include documents, notes, ... " and stop) rather than
**deny-list** personal ones (a helper that says "include everything
except ai_memory, ..." and hope the list is exhaustive forever). An
allow-list fails safe — a future object type nobody thought to add to
the deny-list defaults to *excluded*, not silently included. This is a
concrete implementation constraint for §8, not just a philosophical
preference.

## 6. Exchange Lifecycle

Mapping the brief's eight named stages onto what this codebase already
has and what each stage genuinely requires:

1. **Package Creation** — a user selects a scope (one note, one document
   + its derivatives, one knowledge collection recursively resolved via
   §4.2's existing `listCollectionItems`/evidence-resolution machinery).
   Output: an in-memory package structure (§7's roadmap treats the exact
   serialization format — likely a JSON manifest, an evolution of the
   existing markdown export's *content* but with real structure — as
   implementation detail, not a discovery-phase decision).
2. **Validation** — apply §5.3's allow-list at construction time (reject/
   silently-exclude any object type not on the allow-list, regardless of
   how it was reached — e.g. a `knowledge_links` traversal that would
   otherwise pull in an unintended object); verify every included
   `knowledge_links` row has both endpoints present in the package
   (§1's Knowledge Links row) or drop the dangling link; verify total
   package size is bounded (a concrete, cheap safety check — no existing
   precedent for unbounded export exists to reuse, so this is new,
   narrow logic, not a gap).
3. **Export** — serialize the validated package. Reuses `downloadTextFile`'s
   proven client-side-blob pattern (§0) for the "download a file" case;
   a "hand this package directly to another workspace/account within the
   same NOVA PIP instance" case (§8's smallest-slice candidate) can skip
   serialization to a file entirely and pass the validated in-memory
   structure straight to Import, avoiding a round-trip through a file
   format altogether for the common case.
4. **Transfer** — for the cross-instance/file-based case: however the
   file physically moves (download + re-upload, email attachment, etc.)
   is entirely outside this app's concern, exactly like the existing
   Export Knowledge Package feature today. For the same-instance case:
   no transfer step exists at all — it collapses into Export directly
   handing off to Import, which is exactly why the same-instance case is
   the cheaper, lower-risk slice to build first (§8).
5. **Import** — per §3's full model: parse/validate the package
   structure again (never trust a package as pre-validated just because
   it came from this app's own Export — the file could have been
   hand-edited, or come from a different app version with a different
   schema shape), resolve workspace assignment (§3.2, always explicit),
   create new rows under the importer's `user_id` with fresh ids (§3.1,
   §3.5).
6. **Verification** — confirm every object that was supposed to import
   actually landed (a straightforward count/id-list check against the
   package manifest — the same class of check `mergeNotesIntoOne`
   implicitly relies on today by doing its writes before its deletes,
   §0), and surface a clear success/partial-failure report to the
   importer rather than a silent all-or-nothing.
7. **Integration** — §4.1's rebuild list runs here: embeddings
   regenerated, `resolveCanonicalNode` invoked for nodes, search
   indexing triggered, concept-mention linking triggered. This is the
   stage where an imported object stops being "freshly inserted rows"
   and starts being genuinely usable the way any native object is.
8. **Knowledge Graph Update** — a direct consequence of Integration, not
   a separate mechanism: once `resolveCanonicalNode` and
   `linkKnownConceptsToSource` have run (stage 7), the importing
   account's knowledge graph already reflects the import — there is no
   separate "now update the graph" step to design, because the existing
   extraction pipeline's own graph-update mechanism *is* what stage 7
   invokes. Naming it as a separate stage in the brief is a correct
   description of the *outcome*, not evidence that new graph-update
   machinery needs to be built — reusing what §4.2 already inventories
   satisfies it entirely.

## 7. AI Implications

The brief asks specifically what architectural decisions should be made
*now* to avoid a future redesign, for capabilities this codebase does
not yet have. Answering narrowly, per capability, rather than
speculatively designing any of them:

- **Voice Intelligence** — no architectural dependency on Knowledge
  Exchange either direction, *provided* Exchange's package format
  (§6, stage 1/3) stores content as structured data (title/content/
  metadata fields) rather than only as rendered markdown prose. A future
  voice interface would want to read structured fields (to decide what
  to say, in what order) rather than parse prose back out of a markdown
  export — the one concrete "decide now" item this raises: **build the
  package manifest as structured JSON with the markdown export as one
  possible *rendering* of it, not the other way around** (i.e., don't
  make markdown-as-source-of-truth a Phase 6 decision that a later voice
  feature would need to unwind).
- **Agent Framework** — the load-bearing decision is already made, by
  inheritance from Phases 1–5, and restated in §4.3: an agent acting on
  imported (or any) content has no distinct identity or elevated
  permission, period. The one Exchange-specific addition: if a future
  agent is ever the one *constructing* or *triggering* a package export
  on a user's behalf, it must be subject to the identical §5.3 allow-list
  the human-triggered path uses — there is no code path, human or agent,
  that should ever be able to reach `ai_memory` during package
  construction. Recommend this be stated as an explicit invariant now
  (in whatever implementation eventually lands, not asserted here) so a
  future agent-framework design doesn't have to rediscover it.
- **Expert Plugins** — no decision needed yet; nothing in this codebase
  hints at what a "plugin" would even be structurally. Flagging only:
  if plugins ever produce content that becomes exportable, that content
  should flow through the *same* `generation_metadata`/`creationMethod`
  provenance convention every other AI-generated object already uses
  (§0's `generateBriefing` precedent) — not a plugin-specific provenance
  shape. This is a restatement of an existing convention, not a new
  decision.
- **Shared research / organizational knowledge** — this is the
  multi-recipient extension of what §1–§6 already design for a single
  exporter/single importer. Nothing about the snapshot model prevents
  "export once, multiple people import the same package" — each import
  is independently a fresh-rows-under-the-importer's-account operation
  (§3.1), so N imports of one package is just N independent instances of
  the same Import stage, no new mechanism required. No decision needed
  now beyond confirming the model already scales this way, which it
  does by construction.

**The one genuine "decide now" item, restated plainly**: structure the
package format as typed, structured data from day one (§7's Voice
Intelligence point), not prose-first with structure retrofitted later.
Everything else these four areas might eventually need is either already
guaranteed by the snapshot model's own shape, or is explicitly out of
scope until a real, validated need exists — consistent with the brief's
"no speculative enterprise architecture" constraint.

## 8. Implementation Roadmap

### 8.1 Smallest valuable slice

**Same-instance, single-collection export → import**, entirely within
this app (no file download/re-upload round trip): a user selects a
`knowledge_collections` scope, the system resolves its full membership
via existing `listCollectionItems` (§4.2 — zero new resolution logic),
constructs a validated in-memory package (§6 stages 1–2), and a second
account (a workspace they're a member of, or their own personal space)
imports it directly (§6 stage 5, skipping stages 3–4 entirely since
there's no file boundary to cross). Scoped to **Notes only** as the
transferable content type for this first slice — no Documents/Assets
(defers the storage-copy problem, §1's flagged caveat, entirely), no
Knowledge Nodes/Links (defers §3.6's dedup-under-concurrency risk
entirely). This mirrors this engagement's own established discipline
(stated explicitly in the original discovery's §7.3: "prove the pattern
on one table before generalizing it," the same sequencing Phase 1 used
for `notes` before Phase 3 generalized to the rest of the object model).

### 8.2 Phased plan

| Phase | Scope | Value | Complexity | Migration safety |
|---|---|---|---|---|
| **6A — Package construction & same-instance import, Notes only** | §8.1's smallest slice. New: a package-manifest TypeScript shape (application-layer only — see below), construction logic reusing `listCollectionItems`, an import function creating fresh `notes` rows per §3. | Proves the entire lifecycle (§6) end-to-end on the lowest-risk object type. | Low — no new tables strictly required (a package can be a pure in-memory/JSON structure passed through application code; persistence, if wanted for "package history," is additive and deferrable to 6D). | Zero schema risk — no RLS touched, no migration needed for the core mechanism. |
| **6B — Extend to Documents/Assets, including storage copy** | Solves §1's flagged storage-boundary caveat: a real cross-account (or cross-workspace) storage copy mechanism for the `documents`/`assets` private buckets. | Unlocks the two highest-value, highest-file-size object types. | Moderate-high — this is genuinely new infrastructure (no existing precedent for cross-user storage copy, confirmed §1), not a repeat of an established pattern. | Additive (new storage-copy code path), but needs its own dedicated security review before shipping — a storage-level access boundary is a different risk class than a table RLS OR-clause. |
| **6C — Knowledge Nodes/Links, with re-resolution dedup** | Wires §3.6/§4.1's `resolveCanonicalNode`-based import-time dedup. | Completes the "knowledge graph continues across the exchange" promise in the brief's own framing. | Moderate — reuses existing resolver logic (low code-complexity), but §0/§3.6's flagged race-condition risk becomes real under concurrent multi-account import for the first time; needs either an accepted-risk sign-off (matching the existing accepted trade-off) or a real fix (a hard uniqueness constraint + upsert-on-conflict, which Phase 9A's own migration comment already named as the not-yet-taken option). | Whichever risk resolution is chosen should be a deliberate decision made in 6C's own design pass, not inherited silently from Phase 9A's original acceptance, since concurrency risk changed materially (§3.6). |
| **6D — Cross-instance file export/import** | The full §6 stages 3–4: real file serialization + a file-based import path (parse-and-validate an untrusted uploaded package, §6 stage 5's explicit "never trust a package as pre-validated" note). | Extends Knowledge Exchange beyond this single deployed instance — the literal "across people" case when those people don't share an account database at all. | Moderate — the validation/parsing logic for an externally-sourced file is new attack surface (a hostile or malformed package must never be able to corrupt the importer's account) that 6A–6C's same-instance-only scope never has to consider. | No schema risk on its own; the real risk is application-layer input validation, which needs the same "security review before shipping" posture as 6B. |

### 8.3 Highest-risk components, named explicitly

1. **Storage-level copy (6B)** — genuinely new infrastructure, no
   existing pattern to lean on, the one place this roadmap recommends a
   dedicated security review before implementation rather than folding
   review into the normal per-phase verification gate.
2. **Untrusted file import (6D)** — the first place this app would ever
   parse externally-sourced structured data and use it to create
   database rows; needs rigorous validation (schema shape, size bounds,
   reference integrity — §6 stage 2/5) since "a malicious or malformed
   package" is a real threat model that same-instance-only 6A–6C never
   faces.
3. **Concurrent knowledge-node dedup (6C)** — the one place an *existing*,
   previously-accepted trade-off (§0/§3.6) stops being safely acceptable
   under Phase 6's new concurrency profile; needs an explicit decision,
   not a silent carry-forward.

### 8.4 Deferred capabilities

- Live/hybrid package semantics (§2) — deferred indefinitely pending a
  validated need beyond what snapshot already serves.
- Conversations as a first-class package object (§1) — deferred in
  favor of the existing "save conversation as note" conversion path.
- Automatic dedup for Notes/Documents/Assets (§3.6) — deferred; manual
  cleanup is the accepted answer until real evidence says otherwise.
- Package "history"/audit persistence (a `knowledge_packages` table
  recording who exported/imported what, when) — genuinely useful
  eventually, explicitly not required for 6A's mechanism to work
  (§8.2's note), deferred to whenever a real need for audit/re-import
  tracking is validated rather than spec'd speculatively now.
- Any UI for package browsing, a "marketplace," or organizational
  knowledge sharing at scale — no UI work in this document at all per
  the brief's constraints, and no architecture proposed for anything
  beyond what §7 already covers.

### 8.5 Do Not Build Yet

- **Cross-account live references** (§2.1) — no validated need, and the
  authorization primitive it requires doesn't safely exist in this
  schema today.
- **A generic "attachments" abstraction** — no such concept exists
  (§0/§1), and inventing one specifically to make Knowledge Exchange's
  design cleaner, rather than because the product needs it independent
  of Exchange, is exactly the kind of premature abstraction this
  engagement has consistently avoided elsewhere.
- **Fuzzy/semantic duplicate detection for freeform content** (Notes/
  Documents) — §3.6 already recommends against this; no existing
  precedent, real unscoped complexity (embedding-similarity thresholds,
  false-positive handling), no validated demand yet.
- **A package "marketplace" or public/anonymous package discovery** —
  no public/anonymous access path exists anywhere in this app
  (`ux-14.5.4-collaboration-implementation-blueprint.md` §9 already
  names "public sharing links" as explicitly out of scope for
  collaboration generally), and Knowledge Exchange should not be the
  phase that quietly reopens that question.
- **Real-time package sync / "subscribe to updates"** — this is the
  hybrid model (§2.1) restated as a feature name; same rejection
  reasoning applies.
- **Organization-level knowledge exchange policies** (approval
  workflows, org-wide package governance) — no organization concept
  exists in this schema at all (`ux-14.5.4-collaboration-implementation-
  blueprint.md` §9's "Enterprise organizations — no validated demand
  yet" applies here without modification).

## 9. Summary

Knowledge Exchange is architecturally simpler than Phases 1–5's live
collaboration model, not harder, *because* it deliberately does not try
to solve live cross-account access — it's a well-scoped copy operation
between two accounts that already, individually, have full ownership
authority over their own resulting rows. The recommended shape:
**immutable snapshots**, an **allow-list-based** package-construction
boundary that never risks including personal intelligence (§5), an
**import path that fully re-integrates** with existing search/graph/
embedding machinery rather than treating imported content as
second-class (§4), and a phased rollout that proves the mechanism on the
lowest-risk object type (Notes, same-instance) before taking on the two
genuinely new risk surfaces this brief's scope implies: cross-account
storage copy (6B) and untrusted-file import (6D). No implementation
begins until this document is explicitly approved.
