# Founder Command Center & AI Governance — Discovery Report

Read-only audit performed before any implementation, per this phase's own instruction ("Do not implement until discovery is complete"). Baseline: `main` @ `91b66a0` — the Beta/Admin/AI Governance Foundation phase that shipped `platform_admins`, the four `admin_*` RPCs, `AdminDashboardPage` (v1), and the provider-entitlement model (Free/Beta hidden, Pro/Enterprise via Advanced Settings, Founder via Admin Dashboard).

## 1. Current architecture map

### Authentication & authorization
- `auth.users` (Supabase Auth) + `profiles` (`id`, `email`, `display_name`, `default_chat_provider_id`, timestamps) — one row per user, self-service RLS `UPDATE` (`auth.uid() = id`).
- Workspace ownership: `workspaces.user_id` (implicit single-owner) + optional `workspace_members` rows (explicit `owner`/`editor`/`viewer`) for workspaces created after `0028_workspace_members.sql`. Its `has_workspace_role()` (SQL, `SECURITY DEFINER stable`) + `resolveWorkspaceRole()` (TypeScript, same logic) is the one established "client and database must agree" pattern in this codebase — already reused as the template for platform-admin auth.
- **Platform admin**: `platform_admins(user_id, granted_at, granted_by)` — separate table (not a `profiles` column, since `profiles`' self-service UPDATE would make a boolean self-assignable), RLS: self-`SELECT`-only, zero write policies. `is_platform_admin(uid default auth.uid())` — `SECURITY DEFINER stable`, grants: `authenticated` only. One row exists: `dan@nolmark.co`.
- Four existing `SECURITY DEFINER` admin RPCs, each re-checking `is_platform_admin()` internally and raising on a non-admin caller: `admin_list_users()`, `admin_list_beta_invites()`, `admin_create_beta_invite(...)`, `admin_revoke_beta_invite(...)`. **All read/create/delete beta-invite-shaped data only — none of them can change a plan, reset a quota, or touch account status.** That's the gap this phase closes.
- Route guard: `RequireAdmin` (`src/modules/admin/RequireAdmin.tsx`) — spinner while `usePlatformAdmin()` loads, `<Navigate to="/" replace/>` for a non-admin, else children. Already wraps `/admin`, `/settings/ai-health`, `/settings/ai-health/provider/:id`.

### Plans & entitlements
- `plans` (free/beta/pro/enterprise, RLS: authenticated-read-all), `plan_quotas` (`plan_id`, `quota_key`, `quota_limit`, `quota_period`, RLS: authenticated-read-all), `user_plan_assignments` (`UNIQUE(user_id, active)` prevents duplicate active assignments, RLS: own-row-`SELECT`-only), `quota_usage` (period-scoped via `UNIQUE(user_id, quota_key, period_start)`, RLS: own-row-`SELECT`-only).
- **No write policy exists on any of the four tables for any client role** — every write goes through a `SECURITY DEFINER` function. Today that's exactly two: `assign_default_plan()` (trigger, `AFTER INSERT` on a new user) and `consume_quota(quota_key)` (atomic upsert-increment, resolves caller via `auth.uid()`, not a client-supplied id).
- **There is currently no RPC that can change an existing user's plan, and no RPC that can reset/adjust quota usage.** `user_plan_assignments`/`quota_usage` are effectively write-once-then-append from the client's perspective — a founder today cannot upgrade a user's plan or clear their usage through any sanctioned path. This is the primary gap Phase 3/4 of this task closes.
- `src/modules/plans/` (new last phase): `getCurrentUserPlan(userId)` (direct table reads, fine under existing RLS), `canSelectProvider(planCode)` — `pro`/`enterprise` only, explicitly documented as a presentation-layer decision, not a security boundary.

### AI architecture
Confirmed unchanged from the prior discovery pass (`docs/beta-admin-ai-governance-discovery.md` §6), re-verified this session:

```
User message
  → useSendMessage → AIService.sendMessage
  → resolveProviderChain(preferred, chatProviders, availability, overrides, healthScores) → string[] (ordered candidate ids)
  → runWithFallback(chain, streamChatCompletion)     // sequential, first success wins
  → streamChatCompletion → provider.chat() → streamAiChat() (raw fetch, real streaming)
  → supabase/functions/ai-chat (Deno)                // the ONLY place that reads Deno.env.get('ANTHROPIC_API_KEY' | 'OPENAI_API_KEY' | 'GOOGLE_API_KEY')
  → actual Anthropic/OpenAI/Google HTTP call
  → response streamed back, logged to ai_requests (provider, requested_provider, fallback_reason, tokens, latency, status)
```
- Two registries, correctly separated: `providerRegistry` (`src/modules/core/providers/registry.ts` — static metadata: id/label/kind/status/models) vs. `chatProviders` (`src/modules/ai/providers/registry.ts` — runtime `ChatProvider` implementations). Neither stores or ever sees an API key.
- **`resolveProviderChain()` has no concept of an admin-settable "priority" or "fallback order" today.** Ordering is: the caller's preferred provider first (if eligible), then the remaining eligible candidates sorted by live `healthScore` (from `useAiHealth`, itself derived from recent `ai_requests` success/failure/latency — nothing stored, nothing admin-configured). "Priority" as the new task's Phase 5 describes it (a founder-settable, persisted ordering) **does not exist as data anywhere** — it would need new, additive schema, not a change to the resolver's existing signature/behavior.
- **Provider identity is not exposed to Free/Beta anywhere** (confirmed still true) — `ChatPage`/`ReaderChatPanel` are fully provider-neutral; only `/settings/advanced` (gated by `canSelectProvider`) and the Admin Dashboard show provider names.
- API keys: confirmed again, no leak. Read exclusively inside `supabase/functions/ai-chat/index.ts` / `supabase/functions/provider-availability/index.ts` via `Deno.env.get`.

### Existing admin surface
- `AdminDashboardPage` (`/admin`, `RequireAdmin`-gated) — a single page, six `SurfaceCard` sections (Overview stat tiles, Beta Invites table + create form, Users table, Plans & Quotas cards, AI Providers via `<ProviderStatusCard/>`, System Health stat tiles). No sub-routes, no per-user detail view, no mutation beyond beta-invite create/revoke.
- Reused UI primitives throughout this codebase (and the natural fit for the new pages): `SurfaceCard`, `Button`, `Input`, `Spinner`, `ConfirmDialog`, `EmptyState`, plain semantic-Tailwind `<table>` markup (no dedicated DataTable component exists — every list in this app, admin or otherwise, is a hand-rolled `<table>`), `HealthScoreBadge`.
- **Two real defects found in the existing v1 dashboard**, both worth fixing as part of this phase rather than carrying forward:
  1. **"AI requests (recent)" / "Recent AI errors" / "Providers reachable" are silently scoped to the founder's own `ai_requests` rows, not the platform's.** `useRecentAiRequests` → `listRecentAiRequests` reads `ai_requests` directly under RLS (`auth.uid() = user_id`, `0006_ai_governance.sql`) — there is no cross-user read path. On a real multi-user platform this makes every AI-usage number on the dashboard wrong (it shows the founder's own chat activity, not the platform's). Needs a `SECURITY DEFINER` bridging RPC, same pattern as the other four `admin_*` functions.
  2. **The "AI Providers" section's Enable/Disable toggle is not platform governance — it's the founder's *personal* `provider_overrides` row.** `ProviderStatusCard` → `useProviderIntelligence` → `useSetProviderOverride` writes to `provider_overrides` scoped to `auth.uid()`. If the founder disables Anthropic here today, it turns Anthropics off for the founder's own chat, not for Free/Beta/Pro users — the dashboard currently presents this as if it were platform-wide control, which is misleading for a genuine "AI Governance Console." No platform-wide provider settings table exists at all yet (confirmed: `provider_overrides` is `RLS: auth.uid() = user_id` for every operation, no platform-wide row concept).
- Sidebar: one conditional "Admin" nav item (`usePlatformAdmin()`-gated), linking to `/admin` only — no sub-nav for `/admin/users`, `/admin/plans`, `/admin/ai`.
- Pro's Advanced Settings (`/settings/advanced`, `AdvancedSettingsPage.tsx`) — already built last phase, gated by `isAdmin || canSelectProvider(plan?.planCode)`, a single `ProviderSelect` wired to `profiles.default_chat_provider_id`. **This already satisfies almost all of this task's Phase 6** ("Pro Advanced AI Settings" — optional preferred provider, default stays automatic routing). The one gap: no "preferred model" control exists yet, only preferred provider (the brief mentions both); `ProviderSelect` has no per-model picker today, and no `profiles` column stores a preferred model. This is a small, additive, and genuinely optional extension — flagged for the recommended order below, not assumed required.

## 2. Missing capabilities (what this phase actually needs to build)

1. **Separate admin routes** `/admin/users`, `/admin/plans`, `/admin/ai` (the brief's own routing ask) — currently one page. The existing `/admin` Overview page stays as the landing page; the three new routes get their own nav sub-items.
2. **`admin_change_user_plan(target_user_id, new_plan_id)`** — no write path to `user_plan_assignments` exists today for anyone but the two existing triggers/RPCs. Must deactivate the current active assignment and insert a new active one atomically (respecting the existing `UNIQUE(user_id, active)` constraint), `SECURITY DEFINER`, admin-only.
3. **`admin_reset_user_quota(target_user_id, quota_key)`** — no write/delete path to `quota_usage` exists for anyone. Deletes (or zeroes) the current-period row only — never touches historical periods, preserving usage history the same way `admin_revoke_beta_invite` never touches an already-accepted invite.
4. **`admin_set_user_disabled(target_user_id, disabled boolean)`** — no account-disable mechanism exists anywhere (no `profiles` column, no `auth.users.banned_until` usage). Real SaaS-grade "Disable account" needs to actually block sign-in, not just hide UI — see §3 for the specific mechanism and its safety constraint (no self-disable).
5. **Platform-wide AI provider governance** — genuinely new schema. A `platform_provider_settings(provider_id primary key, enabled, priority, updated_by, updated_at)` table (founder-write via RPC only, authenticated-read-all so `resolveProviderChain` can factor it in) is what turns "AI Governance Console" from personal settings into real platform control. `resolveProviderChain()` needs one additive, backward-compatible extension (an optional parameter) — never a rewrite of its existing preferred→health-score logic, per this phase's explicit "do not redesign existing AI routing" constraint.
6. **Admin-wide AI usage RPC** — `admin_ai_usage_summary()`, bridging `ai_requests`' own-row-only RLS the same way the four existing `admin_*` functions bridge `profiles`/`beta_invites`, so the dashboards' usage numbers are actually platform-wide.
7. **Knowledge counts for the Overview dashboard** (Documents/Conversations/Notes/Collections platform-wide) — `documents`/`conversations`/`notes`/`knowledge_collections` are all owner-scoped RLS tables; a lightweight admin RPC (`admin_platform_counts()`) returning `count(*)` per table is the simplest correct approach — no need to expose row contents, just aggregate counts, which is the minimum the brief's "Knowledge" overview cards actually need.
8. **Preferred model** on Advanced Settings (optional, small) — extends the already-built Pro provider-preference surface with a second, equally-optional field. Not blocking; can be deferred if it doesn't fit cleanly without its own schema decision (which provider's model list applies when no provider is chosen yet).

### 2a. Addendum: a schema defect found while preparing the plan-change migration

Live-schema check (`information_schema`/`pg_constraint`) before writing `admin_change_user_plan` surfaced a real blocker: `user_plan_assignments` has a literal `UNIQUE (user_id, active)` constraint (not a partial index), which caps each user at **at most one active row and at most one inactive row, ever**. The first plan change works; a second plan change for the same user fails on that constraint, because deactivating the current row would try to create a second `(user_id, false)` row. Confirmed live: exactly 1 row total exists today (the founder's own initial assignment, still active) — no data at risk. This is the same class of "at most one active X per user" invariant `0028_workspace_members.sql`'s `workspace_members_one_active_owner_idx` already expresses correctly as a **partial** unique index (`... where role = 'owner' and status = 'active'`). Fixed in `0036` by replacing the flawed table-level constraint with the equivalent partial index (`unique on user_plan_assignments (user_id) where active`), which permits unlimited inactive history rows while still guaranteeing at most one active assignment — a repair, not a redesign, following the same "smallest safe fix, matching an established in-codebase pattern" approach as the prior phase's `beta_invites` defects.

## 3. Security considerations

- **Every new mutation follows the established pattern exactly**: a `SECURITY DEFINER` SQL function that calls `is_platform_admin()` first and `raise exception` if false. No new admin capability is ever a direct client table write — this was already the explicit lesson from the prior phase (`profiles`' self-service UPDATE policy is why `platform_admins` had to be a separate table) and it generalizes: plan changes, quota resets, account disabling, and platform provider settings all go through the same choke point.
- **Self-disable protection**: `admin_set_user_disabled` must reject `target_user_id = auth.uid()` — otherwise a founder (accidentally or via a compromised session) could lock themselves out of the only account that can undo it, since granting admin status has no client-reachable path at all (by design, from the prior phase).
- **Account disabling mechanism**: the correct SaaS-grade approach is `auth.users.banned_until` (Supabase Auth's own field — GoTrue checks it on sign-in and token refresh, so a disabled user is actually locked out, not just UI-hidden). This requires a `SECURITY DEFINER` function to `update auth.users set banned_until = ...` — the same `auth` schema this session's functions already *read* from (`admin_list_users` joins `auth.users` for `last_sign_in_at`) without issue. Since function owner privileges (not caller privileges) govern a `SECURITY DEFINER` function, and migrations run as a sufficiently-privileged role in this project, the write should succeed the same way the existing `enforce_beta_invite_gate` trigger's write path to `auth.users` (an `INSERT` gate) already does. **Contingency**: if the live migration apply reports a permissions error on this specific `UPDATE`, the fallback is an app-level `profiles.disabled_at` flag checked in `AuthContext` (sign the user out client-side, block new sessions) — weaker (doesn't invalidate an already-issued, not-yet-expired JWT) but still additive and safe. This will be resolved empirically during Phase 4 implementation and reported honestly either way, not assumed.
- **Platform provider settings must never let a client bypass the existing key-presence gate.** `platform_provider_settings.enabled = false` can only ever *remove* a provider from `resolveProviderChain`'s eligible set — it must be combined with (never replace) the existing `isProviderAvailable` (key-present-and-not-personally-overridden) check. A provider with no API key configured can never become "available" no matter what the founder sets platform-wide.
- **RLS on all new tables**: `platform_provider_settings` — authenticated-read-all (so routing logic and the AI Governance Console can both read current settings), zero client write policies (write only via a `SECURITY DEFINER` RPC, admin-checked). No new table in this phase gets a client-reachable write policy, matching every existing precedent since `platform_admins`.
- **`admin_ai_usage_summary()`/`admin_platform_counts()` return aggregates only** (counts, sums, averages) — never raw per-user row contents beyond what `admin_list_users` already exposes. Keeps the "no invented metrics, no unnecessary exposure" principle from the original Founder Dashboard brief intact.
- **No provider API keys are ever placed in any new table, RPC return value, or client-visible field.** `platform_provider_settings` stores only `provider_id`/`enabled`/`priority` — identical in shape to what `providerRegistry` already exposes client-side today (provider *identifiers*, not credentials).

## 4. Recommended implementation order

1. Migration `0036_founder_command_center.sql`: `platform_provider_settings` table + RLS; `admin_change_user_plan`, `admin_reset_user_quota`, `admin_set_user_disabled` (with self-disable guard), `admin_set_platform_provider_setting`, `admin_ai_usage_summary`, `admin_platform_counts` — all additive, all `SECURITY DEFINER`, all admin-checked. Applied and empirically verified (including the `auth.users` write contingency above) before any UI is built on top of it.
2. `src/modules/admin/api/adminApi.ts` + `useAdminData.ts` — thin wrappers for the six new RPCs, matching the existing four's exact shape.
3. `resolveProviderChain()` — one additive optional parameter (`platformSettings`) folding in `platform_provider_settings`; existing tests must pass unchanged (no signature-breaking change, no behavior change when the parameter is omitted).
4. Router: `/admin/users`, `/admin/plans`, `/admin/ai` as new `RequireAdmin`-gated routes; `/admin` (Overview) stays as-is content-wise but its stat tiles switch to the new platform-wide RPCs instead of the founder-scoped ones (fixing finding #1 from §1). Sidebar admin nav gets sub-links.
5. `AdminUsersPage`, `AdminPlansPage`, `AdminAiGovernancePage` — new pages, reusing existing primitives (`SurfaceCard`/`ConfirmDialog`/`EmptyState`/plain `<table>`), no new generic DataTable abstraction (no precedent, not enough call sites to justify one).
6. Optional, small: preferred-model field on `/settings/advanced`, only if it fits without inventing new schema beyond one nullable `profiles` column.
7. Tests: admin-authorization (founder allowed/non-admin denied) for every new RPC wrapper, plan-change success/failure, provider-visibility entitlement (already covered, re-verify unchanged), routing fallback (already covered, re-verify unchanged with the new optional parameter), quota-exhaustion handling (already covered by `quotaService.test.ts`, re-verify unchanged).
8. Manual Supabase checklist (new items only — the December items are already documented in `docs/beta-admin-ai-governance-supabase-checklist.md`).
9. Verification gate: `tsc -b`, `oxlint`, `vitest run` (full suite), `vite build` — classify any failure as introduced/pre-existing/unrelated, never report clean if something remains.
10. `docs/feature-matrix.md` new section + this doc; commit only after `git status`/`git diff --stat` confirms scope (no accidental UX/Knowledge Exchange/routing-file changes beyond the one additive parameter in #3).
