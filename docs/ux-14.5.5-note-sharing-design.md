# UX-14.5.5 — Note Sharing Design (UX-14.5 Phase 2 Discovery)

**Status: discovery only. No schema, no RLS text applied, no code in
this document or its commit.** Architecture must be confirmed before any
implementation — this document is that confirmation step, not the
implementation itself.

Builds directly on UX-14.5 Phase 1 (`workspace_members`,
`resolveWorkspaceRole`, `has_workspace_role` — commit `d05fec1`) and the
blueprint's own recommended sequencing (`docs/ux-14.5.4-collaboration-
implementation-blueprint.md` §7's roadmap, §3's object access matrix
putting `notes` in the workspace-shareable bucket). Nothing here departs
from that plan; this document is where it gets worked out precisely
enough to implement.

## 1. Discovery findings

### 1.1 `notes` table schema and ownership model

From `0010_reconcile_knowledge_tables.sql` (unchanged since):

```
notes: id, user_id, workspace_id (nullable), collection_id (nullable),
       document_id (nullable), title, content, created_at, updated_at
```

Ownership is `user_id` — not-null, `references auth.users on delete
cascade`. `workspace_id` is nullable and, per every prior UX-14.5
document's finding, purely an organizational tag today — RLS never
reads it.

### 1.2 Current RLS

One policy, unchanged since `0010`:

```sql
create policy "Users manage their own notes"
  on public.notes for all
  using (auth.uid() = user_id)
  with check (auth.uid() = user_id);
```

A single `for all` policy — no per-command split. Two child tables
follow the same EXISTS-subquery-against-the-parent pattern Doc 2 §1.1
already named as this schema's existing precedent for relationship-based
access:

- **`note_tags`**: `exists (select 1 from notes where notes.id =
  note_tags.note_id and notes.user_id = auth.uid())` — checks the
  *note's* owner, not the tag row's own (it has no `user_id` column).
- **`note_embeddings`** (`0025_note_search.sql`): identical shape,
  `notes.user_id = auth.uid()`.

**This is the discovery's central finding**: both child policies check
`notes.user_id = auth.uid()` directly — neither goes through
`workspace_id` or any role check. Extending `notes`' own policy with a
`has_workspace_role` OR-clause does **not** automatically extend access
to a shared note's tags or its search embedding — they have their own,
separate EXISTS clauses that would need the identical update. This is
the same structural gap Doc 3 found with `match_document_chunks`
(table RLS and a dependent query/policy are two different things in
this codebase, and both need to change together) — found here in a
second, independent place, which confirms it as a general pattern to
check for, not a one-off.

### 1.3 Note creation/update/delete flows

`src/modules/notes/api/notes.ts` — four functions, all thin:
`listNotes`, `getNote`, `createNote`, `updateNote`, `deleteNote`. None
of them perform an application-level ownership check — `getNote`/
`updateNote`/`deleteNote` all filter only by `.eq('id', id)`, relying
entirely on RLS to enforce who may act on that row. This means: **once
`notes`' RLS is correctly extended, these four functions need zero code
changes** — they already defer entirely to the database, which is
exactly where Phase 2's role logic belongs per the blueprint's design.

`createNote` always inserts `user_id: params.userId` — the calling
user, unconditionally. Creating a note is, and remains, always
self-attributed; there's no "create this on behalf of the workspace"
concept, and none is needed — an editor creating a new note in a shared
workspace does so as themselves, which already satisfies `auth.uid() =
user_id` with no membership check required at all (see §4).

`src/modules/notes/hooks/useNote.ts`'s `save`/`summarize` mutations call
`updateNote` with no pre-check either — same story, defers to RLS.

**One real gap found, not hypothetical**: both mutations' `onSuccess`
call `linkKnownConceptsToSource({ userId: note.user_id, ... })` —
using the **note's original owner's** `user_id`, not the id of whoever
is actually saving. Today that's always the same person (only the owner
could ever open the note), so this has never mattered. The function it
calls, `linkKnownConceptsToSource` →
`recordKnowledgeNodeSource({userId: params.userId, ...})`, inserts into
`knowledge_node_sources`, whose RLS (`0016_knowledge_node_identity.sql`)
is `auth.uid() = user_id`. **The moment an editor who is not the note's
owner saves a shared note, this insert's `auth.uid()` (the editor) will
not equal the `user_id` it's writing (the owner's id), and the insert
will fail RLS — silently**, because the whole call is wrapped in a
`try/catch` that only logs to console (`linkKnownConceptsToSource`'s own
doc comment: "swallows its own errors ... never breaks note/message
saving"). Net effect if left unfixed: an editor's edits to a shared note
would stop contributing to the knowledge graph, with no visible error to
anyone. Flagged here as a required Phase 2 code change (§5), not fixed
in this discovery.

### 1.4 `NoteDetailPage.tsx` permission assumptions

Read directly (`src/modules/notes/pages/NoteDetailPage.tsx`): Save,
Summarize, and Delete buttons are all rendered **unconditionally** —
`disabled={!isDirty}` / `disabled={summarize.isPending}` are the only
conditions on them, never a permission check, because until now there
was never a second person who could view this page at all. Title and
content are always-editable `<input>`/`<textarea>` with no read-only
mode. This is the one real UI assumption Phase 2 has to revisit — not
because it's broken today, but because it will render an edit form and
enabled Delete button for a viewer the instant a shared note exists,
even though the database would correctly reject the mutation. That gap
(a control that's visible but silently fails) is worse UX than the
control never appearing, and is the concrete reason §5 recommends a
small, targeted change rather than "RLS will just handle it."

## 2. Design requirements

**Roles are inherited from workspace membership — not a separate,
per-note-configurable permission.** A note's effective access for a
given user is exactly `resolveWorkspaceRole(note.workspace_id, userId)`
— nothing else. Per the brief:

- **Owner** (the resolved workspace role, not merely the note's own
  creator — see §4's reasoning): full control, including delete of any
  note in the workspace, even one an editor authored.
- **Editor**: read and update. Not delete.
- **Viewer**: read only.
- **A note with no `workspace_id` (or in a workspace the user isn't a
  member of)**: invisible, exactly as today — a workspace role can only
  ever grant access, never take it away from the note's own owner via
  `auth.uid() = user_id`, which stays untouched in every policy below.

**Not building this phase** (per explicit constraint, and consistent
with every prior UX-14.5 document's own scope discipline): a generic,
object-independent permissions framework; public/anonymous links;
external (non-account) sharing; guest accounts. Every one of these would
introduce a second authorization concept alongside `workspace_members`,
which is precisely what §3 rules out below.

## 3. Database design: Option A vs. Option B

### Option A — `notes.workspace_id` + membership-based RLS

Reuse the exact primitive Phase 1 already built and live-verified:
extend `notes`' RLS (and `note_tags`/`note_embeddings`'s) to call
`has_workspace_role(notes.workspace_id, <minimum>)`, per-command. No new
table. A note's permission is always "whatever role you hold in its
workspace" — coarse-grained by design, matching exactly what "inherited
from workspace membership" means.

### Option B — dedicated `note_permissions` table

A new table (`note_id, user_id, role, ...`), independent of workspace
membership — Doc 1's "Option A: personal object sharing," applied
literally per-note. Would let one specific note be shared with one
specific person regardless of workspace membership at all.

### Recommendation: Option A — and it isn't close

Three separate signals in this phase's own brief rule out Option B, not
just a preference:

1. The stated object chain is `Workspace → workspace_members → Notes →
   Note permissions` — membership sits *above* notes in the hierarchy,
   not beside it as an independent structure.
2. "Roles inherited from workspace membership" is a direct statement
   that note access *is* the workspace role — not a role a note can
   independently be assigned.
3. "Do not create: generic permissions framework" directly describes
   what Option B would be: a second, table-specific authorization
   primitive running in parallel to `workspace_members`, which is
   exactly the kind of speculative, premature-generalization structure
   every prior UX-14.5 document has deliberately avoided.

**Security implications**: Option A introduces no new security
primitive — it's a second consumer of `has_workspace_role`, already
proven in Phase 1's live verification. The only residual risk is the
propagation gap from §1.2 (`note_tags`/`note_embeddings` need their own,
matching update) — a checklist item, not a new design problem.

**Migration complexity**: low. One migration: split `notes`' single
`for all` policy into four per-command policies (§4), and update two
existing EXISTS-based policies to route through
`has_workspace_role(notes.workspace_id, ...)` instead of
`notes.user_id = auth.uid()` directly. No new table, no backfill —
every existing note keeps whatever `workspace_id` it already has, and a
`null`-workspace note (or one in a workspace with no other members)
continues to satisfy only `auth.uid() = user_id`, identically to today.

**Future compatibility**: this is the second real data point (after
`workspace_members`'s own RLS in Phase 1) proving `has_workspace_role`
generalizes correctly to an actual content table with child tables and
existing application code built on top of it — directly derisking
Phase 3 of the blueprint's roadmap (`documents`, `knowledge_nodes`,
`knowledge_links`, `conversations`, `knowledge_collections`), which will
reuse this exact recipe.

## 4. RLS design

Current model, restated precisely: personal ownership only, one
`for all` policy, no command differentiation. Target design (not
applied — this is the plan Phase 2's implementation would execute):

| Command | Policy condition | Reasoning |
|---|---|---|
| `select` | `auth.uid() = user_id OR has_workspace_role(workspace_id, 'viewer')` | Owner always; any workspace member at viewer-or-above sees it. |
| `insert` | `with check (auth.uid() = user_id)` — **unchanged** | Creating a note is always self-attributed; no membership check is needed because the inserting user is always inserting as themselves, which the existing clause already covers correctly for an editor creating new content in a shared workspace. |
| `update` | `auth.uid() = user_id OR has_workspace_role(workspace_id, 'editor')` | Owner always; editor-or-above (i.e. editor or workspace owner) can edit. |
| `delete` | `auth.uid() = user_id OR has_workspace_role(workspace_id, 'owner')` | The note's own creator, **or** the workspace owner — "full control" (§2) is read as workspace-owner authority over every note in their workspace, not merely creator-only delete, so a workspace owner can remove a note an editor authored. |

Required-behavior check against the brief's own table:

- **Owner** (workspace role): select ✓, insert ✓ (self), update ✓,
  delete ✓ — full control, as specified.
- **Editor**: select ✓ (clears the viewer minimum), update ✓ (clears
  the editor minimum), delete ✗ (does not clear the owner minimum) —
  "read, update," no delete, exactly as specified.
- **Viewer**: select ✓ only; update ✗, delete ✗ — read-only, exactly as
  specified.
- **Non-member / no workspace**: none of the four conditions hold for
  anyone but the note's own `user_id` — **identical to today's
  behavior**, satisfying "existing users: unchanged."

**Required companion change, not optional**: `note_tags`'s and
`note_embeddings`'s EXISTS clauses must be rewritten to check
`has_workspace_role(notes.workspace_id, 'viewer')` (or the appropriate
minimum for their own command) via a join back to the parent note,
instead of checking `notes.user_id = auth.uid()` directly — otherwise a
shared note's tags panel and search embedding stay invisible/unmanageable
to a teammate even though the note itself is correctly visible, the
exact partial-visibility failure mode Doc 3 §4.1 found with
`match_document_chunks`. This is called out explicitly so it isn't
discovered as a bug after Phase 2 ships.

## 5. Application layer

Evaluated against the actual code (§1.3/§1.4), not assumed:

- **Note API (`notes.ts`)**: no changes required. Every function already
  defers entirely to RLS.
- **Hooks (`useNote.ts`, `useNotes.ts`)**: one real fix required —
  `linkKnownConceptsToSource`'s two call sites in `useNote.ts` must pass
  the *saving* user's id, not `note.user_id`. Concretely: `useNote`
  needs `useAuth()`'s `user.id` (it doesn't currently import `useAuth`
  at all) threaded into that call instead of `note.user_id`. This is a
  minimal, targeted fix — not a redesign of the hook — and it's required
  regardless of Phase 2 shipping, since it's a correctness bug the
  moment a second person can ever save a note, which is this phase's
  entire point.
- **`NoteDetailPage.tsx`**: the one real UI change. Resolve the
  viewer's role for the note's workspace (via `resolveWorkspaceRole`,
  Phase 1's existing resolver — no new primitive) and: hide/disable
  Save, Summarize, and Delete for a `viewer`; hide/disable Delete (but
  keep Save/Summarize enabled) for an `editor`; leave everything enabled
  for `owner` — matching exactly the RLS table in §4, so the UI never
  offers a control the database would reject. This is UI *wiring*, not
  new UI *architecture* — no new component, no dialog, no navigation
  change.
- **Save flows** (`saveMessageToNote.ts`, `SaveConversationDialog.tsx`,
  `mergeNotes.ts`): all go through `createNote`, which is unaffected —
  the note they create is still attributed to whoever ran the save,
  exactly as today. No change needed.

**Explicitly not built this phase** (per the brief): a sharing dialog,
an invitations flow, or any notification. A note becomes shareable the
moment its `workspace_id` is set and the workspace has more than one
member — both of those are Phase 1 primitives already in place; there is
no new "share this note" action to design or build yet.

## 6. AI boundary check

Confirmed directly against the retrieval code (not re-derived from
principle): **none of NOVA's three chat-context retrieval functions
query `notes`, `note_tags`, or `note_embeddings` at all.**
`retrieveContext` queries `document_chunks`/`embeddings`;
`retrieveGraphContext` queries `knowledge_node_sources`/
`knowledge_nodes`/`knowledge_links`; `retrieveMemoryContext` queries
`ai_memory` exclusively. Note sharing, as designed in §4, has **zero**
code-path overlap with any of them.

- **`ai_memory`**: untouched. No table in this design references it, no
  policy here changes it, and Doc 3's permanent-exclusion rule for it is
  unaffected by anything in this document.
- **Personal preferences** (`provider_overrides`, `reading_progress`,
  `workspace_objectives`): untouched — none of these tables reference
  `notes` or are modified by this migration.
- **Private retrieval context**: unaffected, per the retrieval-function
  audit above — sharing a note does not change what NOVA can retrieve
  into a chat prompt, today or after this design ships.

One adjacent, intended (not a leak) consequence worth naming precisely
so it isn't mistaken for one: `note_embeddings` feeds Universal Search's
Notes provider — a separate subsystem from `AIService`'s chat retrieval,
used only by the app's search bar. Once `note_embeddings`' RLS is
updated per §4, a shared note correctly becomes findable via Search by
the teammates it's shared with — this is exactly what "shared" should
mean for search, and is unrelated to the `ai_memory`/private-context
guarantee this section exists to verify.

## 7. Testing strategy

To be implemented alongside Phase 2's code, not run yet — recorded here
so the implementation step has a concrete checklist rather than an
open-ended "add tests":

**Database** (live-verified against the production project, mirroring
Phase 1's own verification method — no local Postgres/pgTAP harness
exists in this repo):
- Owner: select/insert/update/delete all succeed on a note in their
  workspace, including one another member authored.
- Editor: select/update succeed; delete fails (RLS-denied).
- Viewer: select succeeds; update and delete both fail (RLS-denied).
- Non-member: select fails entirely — a note in a workspace they don't
  belong to is invisible, matching today's behavior for an unrelated
  account.

**Application** (Vitest, mocked Supabase client, this repo's existing
convention): `notes.ts`'s four functions need no new tests (unchanged
code, already covered); `useNote.ts`'s corrected
`linkKnownConceptsToSource` call needs a test asserting it now passes
the *acting* user's id, not `note.user_id`; existing note flow tests
(create, save, summarize, delete for the note's own owner) must still
pass unmodified — the concrete proof that "existing users: unchanged"
holds in code, not just in the RLS table.

**Security**: an explicit test (live-DB, per Phase 1's method) asserting
a viewer's attempted `update`/`delete` against a shared note is rejected
by RLS, not merely "not exposed in the UI" — the UI gating in §5 is a
UX improvement, never the actual security boundary.

## 8. Explicitly deferred

Per this phase's own scope: no sharing dialog, no invitation flow, no
notification system, no generic permissions framework, no public/guest
access. `documents`, the knowledge graph, `conversations`, and
`ai_memory` remain completely out of scope — this document is about
`notes` alone, per the blueprint's Phase 3+ sequencing for everything
else.

## 9. Summary for approval

Recommended: **Option A** — extend `notes`' RLS (and, required, its two
child tables' RLS) with `has_workspace_role`, per-command, exactly as
§4 specifies. One migration, no new table, no backfill, no new security
primitive. Two required application-layer fixes: `NoteDetailPage.tsx`
role-gating (§5) and the `linkKnownConceptsToSource` attribution bug
(§1.3/§5) — the second one a real, pre-existing latent bug this
discovery surfaced, not a Phase 2 feature addition. No AI retrieval
path is affected (§6). Awaiting approval before implementation.
