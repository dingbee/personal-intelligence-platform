# UX-14.4 Path B — Spreadsheet Specification Contract Discovery

**Status: design only.** No code, migrations, or UI changes were made to produce this document, per explicit instruction. Constraints held: no LLM integration, no Workspace Action registration, no formula generation, no database migrations, no collaboration.

Narrower and more concrete than the Path B architecture discovery (`docs/ux-14.4-path-b-generation-discovery.md`): that document mapped the end-to-end flow onto real modules. This one defines the one piece that flow doesn't yet have a type for — the contract between "what an AI (eventually) produces" and "what `buildSpreadsheetWorkbook` (today) consumes."

---

## Investigation 1 & 2: Does `SpreadsheetArtifactData` Need a New Layer, or Can It Be Extended?

`SpreadsheetArtifactData` (`spreadsheet/types.ts`) is a **cell-addressed** representation: every value or formula is tagged with an explicit A1 address (`{ cell: 'B2', value: 744 }`). `buildSpreadsheetWorkbook` reads it directly — `XLSX.utils.decode_cell(cell.cell)` per cell, no inference. This is the right shape for that consumer: unambiguous, trivially validated per-cell, exactly what SheetJS's `WorkSheet` object wants.

It is the **wrong** shape to ask a model to produce directly, for a concrete, verifiable reason: an LLM asked to emit forty individual `{cell: "?", value: "?"}` objects has to get every row/column index arithmetic correct with no structural help — a single miscounted cell produces a sheet with a silent gap or an overwritten cell, and nothing about the shape itself makes that mistake visible before it's too late (a gap just means one address never got used). This is a real, not hypothetical, failure mode: it is exactly the kind of manual-bookkeeping task LLMs are known to be unreliable at, and it's avoidable by *not asking for that bookkeeping at all*.

**Conclusion: a new type is needed, not an extension of `SpreadsheetArtifactData`.** Extending the existing cell-addressed shape (e.g., adding an optional `row`/`column` index instead of a full address) doesn't remove the bookkeeping burden, it just relocates it. The right fix is a **row-oriented** shape — a matrix of columns and rows, where each row's values align to the column list *by array position*, not by any address the caller computes. The only "counting" a producer has to get right is that each row's `values` array has the same length as `columns` — a single, trivially validated invariant instead of dozens of independent address computations. Address assignment becomes purely mechanical, deterministic, and handled entirely by a new compiler step (Investigation 5) — never something the AI (or a human, or any other producer) needs to reason about.

This mirrors this codebase's own established split (deterministic logic handles anything error-prone; the LLM is kept to what it's actually good at) applied one level deeper than usual: not just "the LLM writes prose, code computes the number," but "the LLM describes structure, code computes the address."

## Investigation 3: Cell, Sheet, Formula, Formatting, and Metadata Requirements

**Cells and rows.** A row is `values: (string | number | null)[]`, index-aligned to the sheet's `columns`. No per-cell address, no per-cell type tag — the column already carries the type hint (below), and `null` represents an intentionally empty cell (not "forgot to fill this in" — the validator, not the type, is responsible for catching an actually-missing value where one was expected).

**Columns.** `{ name: string, type?: SpreadsheetColumnType }`. `type` (`'text' | 'number' | 'currency' | 'percentage' | 'date'`) is a **reserved, not-yet-acted-on** hint — proposed because Investigation 3 explicitly asks about formatting, but this discovery does not extend `buildSpreadsheetWorkbook` to honor it (that function writes a plain `t: 'n'`/`t: 's'` cell today, no Excel number-format string). Recording the intent now, inert until a future milestone maps it to a real `.z` format, is the same pattern this codebase already uses elsewhere (e.g. `updateMemory`'s `confidence` field went into the `Pick` type before any caller set it) — forward room without speculative behavior.

**Formulas — designed, explicitly not built.** Per the "no formula generation" constraint, no formula-producing or formula-validating code is proposed for implementation in this milestone. The type shape is still worth designing now, because retrofitting a formula concept into an already-shipped type later is exactly the kind of churn this initiative avoids. Proposed shape, deliberately **not** using raw A1 addresses (the same reasoning as Investigation 1 & 2 — don't ask a producer for cell-address arithmetic):

```ts
interface SpreadsheetSpecificationFormula {
  column: string   // a real column name from the same sheet
  row: number       // 1-indexed into `rows` — the Nth data row, not a raw sheet row number
  expression: string  // bare text; references other columns as {{ColumnName}}, resolved to a same-row address at compile time
}
```

Scoped narrowly on purpose: `{{ColumnName}}` always means *this row's* value in that column. Cross-row aggregates (`SUM` over a range, a running total) are a materially harder problem — resolving them needs range syntax, not a single address — and are explicitly out of scope for this shape; a future extension, not assumed solved here. Nothing in this document proposes how `expression` gets produced or validated for safety (the formula-injection allowlist from the Path B architecture discovery is a later, separate concern) — the type only reserves where a formula would go once that work happens.

**Metadata.** Two fields belong at the specification's top level, both because the Path B architecture discovery already identified the need and there's no other natural home for them yet:
- `title: string` — becomes the eventual `Note.title`.
- `kind: 'template' | 'data_model'` — the grounding distinction from that document's §2. **Important limitation, stated plainly**: this field records an *intent*, it does not *enforce* it. Nothing in the type system or the validator proposed below can verify that a `data_model`-kind spec's values actually trace back to real retrieved data — that check is an orchestrator-level concern (comparing spec values against `retrieveSpreadsheetContext`'s output), entirely out of scope here since it requires the LLM integration this milestone explicitly excludes. The field exists so that check has somewhere to attach later, not because this milestone can perform it.

## Investigation 4: Validation Boundaries

Two distinct validation layers, deliberately kept separate:

1. **Structural validation of the specification** (new, this milestone's actual deliverable) — runs *before* compilation, on the specification shape itself: non-empty title, `kind` is one of the two allowed literals, at least one sheet, unique sheet names, non-empty column list with unique names, every row's `values.length` equals `columns.length` (the one invariant Investigation 1 identified as the crux), size caps (max sheets / columns / rows / total cells — concrete numbers deferred to implementation, informed by what's actually reasonable to preview and export, consistent with the "low hundreds of cells" guidance the Path B architecture discovery already gave for the same reason). If formulas are present in a spec (structurally possible even though nothing produces them yet): the referenced `column` exists in that sheet, `row` is in range, and every `{{...}}` placeholder in `expression` names a real column — reference-integrity checks only, **not** the content-safety allowlist (rejecting `WEBSERVICE(`, `cmd|`, etc.) — that check belongs at the point a real formula string first exists, which per the constraints is not this milestone.
2. **The compiler is not a validation layer.** `compileSpreadsheetSpecification` should only ever run on an already-valid spec and should not re-derive or double-check what the validator already confirmed — same separation of concerns `parseMarkdownTableToArtifact` already keeps informally (parse first, the workbook builder trusts its output structurally).

**Recommended failure mode: reject the whole spec, don't attempt partial repair.** A row with the wrong number of values, or a formula referencing an unknown column, should fail validation entirely rather than have the validator silently drop the offending row/formula and compile the rest. A spreadsheet artifact with a silently-missing row is arguably worse than no artifact at all — a mangled table looks complete. This is a deliberate departure from `parseConceptsResponse`'s "drop the bad item, keep the good ones" convention, justified because dropping one concept out of fifteen degrades gracefully in a way dropping one row out of a data table does not.

## Investigation 5: Migration Path from Current Path A Artifacts

**Recommendation: leave `parseMarkdownTableToArtifact.ts` untouched.** It already produces `SpreadsheetArtifactData` directly from markdown text, it's shipped, tested, and covered by the UX-14.4.5 acceptance harness. The new specification-based flow becomes a **second, parallel producer** of the same `SpreadsheetArtifactData` output type — `compileSpreadsheetSpecification` is simply a new function with the same output contract Path A's parser already has, and `buildSpreadsheetWorkbook` never needs to know or care which producer a given `SpreadsheetArtifactData` came from. This is the same multi-producer/one-consumer shape already established between Phase 1 (`detectArtifactKind`) and Phase 2 (`parseMarkdownTableToArtifact`) — nothing new architecturally, just one more producer.

**One real, low-risk consolidation opportunity, explicitly not done now.** `parseMarkdownTableToArtifact.ts` has a private `columnLetter(index)` helper (0 → "A", 26 → "AA") that the new compiler needs too. Duplicating it would let the two address-computation implementations drift; extracting it into a shared `cellAddressing.ts` util is a genuine zero-risk refactor (pure function, no behavior change, one new file, two updated imports) in the same category this initiative's Architecture Consolidation Sprint already named "Zero-Risk Refactors." Flagged here as the recommended first step *of implementation*, not performed as part of this discovery.

  name: string

  title: string

  sheets: SpreadsheetSpecificationSheet[]

## Module Boundaries

All three new files sit alongside the existing Path A files in `src/modules/ai/artifacts/spreadsheet/` — the existing flat layout (`types.ts`, `parseMarkdownTableToArtifact.ts`, `buildSpreadsheetWorkbook.ts`, `sheetToGrid.ts`, `exportSpreadsheetArtifact.ts`) has no reason to grow a subdirectory for three more files of the same size and purpose:

- `specificationTypes.ts` — no internal dependencies.
- `validateSpreadsheetSpecification.ts` — depends only on `specificationTypes.ts`.
- `compileSpreadsheetSpecification.ts` — depends on `specificationTypes.ts`, the existing `types.ts`, and (if the Investigation 5 refactor happens first) a shared `cellAddressing.ts`.

None of these files import anything from `workspace-actions/` or touch the prompt/capability registry — per the "no Workspace Action registration yet" and "no LLM integration yet" constraints, this layer is intentionally producer-agnostic. When Path B's orchestrator (`runGenerateSpreadsheetArtifactCommand.ts`, from the earlier discovery doc) eventually exists, it imports `validateSpreadsheetSpecification` and `compileSpreadsheetSpecification` the same way any other consumer would — no coupling in the other direction.

## Risks

- **Type proliferation confusion.** Two spreadsheet types (`SpreadsheetSpecification`, `SpreadsheetArtifactData`) in the same directory risks a future contributor treating them as interchangeable. Mitigated by naming and doc comments making the two-stage pipeline explicit (Specification = "what the author wants," ArtifactData = "the addressed cells the workbook needs") — the same mitigation this document itself models.
- **Divergent addressing logic.** If `compileSpreadsheetSpecification` reimplements `columnLetter` independently instead of sharing it with `parseMarkdownTableToArtifact`, the two could silently drift (e.g. a future off-by-one fix applied to only one of them). Mitigated by the Investigation 5 recommendation to extract a shared `cellAddressing.ts` as implementation's first step.
- **`kind: 'data_model'` implying more safety than the type can deliver.** Already called out in Investigation 3 — worth repeating here as a risk, not just a limitation: a future implementer could mistake "the spec says `data_model`" for "this has been checked against real data," when in fact nothing at this layer performs that check. The orchestrator, when built, must not skip that verification just because the type looks like it promises one.
- **Reject-whole-spec being too strict in practice.** The recommended all-or-nothing validation failure mode (Investigation 4) could prove frustrating once real (imperfect) model output is validated against it — a spec that's 95% fine and fails on one bad row gets discarded entirely. This is a deliberate, disclosed trade-off (favoring "never show a silently-incomplete table" over "always show something"), but should be revisited once real generation output exists to test it against, not assumed correct forever.
- **Formula placeholder syntax (`{{ColumnName}}`) is unvalidated against real model behavior.** Nothing has tested whether an LLM reliably produces this exact syntax rather than inventing its own — this is a real open question the Path B architecture discovery's later "Artifact Specification" phase will need to answer empirically, not something this type-design pass can resolve.

## Testing Strategy

- **`validateSpreadsheetSpecification`**: fixture-based, one test per rejection reason — ragged row, duplicate sheet name, duplicate column name, formula referencing an unknown column, formula row out of range, oversized spec (sheet/row/cell count caps) — plus a happy-path fixture that passes cleanly.
- **`compileSpreadsheetSpecification`**: given a known-valid spec, assert the exact resulting `SpreadsheetArtifactData` — header-row addressing, data-row addressing, and (once formulas are real) `{{ColumnName}}` resolving to the correct same-row A1 reference.
- **Cross-check against Path A, not just against itself.** The strongest test available: feed the same logical table through both `parseMarkdownTableToArtifact` (as markdown) and `compileSpreadsheetSpecification` (as an equivalent specification), and assert they produce identical `SpreadsheetArtifactData` — this ties the new compiler's correctness directly to Path A's already-shipped, already-verified behavior instead of asserting against a second, independently-written expectation.
- **End-to-end, extending the existing harness.** Once this layer exists, `spreadsheetArtifactLifecycle.test.ts` (UX-14.4.5) gains a second fixture entry point — a hand-written `SpreadsheetSpecification` alongside the existing markdown-response fixture — both converging on the same downstream assertions (workbook build, XLSX write/read round trip, formula preservation). This is the exact extension that document's own implementation record already recommended.
- **No LLM/network tests** — nothing in this layer calls a provider; that remains entirely out of scope until the constraint lifts.
