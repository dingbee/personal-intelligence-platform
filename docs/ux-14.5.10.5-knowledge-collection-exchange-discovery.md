# UX-14.5.10.5 — Knowledge Collection Exchange: Discovery

**Status: discovery only. No schema changes, no migrations, no RLS changes, no framework changes, no application code in this document or the commit that adds it.**

Objective: design the final and highest-level Knowledge Exchange package
type — a Collection package represents an entire curated knowledge set,
not a single object — grounded in the actual `knowledge_collections`
schema, membership API, and every UI surface that touches collections
today (every claim below is backed by a migration file, a type
definition, or an API/UI function actually read for this pass).

---

## 0. Audit summary — what's already true, confirmed by reading the code

- **Membership is not a column — it's rows in `knowledge_links`**,
  confirmed directly in `0026_knowledge_collections.sql`'s own comment
  and in `knowledgeCollections.ts`: a membership row is
  `(source_type='knowledge_collection', source_id=<collection id>,
  target_type=<item type>, target_id=<item id>)`. `knowledge_collections`
  itself is "deliberately just an identity/metadata table" (`id`,
  `user_id`, `workspace_id`, `name`, `description`, timestamps) — no
  member list, no ordering column, no icon field, nothing else.
- **The real supported member types are `document`, `note`,
  `conversation`, `asset`, `knowledge_node`** — this is the literal
  `CollectionItemType` union in `knowledgeCollections.ts`, confirmed
  against every real `AddToCollectionButton` call site
  (`DocumentDetailPage`, `NoteDetailPage`, `ChatPage`, `ImageReaderPage`,
  `KnowledgeNodeDetailPage`). **This task's own audit list names
  "Knowledge Node, Knowledge Link, Document, Asset" as example member
  types — `knowledge_link` is not, and never has been, a valid
  `CollectionItemType`.** A relationship cannot be a direct member of a
  collection today. Concretely, `knowledge_collection` also never
  appears as a `target_type` anywhere in the codebase — a collection
  cannot contain another collection either. Both findings matter
  directly for §6 (circular references) and §2 (member descriptors);
  see there for the corrected scope this discovery actually designs
  for, and §2.6 for how relationships *between* a collection's own
  knowledge-node members are still worth carrying, just not as an
  addressable membership type.
- **No Conversation Exchange package type exists** — confirmed by
  listing `src/modules/knowledge-exchange/`: there is `notes/`,
  `knowledge-nodes/`, `assets/`, `documents/`, `knowledge-links/`, and
  no `conversations/` directory at all. `conversation` is nonetheless a
  real, live `CollectionItemType` (wired into `ChatPage` today). This is
  the single most consequential gap this discovery found: a Collection
  Exchange package that tried to fully support every real member type
  would need to *invent* Conversation Exchange as an unplanned side
  effect. §2.5/§9 treat this as an explicit, honest scope boundary
  rather than solving it here.
- **No explicit ordering exists anywhere in the product.** There is no
  position/order column on the membership link, no drag-to-reorder UI.
  `KnowledgeCollectionDetailPage` groups items by type (`itemsByType`,
  a `Map` whose iteration order depends on first-appearance in an
  already-recency-sorted list) and `listCollectionItems` sorts each
  type's items by `created_at` descending. "Ordering" as a
  user-intentional, reconstructable property does not exist today —
  §1 treats this as a real finding to design honestly around, not a
  gap to paper over with an invented feature.
- **Deletion is non-destructive and non-cascading by design**:
  `deleteKnowledgeCollection` explicitly deletes the collection's own
  membership links, then the collection row — the member objects
  themselves (documents, notes, etc.) are never touched, confirmed by
  both the function body and the confirm-dialog copy on
  `KnowledgeCollectionDetailPage` ("The documents, notes, conversations,
  images, and concepts inside it are not affected").
- **RLS is already correct** — `knowledge_collections` was already made
  workspace-shareable by `0031_shared_knowledge_objects.sql` §8, and its
  membership rows (being ordinary `knowledge_links` rows) inherit that
  table's own already-shareable RLS (§7, confirmed in the UX-14.5.10.4
  implementation). No RLS work is a prerequisite here, the same
  conclusion every prior Knowledge Exchange discovery has reached.
- **Every other package type this collection would embed is already
  built and already proven**: Notes (UX-14.5.9), Knowledge Nodes
  (UX-14.5.10.1), Assets (UX-14.5.10.2), Documents (UX-14.5.10.3.1/.2),
  Knowledge Links (UX-14.5.10.4). The central architectural
  opportunity this discovery identifies: **a Collection package should
  nest these four existing package types verbatim as its member
  payloads**, not reinvent per-type export/import logic. This is the
  single biggest simplification available, directly mirroring how
  Document Exchange found that `processDocument` already regenerated
  everything a document package needed.

## 1. Collection package structure

### 1.1 What belongs inside

```
CollectionPackageManifest = {
  version: number
  exportedAt: string
  sourceVersion: string
  collection: {
    name: string
    description: string | null
    members: CollectionMemberEntry[]
  }
}
```

Where each `CollectionMemberEntry` is a **discriminated union keyed by
`memberType`** (an open string, not a closed enum at the wire level —
deliberately mirroring how `knowledge_links.source_type`/`target_type`
are themselves unenforced strings, per `0026`'s own comment):

```
CollectionMemberEntry =
  | { memberType: 'knowledge_node'; originalAddedAt: string; payload: KnowledgeNodePackage }
  | { memberType: 'note'; originalAddedAt: string; payload: NotePackage }
  | { memberType: 'asset'; originalAddedAt: string; payload: AssetPackage }
  | { memberType: 'document'; originalAddedAt: string; payload: DocumentPackageManifest /* + archive entry, see §5 */ }
  | { memberType: 'conversation'; originalAddedAt: string; unsupported: true; title: string } // see §2.5
```

Each `payload` is the *exact*, unmodified package type UX-14.5.9/
.10.1/.10.2/.10.3 already produces — not a new, parallel shape. This is
deliberate: it means importing a Collection member is *exactly* calling
the existing `import<Type>Package` function for that type, with zero
new per-type logic to write or test independently of what already
exists.

### 1.2 Field-by-field, against the task's own suggested list

- **Collection metadata**: `name`, `description` — the only two real
  fields `knowledge_collections` has beyond identity/audit columns.
  Nothing else exists to export.
- **Member list**: `members[]`, per §1.1.
- **Ordering**: **not a first-class, reconstructable property** — see
  §0. Each member carries `originalAddedAt` (the membership link's own
  `created_at`) as *inert display metadata only*, the same "preserve
  the original timestamp without using it to set anything real"
  convention every prior package type already uses for its own
  `createdAt`/`updatedAt` fields. The imported collection's actual
  display order is whatever `KnowledgeCollectionDetailPage`'s existing
  type-grouped/recency-sorted rendering produces for the freshly
  created rows — the same governing order every other collection in
  the product already has. Inventing a real position/order column
  would be speculative architecture this discovery's own constraints
  rule out; if collections ever gain a genuine reorder feature, that's
  a separate, future product decision, not something this package
  format should get ahead of.
- **Descriptions**: covered by `collection.description`; each embedded
  member's own description is whatever that member's existing package
  type already carries (e.g. a Knowledge Node payload's own
  `description` field) — nothing new needed.
- **Tags**: `knowledge_collections` has no tags column and no tagging
  UI of its own (`AddToCollectionButton`'s popover has no tag input) —
  there is nothing to export here. Individual embedded members that
  *do* have tags (Notes, Documents) already carry them inside their own
  nested `payload`, unchanged.
- **Icons**: `knowledge_collections` has no icon column, and no icon
  picker exists anywhere in the collections UI (confirmed by reading
  `KnowledgeCollectionDetailPage`/`AddToCollectionButton` in full).
  Nothing to export; inventing one would be speculative.
- **Future compatibility**: the `memberType`-keyed discriminated union
  (§1.1) *is* the future-compatibility mechanism — a new member type
  (Conversations, or anything not yet imagined) is a new union case and
  a new resolver branch, never a change to the manifest's own outer
  shape or to `CURRENT_PACKAGE_VERSION`/`SUPPORTED_PACKAGE_VERSIONS`.
- **Package versioning**: identical to every other package type —
  `version`/`sourceVersion` fields, `PackageVersion.ts` reused
  unmodified. A version bump is only needed if the *manifest's own*
  shape changes in a way older code can't parse — adding a new
  `memberType` case is additive and does not require one, the same
  principle `PackageVersion.ts`'s own doc-comment already establishes.

## 2. Member descriptors

For each real `CollectionItemType`, grounded in what its own Exchange
phase already built:

### 2.1 Knowledge Node (`memberType: 'knowledge_node'`)

- **Minimum data**: the existing `KnowledgeNodePackage` payload
  verbatim (`nodeType`, `title`, `description`, `metadata`,
  `generationMetadata`, `createdAt`, `updatedAt`).
- **Identity strategy**: title-normalized, within `(user_id,
  node_type)` — `normalizeTitle`'s existing exact-match rule.
- **Resolver**: `resolveCanonicalNode`, reused completely unmodified —
  the same primitive both Knowledge Node Exchange and Knowledge Link
  Exchange already reuse.
- **Fallback**: none needed — `resolveCanonicalNode` always succeeds,
  either reusing a title match or creating a fresh node.
- **Duplicate handling**: reuse-not-overwrite, by construction (the
  `KNOWLEDGE_NODE_IMPORT_SOURCE_TYPE` + fresh-`sourceId`-per-call
  pattern UX-14.5.10.1 already established makes the content-mutating
  `refresh` branch structurally unreachable for imports).

### 2.2 Note (`memberType: 'note'`)

- **Minimum data**: the existing `NotePackage` payload verbatim
  (`title`, `content`, `tags`, `createdAt`, `updatedAt`,
  `generationMetadata`).
- **Identity strategy**: none — Notes have no canonical-identity
  resolver.
- **Resolver**: `createNote`, reused unmodified.
- **Fallback**: n/a.
- **Duplicate handling**: always creates a fresh note — matches Notes
  Exchange's own always-create precedent exactly. Re-importing the
  same Collection package twice produces two copies of any Note member
  (an accepted asymmetry — see §3.5).

### 2.3 Asset (`memberType: 'asset'`)

- **Minimum data**: the existing `AssetPackage` payload verbatim
  (`title`, `mimeType`, `width`, `height`, `sizeBytes`, `createdAt`,
  `fileDataBase64`).
- **Identity strategy**: none.
- **Resolver**: `uploadAsset`, reused unmodified.
- **Fallback**: n/a.
- **Duplicate handling**: always creates a fresh asset — matches Asset
  Exchange's own always-create precedent.

### 2.4 Document (`memberType: 'document'`)

- **Minimum data**: the existing `DocumentPackageManifest` plus its
  ZIP-archived `original` entry (see §5 — this is the one member type
  whose payload is not plain JSON).
- **Identity strategy**: none.
- **Resolver**: `uploadDocument` + `processDocument`, reused unmodified
  (the fire-and-forget regenerate-everything pattern UX-14.5.10.3.2
  already established).
- **Fallback**: n/a.
- **Duplicate handling**: always creates a fresh document — matches
  Document Exchange's own always-create precedent.

### 2.5 Conversation (`memberType: 'conversation'`) — no existing package type

- **Minimum data available today**: only a `title` (via
  `fetchTitlesByIds('conversations', ids)`, the same lookup
  `listCollectionItems` already uses for display). A conversation's
  real content — its `messages` — has no export/import machinery at
  all. The closest existing analog, `SaveConversationDialog`, is a
  one-way, lossy "turn this conversation into a Note" action, not a
  round-trippable package, and it doesn't reconstruct a `conversations`
  row at all.
- **Identity strategy / resolver / fallback / duplicate handling**:
  **none exist, and this discovery does not invent them.** Building a
  full Conversation Exchange package (messages, provider/model
  metadata, streaming state) is its own, separate, undesigned effort —
  well outside "reuse existing resolvers," which is this whole
  engagement's central discipline. Inventing one here would be exactly
  the "speculative architecture" this discovery's constraints forbid.
- **Recommendation**: Collection export includes a conversation member
  as an **honest, explicitly `unsupported: true` stub** carrying only
  its `title` — enough for the export to still be a complete,
  non-lossy *record* of what the collection contained, without
  pretending the content travels. Import always reports it as
  "skipped — conversations aren't yet supported for exchange" (§7),
  never silently dropped and never fabricated. If Conversation Exchange
  is ever built as its own phase, this member type upgrades from a stub
  to a real embedded payload with no change to the Collection
  manifest's own shape — exactly the future-compatibility mechanism
  §1.2 describes.

### 2.6 Knowledge Link — not a member type, but a real cross-cutting concern

Confirmed in §0: a relationship cannot be a direct `CollectionItemType`.
But a collection whose members include several interconnected
`knowledge_node`s very plausibly has real `knowledge_links` edges
*between* those specific nodes (e.g. a curated "here's how these five
concepts relate" set) — and losing those relationships on export would
genuinely understate what the collection represents. Recommendation:
when building a Collection package, separately query for any
`knowledge_links` edges where **both** endpoints are among the
collection's own `knowledge_node` members, and include those as an
**auxiliary `relationships: KnowledgeLinkPackage[]` array** on the
manifest (§1.1), reusing `exportKnowledgeLinkPackage`/
`importKnowledgeLinkPackage` verbatim — not a new membership type, a
bonus payload describing structure the collection's own members
already imply. Import replays each one through
`importKnowledgeLinkPackage` *after* every `knowledge_node` member has
been resolved (so both endpoints are guaranteed resolvable), inheriting
that phase's own "never create a broken link" guarantee unchanged.

## 3. Collection import algorithm

1. **Create the collection row first** (`createKnowledgeCollection`,
   unmodified) — always succeeds, has no dependency on any member
   resolving. The importer becomes the owner; the destination
   workspace is the caller's explicit choice, exactly like every other
   package type's `PackageImportContext`.
2. **Resolve every member**, each through its own type's existing,
   unmodified import path (§2): `resolveCanonicalNode` for
   `knowledge_node`, `createNote` for `note`, `uploadAsset` for
   `asset`, `uploadDocument`+`processDocument` for `document`, and a
   guaranteed skip for `conversation` (§2.5). For each member that
   resolves successfully, add a `knowledge_links` membership row
   (`addItemToCollection`, unmodified) pointing the fresh collection at
   the fresh (or reused, for knowledge nodes) member id.
3. **Replay embedded relationships** (§2.6) after every
   `knowledge_node` member has resolved, via unmodified
   `importKnowledgeLinkPackage` calls.
4. **Handle failures / partial success**: **a single member's failure
   never aborts the whole import.** This is a deliberate, different
   policy from Knowledge Link Exchange's own all-or-nothing
   per-relationship rule — and the difference is principled, not
   inconsistent: a single Knowledge Link import *is* one atomic thing
   (a relationship without both endpoints is meaningless), but a
   Collection is a container of many independent things. Forcing an
   all-or-nothing policy here would mean one corrupted embedded
   Document (member 47 of 50) discards 46 already-successful imports —
   a strictly worse outcome for the user than a clear "47 of 50
   imported, 3 failed" report (§7). Each individual member's own
   internal atomicity guarantee still holds unchanged (e.g. a failed
   Document import still can't leave an orphaned storage object,
   because `uploadDocument` itself is unmodified) — atomicity is
   preserved *per member*, just not escalated to *the whole collection*.
5. **Ordering**: not reconstructed as a real property (§1.2) — members
   are processed in the manifest's own array order (whatever the
   export step produced, itself the source account's own display
   order at export time), but nothing depends on that processing order
   being preserved or meaningful post-import.
6. **Rollback policy**: **none, by the above design** — a partially-
   completed collection (the row exists, some members are linked, some
   were skipped/failed) is the intended, reported outcome, not an
   error state to unwind. The collection row itself is never deleted
   just because some members didn't import; the user keeps whatever
   did succeed and can retry the rest manually (add-to-collection
   already exists as a per-item action on every member type's own
   page).
7. **Conflict policy (the collection itself)**: `createKnowledgeCollection`
   always creates a fresh row — no name-based dedup resolver exists for
   collections (matching Notes'/Assets'/Documents' own precedent: not
   every object type gets a canonical-identity resolver, only Knowledge
   Nodes do). Re-importing the same Collection package twice produces
   **two separate collection rows**.
8. **Duplicate policy (per member, across re-imports)**: an accepted
   asymmetry worth surfacing in the import UX (§7), not hidden: because
   `knowledge_node` members dedup by title (via `resolveCanonicalNode`)
   but `note`/`asset`/`document` members never do, re-importing the
   same Collection package twice leaves the *second* collection
   pointing at the *same* underlying knowledge-node rows as the first,
   while creating brand-new duplicate notes/assets/documents each time.
   This is not a new problem Collection Exchange introduces — it's the
   literal, correct composition of each member type's own,
   already-accepted duplicate-handling policy — but a Collection made
   of many members makes the asymmetry more visible than any single
   prior package type did, so it's worth a plain warning in the import
   dialog rather than only in this document.

## 4. Collection export algorithm

- **Embedded**: `knowledge_node`, `note`, `asset` members — their full
  existing package payload travels whole, matching how those types'
  own single-object Export buttons already work.
- **Referenced (title-only stub, not full content)**: `conversation`
  members only (§2.5) — the one type with no embeddable payload to
  offer.
- **Omitted entirely**: nothing else. There is no member type today
  that the discovery recommends silently dropping — `conversation` is
  represented (as an honest stub), never erased from the exported
  record.
- **`document` members are embedded too**, but flagged distinctly:
  because a Document package is itself a ZIP archive (not JSON), it
  cannot be embedded as a plain nested object the way the other three
  JSON-based package types can — see §5 for how it's actually carried.
- **How package size grows**: linear in the sum of each embedded
  member's own package size, dominated entirely by however many
  `document`/`asset` members are included — a Collection of five
  Knowledge Nodes and two Notes stays kilobytes; a Collection with
  three 150MB documents and photos is realistically hundreds of MB to
  low GB. This mirrors, at collection scale, exactly the size concern
  the Document Exchange discovery already flagged for a *single*
  document — multiplied by however many binary members a collection
  holds. §5/§9 recommend this be treated as a first-class constraint
  from the start of implementation (e.g. a per-member and/or
  total-package size cap, surfaced clearly during export, not
  discovered as a bug during import), not an afterthought.
- **How nested packages behave**: each embedded member's `payload` is
  produced by calling that type's own existing, unmodified
  `export<Type>Package` function — the Collection exporter itself does
  no per-type serialization logic of its own, only orchestration
  (fetch each member, dispatch to the right existing exporter, collect
  the results). This keeps the "no framework redesign" constraint
  trivially true: nothing about `PackageExporter`/`PackageValidator`/
  `PackageImporter`/`PackageVersion` needs to change for a package type
  whose payloads are, themselves, other already-conformant packages.

## 5. Nested package strategy

**Recommendation: the Collection package container itself should be a
ZIP archive (via `jszip`, already a direct dependency), not a plain
JSON file — specifically because it needs to embed Document members
without a second layer of base64 inflation.**

### 5.1 The concrete problem

Three of the five real member types (`knowledge_node`, `note`, `asset`)
produce plain-JSON payloads, trivially nestable inside a larger JSON
object. `document` does not: Document Exchange's own discovery
(UX-14.5.10.3) deliberately chose a ZIP container specifically to avoid
the ~1.33× base64 inflation and ~700MB–1GB peak-memory risk a 200MB
file would cause inside JSON. If the Collection package were itself
plain JSON, embedding a Document member would mean either (a)
re-introducing exactly the base64-inflation problem Document Exchange
was built to avoid — just one level up — or (b) treating Document
members as an exception with a totally different embedding mechanism
than every other member type, which is worse for implementation
consistency than choosing one container format for the whole package
up front.

### 5.2 The recommended shape

A Collection package is a `.zip` with:

- `manifest.json` — the `CollectionPackageManifest` (§1), with each
  `knowledge_node`/`note`/`asset` member's `payload` embedded directly
  as JSON (no size concern — these are all small), and each `document`
  member's manifest-only half (`DocumentPackageManifest`, the JSON
  part) embedded the same way.
- `document-members/<index>.zip` — one raw nested ZIP entry per
  `document` member, containing exactly what a standalone Document
  package's own `original`/`manifest.json` entries already contain
  (§26.1 of the blueprint) — stored, not re-compressed (mirroring
  `buildDocumentPackageZip`'s own STORE choice, for the same
  predictable-size reasoning the zip-bomb defense there depends on).

This reuses `jszip` for both layers (outer collection archive, inner
per-document archives) with no new library and no change to
`buildDocumentPackageZip`/`parseDocumentPackageZip` themselves — a
Collection's document-member handling is "call the existing Document
package builder, then store its output bytes as one more entry in a
bigger zip," not a rewrite of how Document packages work.

### 5.3 Trade-offs considered

| Option | Verdict |
|---|---|
| Collection package as JSON, Document members base64-encoded inline | Rejected — reintroduces the exact memory/size risk Document Exchange's own discovery already ruled out, at collection scale (potentially *several* documents in one package). |
| Collection package as JSON, Document members referenced only (not embedded) | Rejected as the default — would make "export this collection" quietly incomplete for any collection containing a document, the same "silently understates what the collection contains" problem §2.6 avoids for relationships. Not proposed even as a fallback; §9's phased roadmap instead sequences Document members into a later milestone once the ZIP-of-ZIPs mechanism is proven for one document. |
| Collection package as ZIP, everything (including small JSON payloads) stored as separate entries | This discovery's recommendation. Consistent, single container format regardless of which member types a given collection happens to hold; small JSON entries cost nothing extra to store inside a zip. |

## 6. Circular references

**Not possible today, and this is proven by the schema/API as they
exist, not merely assumed:**

- A collection's membership rows always have
  `source_type='knowledge_collection'` — the collection is only ever
  the *source* of a membership link, never a `target`.
- `CollectionItemType` (`knowledgeCollections.ts`'s own literal union)
  is `'document' | 'note' | 'conversation' | 'asset' | 'knowledge_node'`
  — `'knowledge_collection'` does not appear in it, and
  `addItemToCollection`/`AddToCollectionButton` have no code path that
  could ever construct a membership row with
  `target_type='knowledge_collection'`.
- Therefore a collection cannot contain another collection, at all,
  today — not "rarely," not "only via a workaround" — the type system
  and every real call site make it structurally unreachable. With no
  collection-of-collections membership possible, a cycle (A contains B
  contains A) has no path to exist.

**No prevention logic is needed or recommended in this phase.** If a
future, separate product decision ever adds collection-of-collections
membership (expanding `CollectionItemType` to include
`'knowledge_collection'`), that future phase would need its own cycle
check (e.g. a DFS/ancestry walk before allowing the membership write) —
noted here only so it isn't forgotten, not designed now, since
designing it today would be exactly the "speculative architecture" this
discovery's constraints rule out for a feature that doesn't exist.

## 7. Import UX

Reuses the same `<dialog>` shell (file picker → validation summary →
workspace selector → success summary) every prior Import dialog
already established, extended for a collection's multi-member nature:

- **Validation summary**: same shape as every other package type — a
  parsed-but-not-yet-imported preview showing the collection's
  `name`/`description` and a list of its members grouped by type
  (count per `memberType`), mirroring `KnowledgeCollectionDetailPage`'s
  own existing type-grouped display convention rather than inventing a
  new one.
- **Missing / skipped members**: a `conversation` member is always
  shown as "1 conversation — not yet supported, will be skipped" in
  the *validation* summary itself (known before import even starts,
  not discovered as a surprise failure afterward).
- **Imported / duplicate / skipped members — final report**: after
  import completes, a per-member outcome list: created (with a
  created-vs-matched distinction for `knowledge_node` members, the
  same wording `ImportKnowledgeNodePackageDialog`/
  `ImportKnowledgeLinkPackageDialog` already use), skipped
  (conversations), and failed (with each failure's own error message,
  never silently absorbed) — plus a top-line "N of M members
  imported" count and a link to the newly created collection
  (`/knowledge/collections/:id`) so the user can see exactly what
  landed regardless of how many members had trouble.

## 8. Failure recovery

| Failure | Handling |
|---|---|
| Missing package (no file selected) | Same as every prior dialog — the Import button stays disabled until a file is chosen and parses. |
| Unsupported version | Rejected by manifest validation before any member is touched — reuses `isSupportedPackageVersion`/`isFuturePackageVersion` unchanged. |
| Unknown member type | A `memberType` this app build doesn't recognize is treated like `conversation`'s stub case — reported as "not supported by this version of NOVA," never silently dropped, never a hard validation failure that blocks the *rest* of the package (a package from a newer app version might add a member type this build can't handle yet, but everything else in it should still import — same "future is additive" philosophy as the version field itself). |
| Duplicate collection (re-import) | Not an error — §3.7's accepted policy: creates a second collection row. Surfaced as ordinary success, not a failure state. |
| Corrupt package | For the outer zip: the same two-pass structural/CRC verification Document Exchange already built (`parseDocumentPackageZip`'s own pattern, reused for the outer Collection archive) — corruption is caught before any member is trusted. For an individual embedded Document member's own nested zip specifically: that member fails its own import (§3.4's partial-success policy) without blocking any other member. |
| Invalid ordering | N/A — there is no ordering field to be invalid (§1.2); a manifest whose `members` array is simply present and well-formed per-entry is all validation checks for. |

## 9. Security audit

Every embedded member's payload is produced by an **already-audited**
existing exporter (§0) — this audit confirms the Collection wrapper
itself introduces nothing new to check beyond what each nested type's
own phase already verified:

- **No AI Memory, no Provider settings**: neither `ai_memory` nor any
  provider/model configuration is reachable from `knowledge_collections`,
  its membership rows, or any of the four real embeddable member
  types' own package payloads (confirmed by re-checking each type's own
  allow-list: `NotePackagePayload`, `KnowledgeNodePackagePayload`,
  `AssetPackagePayload`, `DocumentPackagePayload` — none reference
  either).
- **No embeddings, no chunks**: `document_chunks`/`embeddings` are
  explicitly excluded from `DocumentPackagePayload` (§26 of the
  blueprint, "regenerate not transfer") and were never part of any
  other member type's payload to begin with.
- **No audit history**: `created_at`/`updated_at` on the collection
  itself are never exported (§1.2, only `name`/`description` travel);
  each member's own original timestamps travel only as already-audited
  inert `importedFrom`-style metadata, never as live audit trail data.
- **No workspace ownership leakage, no user IDs, no internal IDs**: the
  collection's own `id`/`user_id`/`workspace_id` are excluded from
  the manifest (§1.1 lists only `name`/`description`); every embedded
  member payload already excludes these for its own type (verified
  directly in each phase's own allow-list and this discovery's re-read
  of `knowledgeCollections.ts`, which confirms membership rows
  themselves — the only place a collection's internal id is used at
  all — are populated fresh on import via `addItemToCollection`, never
  read from the package).

## 10. Roadmap — smallest safe implementation milestones

Larger in scope than any prior Exchange phase (it depends on all four
existing package types, introduces a new container-of-containers
format decision, and needs a genuinely new partial-success import
model) — recommend splitting further than Document Exchange's own
three-phase split:

1. **UX-14.5.10.5.1 — Collection container + single member type.**
   Prove the ZIP-of-entries container format (§5) and the
   `memberType`-discriminated manifest (§1) end to end using only
   `knowledge_node` members — the type with the smallest payload and
   an existing dedup resolver, so the partial-success/duplicate-
   handling model (§3) can be proven without any binary-content
   complexity yet. Includes the full validation/import-report UX (§7)
   scaffolding from the start, not retrofitted later.
2. **UX-14.5.10.5.2 — Note members + embedded relationships.** Add
   `note` members (still plain JSON, no new complexity) and the
   auxiliary `relationships` array (§2.6), reusing
   `importKnowledgeLinkPackage` unmodified — proving the
   "replay after all knowledge-node members resolve" ordering
   dependency (§3.3) specifically.
3. **UX-14.5.10.5.3 — Asset + Document members.** The two binary-
   content types, where the ZIP-of-ZIPs nesting (§5.2) and the
   package-size-growth concern (§4) actually get exercised for real —
   including a per-member and/or total-package size cap decided and
   tested here, not assumed safe by extrapolation from Document
   Exchange's own single-file cap.
4. **Explicitly out of scope, not a future milestone of this
   roadmap**: Conversation members (§2.5) remain a stub until and
   unless a separate, dedicated Conversation Exchange effort is
   scoped and designed on its own terms — inventing that as a rushed
   side effect of Collection Exchange would violate the same
   "reuse existing resolvers, don't invent new ones under pressure"
   discipline this whole engagement has followed since UX-14.5.9.

After UX-14.5.10.5.3, every real, currently-supported
`CollectionItemType` except `conversation` is exchangeable, and the
Knowledge Exchange roadmap first scoped in
`docs/ux-14.5.10-knowledge-exchange-expansion-discovery.md` is fully
implemented.
