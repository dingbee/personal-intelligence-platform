# UX-14.5.8 — Workspace Invitations: Architecture Discovery

**Status: discovery only. No implementation, no schema changes, no migrations, no RLS changes in this document or the commit that adds it.**

Reported symptom: "Invite by email" on the Collaboration Command Center
(`/collaboration`, UX-14.5.7) fails with **"Failed to send invitation."**
This document audits the complete flow end to end — UI, API, RPC, schema,
email delivery, acceptance, and security — and reproduces the failure
live against the production database (not just read from source),
rather than guessing at a root cause.

---

## 1. Executive summary

The invitation *mechanism* (RPC, schema, RLS) works correctly for the
one case it was built for: inviting someone who **already has a NOVA
PIP account**. Live-reproduced against production:

```sql
select public.invite_to_workspace(<workspace>, 'existing-user@example.com', 'editor');
-- returns a real, correct pending workspace_members row
```

The failure is not a bug in that mechanism — it's a **missing
capability**: `invite_to_workspace` requires the invitee's email to
already match a row in `profiles`, and raises `P0001: No account found
for that email` otherwise. Also live-reproduced:

```sql
select public.invite_to_workspace(<workspace>, 'never-signed-up@example.com', 'editor');
-- ERROR: P0001: No account found for that email
```

**This is the overwhelmingly common real-world case.** The entire point
of "invite a teammate by email" is to bring in someone who is *not*
already a user — and today, that specific, primary use case fails
outright, every time, by design. A second, smaller bug compounds it:
the email match is case-sensitive (`email = invitee_email`, no
normalization), so even an *existing* account fails to be found if the
inviter types the email with different casing than it was stored —
also live-reproduced. And separately, **no email of any kind is ever
sent** for a workspace invitation, even on success — there is no email
delivery infrastructure in this codebase at all, confirmed by exhaustive
search. An invitee only discovers a *successful* invitation by manually
opening Settings → Workspaces and noticing a "Pending invitations"
section.

None of this is a regression — it's exactly what was scoped and
documented at implementation time. UX-14.5's own Phase 3 blueprint
record (`ux-14.5.4-collaboration-implementation-blueprint.md` §14)
never claimed email delivery or invite-a-new-user was in scope; this
discovery is the first pass that names the gap explicitly against a
real, reproduced failure rather than as a hypothetical.

## 2. Current Invite UI wiring

The invite form lives in `src/modules/workspaces/components/
WorkspaceMemberRoster.tsx` (extracted from `WorkspaceMembersPage.tsx` in
UX-14.5.7; both the standalone Settings page and the new `/collaboration`
destination render it, so the bug is visible from either entry point).
It's a plain, owner-gated `<form>`: an email `<Input>`, a role `<select>`
(`editor`/`viewer` only — `owner` is intentionally not offered), and a
submit button wired to `useWorkspaceMembers(workspaceId).invite`
(`src/modules/workspaces/hooks/useWorkspaceMembers.ts`), a TanStack
Query `useMutation` around `inviteToWorkspace()`. On error, the form
renders:

```tsx
{invite.error instanceof Error ? invite.error.message : 'Failed to send invitation'}
```

This is a defensive fallback for a non-`Error` rejection — in the
currently pinned `@supabase/postgrest-js` version, `PostgrestError`
does `extend Error`, so a normal RPC failure's `.message` (e.g. "No
account found for that email") should already surface verbatim, not
the generic fallback string. Two honest possibilities, not
conflated into one false-certain claim: either the user-visible text
really was the specific RPC message and the task description's
"Failed to send invitation" is a paraphrase of "the invite failed,"
or something in the actual deployed runtime is producing a
non-standard rejection shape that this environment (no login
credentials for the live account, the same limitation Phase 3's own
verification record noted) cannot reproduce in a browser. Either way,
the fix is the same and cheap: make the fallback branch informative
regardless of error shape (§10.1) rather than trying to prove which
of the two happened.

There is no client-side pre-validation of the email (format check,
duplicate-invite check, or "does this look like an existing account"
lookup) before the RPC call — the form submits directly and lets the
RPC be the sole source of truth, which is the right general instinct
(never trust the client's own judgment over the server's) but leaves
the *specific* "this person doesn't have an account yet" case with no
guidance for the user beyond a raw database error string.

## 3. API / RPC / Edge Function calls

`src/modules/workspaces/api/workspaceMembers.ts`'s `inviteToWorkspace()`
calls `supabase.rpc('invite_to_workspace', {...})` — the **only** write
path for creating an invitation (its own doc-comment states this
explicitly: a plain client insert can't resolve `email → user_id`
because `profiles` RLS is intentionally self-only). No edge function is
involved in invitation creation at all. This app has exactly two edge
functions today, confirmed by directory listing: `ai-chat` and
`provider-availability` — neither is invitation-related, and **neither
uses a Supabase service-role key** (both run under the caller's own
JWT). This last fact matters directly for §10's recommendation: this
app has never yet crossed the "server-side code with elevated
permissions" boundary, and any solution requiring
`auth.admin.inviteUserByEmail` (§6) would be the first time it does.

`respond_to_workspace_invitation` (accept/decline) and
`list_workspace_members` (roster display) are the other two RPCs in
this flow, both unrelated to the reported failure — confirmed by
tracing the invite path specifically, not assumed clean by association.

## 4. Supabase schema readiness

`workspace_members` (`0028_workspace_members.sql`, extended by
`0030_workspace_membership_management.sql`) is schema-complete for
*already-registered-user* invitations: `role`
(`owner`/`editor`/`viewer`), `status`
(`active`/`pending`/`removed`), a partial unique index enforcing at
most one active owner, and a `(workspace_id, user_id)` unique
constraint the RPC's `on conflict` upsert relies on to let a
previously-declined-or-removed person be re-invited. Nothing here is
broken or missing for that case — live-verified end to end (§9).

What the schema has **no representation for**: an invitation to an
email address with no corresponding `auth.users`/`profiles` row.
`workspace_members.user_id` is `not null references auth.users(id)`
— there is no nullable "pending, unresolved identity" state anywhere in
this table, by design (it's a *membership* table, not an *invitation*
table — the two got conflated when Phase 3 built invitations as a
`status='pending'` row in the membership table itself, which works
perfectly for a known user and structurally cannot work for an unknown
one, since there is no `user_id` to write). This is the schema gap
§10's recommendation has to close.

## 5. `workspace_members` relationship

Confirmed via live query (§9) and the Phase 1/3 migrations: every
workspace gets an implicit or explicit `owner` row (a trigger
auto-creates it for workspaces created after `0028`); `invite_to_workspace`
inserts a `status='pending'` row for the invitee with the *inviting*
owner's id in `invited_by`; `respond_to_workspace_invitation` flips
`pending → active` (accept) or deletes the row (decline); `removeWorkspaceMember`
soft-removes via `status='removed'` rather than deleting, specifically
so the same person can be re-invited later without hitting the unique
constraint (confirmed in the API layer's own doc-comment). This full
lifecycle is sound and already covered by Phase 3's live-verification
matrix (`ux-14.5.4-collaboration-implementation-blueprint.md` §14.3) —
re-confirmed here, not re-litigated, since it isn't where the reported
failure lives.

## 6. Email delivery infrastructure

**There is none, for workspace invitations.** Exhaustive search (case-
insensitive grep for "resend," "sendgrid," "smtp," "nodemailer,"
"mailgun" across `src/` and `supabase/`) returns zero hits. The only
email this application sends anywhere is via **Supabase Auth's own
built-in transactional email** — signup confirmation and password
reset (`src/modules/auth/AuthContext.tsx`'s `supabase.auth.signUp()`/
`resetPasswordForEmail()` calls, with `emailRedirectTo` set to the
app's own origin) — a completely separate system with no code path
connecting it to workspace invitations. A *successful*
`invite_to_workspace` call today creates a silent database row; the
invitee is never notified by the application in any way. They discover
it only by manually navigating to Settings → Workspaces and noticing
the "Pending invitations" section (`WorkspaceManagementPage.tsx`,
`usePendingInvitations` hook) — which itself is not surfaced anywhere
in the new Collaboration Command Center (UX-14.5.7), only on the older
Settings page, a minor additional discoverability gap worth naming
though not the cause of the reported error.

Supabase Auth does offer a built-in primitive that solves exactly this
class of problem — the Admin API's `inviteUserByEmail`, which creates
an unconfirmed `auth.users` row *and* sends a real invitation email
with a link that lets the recipient set a password and land already
authenticated. It requires the **service-role key**, callable only from
trusted server-side code (an edge function), never the browser. This is
the natural mechanism §10.3 evaluates for a future phase — flagged now,
not adopted now, per §3's finding that this app has never used a
service-role key anywhere.

This environment has no visibility into the live Supabase project's
Auth → SMTP dashboard configuration (custom SMTP vs. Supabase's default
rate-limited testing sender) — worth checking before any phase that
depends on Supabase Auth's email actually being reliable at production
volume, but out of scope for what this code audit can confirm.

## 7. Authentication / acceptance flow

Standard Supabase Auth email/password signup
(`supabase.auth.signUp()`), email-confirmation-gated (the signup page's
own copy: "We sent a confirmation link... follow it to activate"). This
is entirely independent of workspace invitations today — signing up
and being invited to a workspace share no code path, no trigger, no
join. The only connection is *indirect and accidental*: an invitee who
already has an account, because they signed up independently at some
earlier point for unrelated reasons, is discoverable by
`invite_to_workspace`'s `profiles` lookup. An invitee who signs up
*after* being invited is never retroactively resolved — there is no
mechanism anywhere (trigger, cron, client-side check) that looks at
newly-created accounts and asks "does this email match a pending
invitation nobody could complete yet." This is the second concrete gap
§10.2's recommendation closes.

Once accepted, the resulting `active` `workspace_members` row is
governed by exactly the same RLS every other Phase 1–5 collaboration
surface already uses — no additional acceptance-time processing exists
or is needed.

## 8. Security requirements

Three findings, one of them a real, live-confirmed information-
disclosure issue worth fixing regardless of which invitation
architecture is chosen next:

1. **Email enumeration via the error message.** `invite_to_workspace`'s
   distinct "No account found for that email" (vs. success, vs. "already
   a member," vs. "only an owner can invite") lets any workspace owner
   determine whether an arbitrary email address has a NOVA PIP account,
   simply by attempting to invite it and reading which error comes
   back — live-confirmed as an exact, distinguishable message in §9.
   This is a genuine, if low-severity, side channel that exists **today**,
   independent of any new feature — worth flagging as a fix candidate in
   its own right (§10.1), not bundled only into the larger invite-a-
   new-user redesign.
2. **Service-role key handling**, if §10.3 is ever built: the key must
   live only in edge-function environment configuration, never
   client-side, and the new edge function must re-implement
   `invite_to_workspace`'s existing authorization checks itself (owner-
   only, no granting `role='owner'`) — calling the Admin API bypasses
   table RLS entirely, the same "security definer re-checks
   authorization explicitly in the function body" discipline the
   existing RPC already follows (per its own migration comment) has to
   be preserved in whatever new code calls `inviteUserByEmail`.
3. **Invite spam / rate limiting.** Nothing in the current schema or
   RPC rate-limits how many invitations one owner can create. Not a
   new problem invented by this discovery (any RLS-gated insert has the
   same property), but worth naming as a real requirement before any
   phase that starts actually sending email on invite — an unrated
   invite-email path is a spam/abuse vector a silent database-row
   invite path never was.

## 9. Live verification (against production)

Performed directly against the live database using two throwaway
accounts (one workspace owner, one pre-existing "invitee") and one
throwaway workspace, cleaned up afterward with zero residual rows:

| Check | Result |
|---|---|
| Invite an email with no matching `profiles` row | ✅ reproduces the exact reported failure mode: `ERROR: P0001: No account found for that email` |
| Invite an email that matches an existing `profiles` row exactly | ✅ succeeds — correct `pending` `workspace_members` row created, correct `invited_by` |
| Invite the same existing account with different letter-casing (`UX148-Test-Existing@example.com` vs. the stored `ux148-test-existing@example.com`) | ✅ reproduces a **second, distinct** failure mode: the same "No account found for that email" error, for an account that genuinely exists |

This confirms both the primary gap (§1) and the case-sensitivity bug
(§1/§8) are real, reproducible, code-level facts — not conjecture from
reading SQL alone.

## 10. Recommended architecture — smallest production-ready increment

Three tiers, ordered by cost and risk, **not** proposed as a single
combined change:

### 10.1 Ship immediately — near-zero risk, fixes real bugs today

- **Case-insensitive email match**: `where email = invitee_email` →
  `where lower(email) = lower(invitee_email)` (or a `citext` column,
  a larger and unnecessary change for one query). One-line SQL fix,
  no migration risk, closes a live-confirmed bug affecting *existing*
  accounts today.
- **Clearer, non-generic UI error text**: replace the blind
  `instanceof Error` fallback with something that always surfaces a
  useful string (`String(invite.error)` or a typed check against the
  RPC's known error messages), and specifically special-case "no
  account found" with actionable copy ("They don't have a NOVA PIP
  account yet — ask them to sign up, then invite them again") rather
  than a raw database sentence. This alone would have made the
  reported symptom self-explanatory without needing this discovery
  document to explain it.
- **Fix the enumeration side channel (§8.1)**: return the same generic
  message for both "no such account" and "already invited"/"already a
  member" cases at the RPC level (or don't distinguish them in what
  reaches the client), removing the oracle without changing any
  legitimate behavior.

None of these require a migration in the schema-shape sense (the email-
match fix is a `create or replace function`, safe and reversible the
same way every other RPC iteration in this codebase has been) and none
touch RLS.

### 10.2 Smallest real fix for "invite someone who hasn't signed up yet" — no email infrastructure required

The schema gap (§4) is that `workspace_members` has no slot for an
identity that doesn't exist yet. Recommend a minimal, additive
**pending-invitations-by-email** table — separate from
`workspace_members`, not a redesign of it:

```
workspace_invitations (
  id, workspace_id, email, role, invited_by, created_at
)
```

`invite_to_workspace` gains a fallback branch: if no `profiles` row
matches, insert here instead of raising. Extend `handle_new_user`
(`0001_init.sql`'s trigger, already the established pattern for
"something automatic happens the moment a new `auth.users` row
appears") to, immediately after creating the new `profiles` row, look
for matching `workspace_invitations` rows by (normalized) email and
promote each one into a real `active` `workspace_members` row,
deleting the `workspace_invitations` row afterward. This closes §7's
gap (nothing today resolves a signup against a prior invitation)
using the exact mechanism this codebase already trusts for
"react to a new user being created," rather than inventing a new
polling/cron mechanism.

**This still sends no email.** The inviter would see a distinct,
honest UI state ("Invitation recorded — they'll gain access
automatically once they sign up with this email") instead of an error,
and would need to tell the invitee to sign up through some channel
outside the app (the same limitation every "invite by email, no email
sent" product has until it adds real delivery). This is deliberately
the **smallest valuable slice**: no service-role key, no edge function,
no new external dependency, additive-only schema change, and it
converts today's hard failure into a working (if manual-handoff)
invitation flow.

### 10.3 Deferred — real email delivery

Wire the same `workspace_invitations` fallback path to actually call
`auth.admin.inviteUserByEmail` from a **new edge function** (the
project's first to hold a service-role key — a genuinely new trust
boundary, per §3/§8.2, warranting its own dedicated security review
before shipping, the same posture this engagement already applied to
Phase 6's storage-copy and untrusted-file-import components). Supabase
sends the actual email and pre-creates the (unconfirmed) `auth.users`
row; `handle_new_user` still does the promotion-to-membership work from
§10.2 unchanged once that row exists, so §10.2's mechanism isn't thrown
away by this phase — it's extended, not replaced. Explicitly deferred
here, not designed further, pending confirmation of whether the live
project's SMTP configuration (§6) can even support production email
volume, and pending a decision on whether the added infrastructure
cost is worth it versus §10.2's "tell them yourself" manual handoff.

## 11. Do Not Build Yet

- **A generic notification system** (in-app, push, or otherwise) as a
  prerequisite for invitations — the "Pending invitations" list on
  Settings already answers "was I invited," synchronously, the moment
  the invitee logs in; a notification is a nice-to-have layered on top
  of §10.2/§10.3, not a blocker for either.
- **Bulk/CSV invitations** — no validated demand, and §10.1–§10.3
  should each be proven on the single-email case first.
- **Custom-branded invitation emails** — depends entirely on §10.3
  being built at all; premature to design template/branding for a
  delivery mechanism not yet approved.
- **Invitation expiry/TTL** — a real eventual concern for
  `workspace_invitations` rows (§10.2) if someone invited never signs
  up, but not a blocker for the first working version; can be added
  additively (a nullable `expires_at` + a cleanup job) later without
  redesigning the table.

## 12. Summary

The reported failure is not a latent bug in what Phase 3 built — it's
Phase 3's own, never-hidden scope boundary (invite an *existing* user
only) being hit by the flow's actual primary use case. The mechanism
that exists is correct and live-verified; the gap is a missing
capability, not a broken one. Recommended path: ship §10.1's two
trivial, zero-risk fixes immediately (they fix real, live-reproduced
bugs regardless of what happens next), then §10.2 as the smallest
increment that makes "invite someone who hasn't signed up yet" actually
work, with §10.3 (real email delivery, the first service-role-key
boundary this app would cross) explicitly deferred to its own,
separately-approved phase.
