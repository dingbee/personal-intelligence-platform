# UX-14.4 Path B — Artifact Intelligence Generation Discovery

**Status: design only.** No code, migrations, or UI changes were made to produce this document, per explicit instruction. Constraints held: no new database tables, no collaboration, no formula calculation logic, no bypass of existing AI governance, deterministic workbook generation preserved.

Builds on UX-14.4 Phase 1 (artifact classification), Phase 2/Path A (deterministic spreadsheet export), and UX-14.4.5 (acceptance harness). Goal: define how NOVA turns a natural-language request into a validated `SpreadsheetArtifactData` payload — the same payload Path A's parser produces from a markdown table — without touching Path A's downstream pipeline at all.

---

## 1. Audit: Five Systems, Grounded in Code

### 1.1 Capability execution framework

Every one-shot AI operation in this codebase (Summarize, Extract Concepts, Generate Briefing, ...) goes through one function: `runCapability` (`src/modules/ai/orchestration/runCapability.ts`). It resolves a `PromptTemplate` by `capabilityId` from a code-registered registry, renders variables into it, optionally appends `<knowledge_connections>`/`<spreadsheet_analysis>` context blocks, and calls `streamChatCompletion` — the same low-level provider call `AIService.sendMessage` uses for ordinary chat. Callers wrap it in `runWithFallback` (tries each candidate in a resolved provider chain) and `withProviderAvailability` (refuses to run at all if the chain is empty, normalizes errors) — this is "the shared choke point every `runCapability` consumer goes through," per that function's own header comment. **A new capability gets this for free by definition — there is no way to call a provider from a capability without going through this path**, which is exactly what "governance" means operationally in this codebase: provider availability, per-workspace overrides, and error normalization are enforced once, centrally, not per-caller.

### 1.2 AI prompt architecture — the actual governance boundary

`promptRegistry` (`src/modules/core/prompts/registry.ts`) holds versioned `PromptTemplate` objects (`{ id, capabilityId, version, template, active }`), registered in code via `registerPlatformModule` calls in each feature module's `module.ts`, imported once for their side effect from `App.tsx`. There is **no runtime-editable prompt store, no live admin UI, no separate approval workflow** beyond ordinary code review and deployment — a prompt template is exactly as governed as any other line of source code in this repository, no more, no less. This is the concrete meaning of "do not bypass existing AI governance": a new capability's prompt must be registered the same way (`registerPlatformModule`, versioned, `active: true`), not constructed ad hoc at call time or fetched from anywhere else.

### 1.3 Existing artifact metadata model (UX-14.4 Phase 1)

`ArtifactKind` registry + `detectArtifactKind` (deterministic classifier) + `generation_metadata.artifactKind`/`artifactData` (Phase 2's additive slot) already exist and are exactly the destination this design needs to land in — a generated spreadsheet is not a new kind of thing, it's the `spreadsheet` kind, produced by a second route into the same `SpreadsheetArtifactData` shape Path A's parser already produces.

### 1.4 Existing spreadsheet export pipeline (UX-14.4 Phase 2, Path A)

`SpreadsheetArtifactData` (`sheets[].cells[].{cell, value, formula}`) → `buildSpreadsheetWorkbook` (pure, writes `.f` for formulas, never evaluates) → `exportSpreadsheetArtifact` (XLSX/CSV dispatcher) → `SpreadsheetArtifactPanel` (preview + Download, lazy-loaded). **This entire chain is format-agnostic about where `SpreadsheetArtifactData` came from.** Nothing here needs to change, know about, or be told whether a payload was parsed deterministically from a markdown table or produced by an LLM — that is the whole point of the schema-first design from Phase 2, and it is what makes "preserve deterministic workbook generation" achievable by construction rather than by discipline: Path B's only job is to produce a value of the same type Path A already produces, then hand it to the same unchanged functions.

### 1.5 Knowledge retrieval/context systems

`retrieveSpreadsheetContext(documentId)` (`processing/api/retrieveSpreadsheetContext.ts`) already formats a document's precomputed `SheetAnalysis` (real sums, trends, anomalies — never re-derived from raw text) into prompt-ready text, mirroring `retrieveGraphContext`'s contract exactly: "never throw, missing data is just null." This is the established, safe way to ground a capability's output in real numbers rather than letting the model invent them, and it's the deciding factor in §2's grounding design below.

### 1.6 The missing-until-now piece: the Workspace Action Router

Not one of the five named areas, but the load-bearing discovery of this audit: `src/modules/workspace-actions/` already implements exactly the "User Request → Intent Detection" step this design needs, end to end, for two existing commands (Save to Notes, Generate Briefing):

```ts
interface WorkspaceAction<TPayload> {
  id: string
  match: (text: string) => TPayload | undefined   // deterministic, no LLM call
  run: (payload: TPayload, context: WorkspaceActionContext) => Promise<WorkspaceActionOutcome>
}
```

`AIService.sendMessage` calls `runWorkspaceAction(text, context)` before falling through to ordinary chat; the first registered action whose `match` recognizes the text short-circuits the normal response with `{ responseText, references? }`. `generateBriefingAction.ts` is a complete, working three-file example of the exact pattern this design needs: a deterministic command parser (`parseExecutiveBriefingCommand`, one regex, no LLM), an orchestrator (`runExecutiveBriefingCommand`) that resolves context and calls a `runCapability`-backed generator, and a thin `WorkspaceAction` adapter connecting the two to the router. **Path B is not new architecture — it is a fourth registration in an already-built, already-governed system.**

## 2. Architecture Proposal — the Flow, Mapped onto Real Modules

```
User Request ("Create a hotel occupancy forecast model")
        │
        ▼
Intent Detection                    parseSpreadsheetGenerationCommand.ts (NEW)
  deterministic regex,              — mirrors parseExecutiveBriefingCommand.ts exactly:
  no LLM call                         one pattern, no model call to decide "was this asked for"
        │
        ▼
Artifact Specification              generate-spreadsheet-artifact capability (NEW)
  one LLM call, via                 — registered via registerPlatformModule, prompt template
  runCapability/runWithFallback       instructs the model to emit ONLY fenced JSON matching
  (existing governance, unchanged)    the SpreadsheetArtifactData schema (§2 of the Phase 2 doc)
        │
        ▼
Validation                          parseSpreadsheetArtifactResponse.ts (NEW)
  defensive parsing + safety caps   validateSpreadsheetArtifactData.ts (NEW)
  — untrusted model output           — the actual new governance surface, see §4
        │
        ▼
Workbook Generation                 buildSpreadsheetWorkbook (UNCHANGED — Path A's function)
  pure, deterministic,              — zero new code; Path B produces the same typed value
  never evaluates formulas            Path A's parser already produces, so this step doesn't
                                       know or care where the value came from
        │
        ▼
Export                              exportSpreadsheetArtifact / SpreadsheetArtifactPanel
  XLSX / CSV, client-side             (UNCHANGED — Path A's functions)
```

### The grounding decision (the one genuinely new judgment call)

Two request shapes need different handling, and conflating them is the single biggest trust risk in this design:

- **"Create an occupancy forecast **formula**"** — a template request. No real data exists to ground it in; the correct output is structure (headers, one illustrative row, a real formula) with no claim that the numbers are anyone's actual figures. This is exactly the roadmap's own worked example, and it maps to `artifactKind: 'formula'`, not `'spreadsheet'`.
- **"Forecast Q3 revenue **based on my uploaded data**"** — a data-grounded request. Here the model must be constrained to the real numbers already computed by `retrieveSpreadsheetContext`/`getSpreadsheetAnalysis` for the referenced document, the same context Chat already grounds spreadsheet Q&A in. Fabricating numbers that look like real data here is a materially worse failure than fabricating a template — it's the "confidently wrong financial figure" failure mode.

The orchestrator (`runGenerateSpreadsheetArtifactCommand.ts`) is where this gets decided: if the request references an active/uploaded document with computed spreadsheet analysis, fetch `retrieveSpreadsheetContext` and pass it into the capability as grounding (same `spreadsheetContext` parameter `runCapability` already accepts); otherwise proceed ungrounded and the output is necessarily a template, not a data model — tagged accordingly.

## 4. Risk Analysis

**Formula injection (the most important finding of this discovery).** `buildSpreadsheetWorkbook` writes `cell.formula` verbatim into a real `.f` field of a real, downloadable `.xlsx`. Today (Path A) that string comes from a markdown table the model already wrote in an ordinary chat response; Path B makes the model the *direct, sole* author of formula content in response to an explicit "build me a spreadsheet" instruction, which is a meaningfully larger attack surface — a compromised or manipulated response could write a formula calling a data-exfiltrating function (`WEBSERVICE(...)`, `HYPERLINK(...)`, `IMPORTXML(...)` are all real Excel/Sheets functions capable of making outbound requests when the file is opened) or emit legacy DDE-style content (`=cmd|'/c ...'!A1`) that some environments still expand. **This is not the same risk as the well-known plain-text-CSV formula-injection class (that one exploits leading `=`/`+`/`-`/`@` in a cell displayed as text; here the field is a genuine `.f` formula field), but the underlying concern — untrusted content becoming an executable formula in a file the user will open in a real spreadsheet application — is the same shape.** `validateSpreadsheetArtifactData.ts` must apply a formula-content allowlist (arithmetic operators, cell references, a fixed set of safe functions like `SUM`/`AVERAGE`/`MIN`/`MAX`/`COUNT` — reject anything else) before a generated formula is ever allowed to reach `buildSpreadsheetWorkbook`. This finding also applies retroactively to Path A's parser, which has no such allowlist today — flagged as a follow-up hardening item for Path A, not blocking Path B, since Path A's formulas come from ordinary chat prose a user already chose to save, a narrower and lower-probability surface than an explicit generation request.

**Fabricated data presented as real.** Covered by the grounding design in §2 — the orchestrator, not the capability, decides whether output is data-grounded or template-only, and that decision must be recorded in `generation_metadata` (e.g. `{ grounded: boolean, sourceDocumentId?: string }`) so the UI can eventually distinguish "NOVA's real numbers" from "NOVA's illustrative structure" (out of scope to build the UI distinction now — recording the fact is enough for this phase).

**Runaway or degenerate output.** An ungrounded generation request has no natural size limit from the model's side. `validateSpreadsheetArtifactData` must cap sheet count, rows per sheet, and total cells (concrete numbers deferred to implementation, informed by what's actually reasonable to preview/export — e.g. low hundreds of cells, not tens of thousands) and reject/truncate rather than silently accept an oversized payload.

**Malformed or non-compliant model output.** The model may not follow the fenced-JSON instruction, especially on a fallback provider mid-chain. `parseSpreadsheetArtifactResponse` must fail closed — throw, not guess — exactly like `extractJsonArray` already does ("The model response did not contain a JSON array"), and the orchestrator's chat response on that failure must say generation didn't produce something usable rather than silently returning an empty or partial artifact.

**Provider/model quality variance.** Validation runs identically regardless of which provider in the fallback chain actually answered — `runWithFallback` already makes this provider-agnostic; nothing in Path B needs to special-case a specific provider's output shape.

**Mislabeling generated content as user-authored.** `generation_metadata` already has a place for this (`savedFrom`, `generatedBy`-style fields other paths already use — e.g. `knowledge_links.generated_by` for AI-detected relationships) — Path B's metadata should record that the artifact was AI-generated (not just AI-classified, the distinction Phase 1 already draws between a note's *kind* and its *provenance*), consistent with existing convention rather than inventing a new field name.

**Consent model — a deliberate departure from the Generate Briefing precedent.** `generateBriefing` auto-saves a `Note` the instant the model responds, no approval step. This document recommends Path B **not** follow that precedent: a generated spreadsheet artifact should be shown as an unsaved preview (reusing `SpreadsheetArtifactPanel` against an in-memory `SpreadsheetArtifactData`, before any `Note` exists) with an explicit save action, mirroring UX-14.3.5's memory-capture consent model ("NOVA proposes, the user approves") rather than the auto-save model. The reasoning: a briefing is reviewable prose a user reads before acting on; a spreadsheet artifact is a file containing formulas that gets opened in a real application — a strictly higher-trust action, and one where the validation layer above, however careful, is not a substitute for a human's own final look before something is saved and downloadable.

## 5. Implementation Phases (for when code work is authorized)

1. **Skeleton + governance wiring**: capability + prompt template registration, intent parser, orchestrator, `WorkspaceAction` registration — behind a strict validator from day one, not added later. Output is an unsaved preview per the consent-model recommendation above, not an auto-saved Note.
2. **Validation hardening**: formula-content allowlist, size caps, malformed-output handling — the actual safety layer, sized and tuned against real (not hypothetical) model output before this phase is considered done.
3. **Grounding integration**: wire `retrieveSpreadsheetContext` into the orchestrator for document-referencing requests; enforce the grounded/template distinction in `generation_metadata`.
4. **Explicit user save action**: the UI step connecting the preview to `createNote`/`generation_metadata.artifactData`, only once 1–3 are done.
5. **Acceptance harness extension**: extend `spreadsheetArtifactLifecycle.test.ts` (UX-14.4.5) with a second fixture path representing AI-generated (not markdown-parsed) input, exercising the same classification → validation → workbook → export chain from that entry point.

Each phase should ship independently verified, per this initiative's established discipline — not as one large drop.

## 6. Verification Strategy

- **Provider call mocking**: `AIService.test.ts` already establishes the exact convention — `vi.mock('@/modules/ai/orchestration/streamChatCompletion', ...)` returning a canned `{ content, model }`. The new capability's tests reuse this, not a new mocking approach.
- **Parser tests**: `parseSpreadsheetArtifactResponse` tested against well-formed JSON, fenced JSON, malformed JSON, and JSON with wrong field types — mirroring `parseKnowledgeExtractionResponse.test.ts`'s existing fixture style.
- **Validator tests — the highest-value new coverage**: adversarial fixtures specifically for the formula-injection allowlist (a formula containing `WEBSERVICE(`, `cmd|`, pipe characters, or anything outside the allowed function set must be rejected, not sanitized-and-passed), oversized payloads (too many sheets/cells), and malformed cell addresses.
- **Orchestrator tests**: grounded vs. ungrounded branch coverage (with/without a referenced document that has spreadsheet analysis), and the failure path when the model doesn't comply with the JSON contract.
- **Reuse, don't duplicate, Path A's coverage**: `buildSpreadsheetWorkbook`/`exportSpreadsheetArtifact`/`sheetToGrid` are unchanged and already have their own tests (UX-14.4 Phase 2) plus the write/read round-trip regression (UX-14.4.5) — Path B's tests should feed validated output *into* those existing, already-verified functions, not re-test them.
- **Acceptance harness**: extend the UX-14.4.5 lifecycle test with a second entry point (an AI-generation fixture) alongside the existing markdown-parsing fixture, both converging on the same downstream assertions (formula preservation, export integrity) — the recommendation already recorded in the UX-14.4.5 implementation record.
- **Bundle-splitting check**: re-run `npm run verify:bundle` once Path B lands — the new capability/orchestrator code has no reason to import `xlsx` directly (it produces `SpreadsheetArtifactData`, not a workbook), so this should pass unchanged, but re-running it is cheap and catches an accidental new eager import.
- **Explicitly still open, not addressed by this phase's tests**: no live Supabase, no real browser save/download, no real spreadsheet application opening a generated file — the same disclosed gap carried since UX-14.2, now applying to one more surface.
