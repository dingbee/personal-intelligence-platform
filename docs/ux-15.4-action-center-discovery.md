# UX-15.4 Discovery — Action Center & Unified Actions

**Discovery only — no implementation.** Ground-truth catalog of every
object-level action across Notes, Documents, Assets, Conversations,
Knowledge Nodes, Knowledge Collections, Hub, Knowledge Explorer, Export
Center, Collaboration, Search, and the Command Registry, grounded in
direct file/line reads (not inference).

## 1. Shared menu infrastructure that already exists

One shared `DropdownMenu`/`DropdownMenuItem` shell exists
(`src/shared/components/ui/DropdownMenu.tsx`) — a plain click-outside
popover, no keyboard nav, no icon slot beyond a `danger` boolean. Eight
call sites (`NoteCard`, `DocumentCard`, `ImageCard`, `ConversationList`,
`WorkspaceCard`, `CollectionTree`, `TagFilterBar`, `ProfileMenu`), each
hand-rolling its own list of items — **there is no shared "menu
builder" or action registry today, only a shared shell**. Detail pages
(`NoteDetailPage`, `DocumentDetailPage`, `KnowledgeNodeDetailPage`,
`KnowledgeCollectionDetailPage`, `ImageReaderPage`, `ChatPage`) don't
use `DropdownMenu` at all — they lay actions out as a flat row of
buttons. `AddToCollectionButton` rolls its own popover for a documented
reason (its inline "create collection" text input breaks
`DropdownMenu`'s close-on-any-inside-click behavior).

## 2. Action inventory by type

**Rename** — every existing Rename uses the same `InlineTextForm`
primitive except Notes (full-form Save button) and Conversations'
header (`ConversationTitleEditor`). Present for Document, Asset,
Conversation. **Absent for Note** (no discrete rename — only a full
edit form), **absent for Knowledge Node** (title is immutable in the
UI), **absent for Knowledge Collection** (the mutation hook
`useKnowledgeCollection().update` already exists and supports
name/description — no UI ever calls it).

**Delete** — 100% consistently routed through the shared
`ConfirmDialog` component, gated by a per-object `canDelete` boolean.
Present for Note, Document, Asset, Conversation, Knowledge Collection.
**Absent for Knowledge Node** (no delete action anywhere — only removal
from a collection, or AI-driven merge via `knowledgeNodeResolution.ts`,
never exposed as a button).

**Move** (to a folder) — only Documents have a real move-to-folder
concept (`CollectionMoveSelect`, backed by the `collections` table).
Notes/Assets/Conversations have no folder concept at all.

**Add to (Knowledge) Collection** — the single most consistent
cross-type action: one component (`AddToCollectionButton`), one label
("Add to collection"), 5 call sites (Note, Document, Asset,
Conversation, Knowledge Node detail pages). **Gap**: never appears on
any list-card surface — only on detail pages, so adding an item to a
collection always requires opening it first.

**Save As / Export (format picker)** — the one action type with **full
coverage across all 6 object types**, already fully unified via
`KnowledgeExportDialog` (built UX-14.5.11/UX-15.1) plus the bulk
`ExportCenterPage`. This is the existing proof that a shared
dispatch-by-object-type pattern (`buildExportRequestForObject` in
`exportCenterRequests.ts`) works well in this codebase — the registry
design below follows the same shape.

**Export Package (`.nova`, Knowledge Exchange)** — the older,
single-format import/export mechanism, still live as separate per-type
Import dialogs. **Placement inconsistency found**: Note/Document/Asset
each get their Import button on their own list page (`NotesPage`,
`LibraryPage`), but Knowledge Node/Link/Collection/**Conversation**
import buttons are all bolted onto `KnowledgeExplorerPage` — a
conversation-import button lives on a page named "Knowledge Explorer,"
not on Chat or a conversations list.

**Share** — **does not exist as an action anywhere.** Only passive
`SharingBadge`/`OwnershipLine` (no click handler). Actual access control
is entirely workspace-level (`Invite` on the member roster) — an
object becomes "shared" only by belonging to a multi-member workspace.
Confirms UX-15.1's own discovery finding, unchanged.

**Ask NOVA** — `createConversationWithQuery`, 5 consistent call sites
(Asset ×2, Knowledge Collection, Knowledge Node, Note), label pattern
"Ask NOVA about this {type}". **Inconsistency found**: Document uses a
*different* mechanism entirely — a plain `<Link to="/chat?documentId=">`
labeled "Chat with NOVA" / "Chat about this document" (document-scoped
chat, not `createConversationWithQuery`), breaking both the mechanism
and the label pattern every other type shares.

**Open** — present everywhere as plain navigation; not itself a
mutation-backed action.

**Continue Reading** — Hub's `ContinueWorkingCard` and the Command
Bar's `buildContinueReadingCommand` both read the same
`getMostRecentReadingProgress` data (already unified in UX-15.2/UX-15.3).

**Import** — see Export Package above; placement inconsistency is the
one finding.

**Pin** / **Favorite** / **Archive** / **Duplicate** — **all four exist
only for Conversations** (plus Archive also exists independently for
Workspaces, confirming Archive is a repeated *pattern* — two separate
`archived_at` columns, two separate hook implementations — not a shared
mechanism). No other object type (Note/Document/Asset/Knowledge
Node/Knowledge Collection) has any of these four.

## 3. Actions found outside the requested taxonomy

Merge (Notes, multi-select already exists today —
`NotesPage`'s "Merge notes" mode), Save as Notes (Document/Asset
cards), Save to Notes (Conversation, per-message and whole-conversation),
Summarize (Note; Document has a different, non-mutation "jump to
summary panel" version), Reprocess (Document), Generate Briefing
(Knowledge Node), Reconcile AI Knowledge Graph (workspace-level, on
Knowledge Explorer), Tag add/remove (Note, Document only), Workspace
Objective status changes (Hub), member management actions
(Collaboration), provider switch (Conversation).

## 4. Surfaces with zero object-level actions

Search results (`SearchResultCard` is a pure navigation link, no menu
at all), Knowledge Explorer's node grid (per-card is navigation-only;
all real actions on that page are page-level), Hub's own page component
(every section either links out or delegates to a child that has real
actions).

## 5. Command Registry action-vs-navigation split

Read every file under `src/modules/commands/commands/`. The large
majority of commands are navigate-only. Real mutation-backed commands:
`createNoteCommand` (creates a note), `buildAskNovaQueryCommand` + all 6
`buildPlanCommand` variants (create a conversation via
`createConversationWithQuery`), `quickCaptureCommand` (opens a modal).
`useCommandActions.ts` is the closest existing thing to a generic
action abstraction — but it only covers 3 action types (create-note,
create-conversation-with-query, open-quick-capture); Rename/Delete/
Archive/Pin/Duplicate/Add-to-collection/Export all live directly inside
each object's own `use<Object>(s)` hook, never through a shared surface.

## 6. What this means for the registry design (Phases 2–5)

Two real, structural facts drive the design:

1. **A "registry" here can't be a plain object calling React hooks
   directly** — mutations are React Query hooks (`useNotes().remove`,
   `useDocumentMutations().rename`, etc.), which must be invoked inside
   a component. The existing Commands system already solves exactly
   this shape (a static `Command[]` registry + a `useCommandActions()`
   hook that binds live mutations at render time) — the action registry
   follows the same split: a pure, static `ActionDefinition[]` (id/
   label/icon/objectTypes/destructive) plus a thin per-object adapter
   that maps an object's *already-existing* hooks to `{actionId: handler}`.
2. **"No behavior changes — only consolidation" (Phase 3) is achievable
   for exactly the actions that are already consistent enough to share
   one rendering component** (Rename/Delete/Add to Collection/Save As/
   Ask NOVA where it already exists) — Pin/Favorite/Archive/Duplicate
   are genuinely conversation-specific today and are represented in the
   registry as conversation-only entries, not generalized to types that
   have no backing field for them (that would be new speculative
   backend work the task explicitly forbids).
