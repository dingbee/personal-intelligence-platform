# UX-14.5.10.3 — Document Exchange: Discovery

**Status: discovery only. No schema changes, no migrations, no RLS changes, no framework changes, no application code in this document or the commit that adds it.**

Objective: produce a complete implementation blueprint for Document
Exchange — the third Knowledge Exchange object type, after Notes
(UX-14.5.9), Knowledge Nodes (UX-14.5.10.1), and Assets (UX-14.5.10.2) —
grounded in the actual current schema, storage architecture, and
processing pipeline (every claim below is backed by a migration file, a
type definition, or an API/pipeline function actually read for this
pass). Documents are the object type both the original UX-14.5.6
discovery and the UX-14.5.10 expansion discovery flagged as the hardest
of the five remaining types: they carry private binary storage (like
Assets) *and* a multi-stage AI derivation pipeline an order of magnitude
larger than any object type Exchange has handled so far (chunks →
embeddings → extraction metadata, plus four further per-chapter
artifact tables). UX-14.5.10.2's own final report flagged this
explicitly: Assets validated the binary-content strategy at a 25MB cap;
Documents run up to 200MB, past where that phase's own base64-in-JSON
approach stays practical. This document treats that as an open question
and answers it (§3), rather than assuming Assets' approach carries
forward unchanged.

---

## 0. Audit summary — what's already true, confirmed by reading the code

- **The binary-storage problem Assets already solved generalizes
  directly.** Documents' storage bucket (`documents`, `0002_library.sql`)
  has the identical shape Assets' bucket does: private, per-user-folder
  RLS (`(storage.foldername(name))[1] = auth.uid()::text`), no
  cross-account read path, download only via `downloadDocumentFile`
  (owner-scoped) — there is no `getDocumentSignedUrl` equivalent used for
  cross-account transfer today, but the same principle Assets already
  proved applies: the *exporting* account already has full read access to
  its own file, so export can always fetch the bytes locally before
  building a package, regardless of what any other account could reach.
  No RLS work is a prerequisite here, exactly as the UX-14.5.10 discovery
  found for all five remaining object types.
- **Documents' own row-level RLS is already workspace-shareable**
  (`0031_shared_knowledge_objects.sql` §1–§4): `documents`,
  `document_chunks`, `embeddings`, and `document_tags` all already carry
  the owner-or-workspace-member OR-clause pattern. This is irrelevant to
  Exchange itself (import always creates fresh, owner-scoped rows — see
  §6), but it means nothing about *sharing* a document inside a
  workspace needs fixing before Exchange can be built.
- **A significant, previously-undocumented coherence gap, found this
  pass**: `extraction_metadata`, `processing_jobs`, `chapter_summaries`,
  `highlights`, `flashcards`, and `reading_progress` were *not* touched
  by `0031_shared_knowledge_objects.sql` and have no `workspace_id`
  column at all — confirmed by reading both `0003_processing.sql`/
  `0008_reading_workspace.sql` (original schema) and `0031`'s own file
  (which lists exactly 14 objects it touches; none of these six are
  among them). Concretely: a workspace member who can already see a
  shared document and its chunks today (via `0031`) **cannot** see that
  document's extraction metadata, chapter summaries, highlights, or
  flashcards — RLS silently blocks all six, regardless of workspace
  role. This is the same category of gap the UX-14.5.10 discovery flagged
  for `flashcards`/`highlights`/`chapter_summaries` in passing (§5 there);
  this pass confirms it in full and adds `extraction_metadata`,
  `processing_jobs`, and `reading_progress` to the list. **It does not
  block Document Exchange** (§6 below — import always writes fresh,
  owner-scoped rows, independent of workspace-sharing RLS) but it is a
  real, orthogonal product gap worth a future ticket, not silently
  worked around here.
- **The single biggest simplification, found this pass**: Documents
  already have a complete, reusable, one-call regeneration pipeline —
  `processDocument(documentId, userId)` — that runs extraction, chunking,
  embedding, and status transitions from nothing but the document's own
  uploaded file bytes (§2). This means the *entire* AI-derived side of a
  document (chunks, embeddings, extraction metadata, and by further
  implication chapter summaries/flashcards, which are themselves
  generated from chunks) never needs to travel in a package at all — the
  package only ever needs to carry what `processDocument` cannot
  reconstruct: the original file bytes, plus genuinely user-authored
  content. This is the same "always regenerate derived content, never
  copy it" rule already established by Notes' search index, Knowledge
  Nodes' canonical identity, and Assets' optimized/thumbnail derivatives
  — applied here to a much larger derivation pipeline, but the same rule.
- **Package format is a real, size-driven decision this phase, not a
  copy of Assets' choice.** Assets' 25MB cap made base64-in-JSON (Option
  A) cheap and safe. Documents' 200MB cap changes the arithmetic enough
  that Option A becomes a genuine browser-memory risk (§3). This
  discovery recommends **Option B — a ZIP package via the `jszip`
  dependency this repo already ships** (already used to *parse* EPUB,
  which is itself a ZIP container) over both Option A and a custom
  Option C hybrid format.

## 1. Document data model — object-by-object audit

Read from `supabase/migrations/0002_library.sql`, `0003_processing.sql`,
`0008_reading_workspace.sql`, `0011_ai_provenance_fields.sql`, and
`src/shared/types/database.ts`.

| Object | Ownership | Workspace-shareable (RLS) | User-authored or AI-derived | Transfer or Regenerate |
|---|---|---|---|---|
| `documents` | `user_id` | Yes (`0031` §1) | **User-authored act** (the upload itself; `title` is user-editable) | **Transfer** — this *is* the object being exchanged |
| `document_chunks` | `user_id` (+ denormalized `workspace_id`) | Yes (`0031` §2) | AI-derived (mechanical chunking of extracted text) | **Regenerate** via `processDocument` |
| `document_tags` | via parent `documents` | Yes (`0031` §4) | User-authored (tag names, user-applied) | **Transfer** — tag *names* only, re-resolved (find-or-create) in the importer's own account, exactly like Notes' `tags` field |
| `embeddings` | via parent `document_chunks` | Yes (`0031` §3) | AI-derived (mechanical, from chunk content) | **Regenerate** via `processDocument` |
| `extraction_metadata` | `user_id` | **No** — not touched by `0031`, no `workspace_id` column (gap, §0) | AI-derived (author/language/page/word/char counts, computed by the extractor from file bytes) | **Regenerate** via `processDocument` — a pure recomputation from the same original bytes, byte-for-byte reproducible for the same file |
| `processing_jobs` | `user_id` | **No** — not touched by `0031`, no `workspace_id` column (gap, §0) | Neither — operational bookkeeping (one row per processing *run*, not user content) | **Neither** — a fresh job row is created automatically as a side effect of calling `processDocument` again; nothing to transfer, nothing to "regenerate" in the content sense |
| `chapter_summaries` | `user_id` | **No** — not touched by `0031` (gap, §0) | **100% AI-derived** — confirmed by reading `src/modules/reader/api/chapterSummaries.ts`: `saveChapterSummary` is only ever called from the AI capability flow (`runCapability`), no manual-authoring code path exists | **Regenerate** — the importer re-runs "Generate summary" per chapter post-import if they want it; see §4 for why this is the safer choice over transferring |
| `highlights` | `user_id` | **No** — not touched by `0031` (gap, §0) | **User-authored in practice** — confirmed by reading `src/modules/reader/api/highlights.ts`: `createHighlight` never sets `source_chunk_ids`/`generation_metadata` (the AI-provenance columns `0011` added exist on this table but are unused by any code path today — every highlight in this app is a manual passage selection) | **Transfer** — quote text + `note` + `chapter_index`, with `source_chunk_ids`/`generation_metadata` defensively nulled on import regardless (never meaningful cross-account, same rule as every other package type) |
| `flashcards` | `user_id` | **No** — not touched by `0031` (gap, §0) | **100% AI-derived** — `createFlashcards` (`src/modules/reader/api/flashcards.ts`) is only called from the AI capability flow, same as chapter summaries | **Regenerate** — same reasoning as chapter summaries |
| `reading_progress` | `user_id` | **No** — not touched by `0031` (gap, §0) | Neither — pure per-account UI position state (`chapter_index`, `scroll_fraction`), not content at all | **Neither** — never transferred; the imported document is new to the importer, so it correctly starts unread (no row at all, matching the state of any newly-uploaded document today) |

### 1.1 Why chapter summaries and flashcards regenerate but highlights transfer

All three are chapter-scoped and share the same theoretical risk: they
reference a document by `chapter_index`, and chapter numbering is
assigned by the extractor at processing time. If chunking/extraction
logic ever changes between the exporter's version of this app and the
importer's, a transferred `chapter_index` could point at the wrong
chapter after import. This risk already exists *today*, internally,
for the "Reprocess" button on an existing document — it is not a new
risk Exchange introduces, but it is a real one worth weighing.

Given that shared risk, the deciding factor is authorship, not
mechanism:

- **Highlights** are an editorial act — the user chose *this specific
  passage*, and `quote` is verbatim text they selected. That act has no
  regeneration path at all (there is nothing to "regenerate" — the
  underlying document reprocessing doesn't recreate what a person
  personally noticed). Losing highlights entirely on import would be a
  real, felt data loss for a "give someone your annotated copy" workflow,
  which is one of Document Exchange's clearest use cases. The
  chapter-index-drift risk is bounded and cosmetic (worst case: a
  correct quote shows up filed under the wrong chapter number, still
  human-readable and still searchable) — an acceptable, documented
  tradeoff, the same category of accepted limitation as Assets'
  no-provenance-column gap.
- **Chapter summaries and flashcards** have no user-editorial content at
  all — every word was written by the AI, deterministically derivable
  again from the chunk content of that chapter, for the cost of one
  button click the importer can choose to make or skip. There is no
  loss in *not* transferring them, and regenerating sidesteps the
  chapter-index-drift risk entirely, since a freshly generated summary
  is always keyed to the importer's own freshly assigned chapter
  numbering by construction. This mirrors the same "structural/derived
  → always regenerate, cheap to reproduce, never carry stale copies"
  rule chunks and embeddings already follow, just extended one layer up
  the derivation chain.

## 2. Storage architecture — what already exists, what's reusable as-is

Read from `src/modules/library/api/documents.ts`,
`src/modules/processing/pipeline/{processDocument,downloadFile}.ts`,
`src/modules/processing/extractors/{registry,pdf,epub,docx,txt,markdown,
spreadsheet}.ts`, `src/modules/library/utils/fileTypes.ts`,
`src/modules/library/hooks/useDocumentMutations.ts`.

| Stage | Existing function | Reusable unmodified for import? |
|---|---|---|
| Upload (storage + row) | `uploadDocument({file, userId, collectionId, workspaceId})` (`library/api/documents.ts`) — validates file type from extension, uploads to a fresh `${userId}/${crypto.randomUUID()}-${sanitizedName}` path, inserts the row (`status: 'uploaded'`) | **Yes, unmodified** — exactly the Notes/Knowledge-Node/Asset precedent: import constructs a `File` from the package's embedded bytes and calls this literally, getting fresh id/fresh storage path/owner-attribution/type-validation for free |
| Download (for export) | `downloadDocumentFile(filePath)` (`processing/pipeline/downloadFile.ts`) — owner-scoped `supabase.storage.from('documents').download()` | **Yes** — the export flow's async fetch step (mirroring `fetchAssetOriginalAsBase64`) uses exactly this, since the exporting account already owns the file |
| Extraction | `getDocumentProcessor(fileType)` → one of 8 registered extractors (pdf/epub/docx/txt/markdown/xlsx/csv/ods), each `.extract(file)` → `{text, chapters?, ...}` | **Yes, unmodified**, via `processDocument` |
| Chunking | `getChunker(strategy)` — `chapter-aware` if the extractor found chapters, else `paragraph` (`processing/chunking/registry.ts`) | **Yes, unmodified**, via `processDocument` |
| Chunk persistence | `replaceDocumentChunks({documentId, userId, workspaceId, chunks})` | **Yes, unmodified**, via `processDocument` |
| Embedding | `OpenAIEmbeddingProvider` + `embedBatchWithRetry` (rate-limit-aware, batched 100 at a time) + `supabaseVectorStore.upsert` | **Yes, unmodified**, via `processDocument` |
| Status/job tracking | `processing_jobs` row created per run, `documents.status` transitions `uploaded → processing → ready`/`error` | **Yes, unmodified**, via `processDocument` |
| Search indexing | **No separate index** — confirmed by reading `documentSearchProvider.ts`: search is title (`ilike`, lexical) + `match_document_chunks` (semantic, via the `embeddings` table) directly against live rows. Unlike Notes (`0025_note_search.sql`'s dedicated index table), there is nothing else to (re-)populate | **N/A — nothing extra needed.** The moment `processDocument` finishes, the imported document is automatically searchable; this is a strictly simpler integration than Notes' search indexing needed |

**Conclusion**: every single processing stage after "the file exists in
storage with a row pointing at it" is already reusable without
modification, by calling the exact same two functions a native upload
already calls in sequence
(`useDocumentMutations.ts`'s `upload` mutation: `uploadDocument()` then
fire-and-forget `void processDocument(document.id, user!.id)`). Document
Exchange's entire *implementation* surface for the processing side is
therefore two function calls, not new pipeline code — directly
answering §7 (below): imported documents should immediately enter the
existing extraction pipeline, because that pipeline already accepts
exactly this input shape (a document row + a file in storage) with zero
awareness of whether the file arrived via upload or import.

## 3. Package format — Option A vs. B vs. C, evaluated not assumed

### 3.1 The size regime is materially different from Assets

Assets capped at 25MB; base64 inflation (~1.33×) meant a ~33MB JSON
string worst case — annoying but tractable in a browser tab. Documents
cap at **200MB** (`MAX_UPLOAD_BYTES`, `library/utils/fileTypes.ts`).
The same 1.33× inflation on a 200MB file means a ~266MB JSON string.
Concretely, for one document at the cap, Option A's peak client memory
during export or import is realistically: 200MB (raw file, held during
fetch/construction) + 266MB (base64 string) + a further transient
allocation while `JSON.stringify`/`JSON.parse` walks that string +
200MB again (the decoded `Uint8Array` on import) — on the order of
700MB–1GB of peak heap for a single document, on a client that may be a
phone or a low-memory laptop. That is a real risk of tab crash or OOM,
not a theoretical one, and it is materially worse than Assets' regime
(where the same arithmetic tops out under 100MB).

### 3.2 Comparison

| Criterion | Option A — base64 in JSON | Option B — ZIP (`jszip`) | Option C — hybrid manifest + binary payload (custom framing) |
|---|---|---|---|
| Browser memory usage | Worst at scale — ~1.33× inflation plus full-string materialization for `JSON.stringify`/`parse`/`atob`; ~1GB peak for a 200MB document (§3.1) | Better — no text inflation; `jszip` builds/reads compressed or stored entries without needing one giant string in memory at once, roughly halving peak memory vs. A for the same file | Comparable to B for memory (also binary, no base64), but a hand-rolled implementation has no guarantee of streaming-friendly framing unless deliberately designed for it |
| Package size | Largest (~1.33× the original file, plus JSON overhead) | Smallest for already-compressed formats (docx/epub/xlsx are themselves ZIPs — store them uncompressed to avoid wasted CPU re-compressing already-compressed bytes) or noticeably smaller for pdf/txt/markdown/csv via DEFLATE | Comparable to B if compression is used; comparable to A if not — depends entirely on custom design choices, no free win over B |
| Portability | High — plain JSON, human-inspectable, no special tooling to open | High — `.zip` is universally openable by any OS/tool, *and* still carries a JSON manifest entry that's inspectable the same way | Lower — a bespoke binary format needs *this app* to open it; nothing else on a user's machine can inspect or recover a `.nova-doc`-style file if the app is ever unavailable |
| Streaming | None — the whole string must exist before `JSON.parse` can begin | Partial — `jszip` still loads the whole archive into memory client-side (this is not a server), but per-entry `.async()` reads let the manifest be parsed before the (much larger) file entry is pulled into memory, so validation can reject a bad package before touching the large payload | Same partial capability as B, if deliberately designed with a length-prefixed manifest read first — no inherent advantage over B, more code to get right |
| Integrity | None built in — a corrupted byte anywhere just produces `atob` garbage or a `JSON.parse` failure with no localized signal | **Free, built-in** — every ZIP entry carries its own CRC32 checksum, checked automatically by `jszip` on read; a corrupted file entry fails loudly and specifically, independent of the manifest | None built in unless deliberately added (e.g. a manifest-declared SHA-256) — extra code, not free |
| Implementation complexity | Lowest to extend (this repo already has `base64.ts`/`assetFileTransfer.ts` from UX-14.5.10.2) but riskiest at this size | Low — `jszip` is already a direct dependency, already used to *read* ZIP (EPUB extractor), so *writing* one for export is the same library, opposite direction, no new dependency | Highest — a full custom format (magic bytes, length-prefixed sections, versioning of the framing itself, separate from `PackageVersion`) with no existing library backing it in this codebase |

### 3.3 Recommendation: Option B — ZIP via `jszip`

Chosen because it is the only option that fixes Option A's real
memory risk at the 200MB scale *without* introducing a new dependency
or a bespoke format this app alone can parse. Concretely:

- **A `.zip` package contains two entries**: `manifest.json` (the same
  role `NotePackage`/`KnowledgeNodePackage`/`AssetPackage`'s JSON body
  already plays — allow-listed metadata, tags, highlights, version
  fields) and `original` (the raw document file bytes, stored — not
  re-compressed — for already-compressed formats like docx/epub/xlsx,
  or deflated for pdf/txt/markdown/csv where it actually helps).
- **`jszip` is already a direct dependency** (`package.json`, used today
  to *parse* EPUB, itself a ZIP container) — no new package, no bundle
  size increase beyond what's already shipped for the epub reader path.
- **Validation reads the manifest entry first**, exactly like every
  other package type's `parse<Type>Package` validates the JSON shell
  before trusting anything inside it — `jszip.loadAsync(file)` then
  `zip.file('manifest.json').async('text')` before ever touching the
  (much larger) `original` entry, so a malformed or oversized package
  can be rejected cheaply (§5).
- This does **not** propose reusing the *notes/nodes/assets*
  `<Type>Package.ts` file shape verbatim — a ZIP-backed package type
  needs its own `documentPackageTypes.ts` (still the same allow-list
  discipline) plus new archive-building/-reading glue analogous to
  `assetFileTransfer.ts`, since `PackageExporter.export()`'s pure/
  synchronous contract still needs the same "async I/O lives outside the
  exporter" treatment UX-14.5.10.2 established — the exact same
  resolution, applied to a different container format. This is the one
  new structural addition the next implementation phase should expect
  to make (an archive-building/-reading helper, not a framework change).

## 4. AI-derived content — transfer or regenerate, with reasoning

Already tabulated in §1; consolidated here per the task's own
structure, "specifically evaluate chunks / embeddings / summaries /
flashcards / highlights / extraction metadata":

- **Chunks — regenerate.** Mechanical, deterministic splitting of
  extracted text; `processDocument` reproduces them from the original
  bytes with zero information loss. Transferring them would also mean
  transferring their content twice over (once via the original file,
  once via the chunk text derived from it) for no benefit, and would
  reintroduce exactly the "copy of a derived thing that can drift from
  its source" problem this framework has avoided in every prior phase.
- **Embeddings — regenerate.** Follows chunks directly; an embedding
  divorced from a live chunk row is meaningless, and re-embedding is
  already a required step of `processDocument` regardless (there is no
  cheaper path — even if embeddings were transferred, the chunks they're
  keyed to would still need to exist first, at which point re-embedding
  costs the same as generating fresh ones).
- **Extraction metadata — regenerate.** A pure function of the original
  file bytes plus this app version's extractor code — recomputing it is
  literally the same computation the exporter's own copy came from,
  applied to the identical bytes now owned by the importer. Nothing is
  lost; nothing can drift.
- **Chapter summaries — regenerate**, per §1.1's reasoning: 100%
  AI-authored, cheap to reproduce, avoids chapter-index-drift risk
  entirely by construction.
- **Flashcards — regenerate**, same reasoning as chapter summaries.
- **Highlights — transfer**, per §1.1's reasoning: the one genuinely
  user-authored artifact among these six, no regeneration path exists
  for it at all, and the chapter-index-drift risk is bounded/cosmetic
  rather than destructive.

## 5. Security review

| Risk | Assessment | Mitigation |
|---|---|---|
| **Malicious package (general)** | Same trust boundary as every prior package type: a package is untrusted input from the moment it's opened, regardless of whether it claims to come from this app's own Export | `validateDocumentPackage`/`parseDocumentPackage` never trusts a package as pre-validated — same discipline as `validateNotePackage`/`validateKnowledgeNodePackage`/`validateAssetPackage`, extended to check the ZIP structure itself (manifest entry present, `original` entry present, declared file type is one of the 8 supported types) before any bytes are handed to `uploadDocument`/`processDocument` |
| **Oversized packages** | A 200MB-plus original file, or a manifest lying about a smaller size while embedding a larger one | Reject based on the ZIP entry's own declared uncompressed size (`jszip` exposes this per-entry before a full `.async()` read) against `MAX_UPLOAD_BYTES`, mirroring exactly how Assets' `estimateBase64DecodedByteLength` check rejects pre-decode; `uploadDocument`'s own downstream validation (file-type/extension check) is unmodified, unbypassable defense in depth |
| **Zip bombs** (ZIP chosen, so directly relevant) | A tiny compressed entry whose *declared* uncompressed size is enormous (the classic 42.zip pattern) — dangerous specifically because decompression can be requested before the real size is known | `jszip`'s central-directory metadata exposes each entry's declared uncompressed size *before* calling `.async()` to actually decompress it — validate that declared size against `MAX_UPLOAD_BYTES` first and refuse to call `.async()` at all if it's over cap, exactly the same "check before you decode" shape Assets already established for base64. This is a real, must-implement check for the next phase, not optional — Option A had no equivalent attack surface at all, so this is a genuinely new risk Option B introduces and must close before shipping, called out explicitly rather than left implicit |
| **MIME/type spoofing** | Documents have no MIME field at all (unlike Assets) — `fileTypeFromName` infers type purely from the reconstructed file's extension, which the import code itself controls (not attacker-supplied), so this is actually a smaller surface than Assets had. A package could still declare a `fileType: 'pdf'` manifest field while embedding bytes that are actually something else entirely | `uploadDocument` does not content-sniff — it trusts the declared type and uploads unconditionally. The real check happens one step later: `processDocument`'s extractor (`getDocumentProcessor(document.file_type)`) will throw when asked to parse bytes that don't match the claimed format (e.g. the PDF extractor on non-PDF bytes), caught by `processDocument`'s existing try/catch, resulting in a clean `status: 'error'` / failed processing job — not code execution, not a crash, not silent corruption. This is the identical failure mode a native upload of a corrupted/mislabeled file already produces today; Exchange inherits it unchanged, doesn't introduce a new one |
| **Parser trust** | The extractors (`pdf.js`, a docx parser, `jszip`+`DOMParser` for epub, a spreadsheet library for xlsx/csv/ods) are the same code a native upload already runs against arbitrary user-supplied files | Not a new risk — whatever hardening or lack thereof exists in these extractors today applies identically regardless of upload-vs-import origin. Out of scope for Exchange to fix; worth its own audit someday, but not created or worsened by this feature |
| **Duplicate documents** | Unlike Knowledge Nodes, there is no existing canonical-identity resolver for documents (no `resolveCanonicaLDocument`-equivalent) | Import should **always create a fresh document row**, exactly like Notes' and Assets' always-create precedent (not Knowledge Nodes' dedup-aware one) — importing the same package twice produces two documents, precisely as uploading the same file twice manually already does today. Not a new risk; inventing a document-identity resolver is a real, separate design problem out of scope for this phase |
| **Storage abuse** (using Import to smuggle non-document content into the `documents` bucket) | Mitigated structurally — import reuses unmodified `uploadDocument`, which only ever accepts one of the 8 registered `DocumentFileType`s and always writes to a fresh, importer-owned, `crypto.randomUUID()`-based path. There is no path by which a package can direct bytes to an arbitrary storage location or bypass the extension allow-list | No new mitigation needed beyond reusing `uploadDocument` unmodified, exactly as Assets' security review concluded for `uploadAsset` |
| **Processing abuse** (cost/rate DoS via repeated large imports) | Import triggers the exact same `processDocument` pipeline (embedding calls, retry/backoff) a native upload already triggers — an attacker importing many large documents has an identical cost/rate profile to an attacker uploading many large documents directly | Not a new risk Exchange introduces; existing rate-limit handling (`embedBatchWithRetry`'s exponential backoff on OpenAI 429s) is inherited unchanged. General upload-abuse throttling (if ever needed) is a platform-wide concern outside Exchange's scope, exactly as it already is for native uploads today |

## 6. Import ownership model

Confirmed against the exact same contract every prior package type
already established (`PackageImportContext`, unchanged):

- **Importer becomes owner** — `uploadDocument`'s `userId` param is
  always `context.userId`; there is no path for a package to assert a
  different owner.
- **Explicit workspace selection** — `uploadDocument`'s `workspaceId`
  param is always the importer's own explicit choice at import time
  (the same `<dialog>` workspace `<select>` every prior Import dialog
  already has), never inferred from the package.
- **Fresh IDs** — `uploadDocument`'s insert always lets Postgres
  generate a new `documents.id`; the package never supplies one (the
  allow-list format, per §1's `documents` row, never includes `id` in
  the first place).
- **Fresh storage path** — `uploadDocument` always derives
  `${userId}/${crypto.randomUUID()}-${sanitizedFilename}`, keyed to the
  *importer's own* `userId`; the package's original `file_path` is
  never read for anything beyond deriving a display filename for the
  reconstructed `File` object.
- **Provenance strategy** — same accepted gap as Assets (§1, `gap`
  rows): `documents` has no JSONB metadata column, so there is no
  `generation_metadata.importedFrom` block to write on the document row
  itself (unlike Notes/Knowledge Nodes). `document_tags` provenance is
  irrelevant (tags are re-resolved by name, not carried as references).
  Transferred `highlights` rows equally have no metadata column
  available for import provenance beyond their own `generation_metadata`
  JSONB column (which does exist on `highlights` per `0011` — so
  **highlights specifically can** record
  `generation_metadata.importedFrom`, unlike the document row itself,
  a small but real asymmetry worth noting for the implementation phase).

## 7. Processing strategy — Option A (immediately enter the pipeline), not Option B (restore directly)

**Recommendation: A — imported documents immediately enter the existing
extraction pipeline** (`processDocument`), the same fire-and-forget call
`useDocumentMutations.ts`'s `upload` mutation already makes after a
native upload.

Why not B ("restore directly" — i.e. reconstruct chunks/embeddings/
extraction metadata from transferred data instead of recomputing them):

- §1/§4 already established that none of chunks/embeddings/extraction
  metadata/chapter summaries/flashcards should transfer in the first
  place — there is nothing to "restore directly" *from*, since the
  package never carries that data. Option B is only a meaningful
  alternative in a design where those objects *do* travel in the
  package; this discovery's own §1–§4 analysis rules that design out on
  its merits (correctness, avoiding stale/drifted copies, avoiding the
  chapter-index-drift risk), independent of which processing strategy
  is chosen afterward.
- Even setting that aside, Option A costs nothing extra to implement —
  it is the literal two-function-call sequence `useDocumentMutations.ts`
  already performs (§2), with zero new pipeline code, zero new failure
  modes beyond ones that already exist for native uploads, and it
  automatically gets progress reporting for free (§8) via the existing
  `useProcessingJob`/`ProcessingStatusBadge` polling infrastructure,
  which "restore directly" would have no equivalent for (there's no job
  to poll if nothing is actually processing).

## 8. User experience

Reuses the exact `<dialog>` shell and dialog-state lifecycle every prior
Import dialog already established (`ImportNotePackageDialog`,
`ImportKnowledgeNodePackageDialog`, `ImportAssetPackageDialog`):
file picker → validation summary → workspace selector → success
summary. What's genuinely new for Documents:

**Export flow**: an "Export" button on the document detail page
(`DocumentDetailPage.tsx`, added by the prior Knowledge Workspace v1
milestone), mirroring `ImageReaderPage.tsx`'s Export button placement.
Its handler is an async mutation (same shape as Assets' `exportPackage`
mutation): download the original file via `downloadDocumentFile`, build
the ZIP archive (manifest + original entry) via `jszip`, then trigger a
download — reusing `downloadBinaryFile`-style blob-URL-anchor-click,
not `downloadTextFile` (the output is binary, not JSON text, for the
first time in this framework).

**Import flow**: an "Import" button on `LibraryPage.tsx`'s Documents
tab, next to the existing `UploadDropzone` — the same page-level
placement pattern Assets used next to `AssetUploadDropzone`. Opens
`ImportDocumentPackageDialog`. File picker accepts `.zip` (not
`.json`) — the one genuinely new affordance this package type needs
(every prior Import dialog's `<input type="file" accept="application/
json,.json">` becomes `accept="application/zip,.zip"` here).

**Progress reporting**: unlike every prior package type (where "import"
completes synchronously — a note/node/asset row exists the moment the
mutation resolves), a document import is only "structurally done" when
`uploadDocument` resolves, but is only *usably* done once
`processDocument` finishes extracting/chunking/embedding it — a process
that can take anywhere from a couple of seconds (a short `.txt`) to
significantly longer (a 200MB PDF). The dialog's success screen should
therefore reuse `ProcessingStatusBadge`/`useProcessingJob(documentId)`
directly, pointed at the freshly created document's id, exactly the
same live-polling UI a native upload's card in the Library grid already
shows — no new progress-reporting code needed, just reuse of an
existing, already-correct component in a new location.

**Validation errors**: same `PackageValidationIssue[]` list-rendering
pattern every prior dialog already uses, extended with the two
ZIP-specific failure modes §5 introduces (declared-size-over-cap,
missing manifest/original entry) as new `PackageValidationIssue` codes
consistent with the existing `'malformed_json' | 'unsupported_version' |
'future_version' | 'invalid_schema' | 'missing_field'` union (likely
needs one addition, e.g. `'oversized_payload'`, promoted from an
ad-hoc `invalid_schema` message the way Assets' size check currently
does it — worth revisiting for all three prior package types at once
rather than only Documents, a small cross-cutting cleanup opportunity
for whichever phase implements this).

**Success summary**: "Document imported — processing in the
background," with a live status badge (see Progress reporting above)
and a "View document" link to `/library/:documentId`, plus (if any
highlights transferred) a count — "3 highlights included" — surfaced
the same way Notes' import success screen already reports tag counts.

## 9. Roadmap — smallest safe implementation phases

Document Exchange is larger than any prior Exchange phase (binary
transfer *and* a multi-stage regeneration pipeline *and* a new
container format), so unlike Knowledge Nodes and Assets (each shipped
as one phase), this discovery recommends splitting implementation:

1. **UX-14.5.10.3.1 — ZIP package plumbing.** Build the archive-
   building/-reading helpers (`documentFileTransfer.ts`-equivalent) and
   `documentPackageTypes.ts`/`validateDocumentPackage.ts`/
   `exportDocumentPackage.ts` covering *only* the document row itself
   (title, original file, tags) — no highlights yet. Validates the ZIP
   container strategy end to end (§3) the same way UX-14.5.10.2
   validated base64-in-JSON, including the zip-bomb/oversized-entry
   checks from §5 as first-class, tested behavior from the start (not
   retrofitted).
2. **UX-14.5.10.3.2 — Import + processing integration.** `import
   DocumentPackage.ts` reusing `uploadDocument`+`processDocument`
   unmodified (§2, §7), the `ImportDocumentPackageDialog` UI with live
   `ProcessingStatusBadge` integration (§8), and the Export button on
   `DocumentDetailPage.tsx`. This is the phase that makes Document
   Exchange actually usable end-to-end for the file itself.
3. **UX-14.5.10.3.3 — Highlights.** Add the `highlights` array to the
   package format and importer (§1, §6's `importedFrom` provenance on
   the highlight rows specifically). Deliberately last and separable:
   the file-transfer/processing core (phases 1–2) is independently
   shippable and already delivers the primary user value (send someone
   a document); highlights are a genuine but smaller addition once the
   core is proven, and isolating them keeps each phase's verification
   gate (tests, security review) focused on one new surface at a time —
   the same "each independently shippable" discipline the original
   UX-14.5.10 discovery recommended for the five-object-type roadmap,
   applied one level deeper within Documents itself.

Chapter summaries, flashcards, extraction metadata, chunks, embeddings,
processing jobs, and reading progress need **no roadmap slot at all** —
per §1/§4, none of them ever travel in a package; they either don't
apply or fall out for free once phase 2's `processDocument` call
completes.

## 10. What this does not include

Bulk export, sharing links, multi-document packages, Knowledge
Collections' own package type (still a separate, later object type per
the original UX-14.5.10 roadmap), and any fix to the RLS gap found in
§0/§1 (`extraction_metadata`/`processing_jobs`/`chapter_summaries`/
`highlights`/`flashcards`/`reading_progress` lacking workspace-sharing
RLS) — none attempted here, consistent with this task's explicit
discovery-only, no-RLS-changes scope. The RLS gap is a real,
independently-schedulable product fix, not a Document Exchange
prerequisite (§6 already establishes import never depends on it).
