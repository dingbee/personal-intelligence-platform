# UX-14.5.2 — Identity, Workspace & Permission Architecture

**Status: discovery only. No schema changes, no RLS text, no code in this
document or its commit.**

This is a second, narrower discovery pass on top of
`docs/ux-14.5-knowledge-exchange-collaboration-discovery.md` ("the
Phase 1 doc"). That document surveyed the whole collaboration space
(sharing models, versioning, audit, migration) and recommended Option B
(team spaces anchored on `workspace_id`) as the target, with Option A
(single-table personal sharing on `notes`) as the safer first proof.

This pass goes one level deeper on exactly five things the brief asks
for: the workspace model itself, its membership model, roles/permissions,
the RLS migration mechanics, and how the AI's existing action-execution
path (Workspace Actions) plugs into a permission model that doesn't exist
yet. Where Phase 1 already answered something at the right depth (e.g.
"AI gets no separate identity," §4.3 there), this document doesn't
re-litigate it — it cites it and goes further only where "further" adds
real design content.

---

## 1. Workspace model

### 1.1 Target shape: workspace stays the one container, but its meaning generalizes

Phase 1 §2.3 already concluded `workspace_id` — not `knowledge_collections`
— should carry the future access-control weight, because it's already
threaded through nearly every content table and matches the app's
existing mental model (`WorkspacePresence`, `WorkspaceSwitcher`, the Hub).
This pass commits to that and asks the next question: does a "team
workspace" need to be a structurally different kind of row from a
"personal workspace"?

**Recommendation: no.** A workspace should not gain a `type` column
(`'personal' | 'team' | 'org'`) that branches behavior. Instead:

- A workspace with exactly one member (its creator, as `owner`) *is* a
  personal workspace — behaviorally identical to every workspace that
  exists today, because the RLS OR-clause (§4) degenerates to exactly
  today's single-owner check when there's nothing else to OR against.
- A workspace becomes a "team space" the moment a second member is added
  — no migration, no flag flip, no different code path. It's the same
  row, same table, same RLS policy; only the membership *count* changed.

This is the single most important design choice in this document: **it
collapses "personal" and "team" into one model with one cardinality
variable**, rather than two parallel systems that need to be kept in sync
or migrated between. It directly serves the brief's ask for "the smallest
safe architecture that can eventually support personal sharing, team
spaces, *and* enterprise" — see §8.

### 1.2 What still needs a real decision, not an architecture

Phase 1 §7.4 already flagged this and it's worth restating precisely here
since it's a workspace-model question: `workspace_id IS NULL` on a
content row currently means "unfiled." Once a workspace can have
multiple members, every row needs to resolve to exactly one of three
states — (a) owned outright, no workspace, always personal; (b) filed
into a single-member workspace, personal in practice but shareable later
by adding a member; (c) filed into a multi-member workspace, already
visible to others. States (a) and (b) need to stay indistinguishable in
behavior from today for every existing user — which they are, automatically,
under the model in §1.1, since nothing changes about a row's visibility
until a second member actually joins its workspace.

### 1.3 Enterprise readiness without building it now

The brief asks for a model that can "eventually" reach enterprise
environments. Per Phase 1 §3 (Option C), building an organization layer
now is speculative — there's no validated demand anywhere in this app
today. But the workspace model in §1.1 already leaves room for it later
without rework: an org layer would be *one more optional parent* above
workspace (an org owns N workspaces, org-level role can seed a
workspace's initial membership), not a redesign of how a workspace itself
carries members. Nothing in §1.1–§1.2 needs to be undone to add that
later — it's additive on top, exactly like Phase 1 §7.2's general
migration principle.

## 2. Workspace membership model

### 2.1 Shape (conceptual — not a schema proposal)

A membership record needs exactly four pieces of information to answer
every question the rest of this document raises: **which workspace,
which user, what role, and who granted it (for the audit trail, §7).**
Conceptually: `(workspace_id, user_id, role, granted_by, created_at)`,
one row per member per workspace, `workspace_id + user_id` unique.

### 2.2 The owner is a member, not a separate concept

The workspace's creator should be represented as a membership row with
role `owner`, not as a special case living only in `workspaces.user_id`.
Two reasons:

- It makes "who has access to this workspace" answerable with one query
  shape (read the membership table) instead of two (check
  `workspaces.user_id` *and* check membership).
- It makes ownership transfer (Phase 1 §4.2) a role update on an existing
  row, not a column reassignment on `workspaces` itself — which matters
  because `workspaces.user_id` should keep meaning "who created this," the
  same provenance-vs-current-state distinction Phase 1 draws for content
  rows. `workspaces.user_id` never needs to change; the `owner` role on
  the membership table is what moves.

### 2.3 Invitation is a status, not a separate table

An invited-but-not-yet-accepted member is the same membership row with a
`status` dimension (`invited` vs `active`) rather than a parallel
"invitations" table that later needs to be reconciled into membership on
acceptance. This keeps one table answering "who's connected to this
workspace and how" at every point in that lifecycle, instead of a join
between two tables with their own sync-drift risk.

### 2.4 Personal workspaces need no membership row at all

Under §1.1's model, a workspace nobody has ever shared has exactly the
membership it always implicitly had (`workspaces.user_id` = the owner) —
no backfill of a membership row is required for the ~100% of existing
workspaces that will never gain a second member. A membership row only
needs to be written the moment sharing actually happens. This is what
makes §5 (backward compatibility) a true no-op for the overwhelming
majority of accounts.

## 3. Roles and permissions

### 3.1 Role set (unchanged from Phase 1, restated with the reasoning specific to this pass)

**owner, editor, viewer.** Phase 1 §4.1 already argued against a
permission-bit matrix given zero existing precedent for one in this
schema; this pass adds the workspace-specific ordering:

- **owner** — everything editor can do, plus manage membership
  (invite/remove/change role), plus the one operation that must never be
  delegable below owner: deleting the workspace itself.
- **editor** — create/update/delete content rows scoped to the workspace.
  Cannot manage membership.
- **viewer** — read scoped content rows. Cannot write anything, cannot
  manage membership.

### 3.2 Where a permission check should live — one resolver, not scattered checks

This codebase has a strong, repeated precedent for "one function that
every call site defers to" rather than duplicated inline logic —
`resolveProviderChain`, `withArtifactKind`/`getArtifactKind`,
`normalizeAiError`, `resolveReaderMode`. The permission model should
follow the same shape: a single client-side resolver (conceptually,
`resolveWorkspaceRole(workspaceId, userId) -> 'owner' | 'editor' |
'viewer' | null`) that every UI call site and every Workspace Action
(§6) defers to, rather than each component independently re-deriving
"can I edit this." This is a design principle for the eventual
implementation, not a function being added now — flagged here because
getting this factoring right the first time avoids the alternative
(role checks copy-pasted across `NoteDetailPage`, `ChatPage`,
`SaveConversationDialog`, ... — a maintenance and correctness risk this
codebase has consistently avoided elsewhere).

### 3.3 What this role set deliberately does not attempt

No per-object-type permission overrides (e.g. "editor everywhere except
conversations"), no time-boxed/expiring roles, no custom role names. All
three are real enterprise-tier asks eventually, and all three fit inside
the membership row's `role` column (a richer enum, or an expiry
timestamp) without changing the table's shape — they're additive
refinements to §2.1, not reasons to design a different model now.

## 4. RLS migration strategy

### 4.1 The mechanical problem stated precisely

Phase 1 §7.2 already established the OR-clause approach:
`using (auth.uid() = user_id OR <space-membership check>)`. Phase 1 did
not resolve *how* `<space-membership check>` should be written across
~14 tables without becoming a maintenance hazard. That's this section's
job.

### 4.2 Recommendation: one reusable helper function, not 14 duplicated subqueries

Writing `EXISTS (select 1 from workspace_members where workspace_id =
<row>.workspace_id and user_id = auth.uid() and role in (...))` inline,
separately, in every one of ~14 policies is exactly the kind of
duplication this codebase avoids everywhere else in its RLS layer already
— the two existing join-table policies (`document_tags`, `note_tags`)
already use the EXISTS-subquery *shape*, but each is table-specific by
necessity (checking a different parent). A membership check is the same
logic every time, checking the same table. This schema already has a
working precedent for a single reusable function invoked from many
places: `public.set_updated_at()` (0001_init.sql), one trigger function
used by every `updated_at` column in every subsequent migration, and
`public.handle_new_user()`, a `security definer` function. The same
pattern applies here: a single `security definer` SQL function —
conceptually `public.workspace_role(workspace_id uuid, uid uuid) returns
text` — that every extended RLS policy calls, e.g.
`using (auth.uid() = user_id OR public.workspace_role(workspace_id,
auth.uid()) is not null)`, with role-gated operations (editor-only
inserts/updates, owner-only membership changes) checking the returned
role value instead of just its presence.

This is a recommendation about the *shape* of the eventual RLS design,
not proposed SQL to run — no function is created by this document. The
value of deciding this now, in the architecture phase, is that it changes
what the "prove it on one table" step in Phase 1 §7.3 actually proves:
proving the helper function's correctness once (on `notes`) is far
stronger assurance than proving one inline subquery once and then having
to trust that its copy-paste onto 13 more tables was faithful every time.

### 4.3 Migration sequencing (refines Phase 1 §7.3)

1. Introduce the membership table and the helper function together — the
   function has nothing to query until the table exists, so they're one
   unit of work, not two.
2. Extend exactly one table's RLS (`notes`, per Phase 1's own reasoning:
   smallest, most self-contained, its one child table `note_tags` already
   uses the EXISTS-subquery pattern this reuses).
3. Verify existing accounts see zero behavior change and that a
   deliberately-constructed second test account genuinely cannot see a
   `notes` row it has no membership path to.
4. Repeat step 2 identically for the remaining ~13 tables from Phase 1
   §1.5, using the same helper function — this step is now pure
   repetition of a proven pattern, not 13 independent design decisions.

### 4.4 Enforcement point for role, not just membership

RLS answers "can this row be seen/touched by this user at all." It does
not by itself answer "does *this* operation (update vs. delete vs.
insert) require editor rather than viewer." Postgres RLS supports
per-command policies (`for select`, `for insert`, `for update`, `for
delete`), which this schema already uses in exactly one place today —
`ai_requests` (0006), whose `select`/`insert`-only split is what makes it
append-only. The same per-command split is the right mechanism for
role-gating: a `viewer`-satisfying membership only grants a `for select`
policy match; `for insert`/`for update`/`for delete` policies additionally
require the helper function to return `editor` or `owner`. This is a
direct reuse of an existing pattern (§7 in Phase 1 already names
`ai_requests` as the append-only precedent; here it's cited again as the
per-command-policy precedent).

## 5. Backward compatibility for existing users

Restated precisely for this narrower scope, building on Phase 1 §7:

- **No data migration.** Under §1.1/§2.4, an existing workspace needs no
  membership row written for it at all — its current sole-owner behavior
  is already what the model produces for a workspace with zero
  membership rows (the OR-clause's right side is simply never true).
- **No RLS behavior change for any row that isn't shared.** The
  OR-clause's left side (`auth.uid() = user_id`) is untouched — it's
  still there, still evaluated first, still sufficient on its own for
  every row that was already only ever seen by its owner.
- **No client code breaks.** Every existing `.eq('user_id', ...)` filter
  in the API layer keeps returning the same rows it always did; RLS
  simply permits a superset now for genuinely shared rows, which no
  existing query filters for yet (that's new, additive query code —
  "shared with me" views, a member list — not a rewrite).
- **No account is ever silently enrolled.** A user only gets a
  `workspace_members` row when someone (including themselves) explicitly
  creates one. There is no scenario in this model where an existing
  account's content becomes visible to a second person without an
  explicit membership-granting action.

## 6. AI action permissions

Phase 1 §4.3 already recommended the AI have no distinct identity or
elevated permission — it acts as the invoking member, scoped to their
role. This section is where that recommendation meets actual code: the
**Workspace Action Router** (`src/modules/workspace-actions/`), the
concrete mechanism by which a chat command like "generate a briefing" or
"save this" turns into a real write.

### 6.1 The exact wiring point

`WorkspaceActionContext` (`workspace-actions/types.ts`) is already the
object threaded into every action's `run(payload, context)` —
today it carries `{userId, workspaceId, conversationId, chain}`. This is
the natural, minimal place for the invoking member's resolved role to
be added, once a role concept exists: the router
(`runWorkspaceAction` in `registry.ts`) is a single chokepoint that
already sits between "user typed a command" and "an action executed,"
so it's also the single place a role-gate would need to be added — not
inside each of the ~4 individual action files.

### 6.2 What the gate should check, conceptually

Not "is this user allowed to use NOVA" (they always are, for their own
account) but "does this specific action's write require more than the
role this member holds in the workspace this command is scoped to."
Generate Briefing and Save to Notes both create content — under §3.1
that requires at least `editor`. A hypothetical future read-only action
("summarize what's in this workspace") would need only `viewer`. The
router doesn't need to know the specifics per action — each action
declaring its own minimum required role (mirroring how each action
already declares its own `match` and `run`) and the router checking it
generically before dispatch is the shape consistent with how the router
already treats actions as uniform, swappable units.

### 6.3 Why this doesn't need a different design than "AI has no separate identity"

This is worth stating explicitly because it's easy to conflate: giving
the router a role-gate is not the same as giving the AI a role. The gate
checks the *human's* role (the one on whose behalf the action is
running) exactly the way a viewer clicking a disabled "Save" button in
the UI would be blocked — the AI path and the manual-click path should
enforce the identical rule, because the AI was never a distinct
principal in the first place (Phase 1 §1.3, §4.3). A viewer asking NOVA
in chat to "save this as a note" should fail exactly as if they'd
clicked a Save button that isn't there for their role — not because the
AI has weaker permissions, but because the human does.

## 7. Audit requirements

Phase 1 §6 already recommended one generic append-only
`space_audit_log`-shaped table, modeled on `ai_requests`'s
select/insert-only RLS, scoped to membership/role/ownership/deletion
events rather than general content edits. This pass adds two things
specific to the workspace/permission model designed above:

### 7.1 What events this model specifically generates

Given §2 and §3, the concrete event set an audit log needs to capture is
now fully enumerable, not open-ended: member added, member removed, role
changed, ownership transferred (owner role reassigned), workspace
deleted. That's five event types — a small, closed set, which reinforces
Phase 1's choice of one generic table over one per event type: five
event kinds sharing one row shape is exactly the case a single
`event_type` column is for for, not five different tables.

### 7.2 AI-invoked actions belong in `ai_requests`, not the new audit log

Because §6 established that an AI-invoked write is, at the permission
layer, indistinguishable from the human performing it directly, an AI
Workspace Action that successfully writes content should be logged the
same way any AI call already is — through the existing `ai_requests`
table (which already exists, already has `workspace_id`, and is already
append-only). It should not additionally generate a row in the new
membership/role audit log from §7's Phase-1 recommendation, because that
log is specifically for *space-administration* events (§7.1's five),
not content writes — keeping that distinction is what stops the audit
log from re-absorbing the job §5 (versioning) of the Phase 1 doc already
assigned to content-version history instead.

## 8. Recommendation: the smallest safe architecture

Putting §1–§7 together, the smallest model that satisfies "eventually
personal sharing, team spaces, and enterprise" without being rebuilt at
each tier is:

1. **One workspace table, unchanged in kind** — personal is the
   one-member case, team is the multi-member case, no type flag, no
   parallel structures (§1.1).
2. **One membership table** carrying role and invitation status, with the
   owner represented as a membership row rather than a special case, so
   ownership transfer and access-checking both go through one mechanism
   (§2).
3. **Three roles** (owner/editor/viewer), enforced through **one reusable
   role-resolution function** — both client-side (§3.2) and as a single
   `security definer` SQL helper reused by every extended RLS policy
   (§4.2) — rather than duplicated logic at either layer.
4. **Per-command RLS**, reusing the one existing precedent for it
   (`ai_requests`), so viewer/editor/owner map cleanly onto
   select/insert-update-delete without inventing new Postgres mechanics.
5. **The AI inherits the human's role** through one chokepoint (the
   Workspace Action Router), never a distinct identity (§6) — the
   cheapest possible answer, and the one that keeps the AI's actions
   auditable through the same `ai_requests` trail that already exists
   (§7.2).
6. **Enterprise is deferred, not designed** — the model above doesn't
   need to be undone to add an optional organization layer above
   workspace later (§1.3); it's the one piece of the brief's three
   targets ("personal, team, enterprise") this document explicitly does
   not attempt to design now, because nothing in the current app
   validates a need for it yet.

The reason this counts as "smallest": every piece above is justified by
an existing precedent already in this codebase (`set_updated_at`,
`handle_new_user`, `ai_requests`'s per-command policies, the
resolver-function convention, the Workspace Action Router's single
dispatch point) — nothing here introduces a new architectural pattern
this app hasn't already validated somewhere else at smaller scale.

## 9. Explicitly out of scope (unchanged from Phase 1, restated)

No schema, no RLS text, no membership table columns finalized, no
`resolveWorkspaceRole` implementation, no `workspace_role()` SQL
function body, no change to `WorkspaceActionContext` or any Workspace
Action file, no invitation UI, no storage-bucket sharing design (Phase 1
§8 flags this remains a separate, harder problem — nothing in this pass
changes that), no organization/enterprise schema. This document is the
target architecture two levels of detail deeper than Phase 1; the next
step, if approved, is Phase 1 §9's already-identified smallest concrete
slice — personal object sharing proven on `notes` — now informed by this
pass's membership-table and helper-function shape rather than an ad hoc
`object_shares` table, since §2.4 shows the same membership table serves
both the single-share and eventual team-space cases without being two
different designs.
