# UX-14.5.10 — Knowledge Exchange Expansion: Discovery

**Status: discovery only. No schema changes, no migrations, no RLS changes, no UI changes, no implementation in this document or the commit that adds it.**

Objective: audit whether and how the package framework UX-14.5.9 built for
Notes (`src/modules/knowledge-exchange/`) extends to Documents, Knowledge
Collections, Knowledge Nodes, Knowledge Links, and Assets — grounded in the
actual current schema, RLS policies, and API code (every claim below is
backed by a migration file, a type definition, or an API function actually
read for this pass, not inferred from the object's name or from
`docs/ux-14.5.6-knowledge-exchange-discovery.md`'s original, pre-
implementation design). That earlier document proposed the overall model
(immutable snapshots, allow-list construction, §8's phased roadmap); this
one checks that model against what UX-14.5.9 actually built and what the
remaining four object types' real schemas actually require, since a
design written before any code existed is exactly the kind of thing worth
re-verifying once real code does.

---

## 0. Audit summary — what's already true, confirmed by reading the code

- UX-14.5.9's package framework (`src/modules/knowledge-exchange/packages/`)
  is genuinely generic at the **type** level —
  `PackageExporter<TSource,TPackage>`, `PackageImporter<TPackage,TResult>`,
  `PackageValidator<TPackage>`, `PackageImportContext` — but the **JSON
  envelope shape** it produces is Notes-specific by construction: the
  literal serialized package is `{version, exportedAt, sourceVersion,
  note: {...}}`, with `note` as a hardcoded key, not a generic `payload`
  field or a `kind` discriminator. A validator for a different object type
  cannot reuse `validateNotePackage`'s logic at all (it's entirely
  Notes-shaped field checks); it would write its own
  `validate<Type>Package` function following the same *pattern*, exactly
  as the framework's own doc-comments already anticipated ("a future
  Documents/Collections package type plugs into this same shape ...
  without touching Notes' own code").
- All five candidate object types (`documents`, `knowledge_collections`,
  `knowledge_nodes`, `knowledge_links`, `assets`) already have the
  **identical** ownership/workspace/RLS shape Notes had before UX-14.5.9:
  an owner column (`user_id` or, for `assets`, `owner_id`), a nullable
  `workspace_id`, and — critically — **all five already went through the
  exact same workspace-sharing RLS extension `notes` did**, in one single
  migration: `0031_shared_knowledge_objects.sql` (UX-14.5 Phase 4). This
  is the single most important finding of this audit: the RLS
  precondition Knowledge Exchange's snapshot model depends on (§2.1 of the
  original discovery doc — "the exporting account reads its own
  already-fully-visible-to-it rows, ordinary existing queries, same
  authorization the export button click already has") is **already true**
  for every object type this task asks about. No RLS work is a
  prerequisite for any of these five types, confirming the task's own "no
  RLS changes" constraint is honestly achievable, not just declared.
- The real new complexity isn't authorization — it's **content shape**.
  Notes are pure text with no binary dependency, which is exactly why
  UX-14.5.9 could treat "the package" as one self-contained JSON object.
  Two of the five remaining types (Documents, Assets) are backed by
  **private-bucket storage objects** with per-user-folder RLS
  (`(storage.foldername(name))[1] = auth.uid()::text`) that has **no
  cross-account read path at all** — a different account literally cannot
  fetch another account's storage object, by design, confirmed in both
  `0002_library.sql` and `0022_assets.sql`. This is the same conclusion
  the original discovery doc reached (§1, "storage is a separate, coarser
  boundary") — but this pass adds a concrete resolution that document
  didn't have available yet (§2 below): embed the original file's bytes
  **inside** the JSON package itself, so the package remains a
  self-contained snapshot needing zero storage-level cross-account access
  of any kind, rather than building the "genuinely new infrastructure"
  cross-account storage-copy mechanism the original doc's §8.2 (Phase 6B)
  assumed was required.

## 1. Package framework audit — extension points

Read directly: `src/modules/knowledge-exchange/packages/{PackageVersion,PackageValidator,PackageExporter,PackageImporter}.ts`.

| Module | What it is today | Extension point | Gap found |
|---|---|---|---|
| `PackageVersion.ts` | Two constants (`CURRENT_PACKAGE_VERSION = 1`, `SUPPORTED_PACKAGE_VERSIONS = [1]`) plus `isFuturePackageVersion`/`isSupportedPackageVersion` helpers — **one global version number**, not namespaced by object type. | A new package type can call `isFuturePackageVersion`/`isSupportedPackageVersion` as-is; the numbers themselves are shared module state. | **Real gap** (detailed in §6.3): if Notes and Documents packages ever need independent version histories, a single shared `CURRENT_PACKAGE_VERSION` can't express "Notes packages are at v1, Documents packages are at v2" simultaneously. |
| `PackageValidator.ts` | `PackageValidationIssue` (typed error codes), `PackageValidationResult<T>` (tagged union, never throws), `PackageValidator<T>` interface. | Fully reusable as-is — a new `validate<Type>Package(input: unknown): PackageValidationResult<TypePackage>` function implements this interface with zero changes needed to the file itself. | None. |
| `PackageExporter.ts` | `PackageExporter<TSource, TPackage>` — one method, `export(source) => package`, deliberately pure (no I/O). | Reusable as-is. `TSource` for Documents would be `{document: DocumentRow, tags: Tag[], fileBytes: ArrayBuffer}` or similar — the interface doesn't constrain what `TSource` contains. | None in the interface; see §6.1 for whether the *envelope shape* needs to change to carry binary content. |
| `PackageImporter.ts` | `PackageImportContext` (`userId`, `workspaceId`), `PackageImporter<TPackage, TResult>` — one async method. | Reusable as-is for a **single-object** import (Documents, Assets, Knowledge Nodes). **Not** sufficient as-is for Knowledge Collections, which must import N member objects (of mixed types) plus the collection row plus membership links as one coordinated operation — no concept of "import a manifest of many typed items" exists anywhere in this interface today. | **Real gap** (detailed in §6.2 and §6.4): object ordering / multi-item packages need new, additive types layered on top of this interface — not a breaking change to it, since a Collection's own N sub-imports can each still be a normal `PackageImporter<TPackage,TResult>.import()` call, sequenced by a new orchestrator that doesn't exist yet. |

**Conclusion**: the framework's four files need **zero modification** to
support Knowledge Nodes, Documents, Assets, or Knowledge Links as
individual object types — each is a new sibling folder under
`src/modules/knowledge-exchange/<type>/` following the exact
`notes/{<type>PackageTypes,export<Type>Package,validate<Type>Package,import<Type>Package}.ts`
pattern already established. Knowledge Collections is the one type that
needs the framework itself extended (a manifest/orchestration layer,
additive) before it can be built — confirmed by tracing its actual data
model in §2 and §3 below, not assumed from its name.

## 2. Existing knowledge objects — schema, RLS, and safety audit

Every row below cites the actual migration and RLS policy read for this
pass.

### 2.1 Documents

- **Table**: `documents` (`0002_library.sql`, `workspace_id` added by
  `0004_workspaces.sql`). Columns: `id, user_id, workspace_id,
  collection_id, title, file_name, file_path, file_type, file_size,
  status, created_at, updated_at`.
- **Ownership**: `user_id`. **Workspace**: `workspace_id` (nullable).
- **RLS**: extended to workspace roles by `0031_shared_knowledge_objects.sql`
  §1 — select at viewer-or-above, insert self-attributed only, update at
  editor-or-above, delete at owner. **Safe to export**: yes, the exporting
  account's own read of a document it can already see uses this exact
  policy, same as Notes.
- **Storage**: private bucket `documents`, one file per document at
  `file_path` (`${userId}/${uuid}-${filename}`), RLS keyed to
  `(storage.foldername(name))[1] = auth.uid()::text` — **no cross-account
  read path exists**, confirmed in `0002_library.sql`.
- **Dependent child tables** (all read directly from their migrations):

  | Table | Own `workspace_id`? | RLS extended by 0031? | Safe to export today? |
  |---|---|---|---|
  | `document_chunks` | Yes (denormalized, `0007_search.sql`) | Yes (§2 of 0031) | Content is derived, not authored — never copied (§3.1). |
  | `embeddings` | No (child of `document_chunks`) | Yes, via EXISTS (§3 of 0031) | Never copied, always regenerated (§3.1, §4). |
  | `document_tags` | No (child of `documents`) | Yes, via EXISTS (§4 of 0031) | Tag *names* transfer, exactly like Notes (§3.1). |
  | `extraction_metadata` | **No column at all** (`0003_processing.sql`) | **No** — still `auth.uid() = user_id` only | Descriptive metadata only; not independently meaningful, but currently **cannot be shared even intra-workspace**, let alone exported — regenerated by re-running extraction, never read from the exporter's row (§3.1). |
  | `processing_jobs` | No column at all | **No** — still own-user only | Purely operational history — **skip entirely**, no export value (§3.1). |
  | `flashcards`, `highlights`, `chapter_summaries` | **No column at all** on any of the three | **No** — all three still `auth.uid() = user_id` only (confirmed: none appear anywhere in `0031_shared_knowledge_objects.sql`) | **Real gap, not a design choice**: these three tables were never even made intra-workspace-shareable, let alone cross-account-exportable. A Documents package this phase would have to explicitly *exclude* them (§3.1), which is a legitimate MVP scope decision but should be **stated**, not silently dropped without documentation — matching this codebase's established discipline of naming a gap explicitly (see the original discovery doc §5.2's identical treatment of `workspace_objectives`). |

### 2.2 Knowledge Collections

- **Table**: `knowledge_collections` (`0026_knowledge_collections.sql`).
  Columns: `id, user_id, workspace_id, name, description, created_at,
  updated_at`. Deliberately thin — **no content of its own**.
- **Membership is not a separate join table** — it's ordinary
  `knowledge_links` rows with `source_type = 'knowledge_collection'`,
  `source_id = <collection id>`, `target_type` one of `'document' |
  'note' | 'conversation' | 'asset' | 'knowledge_node'`, `target_id =
  <member id>` (confirmed in `knowledgeCollections.ts`'s
  `addItemToCollection`/`listCollectionItems`). This means **a Collection
  has no exportable identity independent of Knowledge Links** — exporting
  a collection *is* exporting a set of `knowledge_links` rows plus,
  recursively, each member's own object per its own type's rules.
- **RLS**: extended by 0031 §8, same four-command shape.
- **Safe to export**: the collection's own name/description, yes. Its
  *contents*, only to the extent every member type it references also has
  a working exporter — confirmed structurally in §3.2.

### 2.3 Knowledge Nodes

- **Table**: `knowledge_nodes` (`0012_knowledge_intelligence_foundation.sql`).
  Columns: `id, user_id, workspace_id, node_type ('concept'|'entity'),
  title, title_normalized, description, source_type, source_id,
  source_chunk_ids, generation_metadata, metadata, created_at,
  updated_at`. `unique(user_id, source_id, node_type, title)`.
- **RLS**: extended by 0031 §5, same four-command shape.
- **Identity/dedup**: `resolveCanonicalNode()`
  (`knowledgeNodeResolution.ts`) is a real, tested, already-built
  find-or-create keyed on `(user_id, node_type, title_normalized)` — exact
  match only (`normalizeTitle`), no fuzzy matching. Three outcomes:
  `create` (no existing node), `refresh` (same exact source
  re-extracting), `reuse` (existing node from a *different* source — the
  cross-document merge case). Every outcome writes a
  `knowledge_node_sources` row.
- **Dependent child table**: `knowledge_node_sources`
  (`0016_knowledge_node_identity.sql`) — `id, user_id, node_id,
  source_type, source_id, source_chunk_ids, created_at`. RLS extended by
  0031 §6 (select + insert only — this table is append-only in practice,
  matching the codebase's own comment). **This is the provenance ledger
  itself** — never copied verbatim on import; a fresh row gets written by
  calling `recordKnowledgeNodeSource` exactly as extraction already does.
- **Safe to export**: node content (title/description/node_type/metadata)
  yes; `source_chunk_ids` no (references chunks that only exist in the
  exporter's account — same reasoning the original discovery doc already
  gave for Notes' `source_chunk_ids`, now confirmed to apply identically
  here); `source_type`/`source_id` must be re-pointed, never copied
  verbatim (§3.3).

### 2.4 Knowledge Links

- **Table**: `knowledge_links`, originally created in
  `0010_reconcile_knowledge_tables.sql`, extended with
  `relationship_type/confidence/generated_by/metadata` by
  `0012_knowledge_intelligence_foundation.sql`. Columns: `id, user_id,
  workspace_id, source_type, source_id, target_type, target_id,
  created_at, relationship_type, confidence, generated_by, metadata`.
  `unique(source_type, source_id, target_type, target_id)`.
- **No FK on `source_id`/`target_id`** — deliberately polymorphic,
  enforced only by application code (confirmed by the migration's own
  comment: "source_id/target_id intentionally have no FK"). This means
  **the database itself will never catch a dangling link** pointing at an
  object that doesn't exist in the importing account — that check has to
  happen at the application layer, both at package-construction time and
  at import time (§3.4).
- **RLS**: extended by 0031 §7, same four-command shape.
- **Safe to export**: only as an edge between two endpoints that are
  *both* also present in the same package — confirmed structurally, not
  just as a design preference (§3.4).

### 2.5 Assets

- **Table**: `assets` (`0022_assets.sql`). Columns: `id, workspace_id,
  owner_id, original_path, optimized_path, thumbnail_path, mime_type,
  width, height, size_bytes, created_at`. **Uses `owner_id`, not
  `user_id`** — the one naming inconsistency across all five audited
  types, already correctly handled by 0031's own RLS (`auth.uid() =
  owner_id`).
- **RLS**: extended by 0031 §12, same four-command shape.
- **Storage**: private bucket `assets`, same per-user-folder RLS pattern
  as `documents` — no cross-account read path. Three paths per asset
  (`original`, `optimized`, `thumbnail`), but `optimized`/`thumbnail` are
  **always mechanically derivable from `original`** via
  `generateDerivatives()` (`src/modules/assets/pipeline/generateDerivatives.ts`,
  called by `uploadAsset`) — confirmed by reading `uploadAsset` itself,
  which calls `generateDerivatives(file)` before ever touching storage.
  **This means a package only ever needs to carry the original image
  bytes** — the other two paths regenerate for free by calling the exact
  same function `uploadAsset` already calls, exactly mirroring how
  Documents' `document_chunks`/`embeddings` regenerate via
  `processDocument` rather than being copied (§3.1, §4).
- **Safe to export**: title + original file bytes + mime_type, yes. No
  children at all — the simplest of the five audited types.

## 3. Relationship map and transfer/recreate/skip/private determination

```
Document
 ├── document_chunks ─── embeddings          → SKIP (both): always regenerate via processDocument
 ├── document_tags → tags                    → TRANSFER as name strings, recreate via find-or-create (Notes precedent)
 ├── extraction_metadata                     → SKIP: regenerate via processDocument (not RLS-shareable anyway)
 ├── processing_jobs                         → SKIP: operational history, no export value
 ├── flashcards / highlights / chapter_summaries → REMAIN PRIVATE this phase (not RLS-shareable — real gap, §2.1)
 ├── knowledge_node_sources (as source_type='document') → SKIP: regenerate by re-running extraction against the reimported file
 └── knowledge_links (as source_type/target_type='document') → TRANSFER only if the link's *other* endpoint is also in the package

Knowledge Collection
 └── knowledge_links (source_type='knowledge_collection') → each memberships's target
      ├── document        → recurse into Document's own rules above
      ├── note             → recurse into UX-14.5.9's existing Notes rules (already built)
      ├── conversation      → OUT OF SCOPE (original discovery doc §1: "optionally transferable... by first converting to a note," never a first-class package object — unchanged by this audit)
      ├── asset            → recurse into Asset's own rules below
      └── knowledge_node    → recurse into Knowledge Node's own rules below

Knowledge Node
 ├── knowledge_node_sources (provenance ledger)  → SKIP: never copy the ledger; write ONE fresh row for the import event itself, via the existing recordKnowledgeNodeSource
 ├── source_chunk_ids                            → SKIP (clear to null/empty on import — meaningless cross-account, same reasoning as Notes)
 └── knowledge_links referencing this node        → TRANSFER only if the link's other endpoint is also in the package

Knowledge Link
 ├── source (by source_type/source_id)  → must already exist in the importing account (freshly imported this same operation, or pre-existing) — otherwise DROP the link, don't fail the whole import
 └── target (by target_type/target_id)  → same rule

Asset
 └── (no children) → TRANSFER original file bytes + title + mime_type; RECREATE optimized/thumbnail via generateDerivatives
```

**General rule confirmed across every type in this audit** (already true
of Notes, now shown to generalize cleanly): **anything mechanically
*derived* from user-authored or uploaded content is never copied — it is
always regenerated on import by calling the exact same pipeline function
this app already calls for a native create.** Embeddings
(`SupabaseVectorStore.upsert` via `processDocument`/`indexNote`),
extraction metadata (`processor.extract()`), image derivatives
(`generateDerivatives()`), and knowledge-node canonical identity
(`resolveCanonicalNode()`) are four concrete instances of one principle,
not four separate decisions.

## 4. Security review

Confirmed by reading the actual schema and RLS, not asserted:

- **`user_id`/`owner_id`**: present on every one of the five audited
  types and every dependent child table; **none of them have this as a
  package-exportable field today** (Notes precedent: `NotePackagePayload`
  has no `user_id` field to accidentally forward — the same allow-list
  discipline must hold for every new type's own `*PackagePayload`
  interface).
- **`workspace_id`**: present on `documents`, `knowledge_collections`,
  `knowledge_nodes`, `knowledge_links`, `assets`, and their
  RLS-extended children — same rule, never a package field, always an
  explicit importer choice at import time (§5).
- **`ai_memory`**: a fully separate table, confirmed **never** touched by
  `0031_shared_knowledge_objects.sql` and confirmed to have **zero
  relationship** (no FK, no `knowledge_links` row type, no join) to any
  of the five audited types or their children — there is no code path by
  which exporting a Document, Asset, Collection, Node, or Link could
  reach into `ai_memory`, because nothing in those five types' own tables
  or query code ever references it.
- **Provider settings / API keys**: `provider_overrides`, `ai_requests`,
  and all provider API keys (Supabase Function secrets, `ANTHROPIC_API_KEY`
  etc.) are equally unreachable — no column on any audited table holds a
  provider identifier or credential, and no audited API function reads
  from those tables.
- **Embeddings**: this audit is the first to actually confront a *real*
  vector column (`embeddings.embedding`, `vector(1536)`) rather than
  Notes' `note_embeddings` (which UX-14.5.9 never needed to touch since
  Notes' own export never included an embedding field). Restated as a
  hard rule now that it matters concretely: **`embeddings` rows are never
  read for export and never written by copying an exported vector** — the
  only path to a populated `embeddings`/`note_embeddings` row for
  imported content is calling the existing embedding provider fresh,
  post-import.
- **Audit records**: `processing_jobs` (Documents) and
  `knowledge_node_sources` (Knowledge Nodes) are both append-only
  operational/provenance logs of the *exporting* account's own activity —
  neither is ever copied; `knowledge_node_sources` gets exactly one new
  row recording the *import* event itself (via the existing
  `recordKnowledgeNodeSource`), never the exporter's original entries.
- **Private preferences**: `reading_progress` (Documents' sibling table)
  is confirmed, again, never touched by any of the five audited types'
  own export/import code paths — none of Documents' API functions
  (`documents.ts`, `processDocument.ts`) read or write it, so there is no
  accidental-inclusion risk through Documents specifically, consistent
  with the original discovery doc's "never transferable" classification.
- **New risk class this expansion introduces, not present for Notes**:
  once a package can carry **binary content** (Documents/Assets), the
  package is no longer "just JSON" — file size must be bounded (no
  existing precedent for an unbounded package anywhere in this app,
  confirmed by grep), and the re-uploaded bytes must go through the
  **exact same validation** a native upload already requires
  (`validateImageFile` for Assets, `fileTypeFromName` for Documents) —
  never trusted as pre-validated just because they arrived inside a
  package, the identical "never trust a package as pre-validated"
  principle `validateNotePackage` already applies to JSON, now extended
  to binary content.

## 5. Import ownership model — confirmed against real code

The three rules the task asks to confirm are **already mechanically true
of every audited create-path**, without any change needed to those
functions:

- **Importer becomes owner**: `uploadDocument`, `uploadAsset`,
  `resolveCanonicalNode`'s `create` branch, and `addItemToCollection` /
  the raw `knowledge_links` insert all take `userId` (or `owner_id`) as
  an explicit, caller-supplied parameter — none of them infer it from an
  existing row or a stored session default. A package importer calling
  any of these with the import context's `userId` gets correct ownership
  for free, exactly like `importNotePackage` calling `createNote` today.
- **Fresh IDs**: every one of the five tables' primary keys is
  `gen_random_uuid()`, generated by the same `insert()` path every native
  create already uses — there is no code anywhere in this audit that
  accepts a client-supplied `id` for any of these tables.
- **Explicit workspace assignment**: `workspaceId` is likewise an
  explicit parameter on every audited create-path — never inferred from
  a package's original workspace (which, per §3.2 of the original
  discovery doc, the importer may not even be a member of).

**One genuine gap, not previously visible until this audit**: Notes'
`generation_metadata.importedFrom` provenance convention (packageVersion,
sourceVersion, exportedAt, originalCreatedAt/UpdatedAt, importedAt) has
**nowhere to live** for three of the five audited types.
`knowledge_nodes` already has a `generation_metadata jsonb` column
(reusable as-is). `documents`, `knowledge_collections`, and
`knowledge_links` have **no JSONB metadata column of any kind** —
confirmed by their column lists in §2. `assets` also has none. This means
"original creator metadata is preserved only as provenance" (the task's
own requirement) **cannot be satisfied today for Documents, Collections,
Links, or Assets** without either (a) a small additive migration adding
a `generation_metadata jsonb` column to each — consistent with this
codebase's very established convention (every other AI-provenance-bearing
table already uses exactly this column name) — or (b) accepting "no
importedFrom record" as a stated MVP limitation for whichever types are
implemented before such a migration lands. This is flagged, not resolved,
here — resolving it is implementation work for a future phase, explicitly
out of scope for this discovery-only pass's "no migrations" constraint.

## 6. Gaps in the current package framework

1. **Binary content / package format.** The current framework assumes a
   package is a single JSON object (`JSON.stringify(pkg, null, 2)`,
   downloaded as `.json`). Documents and Assets need the original file's
   bytes to travel with the package (§0, §2.1, §2.5) so import never
   needs cross-account storage access. Two real options, not yet decided:
   (a) base64-encode the file into a JSON field (simplest, reuses the
   existing single-file-download UX exactly, but inflates size ~33% and
   keeps everything in one file), or (b) a two-file package (a
   `manifest.json` plus the original file, e.g. inside a zip — this
   codebase already has a `jszip` dependency, confirmed in `package.json`,
   for spreadsheet export, so the tooling exists but isn't wired to this
   framework). **Decision needed before implementing Documents or
   Assets**, not before Knowledge Nodes (which has no binary content at
   all).
2. **Object ordering / multi-item packages.** `PackageImporter<TPackage,
   TResult>` is single-object by construction. Knowledge Collections
   needs an orchestrator that imports each member (of potentially mixed
   types) first, then the collection row, then re-creates membership
   links with the members' *newly assigned* ids — a genuinely new
   concept this framework doesn't have yet, additive on top of the
   existing per-type importers rather than a breaking change to them.
3. **Migration/version namespacing.** `PackageVersion.ts`'s
   `CURRENT_PACKAGE_VERSION`/`SUPPORTED_PACKAGE_VERSIONS` are a single
   global pair. If a future Documents-package format needs its own
   independent version history (a real, foreseeable need — Documents'
   envelope will look nothing like Notes') while Notes stays at v1
   forever, one shared counter can't express that. **Recommend
   resolving this before the second object type ships**, not
   retrofitting it after two or three types already exist with
   ambiguous version semantics — the cheapest fix (adding a `kind`
   discriminator field alongside `version`, and keying
   `SUPPORTED_PACKAGE_VERSIONS` by kind) is a small, additive change to
   `PackageVersion.ts` that doesn't require touching `notePackageTypes.ts`
   itself if done carefully, but is genuinely easier to design correctly
   now, deliberately, than to retrofit later.
4. **Package manifests.** No concept of "one package, many typed items"
   exists — needed only for Knowledge Collections (§6.2 is the
   orchestration half of this same gap; this is the *serialization*
   half: what does a multi-item package's JSON actually look like).
5. **Conflict handling.** Turns out to be a smaller gap than it first
   appears: Notes' policy (always insert, never dedup) and Knowledge
   Nodes' policy (dedup via the already-built `resolveCanonicalNode`)
   are both fully expressible *inside* each type's own `import<Type>
   Package` function, with zero change needed to the
   `PackageImporter<TPackage,TResult>` interface itself — "conflict
   handling" is a per-type implementation choice the framework already
   accommodates, not a missing framework capability. Confirmed by
   reading `resolveCanonicalNode`, which is already a complete, tested,
   reusable primitive requiring no new design work at all — importing a
   Knowledge Node's package payload through it is a direct function
   call, no new logic to invent.

## Discovery summary

The package framework's four generic files
(`PackageVersion`/`PackageValidator`/`PackageExporter`/`PackageImporter`)
need no changes to support Knowledge Nodes, Documents, or Assets as new,
independent object types — each follows Notes' exact four-file pattern in
its own sibling folder. All five candidate object types already carry the
ownership/workspace/RLS shape the snapshot model requires, confirmed via
`0031_shared_knowledge_objects.sql`'s existing, shipped RLS extension —
this task's "no RLS changes" constraint is trivially satisfiable, not a
constraint fighting the architecture. The one clean, already-general
pattern this audit surfaces and confirms across every type: **content
that's mechanically derived from source material is always regenerated
by calling the exact pipeline function a native create already calls,
never copied** — true for Notes' search index (already shipped), and now
confirmed true for Documents' chunks/embeddings/extraction-metadata,
Assets' optimized/thumbnail derivatives, and Knowledge Nodes' canonical
identity.

Two genuinely new problems this expansion introduces, absent from Notes:
binary content needing a package-format decision (Documents, Assets), and
multi-object orchestration needing a new, additive framework layer
(Knowledge Collections only). Three tables (`flashcards`, `highlights`,
`chapter_summaries`) were found to be **not RLS-shareable at all today**,
which caps what a Documents package can honestly include this phase
regardless of Knowledge Exchange work — a pre-existing gap this audit
surfaced, not one this task is scoped to fix.

## Recommended implementation order

1. **Knowledge Nodes** — no binary content, no multi-object
   orchestration, and an already-built, tested dedup primitive
   (`resolveCanonicalNode`) that *is* the correct conflict-handling
   policy. Proves the "second object type" pattern (does the envelope
   need a `kind` field now — §6.3) at the lowest possible complexity.
2. **Assets** — one binary blob, zero children, zero relationships.
   Proves the package-format decision (§6.1) on the smallest possible
   surface (a single image, one existing regeneration call —
   `generateDerivatives`).
3. **Documents** — same binary-content pattern as Assets, at higher
   complexity (a three-stage regeneration pipeline instead of one call)
   and with an explicit, documented exclusion of
   `flashcards`/`highlights`/`chapter_summaries` until a separate,
   dedicated migration extends their RLS (out of scope for Knowledge
   Exchange work specifically).
4. **Knowledge Links** — depends on whichever endpoint types are already
   importable (at minimum Notes + Knowledge Nodes); needs the
   both-endpoints-present package-construction rule built and tested.
   Comes after, not before, steps 1–3.
5. **Knowledge Collections** — last by construction: a pure orchestrator
   over whichever member-type importers already exist, and the one type
   requiring both new framework gaps (§6.2 object ordering, §6.4
   manifests) to be solved first.

## Security considerations

The allow-list discipline UX-14.5.9 established (a package's payload type
has a field for exactly what's meant to travel, and nothing else) carries
forward unchanged and is sufficient for every audited type's
user-authored content. The two genuinely new risk surfaces are binary
content (needs the same re-validation-on-import rigor a native upload
already gets — never trust package bytes as pre-validated) and
multi-object package integrity for Collections (needs an explicit
partial-success report, matching the "clear success/failure report" this
engagement has followed since the original Knowledge Exchange design).
Neither risk is present in Notes' shipped implementation, and neither is
resolved by this document — both are concrete, scoped design questions
for whichever future phase actually implements Documents/Assets/Collections.

## Should UX-14.5.10 proceed as one phase, or split?

**Split**, matching this engagement's own established discipline (the
same reasoning that made UX-14.5.9 "Notes only" rather than attempting
all six object types at once, and that split UX-14.5.8 into a
Foundation/Management/Delivery sequence). The five recommended steps
above have materially different risk profiles — pure-metadata (Knowledge
Nodes), binary-content-introducing (Assets, then Documents),
orchestration-dependent (Links, then Collections) — and each is
independently shippable and independently verifiable, exactly the
"prove the pattern on one type before generalizing" sequencing the
original discovery doc's own §8.1 already argued for. Recommend the next
concrete implementation phase (UX-14.5.11, if approved) scope itself to
**Knowledge Nodes only**, the lowest-risk next step this audit
identifies.
