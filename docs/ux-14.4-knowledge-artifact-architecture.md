# UX-14.4 — Knowledge Artifact & Collaboration Architecture Discovery

**Status: design only.** No code, migrations, or UI changes were made to produce this document. Per explicit instruction: audit first, design the Artifact Engine, define the "Save As" architecture and artifact schemas, define sharing architecture — no implementation yet, blueprint first.

This follows UX-14.1–14.3.5, which built and activated NOVA's intelligence substrate (unified recommendations, pre-response planning, memory confidence + capture). This document is the first UX-14 milestone aimed at the platform's *output* and *multi-user* surface rather than its reasoning surface.

---

## 1. Audit: Current Capabilities, Grounded in Code

### Notes (`src/modules/notes/`)

- `Note` (`database.ts`): `id, user_id, workspace_id, collection_id, document_id, title, content, source_chunk_ids, generation_metadata: Record<string, unknown> | null, created_at, updated_at`.
- `generation_metadata` is **already a free-form JSONB field**, already written today by two producers: `useNote.ts`'s "create note from highlight" flow and `saveMessageToNote.ts`'s "Save to Notes" flow — both use it for provenance (what conversation/highlight this came from), not for a typed "kind" of note. No consumer reads a `type`/`kind` discriminator out of it today.
- `generateBriefing.ts` (Knowledge Actions v1) is instructive: a "Briefing" is **not a separate schema or table today** — it is a `Note` with a `"Briefing: {title}"` prefix and no `generation_metadata` tagging at all. This confirms the user's instinct that briefings, notes, and (future) other artifact "kinds" are currently indistinguishable once persisted, which is exactly the gap Save As needs to close.
- `mergeNotes.ts` / `useMergeNotes.ts` (Knowledge Actions v1) already do the one existing example of artifact *composition* — combining multiple notes' content into one, deterministically, client-side.
- Full CRUD (`notes/api/notes.ts`), tagging (`noteTags.ts`), search indexing (`indexNote`), and knowledge-graph linking (`linkKnownConceptsToSource`) all already exist and are artifact-kind-agnostic — they operate on any `Note` regardless of what produced it.

### Collections (`src/modules/knowledge-intelligence/api/knowledgeCollections.ts`)

- `KnowledgeCollection`: `id, user_id, workspace_id, name, description, created_at, updated_at` — **identity/metadata only**.
- Membership is **not a column** — it's rows in the existing generic `knowledge_links` table (`source_type='knowledge_collection', source_id=<collection>, target_type=<item type>, target_id=<item>`), the same polymorphic-link pattern `linkNoteToHighlight`/`linkNoteToConversation`/`linkNoteToAsset` already use.
- `CollectionItemType = 'document' | 'note' | 'conversation' | 'asset' | 'knowledge_node'` — a Collection can **already** hold a heterogeneous mix of documents, notes, conversations, images, and concepts.
- **This is, in substance, already the "Knowledge Space" the user is proposing.** A `KnowledgeCollection` named "Mtoni Expansion Project" holding a market-analysis document, a revenue-model note, guest-research conversations, and a strategy brief is buildable *today*, with zero schema changes — it is exactly `listCollectionItems`'s existing return shape. What's missing is not the container; it's **membership beyond a single owner** (see §2 below) and a name that reflects the broader purpose (`KnowledgeCollection` → conceptually a "Knowledge Space").

### Reader (`src/modules/reader/`) and Chat (`src/modules/ai/chat/`)

- Both surfaces already have a "turn this into something durable" action: `SaveConversationDialog` (Save to Notes) is wired into both `ChatPage.tsx` and `ReaderChatPanel.tsx`, producing a `Note` via `conversationToNote.ts`. This is the existing, narrow precursor to a general "Save As" menu — one artifact kind (Note), one source (a conversation), no kind picker.
- `AddToCollectionButton.tsx` already exists and is wired into at least one surface — the "add this to a Knowledge Space" affordance the Collaboration Layer needs is not new UI, it already renders.
- Spreadsheet analysis (`src/modules/processing/spreadsheet/types.ts`) is real, structured, and read-side only: `SheetAnalysis` (per-sheet `ColumnAnalysis[]` with `hasFormulas: boolean`, `SheetAggregates` with `columnStats`/`categoryBreakdowns`/`trends`/`anomalies`) is computed once at *ingestion* time for uploaded spreadsheets and grounds Chat/Reader answers about them. **There is no write-side equivalent** — nothing today takes an AI response and emits a new structured spreadsheet/formula object. The user's "Formula Template"/"Spreadsheet Model" artifact idea is genuinely new capability, not an extension of this.

### Export

- Exactly one export capability exists in the entire codebase: `buildKnowledgeExportMarkdown()` (`knowledgeExportMarkdown.ts`) — a pure, client-side function that renders a knowledge node's already-fetched evidence into a Markdown string, downloaded as `.md`. No PDF, DOCX, XLSX, or CSV generation exists anywhere in `src/`.
- `package.json` already depends on `xlsx` (`^0.18.5`) — used today only for *reading* uploaded spreadsheets (`processing/extractors/spreadsheet.ts`). It is also capable of *writing* `.xlsx`/`.csv`, which is directly relevant to a future Spreadsheet Model export and means that specific export doesn't need a new dependency. No PDF or DOCX-writing library is present at all — a genuine new dependency would be needed for those two export formats.

### Sharing / Multi-User — the load-bearing finding

Grepped across `src/shared/types/database.ts` and every RLS policy in `supabase/migrations/`: there is **no membership, role, or invite concept anywhere in this codebase.**

- Every user-owned table (`notes`, `documents`, `knowledge_collections`, `knowledge_nodes`, `assets`, `ai_memory`, `conversations`, …) carries a single `user_id`/`owner_id` column.
- Every RLS policy found follows the same one pattern, verbatim: `using (auth.uid() = user_id) with check (auth.uid() = user_id)`. Sixteen migration files contain `create policy`; all of them are single-owner policies.
- `Workspace` itself (`database.ts`) is `{ id, user_id, name, archived_at, sort_order, ... }` — a workspace is owned by exactly one user. There is no `workspace_members` table, no concept of a second person ever seeing a workspace's contents.

**This means "Members: Ding, Finance Team, Marketing Team" on a Knowledge Space is not an incremental feature — it is the first multi-user capability this application would ever have.** Every existing screen, query, and RLS policy currently assumes single ownership. This finding reframes the Collaboration Layer from "add a members list to Collections" into "design and land a new authorization model the rest of the schema doesn't yet support," and it is treated as its own phased track below rather than folded into the artifact-schema work, consistent with this sprint's instruction not to introduce speculative or premature architecture.

## 2. The Artifact Engine

### Design principle

An "artifact" is not a new kind of storage — it is **a `kind` + `payload` tag on content that already has a home.** Three of the six requested kinds (Note, Briefing, Knowledge Card) are already `Note` rows in substance (§1); the other three (Spreadsheet Model, Formula Template, Chart) are new structured-data shapes with no current home. The Artifact Engine's job is to give every kind a single, typed persistence and rendering contract, not to build six parallel subsystems.

### Recommended shape

```
AiArtifact (new table, or a typed `generation_metadata` convention on Note — see below)
  id
  user_id, workspace_id
  kind: 'note' | 'briefing' | 'spreadsheet_model' | 'formula_template' | 'chart' | 'knowledge_card'
  title
  payload: jsonb            -- kind-specific structured data, see §4
  source_type / source_id   -- conversation | knowledge_node | document, reusing the existing
                                polymorphic pattern (knowledge_links, note.document_id) rather
                                than inventing a new provenance mechanism
  created_at, updated_at
```

**Recommendation: do not build this as a new table on day one.** Two of the six kinds (`note`, `briefing`) are textual and already have a fully-built home in `notes` — search indexing, tagging, collection membership, knowledge-graph linking, the editor UI, all of it. Splitting them into a new `ai_artifacts` table would duplicate all of that infrastructure for no gain. The lower-risk path:

- **Text-shaped artifacts** (`note`, `briefing`, `knowledge_card`) stay as `Note` rows. `generation_metadata` gains one new, additive, non-breaking field — `{ artifactKind: 'note' | 'briefing' | 'knowledge_card', ... }` — read by a new "Save As" picker and rendered with a kind badge, but every existing Notes capability (search, tags, collections, merge) keeps working unmodified, because a `Note` is still exactly a `Note`.
- **Structured-data artifacts** (`spreadsheet_model`, `formula_template`, `chart`) are genuinely new — they have no textual `content` to persist and need a `payload` shape a spreadsheet/chart renderer can consume directly (§4). These are the actual candidates for a new `ai_artifacts` table (or three narrow, purpose-fit tables) — deferred to the implementation phase, scoped only once the exact payload contracts below are validated against real chat output.

This mirrors UX-14.3.5's own lesson: the cheapest, lowest-risk move is composing over what already exists (Notes' full stack) rather than building a parallel system for capabilities that already work.

## 3. "Save As" Architecture

A `Save As ▾` affordance, available anywhere an AI response already renders (`MessageBubble` in Chat/Reader, a `KnowledgeNodeEvidence` drill-down, a spreadsheet analysis card) — the same entry-point pattern `AddToCollectionButton` and `SaveConversationDialog` already establish, generalized:

```
AI Response
    │
    ▼
Artifact Kind Detector (deterministic, not a new AI call)
    │   — inspects response shape/content: has structured
    │     numeric/tabular data? cites a knowledge node? is a
    │     multi-paragraph explanation? — same "classify, don't
    │     ask the model to self-report" pattern intentClassifier
    │     and detectMemoryCandidates already use.
    ▼
Save As menu, pre-selected to the detected kind, user can override
    │
    ▼
Kind-specific persistence:
  note / briefing / knowledge_card  → createNote({ ..., generation_metadata: { artifactKind } })
  spreadsheet_model / formula_template / chart → new artifact API (§2), scoped at implementation time
```

The detector is the one genuinely new piece of logic here, and it should follow this codebase's established deterministic-first rule (`detectMemoryCandidates`, `buildInteractionState`, the recommendation engine are all regex/rule-based, not LLM calls) — kind detection from response shape is a pattern-matching problem, not a reasoning problem, and adding a new AI round-trip just to classify "is this a spreadsheet or a note" would be a real regression against that rule.

## 4. Artifact Schemas

| Kind | Backing store | Payload shape | Grounded in |
|---|---|---|---|
| **Note** | `notes` row, `generation_metadata.artifactKind = 'note'` | existing `content: string` (markdown) | Already fully built. |
| **Briefing** | `notes` row, `generation_metadata.artifactKind = 'briefing'` | existing `content: string`; `generation_metadata` also carries `{ nodeId, collectionIds }` (already computed by `buildBriefingVariables`, just not persisted today) | `generateBriefing.ts` — only needs metadata tagging, no new persistence. |
| **Knowledge Card** | `notes` row, `generation_metadata.artifactKind = 'knowledge_card', cardFields: { insight, confidence, sourceCount, relatedTitles }` | short-form structured summary, rendered via the *existing* `KnowledgeCard`/`ConfidenceBadge`/`SourceReference` primitives (`knowledge/components`, built in Phase 7B) instead of new components | The exact card shape the user's example describes already has matching UI primitives — this is a new *save* path onto existing *render* components. |
| **Spreadsheet Model** | new artifact table (or `notes.generation_metadata` if kept read-only/display-only — a real *editable* model needs its own table) | `{ sheets: [{ name, columns: string[], rows: (string\|number)[][] }] }` — plain values only; formulas are a separate field per cell (see Formula Template) so a cell can be both a literal value and, when present, a formula that produced it | Deliberately mirrors `SheetAnalysis`'s existing plain-JSON convention (`types.ts`'s own comment: "no Date objects, no functions, persisted verbatim into jsonb") rather than inventing a new convention. |
| **Formula Template** | new artifact table, or a field on Spreadsheet Model artifacts | `{ name, category, inputs: { name, label }[], formula: string (e.g. "occupied / available"), description }` — reusable, not tied to one spreadsheet instance | New; no current formula-authoring exists anywhere (`SheetAnalysis.columns[].hasFormulas` only *detects* formulas in uploaded files, it doesn't represent or generate them). |
| **Chart** | new artifact table, or a rendering annotation on a Spreadsheet Model artifact | `{ chartType: 'line' \| 'bar' \| 'pie', dataRef: { sheetIndex, xColumn, yColumn }, title }` — a reference into a Spreadsheet Model's data, not a duplicated copy of it, so the chart always reflects the model's current values | New; no charting library is currently a dependency — this is a real new-dependency decision to make at implementation time (the `dataviz` design skill this environment has available is a good default source for chart styling once a library is picked). |

**Export formats per kind** (per the user's spec): Note/Briefing → PDF, DOCX; Spreadsheet Model → XLSX, CSV. All four require new capability — only the `xlsx` write path is unblocked today (dependency already present); PDF and DOCX writing both need a new library choice, which is an implementation-phase decision, not a blueprint-phase one.

## 5. Sharing Architecture

Given §1's finding (zero multi-user infrastructure exists anywhere in this schema), sharing is proposed as its **own two-phase track**, sequenced *after* the Artifact Engine's schema work, not bundled into it:

**Phase A — foundation (a real, separate milestone, not a UX-14.4 deliverable).** A `workspace_members` (or `knowledge_space_members`) table: `{ workspace_id, user_id, role: 'owner' | 'editor' | 'viewer', invited_at, accepted_at }`. Every RLS policy on every shared-relevant table (`knowledge_collections`, `notes`, `documents`, `knowledge_links`, …) needs a second policy branch added alongside the existing `auth.uid() = user_id` one — `exists (select 1 from workspace_members where workspace_id = <row>.workspace_id and user_id = auth.uid() and role >= required_role)`. This is real, non-trivial, security-sensitive schema and policy work across most of the application's tables — it is the single largest single piece of net-new infrastructure implied by this document, and should get its own audit-first sprint before any code lands, per this whole initiative's established discipline.

**Phase B — the three sharing levels** (Private / Shared / Collaborative) become a straightforward `role` value once Phase A exists: `viewer` = Shared, `editor` = Collaborative, and "Private" is simply zero rows in `workspace_members` beyond the owner (today's exact current state, requiring no change to keep working).

**Recommendation:** scope UX-14.4's actual implementation to the Artifact Engine + Save As (§2–4) first, entirely within the existing single-owner model — every artifact kind above works correctly today with zero sharing, since `Note`/new artifact tables inherit `workspace_id` the same as everything else. Sharing (Phase A/B) becomes UX-14.5, audited on its own terms, once there's something worth sharing. This avoids exactly the kind of premature, speculative authorization architecture this initiative's rules have consistently flagged against building ahead of real need.

## 6. Recommended Sequencing

1. **Save As tagging for text artifacts** (`note`, `briefing`, `knowledge_card`) — additive `generation_metadata.artifactKind`, a kind badge on `NoteCard`, a `Save As` menu generalizing `SaveConversationDialog`. Zero schema migration, reuses 100% of existing Notes infrastructure. Lowest risk, ships first.
2. **Artifact kind detector** — deterministic classification of an AI response's shape, feeding the Save As menu's default selection.
3. **Spreadsheet Model artifact** — new table, `xlsx`/`csv` export (dependency already present). Second-lowest risk; no new external dependency.
4. **Formula Template artifact** — depends on (3)'s table existing; smaller payload, same table family.
5. **Chart artifact** — depends on (3); requires a new charting-library decision.
6. **PDF/DOCX export** for Note/Briefing — requires a new dependency; no schema dependency on the above, could run in parallel with (3)-(5) if prioritized.
7. **Knowledge Spaces rename/reframing** of Collections in the UI (no schema change — `KnowledgeCollection` already supports this) — cosmetic/IA work, can happen any time after (1).
8. **Sharing Phase A/B** — separate milestone (UX-14.5), audited independently, after real artifact usage exists to justify it.

## 7. Acceptance Criteria for This Discovery Phase

- [x] Notes, Collections, Reader, Chat, and Export capabilities audited against actual code (not assumed) — §1.
- [x] Artifact Engine designed, explicitly reusing existing Notes infrastructure for text-shaped kinds rather than duplicating it — §2.
- [x] "Save As" architecture defined, reusing the existing `AddToCollectionButton`/`SaveConversationDialog` entry-point pattern — §3.
- [x] All six requested artifact schemas defined, each traced to what already exists vs. what's genuinely new — §4.
- [x] Sharing architecture defined and explicitly separated into its own phased track given the zero-multi-user-infrastructure finding — §5.
- [x] No implementation performed — this document only.

## Implementation Record — Phase 1: Artifact Intelligence Foundation (completed)

Scope, as authorized: (1) artifact metadata model on `generation_metadata`, (2) an artifact type registry, (3) Save As architecture, (4) classification wired into generated notes/briefings, (5) Knowledge Card rendering activated where appropriate, (6) no exports, (7) no collaboration, (8) no schema changes. All eight held.

**What was built.**

- `src/modules/ai/artifacts/artifactTypes.ts` — the `ArtifactKind` registry: the eight kinds from the roadmap (`note`, `briefing`, `formula`, `spreadsheet`, `chart`, `report`, `template`, `knowledge_card`), each with a label/description, plus `isArtifactKind` and a Save-As display order.
- `src/modules/ai/artifacts/artifactMetadata.ts` — `getArtifactKind(note)` (reads `generation_metadata.artifactKind`, defaulting to `'note'` for every note that predates this milestone or never sets one — no backfill, no migration, honest absence) and `withArtifactKind(metadata, kind)` (merges the tag in without disturbing whatever else a caller already stores there).
- `src/modules/ai/artifacts/detectArtifactKind.ts` (+ tests) — deterministic, regex-based classification of response *shape* into a kind: an explicit chart-type mention → `chart`; a markdown table → `spreadsheet`; a `Formula:` line or a spreadsheet cell-reference pattern → `formula`; a short response with an explicit confidence marker → `knowledge_card`; checklist/template framing → `template`; multiple section headings in a long response → `report`; otherwise → `note`. No AI call — same "classification is pattern-matching, not reasoning" rule `detectMemoryCandidates`/`intentClassifier`/the spreadsheet module's `financialPatterns.ts` already follow, so running it on every save is free. Tested against the roadmap's own three worked examples (the hotel occupancy formula, the Month/Revenue chart, the peak-booking knowledge card) plus false-positive guards (a long response that merely mentions "confidence" isn't a knowledge card; two short headings don't make a report).

**Where classification is now connected** (item 4 — "connect generated notes/briefings to artifact classification"):

- `saveMessageToNote.ts` (the per-message "Save to Notes" button and the "Save this"/"Remember this" chat command — one shared function, one place to wire) now tags every note it creates with `detectArtifactKind(message.content)`. No picker here by design — this is the automatic, always-on classification path; a note gets a kind whether or not the user ever looks at a menu.
- `generateBriefing.ts` now tags its note `'briefing'` explicitly — already a known kind, no need to run the detector on an AI-generated summary.

**Save As architecture** (item 3), scoped to the one existing save surface that already has a form — `SaveConversationDialog.tsx` — rather than inventing a new UI surface: a "Save as" select field, pre-filled by running the detector over the content that scope/selection would actually save, re-suggested whenever that content changes, until the user picks a kind themselves (then their choice sticks). The per-message quick-save button (`MessageBubble`'s single-click "Save to Notes") deliberately keeps its existing one-click behavior rather than gaining a menu — it still gets full automatic classification (above), just no interactive override, to keep this phase's UI footprint to the one surface that already asked the user to make choices before saving.

**Knowledge Card activation** (item 5): `ArtifactKindBadge.tsx` (new, thin wrapper over the existing `StatusBadge`) renders a kind label next to a note's title in `NoteCard.tsx` — the grid gets to show what NOVA thinks it created, for every non-default kind, without a redesign (renders nothing for the default `'note'` kind — a plain note still looks like a plain note). `NoteDetailPage.tsx` goes further for the one kind that's a genuine "smart document" candidate: when `getArtifactKind(note) === 'knowledge_card'`, it renders the actual `KnowledgeCard` primitive (Phase 7B, previously unused outside the knowledge graph) as a summary block above the editable content — the first time that component has rendered anything other than an AI-extracted concept/entity.

**What was deliberately not built**, per items 6-8: no export of any kind (PDF/DOCX/XLSX) — Save As always persists as a `Note`, same as before this milestone, just tagged; no new artifact table (`spreadsheet`/`formula`/`chart` are classifiable and taggable today, but a note tagged `'spreadsheet'` still just holds text — the structured `payload` shape from §4 is unbuilt, correctly deferred until a real export/generation consumer needs it); no sharing, no workspace members, no RLS changes.

**Files changed:** 3 new (`artifactTypes.ts`, `artifactMetadata.ts`, `detectArtifactKind.ts`, plus their test files and `ArtifactKindBadge.tsx` — 5 new files total), 6 modified (`saveMessageToNote.ts` + its test, `generateBriefing.ts`, `SaveConversationDialog.tsx`, `NoteCard.tsx`, `NoteDetailPage.tsx`). Zero schema/migration changes.

**Verification.** `tsc -b`: clean. `vitest run`: 978/978 passing (up from 959 — 19 new tests: 12 for `detectArtifactKind`, 7 for `getArtifactKind`/`withArtifactKind`; one pre-existing `saveMessageToNote.test.ts` assertion updated to expect the new `artifactKind: 'note'` field, a mechanical fixture update, not new behavior). `lint`/`build`: clean. Browser: boot-smoke-tested (fresh dev server, Playwright, zero console/page errors). **Not verified live**: the full authenticated Save As flow (pick a kind, save, see the badge in the Notes grid, see the Knowledge Card render) — same disclosed gap as every UX-14 milestone since UX-14.2, for the same reason (no mocked-Supabase harness, no live-production test account).

**Recommendation for next step:** per this milestone's own guiding principle ("first teach NOVA what it creates, then teach NOVA how to export it, then teach NOVA how to share it"), the next justified move is either (a) closing the live-verification gap now flagged on five consecutive milestones, or (b) §6's step 3, the Spreadsheet Model artifact — the first kind that needs a real `payload`-bearing table rather than a tag on a `Note`, and the one export (`xlsx`/`csv`) with no new dependency to pick first. Sharing remains correctly out of scope until an artifact-authoring surface exists worth sharing.
