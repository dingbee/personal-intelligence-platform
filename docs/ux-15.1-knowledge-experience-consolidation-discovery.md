# UX-15.1 Discovery — Knowledge Experience Consolidation & Export Center

**Discovery only — no code, no migrations, no RLS changes, no Knowledge
Exchange framework changes.** Audits every Export/Save As/Download
button, every Import dialog, every object action menu, every detail
page, and every list page across the six knowledge object types (Note,
Conversation, Knowledge Node, Document, Asset, Knowledge Collection),
grounded in the actual UI code as it exists after UX-14.5.12, not
assumptions about what "should" be there.

## 1. Method

Read every detail page (`NoteDetailPage`, `ChatPage`, `KnowledgeNodeDetailPage`,
`DocumentDetailPage`, `ImageReaderPage`, `KnowledgeCollectionDetailPage`),
every list page (`NotesPage`, `LibraryPage`, `KnowledgeExplorerPage`,
ChatPage's `ConversationList`, `KnowledgeCollectionsPage`), every card
component (`NoteCard`, `DocumentCard`, `ImageCard`), and every file
under `src/modules/knowledge-exchange/components/` and
`src/modules/export/components/`. Every finding below is a direct
grep/read result, not an inference — file:line references are given
where useful.

## 2. Headline findings

1. **Two object types never got the unified Save As experience.**
   UX-14.5.11 wired `KnowledgeExportDialog` into `NoteDetailPage`,
   `KnowledgeNodeDetailPage`, and `KnowledgeCollectionDetailPage`, and
   UX-14.5.12 added it to `ChatPage`. **`DocumentDetailPage` and
   `ImageReaderPage` still have the old, single-format "Export" button**
   (`documentPackageFilename`/`assetPackageFilename` → `.zip`, direct
   `downloadBinaryFile` call, no dialog, no format choice) — a user can
   Save As a Note, Conversation, Knowledge Node, or Collection as
   PDF/Markdown/Word, but not a Document or an Asset. This is the
   single biggest functional gap the task's "identical whether Note/
   Conversation/Knowledge Node/Document/Asset/Collection" goal needs to
   close.
2. **Import entry points are scattered across three unrelated pages**,
   with no single "Import" or "Knowledge Exchange" hub:
   `NotesPage` → Import Note; `LibraryPage` → Import Document, Import
   Asset (one page, two separate dialogs, two separate buttons); `KnowledgeExplorerPage`
   → Import Node, Import Link, Import Collection, Import Conversation
   (four dialogs on one page). A user has to already know which page
   owns which import type. Nothing on any of these pages hints that the
   other two exist.
3. **Button wording for the same action is inconsistent across those
   same three pages.** `NotesPage`/`LibraryPage` both use a bare
   `Import` label (`NotesPage.tsx:66`, `LibraryPage.tsx:117,176` —
   twice on the same page, once per tab) relying on page context to
   disambiguate; `KnowledgeExplorerPage` instead spells out the type in
   every label (`Import Node`/`Import Link`/`Import Collection`/`Import
   Conversation`, lines 116-128). Two different naming conventions for
   the identical underlying action.
4. **`KnowledgeNodeDetailPage` has three different things labeled
   "Export" on one page**: (a) `Export knowledge package`
   (`KnowledgeNodeDetailPage.tsx:121` — Knowledge Actions v1's older,
   markdown-only briefing download, kept deliberately unchanged by
   UX-14.5.11), (b) `Save As…` (line 130 — the new NOVA
   Package/PDF/Markdown/Word dialog for the node itself), and (c) a
   small inline `Export` button per related-concept row (line 181 —
   exports a single relationship as a Knowledge Link package). Three
   distinct exports, three distinct outputs, one word.
5. **No object's list-level card menu exposes Export/Save As/Add to
   Collection at all.** `NoteCard`'s dropdown has only Delete
   (`NoteCard.tsx:78`); `DocumentCard`'s has View details/Read/Chat/
   Summarize/Save as Notes/Rename/Reprocess/Delete but no Export/Save
   As/Add to Collection (`DocumentCard.tsx:130-176`); `ImageCard`'s has
   Ask NOVA/Save as Notes/Rename/Delete, same gap
   (`ImageCard.tsx:131-143`); `ConversationList`'s item menu has Rename/
   Pin/Favorite/Duplicate/Archive/Delete, same gap
   (`ConversationList.tsx:124-145`). Every one of these actions exists
   only once a user has already navigated into the object's own detail
   page — there is no "Export this from the list" path for any object
   type, which directly explains why the task names "actions users are
   unlikely to discover" as a concern.
6. **"Ask AI" exists for 2 of 6 object types, worded two different
   ways, and is missing entirely from the other 4.** `DocumentCard`/
   `DocumentDetailPage` link to `/chat?documentId=` labeled "Chat with
   NOVA"; `ImageReaderPage` instead calls `createConversationWithQuery`
   labeled "Ask NOVA about this image" (a different mechanism —
   deep-link vs. programmatic conversation creation — and a different
   verb). `NoteDetailPage`, `KnowledgeNodeDetailPage`, and
   `KnowledgeCollectionDetailPage` have no "start a conversation about
   this object" entry point at all today.
7. **"Share" has no real action anywhere in the app.** A repo-wide
   search for a `Share` button/label found nothing. Sharing today is
   entirely implicit — an object becomes visible to a workspace by
   having a non-null `workspace_id`, surfaced passively via
   `SharingBadge`/`OwnershipLine` on a few detail pages (Notes,
   Conversations) — but there is no user-initiated "share this" action
   to standardize. The task's target action list names `Share` as one
   of nine actions; this phase cannot invent a new sharing capability
   (out of scope — "Do NOT introduce new backend services"), so the
   unified action model can only surface the *existing* passive
   sharing indicator consistently, not add a new action.
8. **Seven Import dialogs and one Export dialog each hand-roll an
   identical native `<dialog>` shell** (`showModal()`/`close()`/
   reset-on-reopen effect, copy-pasted per file — confirmed by grepping
   `showModal()` across all eight files in
   `knowledge-exchange/components/` + `export/components/`). The
   *visual* result is consistent today only because each new dialog was
   built by copying the previous one — there is no shared `Dialog`
   primitive underneath. Any future drift (a new file copied
   incorrectly) has no structural guard against it.
9. **File-naming convention differs by which path an object's export
   took.** The four objects wired into `KnowledgeExportDialog` (Note/
   Knowledge Node/Collection/Conversation) present a `.nova` filename
   for their "NOVA Package" choice (`exportFilename(title, 'nova')`,
   the same helper every one of those four call sites uses) — but
   Documents and Assets, still on the old single-button path, download
   as `documentPackageFilename(...)`/`assetPackageFilename(...)`, which
   produce `.zip`, never `.nova`. A user who has learned "NOVA Package
   files end in `.nova`" from Notes will find Document/Asset exports
   still end in `.zip`.
10. **No icon system exists anywhere in the shared UI layer.** Neither
    `Button.tsx` nor `DropdownMenu.tsx` accepts an `icon` prop, and no
    button/menu-item anywhere in the audited pages renders one — every
    action today is a plain text label. This is actually *consistent*
    (100% text-only, zero icons, app-wide) rather than a gap; the risk
    is Phase 4 "unify icons" being read as "add icons," which would be
    a new design-system decision this consolidation phase should not
    make unilaterally. Recommendation in §5.

(Note/Conversation/Knowledge Node/Document/Asset — a Collection can't
be a member of itself). Knowledge Nodes have no delete action anywhere
in the app — see §4's note on why that's an intentional gap, not one
to fix here.

## 4. What constitutes "the same interaction model" here

Given the findings above, the task's target action list needs three
adjustments before it can be applied literally to this codebase:

- **`Share`**: no backend capability exists to build a real share
  action without violating "do not introduce new backend services."
  Recommend rendering the existing passive sharing indicator
  (`SharingBadge`/`OwnershipLine`, already built in UX-14) consistently
  on every detail page that has a `workspace_id`, rather than adding a
  button that does nothing new.
- **`Ask AI`**: only applicable to objects that can meaningfully seed a
  conversation (Document, Asset, Note, Knowledge Node, Collection — not
  Conversation itself, since a conversation *is* the AI interaction).
  Should converge on one mechanism (`createConversationWithQuery`,
  already used by Assets) and one label, rather than Document's
  separate `?documentId=` deep-link convention.
- **`Delete`**: Knowledge Nodes have no delete action today at all
  (nodes are derived/canonical, resolved by `resolveCanonicalNode` —
  deleting one could orphan evidence links). Recommend leaving this
  gap as an intentional exclusion (the task says "only include actions
  applicable to that object"), not adding delete for nodes as a side
  effect of this phase.

## 5. Recommendations for Phase 2/3/4 (not yet implemented)

- **Phase 2 (action model)**: extend `KnowledgeExportDialog`'s Save As
  pattern to `DocumentDetailPage` and `ImageReaderPage`, replacing their
  old single-button `.zip`-only Export with the same dialog every other
  object type uses — this is the one functional gap that must close for
  "identical whether Note/Conversation/Knowledge Node/Document/Asset/
  Collection" to be true. Add `AddToCollectionButton` to
  `KnowledgeNodeDetailPage`. Converge "Ask AI" onto one mechanism/label
  and add it to Note/Knowledge Node/Collection detail pages.
- **Phase 3 (Export Center)**: a single new page (e.g.
  `/knowledge/export`) is the natural answer to finding #2 — one place
  that lists exportable objects across all six types and launches the
  same `KnowledgeExportDialog` already built, rather than requiring a
  user to know which of three pages owns which Import dialog. Existing
  per-page Import buttons can remain (removing them would be its own
  regression), but the Export Center should also surface Import as a
  single, discoverable entry point spanning all package types.
- **Phase 4 (consistency)**: extract one shared `Dialog` shell (native
  `<dialog>` + `showModal`/`close`/reset-on-reopen) that every existing
  Import dialog and `KnowledgeExportDialog` adopts, removing the 8x
  copy-pasted boilerplate found in §2.8 — this is a pure UI refactor,
  touches no package/import/export logic. Standardize the bare
  `Import`-button convention (`NotesPage`/`LibraryPage`) vs. the
  type-labeled convention (`KnowledgeExplorerPage`) on one wording rule.
  Consolidate `KnowledgeNodeDetailPage`'s three "Export"-labeled actions
  under distinct, non-colliding labels. Leave iconography as text-only
  (§2.10) rather than introducing a partial icon set.

## 6. Explicitly out of scope (per the task's own constraints)

No change to `PackageVersion`/`PackageValidator`/`PackageExporter`/
`PackageImporter`, no change to any package format
(`*PackageTypes.ts`), no change to any `export<Type>Package`/
`import<Type>Package`/`validate<Type>Package` function's logic, no
migrations, no RLS changes, no new backend/edge functions. Every
recommendation above is UI-only: which existing dialog/button a page
renders, and how it's labeled — never what data crosses the wire.
