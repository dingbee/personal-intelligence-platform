# UX-14.5 — Knowledge Exchange & Collaboration Infrastructure: Architecture Discovery

**Status: discovery only. No schema changes, no RLS changes, no code in this document or the commit that adds it.**

Goal per the brief: design the foundation that lets NOVA PIP evolve from a
personal intelligence platform into a trusted intelligence exchange
platform, without breaking any existing single-user account. This document
is grounded directly in the current schema (27 migrations, `0001_init.sql`
through `0027_ai_memory_confidence.sql`) and the current client
architecture (`src/modules/auth`, `src/modules/workspaces`,
`src/modules/notes`, `src/modules/knowledge-intelligence`), not
assumptions about what a typical multi-tenant app looks like.

A naming note up front: `docs/ux-14-strategic-roadmap.md` originally used
"UX-14.5" for a different, narrower idea ("Knowledge Intelligence
Expansion" — bounded pattern/trend detection). This document uses the
numbering as redirected in this session's instructions — UX-14.5 is now
Collaboration Infrastructure. The roadmap doc's old 14.5 entry should be
renumbered or folded into 14.6 when this work is actually scheduled; not
done here since it's a documentation-only side effect, not part of this
discovery's scope.

## 1. Current ownership model

### 1.1 The pattern, without exception

Every single content table in this schema follows one pattern, with zero
deviation across 27 migrations:

```sql
user_id uuid not null references auth.users (id) on delete cascade
```

```sql
create policy "Users manage their own <thing>"
  on public.<thing> for all
  using (auth.uid() = user_id)
  with check (auth.uid() = user_id);
```

This exact shape (or the `owner_id` variant on `assets`) appears on:
`workspaces`, `documents`, `collections`, `tags`, `notes`, `knowledge_links`,
`ai_memory`, `conversations`, `messages`, `ai_requests`,
`provider_overrides`, `reading_progress`, `highlights`,
`chapter_summaries`, `flashcards`, `knowledge_nodes`,
`knowledge_node_sources`, `workspace_objectives`, `assets`,
`knowledge_collections`. Two child/join tables (`document_tags`,
`note_tags`) have no `user_id` column of their own; their RLS instead does
`EXISTS (select 1 from <parent> where <parent>.id = <child>.<parent>_id and
<parent>.user_id = auth.uid())` — a subquery-based check against the
parent's owner. This is the one existing precedent in the codebase for
"access determined by a relationship, not a direct column," and it is
architecturally relevant below (§4, §7): a membership check for a shared
space can be written the same way, substituting a membership table for the
parent-ownership subquery.

Every policy in the schema is a single equality check
(`auth.uid() = user_id`). There is no OR-clause, no role check, no
subquery-against-a-membership-table anywhere. **Introducing the first
shared object is the first time this schema will need a compound RLS
condition.** That is a meaningful precedent-setting step on its own,
independent of how large the eventual collaboration model gets.

### 1.2 `workspace_id` is not an authorization boundary

Nearly every content table also carries a nullable `workspace_id uuid
references public.workspaces (id) on delete set null`. It is tempting to
assume "workspace" is already the sharing unit. It is not:

- RLS policies never reference `workspace_id`. Access is decided purely by
  `user_id`. A row with `workspace_id = X` is visible only to its owner,
  identically to a row with `workspace_id = null`.
- `workspaces` itself is single-owner: `user_id uuid not null`, one blanket
  RLS policy, no membership table exists.
- "Current workspace" is not even server state. `WorkspaceProvider.tsx`
  keeps `currentWorkspaceId` in a `localStorage` key namespaced by user id
  (`current-workspace:${userId}`) — purely a client-side filter
  preference. The server has no concept of "the workspace I'm acting in
  right now."

So today, `workspace_id` is an **organizational tag**, not a security
boundary. This distinction matters a great deal for §3 and §7: whichever
container becomes shareable, workspace_id's current nullable, non-enforced
nature has to be preserved for users who never opt in.

### 1.3 Authentication assumptions

Standard Supabase Auth (`AuthContext.tsx`): email+password, magic link
(OTP), password reset — one `auth.users` row per person, `profiles`
1:1-keyed to it (`0001_init.sql`). No organization/team identity exists
anywhere in the auth layer, no invitations table, no concept of a
service/system principal.

Both edge functions (`supabase/functions/ai-chat`,
`supabase/functions/provider-availability`) run under the **calling user's
own JWT** — neither uses a Supabase service-role key. That means every
write NOVA's AI ever makes (a generated note, a knowledge node, a
generation_metadata blob) is written and RLS-checked as an ordinary write
by that human user. **The AI has no distinct identity or permission
boundary in the database today** — it is indistinguishable, at the RLS
layer, from the human clicking buttons. It's only distinguished
after the fact, by convention, via the `creationMethod`/
`generation_metadata` provenance fields this session's UX-14.4.x work
extended. This is the load-bearing fact for §4's AI-agent-permissions
recommendation.

### 1.4 Storage is a separate, coarser boundary

The `documents` and `assets` storage buckets are private, with RLS on
`storage.objects` keyed to folder prefix: `(storage.foldername(name))[1] =
auth.uid()::text`. This is coarser than table RLS — it can't express
per-object sharing at all, only "this whole folder is yours." Any
collaboration model that needs a shared file (not just a shared row of
metadata) has to solve this separately; it doesn't fall out of a
row-level-sharing design for free (see §7 risks).

### 1.5 Tables affected by future sharing (complete list)

Every table in §1.1's list is a candidate, since every one is scoped by
`user_id` alone today. Ranked by how central they are to a first
collaboration slice:

- **Core content**: `documents`, `notes`, `collections`,
  `knowledge_collections`, `conversations`, `messages`, `assets`.
- **Connective tissue**: `knowledge_links`, `knowledge_nodes`,
  `knowledge_node_sources`.
- **Derived/AI content**: `chapter_summaries`, `flashcards`, `ai_memory`.
- **Per-user preference, unlikely to ever be shared**: `tags`,
  `provider_overrides`, `workspace_objectives`, `reading_progress`,
  `ai_requests` (this one specifically should probably stay
  strictly-personal even inside a shared space — see §6).

## 2. Knowledge Space architecture — can existing containers unify?

### 2.1 The two candidate containers

**`workspaces`** — the coarsest existing grouping. Almost every content
table already carries an optional `workspace_id`. Pro: minimal new
plumbing needed to make "everything in this workspace" resolvable, since
the column already exists everywhere. Con: today it's just a nullable tag,
not reliably populated — a document created before a workspace existed,
or created with no workspace selected, has `workspace_id = null` and
would not be part of any space-based sharing by definition.

**`knowledge_collections`** (`0026_knowledge_collections.sql`) — the
newer, more interesting candidate. Its own migration comment describes it
exactly as the brief's "unified container" idea: *"a curated set of items
spanning any mix of documents/notes/conversations/assets/concepts."* It's
deliberately a thin identity/metadata row; membership is expressed as
ordinary `knowledge_links` rows: `(source_type='knowledge_collection',
source_id=<collection id>, target_type=<'document'|'note'|'conversation'|
'asset'|'knowledge_node'>, target_id=<item id>)`. This already is a
cross-type container, by construction, today — for a single user.

### 2.2 Why neither is a container yet, in the access-control sense

Putting a note into a `knowledge_collections` row (or a `workspace_id`)
does **not** currently grant anyone else access to that note — the note's
own RLS policy still checks the note's own `user_id`. A "Knowledge Space"
is only a real container, in the sense the brief means, once *membership
in the container* is itself checked by the RLS of every item inside it.
That's new authorization plumbing regardless of which existing table
becomes the anchor — neither `workspaces` nor `knowledge_collections`
gets this "for free" from its current shape.

### 2.3 Recommendation

Use **`workspace_id`** as the sharable unit for a first Team Space model,
not `knowledge_collections`, for three reasons:

1. It's already threaded through nearly every content table (§1.5),
   whereas collection membership is a link-table hop away and today only
   populated for whatever a user has manually curated into a collection —
   most documents/conversations are never in one.
2. It matches the app's existing primary mental model: `WorkspacePresence`,
   `WorkspaceSwitcher`, and the Hub already frame "workspace" as "the
   project/context I'm working in." Users already think in workspaces;
   asking them to additionally think in "spaces" as a second, overlapping
   concept is a UX cost with no clear payoff.
3. `knowledge_collections` keeps its current role unchanged and useful: a
   **curated subset within a space** (e.g. "everything about the Q3
   launch," cutting across document/note/conversation types) — it doesn't
   need to become the access-control boundary itself to stay valuable.
   Once workspace membership exists, a collection scoped to that
   workspace inherits the space's membership for free (its own RLS is
   already `workspace_id`-nullable in the same shape as everything else).

So: **workspace becomes the intelligence container's access boundary;
knowledge_collections stays the curation layer inside it.** No schema
change implied by this recommendation — it's a statement of which
existing column carries the future authorization weight, for §7 to build
on.

## 3. Collaboration models — options and tradeoffs

### Option A — Personal object sharing

Share one object (a note, a collection, a document) with a specific other
user at a specific permission level. Smallest conceivable unit: a new
`object_shares`-shaped table (`source_type, source_id, grantee_user_id,
permission`), and each shared table's RLS gains one OR-clause referencing
it.

- **Pro**: smallest blast radius — one new table, no change to
  `workspaces` at all. Fast to ship, easy to reason about, fully
  reversible (dropping the shares table returns the app to exactly
  today's behavior). Proves the "OR-clause" RLS pattern (§1.1) on a single
  table before it's repeated 14 times.
- **Con**: doesn't scale as *space* collaboration — sharing is per-object,
  so "give my collaborator access to everything in this project" means N
  individual share rows, not one membership grant. No natural home for
  "who's on this team," just a flat list of grants.

### Option B — Team spaces (workspace membership)

`workspaces` gains real membership: a `workspace_members`-shaped table
(`workspace_id, user_id, role`), and every `workspace_id`-scoped table's
RLS gains `OR EXISTS (select 1 from workspace_members where
workspace_id = <row>.workspace_id and user_id = auth.uid())`.

- **Pro**: matches the app's existing organizational unit (§2.3). One
  consistent pattern applied uniformly across ~14 tables, rather than N
  bespoke share grants.
- **Con**: real migration surface — every one of those ~14 RLS policies
  needs the same coordinated rewrite, not an additive-only change (the
  policy body itself changes, even though it changes in a backward
  -compatible way — see §7.2). Requires resolving the "workspace_id IS
  NULL means what?" ambiguity (§7 risk) before it ships, since that
  currently-harmless null becomes a real design fork the moment a
  workspace can have more than one member.

### Option C — Organization spaces

A tier above workspace: an `organizations`/`organization_members` layer,
workspaces gain an optional `organization_id`, org-level roles cascade
down to the workspaces inside them.

- **Pro**: matches an eventual "team of teams" / enterprise shape.
- **Con**: two authorization layers designed and tested at once (org role
  → workspace role inheritance rules), with **zero present evidence of
  demand** — there is no team/org concept anywhere in the current schema
  or UI, not even a placeholder. Building this ahead of a single validated
  team use case is exactly the "speculative architecture" this brief asks
  to avoid.

### Option D — Intelligence packages (snapshot exchange)

No live shared ownership at all — export a self-contained bundle
(notes + documents + graph nodes, in the spirit of the "Export Package"
Knowledge Action already built in the UX-13.7 era) and let a recipient
import it into their own single-owner account. No RLS change required,
since it's a point-in-time copy.

- **Pro**: zero authorization-model change, ships fastest, extends a
  feature direction that already exists.
- **Con**: not real collaboration — no live sync, no shared editing, no
  "we're both looking at the same note." The recipient's copy diverges
  immediately after import.

### Recommendation

**B (Team spaces) is the right answer to "trusted intelligence exchange
platform"** — it's the only option that gives collaborators a persistent,
living shared context rather than either a flat pile of individual grants
(A) or a one-time copy (D), and it doesn't take on unvalidated
organizational complexity (C).

But **ship A or D first, as a deliberately smaller proof**, before taking
on B's full ~14-table RLS migration. Nothing in this schema has ever had a
compound RLS condition; proving that pattern is safe (existing users see
zero change, the OR-clause genuinely doesn't leak rows) on one narrow
table is cheap insurance before repeating it across the whole content
model. This mirrors how this codebase has always proven a pattern narrow
before generalizing it — e.g. `knowledge_node_identity` (0016) landed
before it was wired through the extraction pipeline generally.

## 4. Authorization model

### 4.1 Roles

Recommend a minimal three-role set to start: **owner, editor, viewer.**
Not a granular permission-bit matrix (separate read/write/comment/share/
delete flags). Reasoning: every RLS policy in this schema today is a
single boolean check (yours or not) — there is no existing precedent for
fine-grained permissions anywhere in the app, and inventing a permission
matrix ahead of a second real differentiated need is speculative. Three
roles is enough to answer every question §5–§7 raise (can this person
edit? can they manage membership?) without pre-building machinery nothing
yet asks for.

### 4.2 Ownership transfer

Transfer of a **space's** ownership (who's the `owner` role on a
workspace) should be a distinct operation from anything touching content
rows. Content should keep being attributed to its original creator via
the existing `user_id` column — that's provenance, not current ownership,
and this session's UX-14.4.x work (`creationMethod`, `withArtifactKind`)
was built specifically to make that provenance trustworthy. Repurposing
`user_id` to mean "current owner of this row" (so it could be reassigned
on transfer) would destroy that signal. Keep them as two different
questions: "who authored this" (`user_id`, never changes) vs. "who
administers this space" (the membership/role table, can change).

### 4.3 AI agent permissions

Recommend the AI continues to have **no distinct identity or elevated
permission** — it acts strictly as *the invoking member, scoped to
whatever role that member holds in the space.* Three reasons:

1. No edge function uses a service-role key today (§1.3); introducing one
   so the AI could write with elevated permissions would be the first
   RLS-bypassing pathway anywhere in this codebase — a materially bigger
   trust-boundary change than collaboration itself requires.
2. It preserves the existing, working provenance model —
   `creationMethod: 'ai_generated'` already distinguishes AI-authored
   content without needing a separate principal in the database.
3. It avoids a privilege-escalation-via-chat class of bug: a viewer-role
   member asking NOVA to "create a note" should get exactly the outcome
   they'd get clicking the UI themselves — refused, or created as
   personal-only outside the space, never silently granted the writing
   permission of a role they don't hold.

## 5. Versioning requirements

Two different things are easy to conflate here, and the current schema
already answers one of them:

- **Content provenance** (where did this come from) — already exists:
  `source_chunk_ids` / `generation_metadata` (0011, nullable JSONB,
  additive) on `chapter_summaries`/`flashcards`/`notes`/`highlights`, plus
  this session's `artifactKind`/`creationMethod` convention layered on
  top. This answers "what produced this," not "what did this look like
  before the last edit."
- **Edit history** (what did this look like before) — **does not exist
  anywhere.** `updated_at` triggers stamp a timestamp only; there is no
  table anywhere that stores a prior value of `content`/`title` after an
  update. Every update in this schema today is destructive.

**Does collaboration need edit history before it ships?** Not uniformly —
it depends on the role:

- **Viewer-only sharing (Option A, or Option B with only the viewer role
  enabled)**: no, this doesn't change today's risk profile. Only the
  owner can ever overwrite content, exactly as today.
- **Shared editing (Option B/C with the editor role active)**: yes, this
  is a real prerequisite, not a nice-to-have. Without version history, a
  second editor's save silently overwrites the first editor's with no
  recovery path — and unlike today (where only the *one* person who can
  ever cause that kind of loss is the owner themselves), this becomes
  data loss inflicted by *someone else*, which is a categorically worse
  experience.

**Recommendation**: sequence version history as a prerequisite for
shipping the **editor** role specifically — it is not a blocker for
shipping viewer-only sharing. If/when it's designed (not now — no schema
work in this document), the natural shape to evaluate is an append-only
`*_versions`-style table per versioned content type, mirroring the
`ai_requests` append-only RLS pattern described next.

## 6. Audit trail requirements

`ai_requests` (0006) is the one genuinely audit-shaped table in the
schema today: RLS grants `select` and `insert` only — no `update`, no
`delete` policy — making it append-only by construction, not by
convention. That's the right precedent to reuse.

Everything else has only `updated_at`; there has never been an
"actor of change" trail separate from `user_id`, because until now
`user_id` and "who changed this" were always the same person by
definition. Once a space has multiple members, that stops being true, and
several real questions currently have no answer:

- Who added or removed a member, and when?
- Who changed someone's role?
- Who deleted a shared object (vs. it simply no longer existing)?
- Who transferred space ownership?

**Recommendation**: one generic, append-only audit table
(`space_audit_log`-shaped: `space_id, actor_user_id, event_type,
target_type, target_id, metadata, created_at`), not a per-table audit
table per content type — this mirrors the choice this schema already made
with `knowledge_links` (one generic polymorphic edge table instead of one
join table per relationship). Scope it to **membership/role/
ownership/deletion events**, deliberately not general content edits —
that's what §5's version history is for, a different concern that needs a
different, content-shaped table.

`ai_requests` itself should very likely stay strictly personal even inside
a shared space (§1.5) — a member's individual AI usage/cost history isn't
naturally something their space-mates should see by default, and nothing
in this discovery requires changing that.

## 7. Migration strategy: single-user RLS → multi-user spaces

### 7.1 The hard constraint

Every existing row and every existing RLS policy must keep working,
unmodified in effect, for a user who never opts into sharing. Concretely,
that means:

### 7.2 Additive, not replacing

New tables only — `workspace_members` (or `object_shares` for Option A),
and the audit table from §6. No existing column gets removed or renamed;
this matches the pattern of every migration in this repo's history so
far (0001–0027 never drop a column). Existing RLS policies gain an
OR-clause rather than being rewritten from scratch:

```
using (auth.uid() = user_id OR <space-membership check>)
```

A `user_id`-owned row with no matching membership row continues to
satisfy the policy exactly as it does today — the OR-clause is simply
never true for it. No data backfill is required: `workspace_id` stays
nullable, and existing `NULL` rows are never matched by a membership
check keyed on `workspace_id`.

### 7.3 Sequencing

Prove the pattern on one table before generalizing it. Recommend starting
with `notes` — the smallest, most self-contained content table (its only
child is `note_tags`, already using the EXISTS-subquery pattern this
plan reuses). Ship membership + the single RLS extension for `notes`
alone, verify existing users see zero behavior change and that the new
OR-clause genuinely doesn't leak rows across accounts, *then* repeat the
identical pattern across the other ~13 tables in §1.5's list. This is the
same "prove narrow, then generalize" discipline this session's UX-14.4.x
work used repeatedly (e.g. artifact provenance fields proved on notes
before being treated as a platform-wide convention).

### 7.4 The one ambiguity that must be resolved before Option B ships

Today, `workspace_id IS NULL` means "unfiled" — a harmless default with
no security meaning, since RLS never looks at it. The instant a workspace
becomes shareable, that null takes on a second, very different possible
meaning: "intentionally kept personal, even though I'm a member of a
space." Those two meanings need to be disambiguated as a **product**
decision before B ships, not defaulted by whichever behavior falls out of
the migration's implementation:

- If null always stays personal-only regardless of space membership, a
  user has no way to move existing unfiled content into a space without
  re-assigning it (arguably the safer default — nothing becomes visible
  to anyone without an explicit action).
- If null is treated as "belongs to whichever space is currently active,"
  existing unfiled rows could become visible to space-mates the moment
  their owner joins a space and the client starts writing a
  `workspace_id` — a much larger behavior change to get right.

This document doesn't resolve it — it's flagged because the migration in
§7.3 cannot start until it is.

### 7.5 Client-code impact

Every existing `.eq('user_id', ...)` filter in the API layer
(`src/modules/*/api/*.ts`) keeps working unchanged — RLS makes the filter
redundant-but-harmless for a row the OR-clause also permits, never
broken. New UI (browsing "shared with me," a member list, a role picker)
is additive query code, not a rewrite of the ~40 existing API modules
this engagement has already built.

## 8. What this discovery deliberately does not decide

Per the brief's constraints, none of the following is designed or
implied as a next step by this document — each is a separate, later
discovery once a specific option above is chosen:

- The exact shape/columns of `workspace_members`, `object_shares`, the
  audit table, or any versioning table.
- Any actual RLS policy text.
- Realtime/live-presence (`WorkspacePresence.tsx` is a naming false
  friend worth flagging: it's a personal richer workspace-switcher, not
  multi-user presence; real "who else is viewing this right now" is a
  separate later capability needing Supabase Realtime channels, unrelated
  to the ownership work here).
- Storage-level sharing for `documents`/`assets` buckets — the current
  per-user-folder `storage.objects` policy (§1.4) is coarser than table
  RLS and doesn't fall out of a row-sharing design; it needs its own
  design pass (likely: copy-on-share, rather than trying to express
  per-object storage ACLs).
- Cross-user canonicalization: `knowledge_nodes`'s dedup key is `unique
  (user_id, source_id, node_type, title)` — scoped per user. In a shared
  space, two members' independently-extracted "Q3 Revenue" nodes would
  not merge into one canonical node today; making `resolveCanonicalNode`
  space-aware is a real, separate design change, not a side effect of
  membership RLS.
- Any UI for invitations, role management, or space creation flows.

## 9. Suggested next step

Given §3's recommendation, the smallest concrete next milestone (if and
when this is approved for implementation, separately from this document)
is **Option A — personal object sharing on a single table (`notes`)** —
both because it's the safer proof of the OR-clause RLS pattern in
isolation, and because it's the same table §7.3 already identifies as the
right first mover for the larger Option B migration later. It validates
the sharing UX and the RLS pattern with the smallest possible blast
radius before any workspace-membership schema work begins.
