# UX-14.5.3 — Intelligence Object Access Model

**Status: discovery only. No schema, no migrations, no RLS text, no code
in this document or its commit.**

Third pass in the UX-14.5 series, built directly on:

- `docs/ux-14.5-knowledge-exchange-collaboration-discovery.md` ("Phase 1")
  — surveyed the collaboration space broadly, recommended workspace
  membership (Option B) as the target with per-object sharing (Option A)
  as the safer first proof.
- `docs/ux-14.5.2-identity-workspace-permission-architecture.md`
  ("Phase 2") — designed the target workspace/membership/role model and
  the RLS mechanics: one reusable helper function, an OR-clause added to
  every `workspace_id`-scoped table's policy, applied uniformly across
  the ~14 tables Phase 1 §1.5 enumerated.

This pass exists because "apply the same OR-clause uniformly to every
table" is not actually safe for every table, and the reason why only
becomes visible by reading how NOVA's AI retrieval code actually queries
each table today — not by reading the RLS policies in isolation. That
finding is this document's core contribution; §4 and §5 below are built
around it.

---

## 1. Current objects — what they are, where they live, how the AI reads them

The brief names seven object categories. Two of them ("artifacts",
"collections") aren't literal tables — mapping each name to its real
storage and retrieval path first, since the access model has to be
designed against what's actually there.

| Object | Table(s) | RLS today | Read into AI context by |
|---|---|---|---|
| **Notes** | `notes` | `auth.uid() = user_id` | Not retrieved into chat context automatically today — read directly by the user (Notes pages) and by Save-to-Notes. |
| **Documents** | `documents`, `document_chunks`, `embeddings` | `auth.uid() = user_id` on all three | `retrieveContext` → `match_document_chunks` SQL function (see §4.1 — has its **own** hard-coded `user_id` filter, independent of table RLS) |
| **Memories** | `ai_memory` | `auth.uid() = user_id` | `retrieveMemoryContext` → `listMemories` — a plain `.select('*')` with **no explicit user filter at all**, scoping relies entirely on RLS (see §4.2) |
| **Knowledge nodes** | `knowledge_nodes`, `knowledge_node_sources`, `knowledge_links` | `auth.uid() = user_id` on all three | `retrieveGraphContext` — plain selects, **no explicit user filter**, relies entirely on RLS, gated transitively by the document IDs `retrieveContext` already found |
| **Conversations** | `conversations`, `messages`, `message_embeddings` | `auth.uid() = user_id` | Not cross-retrieved — a conversation's own messages are its own context; `contextTrace`/references surface within it, never across conversations |
| **Artifacts** | Not a table — a `notes` row distinguished by `generation_metadata.artifactKind` (one of 8 kinds: note, briefing, formula, spreadsheet, chart, report, template, knowledge_card — `artifactTypes.ts`) plus `creationMethod` | Inherits `notes`'s RLS exactly — no separate boundary exists or is needed | Same as Notes — an artifact is a note for every access-control purpose |
| **Collections** | `collections` (single-type, documents-only folders) and `knowledge_collections` (cross-type curated set, membership via `knowledge_links` rows) | `auth.uid() = user_id` on both | Not read into AI context directly — used for organization/browsing and as an input to Knowledge Actions (Export Package, Generate Briefing) |

Two findings from this table matter more than they look:

1. **"Artifacts" need no design of their own.** Whatever access model
   `notes` gets, artifacts get for free — there is no separate artifact
   identity in the database, and Phase 1/Phase 2's reasoning about
   `notes` already covers them completely.
2. **Retrieval scoping is inconsistent today, in a way that matters a
   great deal once RLS changes.** Some retrieval paths hard-code their
   own ownership filter; others lean entirely on RLS. §4 is about exactly
   this.

## 2. Sharing boundaries: workspace-level, object-level, or hybrid

### 2.1 Workspace-level only

Every object in a shared workspace becomes visible to every member at
whatever role they hold (Phase 2's model). Simple to reason about, one
RLS pattern, no per-object decisions to make.

- **Con, sharply illustrated by §1's table**: this is exactly the model
  that would make `ai_memory` — a user's personal profile facts, learned
  preferences, and conversation-derived memories — visible to every
  teammate the instant they join a workspace that memory happens to be
  tagged with, because `listMemories` has no per-object opt-in mechanism
  at all today. Workspace-level-only sharing has no way to keep that from
  happening short of moving memories out of the workspace entirely.

### 2.2 Object-level only

Nothing is visible by workspace membership at all; every single note,
document, or memory needs its own explicit share grant (Phase 1's Option
A, generalized to every table).

- **Con**: doesn't deliver what "team knowledge collaboration" actually
  means in practice — a team wanting to build a shared knowledge base
  from documents they all upload would need to individually re-share
  every single document and every concept extracted from it, forever.
  That's not collaboration infrastructure, it's a very manual permission
  system layered under a UI that implies something automatic.

### 2.3 Hybrid — the right shape, and why

**Recommendation: hybrid, with the workspace as the default-visibility
boundary for some object types and a hard opt-out for others, rather than
a per-object toggle everywhere.** Concretely:

- For object types where "if you're on the team, you see it" is the
  entire point (documents uploaded to the space, notes filed into it,
  knowledge extracted from those documents) — **workspace-level
  visibility is correct and is what users will expect.**
- For object types that are inherently about the *individual*, not the
  *project* (memories, and — see §3 — a member's own AI usage/`ai_requests`
  history) — **workspace membership must never be sufficient on its own.**
  These need to stay object-level (in practice: excluded from the
  workspace OR-clause entirely, not merely defaulted off) — see §4.2 and
  §6.

This isn't "hybrid" in the sense of exposing a toggle per object to
users (a UX and implementation surface this discovery isn't proposing).
It's hybrid in the sense that **the boundary rule itself is
type-dependent** — a smaller, more inspectable design than a universal
per-object permission system, and a safer one than a single universal
workspace-level rule.

## 3. What stays personal, what becomes workspace intelligence, what must never auto-share

### 3.1 Stays personal by default (workspace membership never grants access)

- **`ai_memory`** — all three types (`explicit_profile`,
  `learned_preference`, `conversation_memory`) are about the individual
  account, not the project. None of the three names describe something a
  teammate should see just by being in the same workspace.
- **`ai_requests`** — Phase 1 §6 already called this out: a member's own
  AI usage/cost history isn't naturally a teammate's business.
- **`provider_overrides`, `reading_progress`, `workspace_objectives`** —
  per-user preference/state, no collaborative meaning at all (already
  noted in Phase 1 §1.5's ranking).

### 3.2 Becomes workspace intelligence once its container is shared

- **`documents`** (and their `document_chunks`/`embeddings`) — this is
  the clearest, most legitimate "team knowledge" case: a document
  uploaded into a shared workspace is exactly the kind of thing a
  teammate should be able to read and chat about.
- **`knowledge_nodes`/`knowledge_links`** extracted from a shared
  document — §1's retrieval trace shows `retrieveGraphContext` is already
  gated transitively by which documents were retrievable; once a document
  is workspace-visible, the concepts/entities extracted from it becoming
  workspace-visible too is the natural, expected extension, not a new
  category of risk.
- **`notes`** (including artifacts) explicitly filed into a shared
  workspace — a briefing or knowledge card someone chose to save *into*
  the team's workspace is exactly what "sharing my output with the team"
  means. Notes with no workspace (or in a personal-only workspace) stay
  personal under Phase 2 §1.1's model with zero extra logic.
- **`collections`/`knowledge_collections`** scoped to a shared workspace
  — a curated view over the above, inherits their visibility for free
  (Phase 1 §2.3).

### 3.3 Must never share automatically, even inside a shared workspace

This is the sharpest line this document draws, and it's worth stating
as its own rule rather than folding into §3.1: **content that was true of
the person before the workspace existed, or that NOVA inferred about the
person rather than about the project, must never become visible to a
teammate as a side effect of workspace membership.** `ai_memory` is the
concrete case (§4.2), but the rule is the test to apply to any future
object type, not just the one that happens to exist today.

## 4. RLS implications

### 4.1 Documents: retrieval already has its own hard boundary, independent of table RLS

`match_document_chunks` (the pgvector similarity-search SQL function
`retrieveContext` calls via `supabaseVectorStore.query`) is not a bare
`select` — it's a SQL function with `filter_user_id uuid default
auth.uid()` and an explicit `where document_chunks.user_id =
filter_user_id` in its body (`0007_search.sql`). This means: **even
after `documents`/`document_chunks`'s table-level RLS gains Phase 2's
workspace OR-clause, this function would keep returning only the
caller's own chunks, unchanged, until the function itself is also
updated** (e.g. a new `filter_workspace_id` parameter, following the
same pattern the function already added once before for
document/workspace scoping in `0007_search.sql`). This is a real,
separate piece of follow-up work implied by "documents become shareable"
— it does not fall out of the table RLS change for free, and skipping it
would produce a confusing bug: a document's *metadata row* becomes
visible to teammates (able to see it exists, open it) while chat
retrieval over its *content* silently keeps ignoring it for anyone but
its uploader.

### 4.2 Memories and knowledge nodes: retrieval has no boundary of its own — it inherits whatever RLS says, automatically

`retrieveMemoryContext` → `listMemories` and `retrieveGraphContext` both
issue **plain `.select()` calls with no explicit `user_id` filter in the
client code at all** — both files say so directly in their own comments
("userId isn't used in the query — RLS already scopes ai_memory to
auth.uid()" / "RLS already scopes every table here to auth.uid()"). This
was a completely reasonable thing to write in a single-user schema: RLS
was the only boundary that could exist, so relying on it was simply
correct and non-redundant.

**This is exactly the sentence that stops being true the moment Phase
2's OR-clause is applied.** If `ai_memory`'s RLS policy is extended the
same way every other table's is — `auth.uid() = user_id OR
<workspace-membership check>` — then `listMemories`'s bare `.select('*')`
would, with no application code change whatsoever, start returning every
workspace member's personal memories to every other member, and
`retrieveMemoryContext` would start silently injecting them into NOVA's
system prompt for anyone chatting in that workspace. **This is not a
hypothetical edge case; it is the literal, direct consequence of
Phase 2 §4.3's migration sequencing ("repeat identically for the
remaining ~13 tables") applied to `ai_memory` without modification.**

### 4.3 The correction this implies for Phase 2's migration plan

Phase 2 §4.3 treated the RLS extension as one repeatable pattern applied
uniformly to Phase 1 §1.5's table list. That list needs to be split, and
the split needs to happen **before** any implementation, not discovered
by an incident afterward:

- **Tables where the uniform OR-clause is correct and sufficient**:
  `documents`, `notes`, `note_tags`, `knowledge_links`, `knowledge_nodes`,
  `knowledge_node_sources`, `conversations`, `messages`, `assets`,
  `knowledge_collections` — content whose whole purpose, once filed into
  a shared workspace, is to be seen by the workspace.
- **Tables that must be explicitly excluded from the uniform pattern**:
  `ai_memory`, `ai_requests`, `provider_overrides`,
  `workspace_objectives`, `reading_progress` — per §3.1/§3.3, these stay
  on the original single-clause policy (`auth.uid() = user_id`, full
  stop) regardless of what the row's `workspace_id` says, because
  workspace membership is never the right test for them.
- **A retrieval-layer, not just RLS-layer, follow-up**: `match_document_
  chunks` needs its own explicit update (§4.1) — the one table-level
  change that is *not* sufficient on its own for its object type to
  actually become usable as shared team knowledge.

## 5. AI behavior in shared spaces

### 5.1 What context NOVA can retrieve in a shared workspace

Given §4's split, the target behavior is straightforward to state
precisely: when a member chats inside a shared workspace, NOVA should be
able to retrieve — document chunks from documents any member uploaded
into that workspace (once §4.1's function update ships), knowledge nodes
extracted from those documents, and notes filed into that workspace by
any member. It should **not** be able to retrieve any teammate's
`ai_memory` rows, regardless of workspace — only the invoking member's
own.

### 5.2 Memory isolation rule

Stated as a single rule so it's checkable independent of implementation
detail: **`retrieveMemoryContext` must only ever surface memories whose
`user_id` is the invoking member, never memories belonging to another
member of the same workspace, no matter how the workspace's role model
evolves.** Per §4.3, the mechanism for this is that `ai_memory`'s RLS
policy is deliberately never extended with a workspace OR-clause — the
existing single-clause policy already guarantees this rule by
construction, and the correct action for this table is to leave it alone
while every other table's policy changes around it.

This doesn't foreclose an *explicit*, future "share this specific
memory with my team" feature (Phase 1's Option A shape, applied to one
memory row) — that's a deliberate, visible, one-object action a user
takes, categorically different from an ambient side effect of joining a
workspace.

### 5.3 Knowledge retrieval boundaries

`retrieveGraphContext`'s current transitive gating (only returns nodes
sourced from documents the vector search already found) means it needs
no independent fix the way `ai_memory` does — once §4.1's document-
retrieval update ships and correctly includes workspace-shared
documents, the knowledge-graph context correctly follows along, because
it was already deriving its boundary from documents rather than
maintaining its own. This is the one retrieval path in the app where
"apply the same pattern as documents" is actually the right instruction,
precisely because it has no independent scoping logic of its own to
conflict with the change.

## 6. Recommendation: the smallest architecture

Combining this pass with Phase 1/Phase 2's conclusions:

1. **Object taxonomy is two-valued, not per-object configurable.** Every
   table falls into exactly one of two buckets — "extends with the
   workspace-membership OR-clause" (§4.3's first list) or "stays
   single-clause, permanently" (§4.3's second list). No per-row or
   per-object sharing flag is needed for the workspace-collaboration
   case; that keeps the RLS design exactly as uniform as Phase 2 already
   proposed, just applied to the correct subset of tables rather than
   all of them.
2. **`ai_memory` is architecturally excluded from workspace sharing, not
   merely defaulted private.** This is a permanent design decision, not
   a v1 gap to close later — a future "share one memory" feature (§5.2)
   is additive on top (Phase 1 Option A's per-object share shape), never
   a loosening of `ai_memory`'s own workspace-level RLS.
3. **Document retrieval needs one explicit, scoped follow-up**
   (`match_document_chunks` gaining workspace-aware filtering, §4.1) as
   part of the same unit of work that extends `documents`' table RLS —
   the two must ship together, or a shared document becomes visible in
   the UI while invisible to chat, which is a confusing partial state
   worse than shipping neither yet.
4. **Knowledge-graph retrieval needs no independent change** — it
   inherits correctness from the document-retrieval fix by construction
   (§5.3).
5. **Artifacts and collections need no design of their own** — they
   inherit `notes`'s and `knowledge_collections`'s rules exactly (§1).
6. **This scales to enterprise without rework**, for the same reason
   Phase 2 §1.3 gave for the workspace model itself: the two-bucket
   taxonomy in point 1 is a property of the *object type*, not of
   workspace cardinality or an organization layer above it. Whether a
   workspace has one member, ten, or is one of many under a future
   organization, `ai_memory` stays excluded and `documents` stays
   included, unconditionally — nothing about adding an org tier requires
   re-deciding which bucket any table belongs to.

The reason this counts as the smallest safe architecture: it adds
exactly one new idea to Phase 1/Phase 2's design — a fixed, closed
classification of every existing table into "shareable via workspace" or
"never shareable via workspace" — discovered by tracing actual retrieval
code rather than assumed from table shape, and it prevents a real,
concrete privacy defect (teammates' personal memories leaking into each
other's chat context) that a naive uniform rollout of Phase 2's own plan
would otherwise introduce silently.

## 7. Explicitly out of scope

No schema, no RLS text, no change to `match_document_chunks` or any
other SQL function, no `retrieveMemoryContext`/`retrieveGraphContext`
code changes, no per-object share UI, no organization-tier design. This
document's job was narrower: given Phase 1 and Phase 2's target
architecture, determine which existing tables the workspace-sharing
mechanism should and should not ever apply to, grounded in what the AI
retrieval code actually does today rather than what the table schema
implies in isolation. The next step, if approved, remains Phase 1 §9's
identified slice (personal sharing proven on `notes`) — unaffected by
this document's findings, since `notes` sits squarely in the "extends
with the OR-clause" bucket.
