# UX-14.5.4 — Collaboration Implementation Blueprint

**Status: discovery/architecture only. No schema, no migrations, no RLS
text, no code in this document or its commit.**

This is the synthesis document the three prior UX-14.5 discovery passes
were building toward — not new investigation, but a decision-ready
blueprint that resolves the open questions those three left open and
turns their findings into an implementation-ready contract. It is
grounded in, and does not repeat the reasoning of, its three inputs:

- `docs/ux-14.5-knowledge-exchange-collaboration-discovery.md` ("Doc 1")
- `docs/ux-14.5.2-identity-workspace-permission-architecture.md` ("Doc 2")
- `docs/ux-14.5.3-intelligence-object-access-model.md` ("Doc 3")

Doc 3's finding is why this blueprint exists as a fourth pass rather than
implementation starting directly after Doc 2: Doc 2 proposed a uniform
RLS rollout across every `workspace_id`-scoped table; Doc 3 found, by
reading the actual retrieval code, that a uniform rollout would silently
leak personal `ai_memory` content into shared-workspace chat context.
Nothing about the workspace/membership/role model itself needed to
change — the object-level exceptions did. This document is where that
correction becomes the actual contract implementation will follow.

---

## 1. Final collaboration architecture decision

### 1.1 The chain, resolved

```
User
 ↓
Workspace                  — unchanged table, no `type` column (Doc 2 §1.1)
 ↓
Workspace Membership       — new table; owner is a membership row, not a
 ↓                           special case on workspaces.user_id (Doc 2 §2.2)
Workspace Objects
(notes, documents, knowledge nodes/links, conversations, artifacts)
```

**Personal workspace remains the default, permanently — not a bootstrap
state that gets migrated away.** Under Doc 2 §1.1's model, a workspace
with exactly one membership row (its creator, role `owner`) *is* what
"personal workspace" means; there's no second table, no separate code
path, no data migration the moment sharing starts. A workspace becomes a
team workspace the instant a second membership row exists, and stops
being one the instant it doesn't — the same row, the same RLS policy,
the same everything, differing only in how many members currently
satisfy the membership check.

**No parallel "team app."** Every existing page (Library, Notes, Chat,
Knowledge Explorer, the Hub) keeps operating on the same
`workspace_id`-scoped queries it already runs. The only things
collaboration adds are: (a) more rows can now satisfy a given RLS check
if a second member exists, and (b) new UI surfaces for managing that
membership (an invite flow, a member list, a role picker) — genuinely
new screens, but not a new application shell or a second query layer
running alongside the existing one.

**No enterprise layer yet.** Per Doc 1 §3 (Option C) and Doc 2 §1.3: an
organization tier above workspace is structurally compatible with this
model later (one more optional parent, not a redesign) but is not
designed here because nothing in the current app validates a need for
it.

### 1.2 Which objects become shareable — the final answer

This was Doc 3's central question, and its answer is now final, not
provisional (§3 makes it a definitive table):

- **Shareable via workspace membership**: documents, notes (and
  therefore artifacts — Doc 3 §1 established artifacts are `notes` rows,
  not a separate object), knowledge nodes, knowledge links, conversations,
  collections/knowledge_collections.
- **Never shareable via workspace membership, under any future
  extension of this model**: `ai_memory`, `ai_requests`,
  `provider_overrides`, `reading_progress`, `workspace_objectives`. These
  stay on the original single-clause RLS policy permanently — this is an
  architectural boundary, not a v1 gap.

## 2. Final data model proposal

Proposed tables only — names and columns to guide implementation
planning, not schema to run. No column list here should be read as final
DDL; it's the minimum additive shape the rest of this blueprint's
reasoning depends on.

### 2.1 `workspaces`

**No structural change required.** The existing table
(`0004_workspaces.sql`: `id, user_id, name, created_at, updated_at`,
plus `archived_at`/`sort_order` from `0017_workspace_management.sql`)
already has everything §1.1's model needs. `user_id` keeps meaning "who
created this workspace" — provenance, never repurposed as "current
owner" (Doc 2 §2.2's explicit rule, restated because it's the one rule
most likely to be violated by a well-intentioned shortcut during
implementation).

### 2.2 `workspace_members`

```
workspace_id   uuid  -> workspaces.id
user_id        uuid  -> auth.users.id
role           text  ('owner' | 'editor' | 'viewer')
status         text  ('invited' | 'active')
invited_by     uuid  -> auth.users.id, nullable (null for the creator's own owner row)
created_at     timestamptz
updated_at     timestamptz
```
unique on `(workspace_id, user_id)`.

**Roles**: owner, editor, viewer — unchanged from Doc 2 §3.1, no fourth
role added here. Doc 2's reasoning stands: every RLS policy in this
schema today is a single boolean, and nothing in this app has ever
needed more than three tiers of "can touch this."

**Ownership transfer**: a role update on an existing membership row
(the new owner's row becomes `role = 'owner'`; the prior owner's row
becomes `role = 'editor'` or is removed, a product decision not an
architectural one) — never a column change on `workspaces` itself (Doc 2
§2.2). Exactly one `owner` role should exist per workspace at a time;
enforcing that (a partial unique index, or an application-level
invariant) is an implementation detail for whichever approach is chosen
when this is built, not decided here.

### 2.3 Workspace invitations: pending rows in `workspace_members`, not a separate table

**Decision: a `workspace_members` row with `status = 'invited'`, not a
parallel `workspace_invitations` table.** Justification:

- Doc 2 §2.3 already reasoned through this and reached the same
  conclusion — restating it here because this blueprint is where the
  decision becomes final rather than a recommendation. A separate
  invitations table needs its own reconciliation step at acceptance time
  (delete the invitation row, insert a membership row) — two tables that
  must stay in sync for one lifecycle, with a real failure mode (a
  crash between the delete and the insert leaves the invitee in neither
  table).
- One row answers "who's connected to this workspace and how" at every
  point in the lifecycle — invited-but-not-yet-accepted and
  active-member are the same question asked at different times, not two
  different questions.
- `invited_by` on the row already carries what a separate invitations
  table would otherwise need to record as its own provenance.
- The only thing a separate table would buy is a natural place to put
  invitation-specific ephemera (a token for an email link, an expiry).
  That's addable later as more nullable columns on `workspace_members`
  itself (an `invite_token`, an `invite_expires_at`) without becoming a
  second table — consistent with Doc 1 §7.2's additive-only migration
  principle.

### 2.4 Audit trail: hybrid, not a single reused table and not a wholesale new one

Doc 1 §6 and Doc 2 §7 already reasoned through this; final decision:

- **Reuse `ai_requests`** for anything the AI does — an AI-invoked
  Workspace Action that writes content logs there exactly the way every
  other AI call already does (Doc 2 §7.2). No change to that table, no
  new event type needed on it.
- **Introduce one new table, `workspace_audit_events`**, for the closed,
  enumerable set of space-administration events Doc 2 §7.1 identified:
  member added, member removed, role changed, ownership transferred,
  workspace deleted. Shape: `(id, workspace_id, actor_user_id,
  event_type, target_user_id, metadata jsonb, created_at)`, RLS modeled
  directly on `ai_requests`'s existing append-only precedent — `select`
  and `insert` policies only, no `update`/`delete` policy, so it's
  append-only by construction rather than by convention (0006's exact
  pattern).
- This is the "hybrid" the brief asked to evaluate: not one generic
  table doing both jobs (content-audit and AI-usage-audit are different
  concerns with different existing homes), and not two entirely separate
  new subsystems (AI usage already has a home; only space-administration
  genuinely lacks one).

## 3. Object access matrix — the security contract

| Object | Shareable? | Why |
|---|---|---|
| `notes` (incl. artifacts) | **Yes** | The clearest "share my output with the team" case; a note filed into a shared workspace is exactly what a user means by that action (Doc 3 §3.2). |
| `documents` | **Yes** | Canonical team-knowledge case — but requires a companion fix to `match_document_chunks` (§4.3 below) or table-level sharing is real while retrieval-level sharing silently isn't (Doc 3 §4.1). |
| `knowledge nodes` | **Yes** | Inherits correctness transitively from documents — `retrieveGraphContext` already derives its boundary from which documents were retrievable, so it needs no independent fix once documents' fix ships (Doc 3 §5.3). |
| `knowledge links` | **Yes** | Same reasoning as knowledge nodes; it's the edge table connecting them. |
| `conversations` (+ `messages`) | **Yes** | A conversation explicitly shared into a workspace is a deliberate, visible act, consistent with every other shareable object here. |
| `ai_memory` | **No — permanently excluded** | Doc 3 §3.1/§4.2's headline finding: `listMemories`/`retrieveMemoryContext` have no explicit user filter of their own and rely entirely on RLS; a uniform OR-clause would silently inject one member's personal profile facts, learned preferences, and conversation-derived memories into every teammate's chat context. This is an architectural boundary, not a default. |
| `reading progress` | **No** | Per-user reading position has no collaborative meaning (Doc 1 §1.5). |
| `provider settings` (`provider_overrides`) | **No** | A member's own AI-provider preference is not project state. |
| `workspace objectives` | **Reconsidered — see note below** | Table name suggests workspace-scoped, but its RLS today is still single-owner (`auth.uid() = user_id`, same as everything else) — see the note immediately following this table. |

**Note on `workspace_objectives`**: this is the one row in the matrix
worth flagging explicitly rather than answering with a bare yes/no. Its
purpose (the Hub's stated goals for a workspace) *reads* like exactly
the kind of thing a team should share — everyone working toward the
same objective should see it. But nothing about it resembles `ai_memory`
or `ai_requests`'s reasons for exclusion (it isn't inferred about an
individual, it isn't usage/cost data). **Recommendation: `workspace_
objectives` belongs in the shareable bucket, not the excluded one** —
its exclusion from Doc 1 §1.5's "unlikely to ever be shared" list should
be read as "no evidence yet either way" rather than "excluded for the
same architectural reason as `ai_memory`." Implementation should treat
it identically to `notes`/`documents` (uniform OR-clause), not identically
to `ai_memory` (permanent exclusion). This is a one-row correction to
Doc 1 §1.5's ranking, made explicit here so it isn't silently
inconsistent with this document's own matrix.

This table **is** the security contract implementation must satisfy:
every table in the "Yes" rows gets the workspace-membership OR-clause;
every table in the "No" rows keeps its original single-clause policy,
unconditionally, regardless of what future role/workspace features ship.

## 4. RLS migration strategy

### 4.1 Two categories, not one universal pattern

Doc 3's finding requires abandoning Doc 2 §4.3's original "repeat
identically across all ~14 tables" instruction. The replacement:

**Workspace-aware objects** (the "Yes" rows in §3): RLS gains the
OR-clause pattern Doc 2 §4.2 already designed — `using (auth.uid() =
user_id OR public.workspace_role(workspace_id, auth.uid()) is not
null)`, via the single reusable `security definer` helper function, with
role-gated write operations (insert/update/delete) additionally checking
the returned role is `editor` or `owner` (Doc 2 §4.4's per-command
policy split, modeled on `ai_requests`'s existing select/insert-only
precedent).

**Personal intelligence objects** (the "No" rows in §3, plus
`workspace_objectives` moved into the "Yes" bucket per §3's note): RLS
stays exactly as it is today — `auth.uid() = user_id`, no OR-clause, no
helper function call, no exception logic. The correct instruction for
these tables is: **do not touch their RLS policy at all.** That's the
entire mechanism that makes Doc 3's exclusion permanent rather than a
default someone could accidentally widen later while "generalizing the
pattern" — there is no generalized step that reaches them, by design.

### 4.2 Why "personal intelligence objects" must never inherit workspace access

Restating Doc 3 §3.3's rule as the operative principle for
implementation: **content that was true of the person before the
workspace existed, or that NOVA inferred about the person rather than
the project, must never become visible to a teammate as a side effect of
workspace membership.** `ai_memory` is the concrete instance; `ai_
requests` and `provider_overrides` satisfy the same rule for different
reasons (usage data and preference data respectively, neither
project-shaped). This is the test to apply to any future object type,
not a closed list to stop updating.

### 4.3 The retrieval-layer follow-up documents can't skip

Doc 3 §4.1's finding, restated as an implementation requirement rather
than an observation: `match_document_chunks` (the pgvector RPC behind
`retrieveContext`) has its own `where document_chunks.user_id =
filter_user_id` clause, hard-coded independent of table RLS, defaulting
to `auth.uid()`. Extending `documents`/`document_chunks`'s table RLS
with the OR-clause is **necessary but not sufficient** for shared
document retrieval to work — the function itself needs a
`filter_workspace_id`-style parameter added (the same pattern
`0007_search.sql` already used once to add workspace-scoping to this
exact function). This must ship in the same unit of work as the
`documents` RLS change; shipping one without the other produces a
document that's visible as a row (teammate can see it exists, open it)
but invisible to chat retrieval over its content — a confusing partial
state, not a safe intermediate one.

## 5. AI intelligence boundary design

This is the section that turns Doc 3's finding into an actual decision
procedure NOVA's retrieval path follows.

### 5.1 The two questions, and how retrieval already answers one of them correctly

*"Summarize our project documents"* and *"tell me my preferences"* are
not distinguished today by intent classification — there is no NLU step
deciding "this is a workspace-knowledge question" vs. "this is a
personal-memory question." They're distinguished by **which retrieval
functions run at all, and what each one is allowed to see**, per
message, unconditionally:

- `retrieveContext` (documents/chunks) and `retrieveGraphContext`
  (knowledge nodes/links) run on every turn — this is what answers "our
  project documents." Once §4.3's fix ships, its boundary is
  workspace-membership-based: it can see any document the current
  workspace's membership grants access to, regardless of which member
  uploaded it.
- `retrieveMemoryContext` (`ai_memory`) also runs on every turn — this is
  what answers "my preferences." Its boundary, per §4.1/§4.2, stays
  single-owner permanently: it can only ever see the *invoking member's
  own* memories, never a teammate's, regardless of workspace.

**Both already run together on every turn today** (`AIService.sendMessage`
composes `retrieveContext` + `retrieveGraphContext` + `retrieveMemoryContext`
into one system prompt) — the boundary isn't "pick the right retrieval
function based on the question," it's "every retrieval function has its
own correctly-scoped boundary, and the union of their outputs answers
whichever question the user actually asked." A workspace question gets a
good answer because the workspace-scoped functions found relevant
content; a personal question gets a good answer because the
user-scoped memory function found relevant content; asking both doesn't
leak the wrong scope into the wrong answer, because each function's
*retrieval* boundary — not the prompt's phrasing — is what's actually
enforced.

### 5.2 The retrieval boundary, stated as one table

| Retrieval path | Source | Scope after collaboration ships |
|---|---|---|
| Vector search (`retrieveContext` → `match_document_chunks`) | `document_chunks`/`embeddings` | Workspace-membership-based (§4.3 fix) — any member can retrieve any workspace document's chunks |
| Knowledge graph (`retrieveGraphContext`) | `knowledge_nodes`/`knowledge_links`/`knowledge_node_sources` | Workspace-membership-based, inherited transitively from which documents the vector search could see (Doc 3 §5.3) — no independent change needed |
| Memory (`retrieveMemoryContext`) | `ai_memory` | **Single-owner, unconditionally** — the invoking member's own memories only, never affected by workspace membership at any point |
| Workspace context (objectives, Hub summaries) | `workspace_objectives` and friends | Workspace-membership-based (per §3's correction) |

### 5.3 What this means for "private intelligence" specifically

Doc 3 §5.2 already stated the isolation rule; this section adds the one
thing not yet said: this design doesn't foreclose a future *explicit*
"share this memory with my team" action (Doc 1's Option A shape, applied
to one `ai_memory` row). That would be a deliberate, visible,
per-object action — categorically different from, and never a
loosening of, the ambient rule that workspace membership alone never
grants memory access. If that feature is ever built, it's additive on
top of this boundary, not a change to it.

## 6. Workspace Action permissions

### 6.1 Current architecture (confirmed against the actual code, not assumed)

```
Action request (chat text)
 ↓
matchWorkspaceAction(text)         — registry.ts, tries each registered
 ↓                                   action's `match` in order, first hit wins
runWorkspaceAction(text, context)  — registry.ts, single dispatch chokepoint
 ↓
action.run(payload, context)       — the matched WorkspaceAction's own logic
```

`WorkspaceActionContext` (`workspace-actions/types.ts`) today carries
`{userId, workspaceId, conversationId, chain}`. `runWorkspaceAction` is
the one place every action's execution passes through — confirmed by
reading `registry.ts` directly, not inferred from the type shape alone.

### 6.2 Permission middleware layer — the target design

```
Action request
 ↓
matchWorkspaceAction(text)              — unchanged, still just pattern matching
 ↓
Permission resolver                     — new: resolveWorkspaceRole(context.workspaceId, context.userId)
 ↓
Workspace role check                    — new: does the matched action's declared
 ↓                                        minimum role satisfy the resolved role?
Capability execution (action.run)       — unchanged, only reached if the check passes
```

The gate belongs in `runWorkspaceAction` itself, not inside each
action's `run` — one chokepoint, one place the check can be verified
correct, rather than four (and growing) independent implementations of
"am I allowed to do this" copy-pasted across action files. This mirrors
Doc 2 §6.1's reasoning exactly, now stated as the concrete function each
piece belongs in.

Each `WorkspaceAction` gains one new declared property — a minimum
required role — read by the gate, not enforced by the action itself.
This is additive to the existing `WorkspaceAction<TPayload>` shape
(`id, match, run`), not a redesign of it.

### 6.3 Role → capability mapping

- **viewer** — read-only. No Workspace Action that creates or modifies
  content should be reachable; a viewer's chat can still answer
  questions (the normal RAG path, which isn't a Workspace Action and
  isn't gated by this layer at all — §5 already established what it can
  see), but "generate a briefing" or "save this" should be refused with
  a clear message, the same way a disabled Save button would refuse it
  in the UI.
- **editor** — create/update/delete shared objects. Both existing
  content-creating actions (Generate Briefing, Save to Notes) require at
  least this role.
- **owner** — everything editor can do, plus workspace administration
  (member/role management) — administration itself is not expressed as
  a Workspace Action at all (it's membership-table CRUD, a different
  surface), so this row exists for completeness rather than because any
  current action needs an owner-only gate.

### 6.4 Why the AI still has no distinct identity

Doc 1 §4.3 and Doc 2 §6.3 already settled this; restated once more
because it's the fact that makes §6.2's gate simple rather than a second
permission system: the gate checks the **human's** resolved role, the
same role a manual UI action would check. The AI was never a separate
principal in the database (no service-role key anywhere,
§1.3 of Doc 1) and this design doesn't introduce one — a viewer asking
NOVA to "save this as a note" fails for the identical reason a viewer
clicking a Save button that isn't rendered for their role would fail.

## 8. Migration safety

**How existing users remain unchanged**: under §1.1/§2.2's model, an
existing workspace needs zero data migration — it already has exactly
the implicit single-member state the new model produces automatically
for a workspace with no `workspace_members` rows (Doc 2 §2.4). No
backfill script, no `workspace_id` reassignment, nothing written for an
account that never shares anything.

**How existing RLS policies evolve**: per §4.1's split, "Yes"-row tables
gain an additional `OR` clause — the original `auth.uid() = user_id`
condition is never removed, only extended, so it continues to be
independently sufficient for exactly the rows it always covered.
"No"-row tables (§3) are not touched at all. No policy is dropped and
recreated with different semantics for existing rows; every change is
strictly additive in effect, not just additive in the sense of "new
tables."

**How rollback works**: because every RLS change is an OR-clause
addition rather than a policy replacement, rollback is dropping the
added clause (or disabling the `workspace_members`-checking helper
function) and every account reverts to exactly today's single-owner
visibility — no data was moved, transformed, or deleted to reach the
shared state, so there's nothing to reconstruct on the way back. The one
piece of rollback that isn't a pure RLS revert is §4.3's retrieval
function change (a new parameter added to `match_document_chunks`) —
rolling that back means removing the parameter, which is safe precisely
because it's additive (a new optional parameter with a default,
following the same shape `0007_search.sql` already used once when this
function last gained a new filter).

## 9. Do Not Build Yet

Explicitly deferred, per every prior discovery pass's consistent
position and this blueprint's own scope:

- **Enterprise organizations** — no validated demand yet (Doc 1 §3
  Option C, Doc 2 §1.3).
- **Billing seats** — no monetization model exists anywhere in this app
  to attach seat-based billing to.
- **Advanced RBAC** (per-object-type permission overrides, custom role
  names, time-boxed roles) — Doc 2 §3.3 already noted these fit inside
  the `role` column's shape later without redesign; not needed until a
  second real differentiated need exists.
- **External guest portals** — this entire blueprint assumes every
  collaborator is an existing `auth.users` account; a guest-access model
  (someone without an account viewing shared content) is a materially
  different auth problem, untouched here.
- **Public sharing links** — no anonymous/unauthenticated access path
  exists or is designed; every access check in this blueprint assumes
  `auth.uid()` is non-null.
- **Document versioning** — Doc 1 §5 already drew the line precisely:
  version history is a prerequisite for the **editor** role specifically
  (concurrent edits need a recovery path), not for the viewer-only
  sharing that Phase 2/3 above ship first. It becomes a real blocker only
  when multi-editor content editing is actually being built, later than
  everything in §7's roadmap.
- **AI autonomous collaboration agents** — nothing in this blueprint
  gives the AI any identity, role, or capability beyond what the
  invoking human already holds (§6.4); an AI that acts on a workspace
  without a human turn initiating it is a different, unaddressed
  problem.

## 10. Summary for implementation planning

The four-document UX-14.5 discovery sequence resolves to one blueprint
with three governing rules implementation must satisfy simultaneously:

1. **One workspace/membership/role model** (Doc 2), where personal is
   the one-member case of team, not a separate structure.
2. **A closed, two-bucket object classification** (§3's matrix, correcting
   Doc 2's originally-uniform RLS plan per Doc 3's finding) — most
   content becomes workspace-shareable; personal intelligence
   (`ai_memory` foremost) never does, by construction, permanently.
3. **A retrieval-layer follow-up that isn't optional** (§4.3) — table
   RLS and retrieval-function scoping are two different things in this
   codebase's actual architecture, and shared-document chat doesn't work
   until both change together.

Phase 1 of §7's roadmap — the membership table, the helper function, and
proving the OR-clause pattern on `notes` alone — is the safe, smallest
next step this entire discovery sequence has been converging on since
Doc 1 §9 first named it. Nothing in this blueprint changes that
starting point; it only makes precise what happens after it.

## 11. UX-14.5 Phase 1 implementation record

Implemented and applied to the live `personal-intelligence-platform`
Supabase project. This section records exactly what shipped, so it's
checkable against §2/§4's design above rather than taken on faith.

### 11.1 Migration created

`supabase/migrations/0028_workspace_members.sql` — the only migration
this phase adds. Applied directly to the production project
(`uzshazetfkjkrdnxwjtl`), matching this repository's established
practice of applying every migration to the live project rather than
maintaining a separate local-only schema. Contents, exactly as §2
proposed:

- `workspace_member_role` enum (`owner`, `editor`, `viewer`) and
  `workspace_member_status` enum (`active`, `pending`, `removed` — the
  status vocabulary this phase's own instructions specified, superseding
  Doc 2 §2.3's earlier `invited`/`active` wording).
- `workspace_members` table: `id, workspace_id, user_id, role, status,
  invited_by, created_at, updated_at`, unique on `(workspace_id,
  user_id)` — §2.2's "one membership per user/workspace pair."
- A partial unique index (`role = 'owner' and status = 'active'`)
  enforcing at most one active owner per workspace.
- A new trigger, `on_workspace_created_add_owner` (via
  `create_workspace_owner_membership()`), firing `after insert on
  workspaces`, that auto-creates the creator's explicit `owner`
  membership row for every workspace created from this migration
  forward — mirroring `handle_new_user`'s existing `auth.users ->
  profiles` auto-provisioning pattern exactly. This is what makes
  "an owner must exist" true by construction for new workspaces; it is
  the one place this phase adds live behavior to an existing table
  (`workspaces`), and it changes nothing visible to the application —
  every existing query against `workspaces` returns exactly what it did
  before.
- **No backfill.** Every workspace that existed before this migration
  has zero `workspace_members` rows, unchanged, per Doc 2 §2.4's
  explicit recommendation and this phase's own "existing users remain

### 11.2 Security primitives added

## 12. UX-14.5 Phase 2 discovery — Note Sharing Design

Discovery only (`docs/ux-14.5.5-note-sharing-design.md`) — no
implementation, no RLS applied. Summary, full detail in that document:

- **Recommended model**: Option A — extend `notes`' existing RLS (plus
  its two child tables, `note_tags`/`note_embeddings`) with
  `has_workspace_role`, per-command, rather than a new dedicated
  `note_permissions` table. The brief's own object chain
  (`workspace_members → Notes`, "roles inherited from workspace
  membership," "do not create a generic permissions framework") rules
  out the dedicated-table option directly, not just by preference.
- **Target per-command RLS**: `select` — owner or viewer-or-above;
  `insert` — unchanged (self-attributed, no membership check needed);
  `update` — owner or editor-or-above; `delete` — owner (note creator)
  or the resolved *workspace* owner specifically (not editor) — "full
  control" is read as workspace-owner authority over every note in the
  workspace, not merely creator-only delete.
- **Required companion fix, found by tracing the code, not assumed**:
  `note_tags`/`note_embeddings`'s own EXISTS-based policies check
  `notes.user_id = auth.uid()` directly today — extending `notes`' own
  policy does not automatically extend to them. The identical structural
  gap Doc 3 found with `match_document_chunks`, found here independently
  in `notes`' child tables — confirming it as a pattern to check for
  every time a table's RLS is extended, not a one-off.
- **A real, pre-existing bug found, not introduced**: `useNote.ts`'s
  `save`/`summarize` mutations call `linkKnownConceptsToSource` with
  `note.user_id` (the note's original owner) rather than the id of
  whoever is actually saving. Harmless today (always the same person);
  the moment an editor other than the owner saves a shared note, the
  resulting `knowledge_node_sources` insert would fail RLS silently
  (the call swallows its own errors), quietly breaking that note's
  contribution to the knowledge graph. Flagged for a required, minimal
  fix in Phase 2's implementation, not fixed in this discovery pass.
- **AI boundary confirmed**: none of `retrieveContext`/
  `retrieveGraphContext`/`retrieveMemoryContext` query `notes` or its
  child tables at all — note sharing has zero code-path overlap with
  NOVA's chat-context retrieval, and `ai_memory`/personal preferences
  are untouched by this design.
- **Application layer**: the Note API and hooks need no structural
  change (they already defer entirely to RLS); `NoteDetailPage.tsx`
  needs role-gating of its Save/Summarize/Delete controls to match the
  RLS table exactly, so the UI never offers a control the database would
  reject. No sharing dialog, invitations, or notifications — explicitly
  out of scope.

Approved and implemented — see §13.

deferred this), which meant a member added via `workspace_members`

### 14.1 Migration created

`supabase/migrations/0030_workspace_membership_management.sql`, applied
to the live project:

- **`workspaces` RLS split into four per-command policies**, matching
  the `notes` pattern from Phase 2: `select` now includes
  `has_workspace_role(id, 'viewer')` (any member can see a workspace
  they belong to) plus a narrower clause so a still-*pending* invitee
  can see the workspace's basic info before accepting — `pending` rows
  don't satisfy `has_workspace_role` at all (it only resolves `status =
  'active'` rows, by design), so this needed its own EXISTS clause.
  `insert` stays creator-only, unchanged. `update`/`delete` extend to
  `has_workspace_role(id, 'owner')` in addition to `auth.uid() =
  user_id` — an explicit workspace owner (not just the row's creator)
  gets the same authority, matching how `notes`' delete policy already
  reads "owner" in Phase 2.
- **`invite_to_workspace(workspace_id, email, role)`** — a
  security-definer RPC, the only way to create an invitation. Re-checks
  `has_workspace_role(..., 'owner')` explicitly inside the function body
  (running as security definer bypasses `workspace_members`' RLS, so
  this check is load-bearing, not redundant). Rejects `role = 'owner'`
  — ownership transfer is out of scope for this phase, and the Phase 1
  partial unique index would reject a second simultaneous active owner
  anyway. Looks up the invitee by email against `public.profiles`
  (never `auth.users` directly). Upserts rather than inserts — the
  `on conflict (workspace_id, user_id) do update ... where status <>
  'active'` guard makes re-inviting someone who declined or was removed
  work (instead of hitting the unique constraint), while re-inviting a
  *currently active* member is a no-op that surfaces as a clear error
  rather than silently changing their role.
- **`respond_to_workspace_invitation(membership_id, accept)`** — a
  second security-definer RPC, the only way an invitee accepts or
  declines their own pending invitation. Deliberately narrow: only ever
  touches `status` (accept) or removes the row (decline), for a row
  that is the caller's own and still pending — never touches `role`, so
  there's no privilege-escalation surface through this path (a plain
  self-service `UPDATE` policy would have needed extra guarding against
  exactly that; the RPC sidesteps the problem instead of guarding
  against it).
- **`list_workspace_members(workspace_id)`** — a third security-definer
  RPC, the member-management page's read path. Bridges `profiles`'
  self-only RLS (needed to show each member's email/display name)
  without loosening it for everyone. Re-checks membership explicitly.
  Synthesizes the implicit owner as a row when a workspace has no
  explicit `workspace_members` entry for its creator — every workspace
  older than the 0028 trigger — so a pre-Phase-1 single-user
  workspace's roster is never empty; that synthetic row's `id` is
  `null` and isn't actionable (no role-change/remove) since it isn't a
  real row.

One policy-name-length check (learned from Phase 2's near-miss) was run
before applying — all four new `workspaces` policy names came in under
Postgres's 63-character `NAMEDATALEN` limit, confirmed before, not
after, this time.

## 17. UX-14.5 Phase 6 discovery — Knowledge Exchange

Discovery only (`docs/ux-14.5.6-knowledge-exchange-discovery.md`) — no
implementation, no schema/migration/RLS/UI changes. **Not yet approved
for implementation.** Summary, full detail and justification in that
document:

- **Framing**: Phases 1–5 solved *live, in-place* collaboration (multiple
  accounts against the *same* row, inside one workspace, via RLS).
  Knowledge Exchange is a different problem — moving intelligence
  *across* the RLS boundary entirely, to an account that may never have
  had access to the source data. No RLS OR-clause can safely express
  "let a stranger's account read my row."
- **Package model**: classified all 12 named object types plus 2 the
  audit surfaced (`extraction_metadata`, `tags`) against the current
  codebase. Transferable: Notes, Documents (with a flagged storage-copy
  caveat — no cross-user storage copy exists anywhere today), Knowledge
  Collections (as a recursive container), Knowledge Nodes (re-resolved,
  never identity-preserved), Knowledge Links (only between two
  already-included endpoints), Assets (same storage caveat as
  Documents). Optionally transferable, document-attached only:
  Flashcards, Highlights, Chapter Summaries — the same "residual gap"
  object class Phase 4 (§15.6) already flagged as never extended to
  workspace RLS at all. Optionally transferable via conversion, not as a
  raw object: Conversations — the existing `SaveConversationDialog`
  precedent already treats "durably preserve a conversation" as
  *becoming a note*, and Phase 6 should follow that same product
  pattern rather than inventing a conversation export format. Never
  transferable: Reading progress. No such object exists: Attachments
  (confirmed — no `attachments` table anywhere).
- **Package semantics**: recommends **immutable snapshots**, not live
  references or a hybrid — the only option requiring zero RLS change of
  any kind, matching the one existing precedent this codebase already
  has (the client-side-only "Export Knowledge Package" markdown
  download, which has no import counterpart today).
- **Import model**: importing account always becomes the new owner
  (`user_id`/`owner_id`), workspace assignment is always an explicit
  importer choice (never inferred from the source), source `id`s are
  never reused (fresh UUIDs via the ordinary insert path), and
  duplicate detection is scoped narrowly — no dedup at all for
  freeform Notes/Documents/Assets, but real reuse of the existing
  Phase 9A `resolveCanonicalNode` resolver for Knowledge Nodes, which
  gets Phase 6 tested dedup logic for the one object type that actually
  needs it with zero new logic — flagging that its known
  accepted-but-unenforced race-condition trade-off becomes a real risk
  under concurrent multi-account import for the first time, not silently
  carried forward unchanged.
- **Personal intelligence boundary**: confirms `ai_memory`,
  `provider_overrides`, `ai_memory.confidence`, `ai_requests`, and
  per-account preferences (`reading_progress`) must never leave an
  account, per the existing §3.3 rule from `ux-14.5.3-intelligence-
  object-access-model.md`, applied with at least equal force across the
  harder account-boundary Exchange crosses. **One correction to the
  brief's own framing, caught by checking the live migration rather
  than assuming**: the brief listed "objectives" alongside personal
  items, but `workspace_objectives` was explicitly reclassified into
  the *shareable* bucket by `0031_shared_knowledge_objects.sql` — this
  discovery recommends treating it like `notes`/`documents` for
  Exchange purposes, not silently overriding a shipped decision to
  match an outdated assumption.
- **Lifecycle**: maps the brief's 8 stages onto existing machinery —
  package construction reuses the already-built `listCollectionItems`/
  evidence-resolution code; integration reuses the existing embedding/
  `resolveCanonicalNode`/search-indexing/concept-linking pipeline
  (the `generateBriefing` precedent); "Knowledge Graph Update" is not a
  separate mechanism to build, it's the direct outcome of Integration
  running those existing calls.
- **AI implications**: the one "decide now" item — build the package
  format as structured/typed data with markdown as one possible
  rendering, not the reverse, so a future Voice Intelligence surface
  isn't stuck parsing prose back out of an export. Everything else
  (Agent Framework, Expert Plugins, shared research) inherits existing
  invariants (no AI identity/permission beyond the invoking human,
  per §6.4 of the original discovery) with no new architecture required.
- **Roadmap**: smallest valuable slice is same-instance, single-
  collection, Notes-only export→import (6A) — zero new tables, zero RLS
  change. Phased after that: Documents/Assets with real cross-account
  storage copy (6B, flagged as the first genuinely new, security-
  review-worthy infrastructure this feature needs), Knowledge Nodes/
  Links with concurrent-dedup risk resolution (6C), then cross-instance
  file-based export/import with untrusted-input validation (6D, the
  second security-review-worthy component). Do Not Build Yet: live/
  hybrid semantics, a generic attachments abstraction, fuzzy content
  dedup, a package marketplace or public/anonymous sharing, real-time
  package sync, and organization-level exchange policies — all
  restating or directly extending constraints already established in
  prior UX-14.5 discovery/blueprint sections (§9).

Awaiting approval; no implementation performed.

## 18. UX-14.5.8 Phase 1 implementation record — Invitation Foundation

### 18.1 Migration created

`supabase/migrations/0032_workspace_invitations.sql`, applied to the
live project. Three parts:

- **New `workspace_invitations` table** — separate from
  `workspace_members` because `workspace_members.user_id` is `not null`,
  so there is no slot in that table for an identity that doesn't exist
  yet. Columns exactly as specified in the approved design: `id`,
  `workspace_id`, `email` (always stored lower-cased), `role`
  (`workspace_member_role`, checked `<> 'owner'`), `status`
  (new `workspace_invitation_status` enum: `pending`/`accepted`/
  `cancelled`), `invited_by`, `created_at`/`updated_at`, `expires_at`
  (defaults to 30 days out — not yet surfaced or enforced by any UI
  this phase, only honored by the reconciliation query so a very old
  invitation can't silently grant access), `accepted_at`, `accepted_by`.
  A partial unique index (`workspace_id, email`, `where status =
  'pending'`) means re-inviting someone with an existing pending
  invitation updates it rather than duplicating; accepted/cancelled
  rows never block a fresh invitation later. RLS: one SELECT policy,
  any workspace member (viewer-or-above) — unlike `list_workspace_members`,
  no security-definer RPC is needed to view this table, since each row
  already carries the invitee's email directly with no `profiles`
  cross-user join to bridge. Zero INSERT/UPDATE/DELETE client policy —
  the only writers are the two security-definer functions below, which
  bypass RLS entirely; cancel/resend/role-change (UX-14.5.8.2, not this
  phase) will add their own narrow policy when built.
- **`invite_to_workspace` redefined** (dropped and recreated — its
  return type changes, which `create or replace` can't do in place).
  Gains a fallback branch: no matching `profiles` row → insert a
  `workspace_invitations` row instead of raising. Both branches now
  return success (a small jsonb outcome descriptor,
  `{outcome: 'member_invited'|'invitation_created', ...}`) —
  indistinguishable to the caller in every way that matters, which
  closes the discovery's live-confirmed account-enumeration finding as
  a direct side effect of the redesign, not a separate patch. Email
  comparison against `profiles` is now `lower(email) = lower(trim(...))`,
  closing the discovery's second live-reproduced bug (case-sensitive
  matching).
- **`handle_new_user` extended** — one additive step after its existing
  profile-creation insert: loop over every `pending`, unexpired
  `workspace_invitations` row matching the new user's lower-cased
  email, promote each into a real `active` `workspace_members` row,
  mark the invitation `accepted`. Reuses the one mechanism this
  codebase already trusts for "react to a new `auth.users` row" —
  no cron, no polling. An invitee invited to three workspaces before
  signing up gets all three the moment signup completes.

### 20.1 New Edge Function: `send-workspace-invitation`

`supabase/functions/send-workspace-invitation/index.ts`, deployed to
the live project (`verify_jwt: true`, matching `ai-chat`/
`provider-availability`). No migration — zero schema/RLS changes, per
scope.

**Trust boundary, explicitly** (also documented in the function's own
header comment):

1. **Authenticate as the caller.** The browser's `supabase.functions.invoke()`
   automatically forwards the caller's own session JWT as the
   `Authorization` header — never a service-role key, which only exists
   server-side (`Deno.env`, a Supabase Function secret). A plain
   anon-key client calls `auth.getUser()` against that JWT; missing or
   invalid → 401. Never callable anonymously, both because of this
   explicit check and because `verify_jwt: true` rejects a missing/
   malformed JWT before the function body even runs (defense in depth,
   not the only gate).
2. **Authorize as the caller.** Re-checks ownership by calling the
   *existing* `has_workspace_role(workspace_id, 'owner')` RPC
   (0028_workspace_members.sql) through that same caller-scoped client
   — reusing the one authorization primitive this codebase already
   trusts rather than reimplementing an owner check in a second place.
   Not an owner → 403.
3. **Only then escalate to service role**, and only for the two reads
   RLS would otherwise block: the invitation/membership row itself (no
   client-read grant for this exact lookup-by-id shape) and, for the
   known-account path, the invitee's email from `profiles` (self-only
   RLS) — the identical reason `list_workspace_members` (0030) needed a
   security-definer SQL function instead of a plain client select. The
   service-role key never appears in any response body or client-visible
   code path.
4. **Re-verify eligibility against the freshly-read row**, not the
   request body: `workspace_invitations` must be `status = 'pending'
   and expires_at > now()`; `workspace_members` must be `status =
   'pending'`. A caller can't email an already-accepted, cancelled, or
   expired invitation by resubmitting stale client state — 409 either
   way, with the specific reason (`not_found` / `not_pending` /
   `expired`) in the error body but not otherwise exposed to the UI
   (no email-enumeration value in a 409 the owner already has legitimate
   access to trigger).

**Two invitation shapes, one function.** The request body is `{
workspaceId, kind: 'invitation' | 'membership', id }` — never workspace
name, role, or email, so a compromised or stale client can't inject
content into the email; the function re-resolves everything from the
database. `kind: 'invitation'` is UX-14.5.8 Phase 1's unknown-email
`workspace_invitations` path (has `expires_at`, accept link goes to
`/signup?email=<prefilled>`). `kind: 'membership'` is Phase 3's
known-account `workspace_members` pending-row path (no expiry concept
exists for that table; accept link goes to `/settings/workspaces`,
where the existing Accept/Decline UI already lives). Both are sent for
symmetrically — an owner inviting a known colleague gets an email too,
not just the previously-silent in-app "Pending invitations" list.

**Email provider: Resend, via plain `fetch`.** No SDK dependency —
matches this codebase's existing `ai-chat` pattern of calling providers
directly over HTTP rather than through a client library. Secrets:
`RESEND_API_KEY` (required — missing → 500, matching `ai-chat`'s
`<PROVIDER>_API_KEY is not configured` shape for a missing key),
`RESEND_FROM_EMAIL` (optional, falls back to Resend's sandbox
`onboarding@resend.dev`), `SITE_URL` (optional — falls back to the
request's `Origin` header, since Deno has no `window.location`).
**`RESEND_API_KEY` was not set by this implementation** — no MCP tool
in this environment can set Supabase Function secrets, and provisioning
a real Resend account is outside what an agent can do unattended. The
user must run `supabase secrets set RESEND_API_KEY=...` (and optionally
`RESEND_FROM_EMAIL`/`SITE_URL`) post-deployment for actual delivery to
work; every other step (auth, authorization, row eligibility, template
building) is fully live and functions correctly without it, failing
gracefully with a 500 at the last step.

### 20.5 Security audit

- **Owners only**: enforced twice — the platform-level `verify_jwt`

- **No bypass around existing invitation validation**: the function
  never writes to `workspace_invitations`/`workspace_members` — it only

  Invitation creation/cancellation/role rules are entirely unchanged,

### 21.1 The package framework

Four small, isolated modules under `src/modules/knowledge-exchange/
packages/`, each a generic contract a future package type (Documents,
Collections — §8.2's later phases) plugs into without touching Notes'
own code:

- **`PackageVersion.ts`** — `CURRENT_PACKAGE_VERSION`/
  `SUPPORTED_PACKAGE_VERSIONS` (both `1` today, kept as separate
  constants for how a version bump actually sequences: widen "supported"
  before narrowing "current"), `PACKAGE_SOURCE_VERSION` (a stable
  exporter-format identifier, independent of `package.json`'s
  unmaintained `"0.0.0"`), and `isFuturePackageVersion`/
  `isSupportedPackageVersion` helpers.
- **`PackageValidator.ts`** — `PackageValidationResult<T>` (a tagged
  union, never a thrown exception — an invalid package is an expected
  outcome, not exceptional) and the `PackageValidator<T>` interface.
- **`PackageExporter.ts`** — `PackageExporter<TSource, TPackage>`; an
  exporter never fetches its own data (kept pure and trivially testable).
- **`PackageImporter.ts`** — `PackageImporter<TPackage, TResult>` plus
  `PackageImportContext` (`userId`, `workspaceId`); async, since
  importing means writing rows and re-running integration steps.

`src/modules/knowledge-exchange/notes/` is the one concrete
implementation today: `notePackageTypes.ts` (the versioned `NotePackage`
shape — `{version, exportedAt, sourceVersion, note: {title, content,
tags, createdAt, updatedAt, generationMetadata}}`, an explicit
**allow-list** per the discovery doc's §5.3, not a deny-list — `id`,
`user_id`, `workspace_id`, embeddings, `ai_memory`, and provider
configuration simply have no field to populate, so there's nothing to
accidentally forward), `exportNotePackage.ts`, `validateNotePackage.ts`,
`importNotePackage.ts`.

`generationMetadata` satisfies both the "generation_metadata" and
"artifact metadata" requirements as one field, deliberately — this
schema has no separate "artifact metadata" column; `artifactKind`/
`artifactData`/`creationMethod` already live inside
`generation_metadata` (`src/modules/ai/artifacts/artifactMetadata.ts`),
so a second field would just duplicate the same object.

### 21.3 Import

`importNotePackage(pkg, {userId, workspaceId})`:

1. Always `createNote` (insert) — **never** an update/upsert against an
   existing row, so "never overwrite an existing note" holds by
   construction, not by a defensive check. The package's own `id`
   (there isn't one — notes have no `id` field in the package at all)
   has nothing to collide with; a fresh id comes from the same
   `insert()` path every other create operation in this app already
   uses.
2. The importer becomes the owner (`userId` from context) — exactly the
   same as every other "create a note" path; there is no precedent
   anywhere in this codebase for inserting a row under someone else's
   `user_id`, and this doesn't start one.
3. `workspaceId` is always an **explicit** choice made in the Import
   dialog at import time (§3.2 of the discovery doc) — never inferred
   from the package, which carries no workspace identity at all. `null`
   means "no workspace," the same meaning it already has everywhere.
4. Original timestamps travel as inert `generation_metadata.
   importedFrom` data only (`packageVersion`, `sourceVersion`,
   `exportedAt`, `originalCreatedAt`, `originalUpdatedAt`, `importedAt`)
   — the new row's own `created_at`/`updated_at` are whatever the
   database sets on insert, correctly reflecting when *this account*
   received it (§3.3/§3.4 of the discovery doc).
5. Tags are re-resolved by **name** for the importing account (the same
   `ensureTag`-backed `addTagToNote` ordinary tag creation already uses)
   — never a reference to the exporter's `tags.id`.
6. Full integration, matching every other note-creation path in this
   app (`useNotes.create`, `SaveConversationDialog`,
   `saveMessageToNote`): `indexNote` (search) and
   `linkKnownConceptsToSource` (concept-mention linking), both
   fire-and-forget, both swallowing their own errors, exactly as those
   functions already do everywhere else they're called. An imported
   note is, from the moment this function returns, indistinguishable at
   the database level from any note the importer created by hand (§4.3
   of the discovery doc) — it gets the same `SharingBadge`/
   `OwnershipLine`/role-gated editing as anything else the moment it
   lands in a workspace, with zero Knowledge-Exchange-specific
   collaboration code.

### 24.1 Audit findings — asset schema and storage

`assets` (`0022_assets.sql`): `id, workspace_id (nullable), owner_id,
title, original_path, optimized_path, thumbnail_path, mime_type, width,
height, size_bytes, created_at`. **No JSONB metadata column of any
kind** — the discovery doc's §5 gap, confirmed again here (see §24.6).
Storage: private `assets` bucket, per-user-folder RLS
(`(storage.foldername(name))[1] = auth.uid()::text`), no direct public
URL — display/download both go through a short-lived signed URL
(`getAssetSignedUrl`). `uploadAsset` (`assets/api/assets.ts`, unchanged)
is the single existing pipeline: `resolveFileSize` → `validateImageFile`
(`SUPPORTED_IMAGE_MIME_TYPES` = jpeg/png/webp/gif, `MAX_ASSET_UPLOAD_BYTES`
= 25MB) → `generateDerivatives` (`createImageBitmap`-based decode +
re-encode, a real content-integrity check) → uploads all three paths
under a fresh `${userId}/${crypto.randomUUID()}/...` → inserts the row

the discovery, unchanged) — no RLS work needed.

### 24.2 Package design decision — Option A (embed bytes), not Option B

Chosen over metadata-only + manual re-upload, on the same four criteria
this task named:

- **Portability**: a package stays one self-contained file, matching
  Notes'/Knowledge Nodes' own invariant — "import" never becomes
  "create a row, then separately go find the original file again."
- **Security**: the base64 payload never executes. Import decodes it
  into a `File` and routes it through the *exact same* `uploadAsset`
  pipeline a manual upload already uses — same MIME/size validation,
  same `createImageBitmap` decode-integrity check, same derivative
  regeneration. Embedding bytes adds no new attack surface beyond what
  a manual upload already has (§24.5).
- **File size**: bounded by the same `MAX_ASSET_UPLOAD_BYTES` (25MB)
  cap the native upload path already enforces, checked pre-decode via
  a formula-based byte-length estimate (`estimateBase64DecodedByteLength`)
  so an oversized package is rejected before a potentially ~33MB string
  is ever fully decoded.
- **Existing infrastructure**: zero new services — no storage-to-storage
  copy, no edge function, fully client-side.
- **Future Documents support — explicitly flagged, not solved here**:
  Documents run up to 200MB (discovery §2), well past what base64-in-JSON
  (~1.33× inflation) scales to comfortably in a browser. This is a
  finding for the Documents phase, not resolved in this one — see §24.8.

### 24.5 Import behavior — reuses `uploadAsset` unmodified

Always `uploadAsset` (the same full pipeline a manual upload already
uses) — never a direct storage/table write — so import creates a
brand-new asset by construction, mirroring Notes' always-create
precedent rather than Knowledge Nodes' `resolveCanonicalNode` dedup
(there's no meaningful "same asset" identity to resolve against here).
`importAssetPackage` decodes `fileDataBase64`, constructs a `File` with
a generic placeholder name (`imported-image.<ext>` — traced that
`uploadAsset`'s real storage path never derives from `File.name`, and
`title` is always passed explicitly, so the placeholder is functionally
inert and needs no sanitization) and the declared `mimeType`, then calls
`uploadAsset({file, userId: context.userId, workspaceId: context.workspaceId,
title: pkg.asset.title})` verbatim.

**Security review** (per this task's explicit checklist):

- **No arbitrary storage path injection** — `uploadAsset` always
  generates its own fresh path from `crypto.randomUUID()` keyed to the
  *importer's own* `userId`; the package contains no storage path field
  at all.
- **No unsigned/signed URL reuse** — the package format has no storage
  path or URL, only raw base64 bytes; nothing to reuse.
- **No ownership escalation** — `owner_id` is always `context.userId`
  from `uploadAsset`'s own contract, never derived from the package.
- **No execution of uploaded content** — decoding is client-side
  canvas/Blob work (`createImageBitmap` inside `generateDerivatives`),
  never script execution; SVG (the one raster-adjacent format with
  embeddable-script risk) is already excluded from
  `SUPPORTED_IMAGE_MIME_TYPES` by pre-existing, unmodified validation.
- **No bypass of existing asset processing** — this calls the literal,
  unmodified `uploadAsset`; there is no fast path skipping
  `validateImageFile`/`generateDerivatives`.
- **Trust-boundary finding, directly tested** (`assetPackageRoundTrip.test.ts`):
  the package's own declared `mimeType`/`width`/`height`/`sizeBytes` are
  informational only, used solely for the import dialog's preview. The
  imported row's *real* values are always independently recomputed from
  the actual decoded bytes by `generateDerivatives` inside `uploadAsset`
  — a package hand-tampered to lie about its own metadata cannot poison
  the imported row, because the real content still flows through
  unmodified, unbypassable validation.

## 25. UX-14.5.10.3 discovery record — Document Exchange

**Discovery only — no code, no migrations, no RLS changes, no framework
changes.** Full detail:
`docs/ux-14.5.10.3-document-exchange-discovery.md`. Summary here per
this phase's own documentation requirement.

### 25.1 Headline findings

- **The binary-storage problem is already solved** — Documents' bucket
  has the identical private/per-user-folder RLS shape Assets' bucket
  does, no cross-account read path, and the exporting account already
  has full read access to its own file (`downloadDocumentFile`). No new
  RLS work, same conclusion Assets already reached.
- **A previously-undocumented RLS gap, found this pass**:
  `extraction_metadata`, `processing_jobs`, `chapter_summaries`,
  `highlights`, `flashcards`, and `reading_progress` were never touched
  by `0031_shared_knowledge_objects.sql` and have no `workspace_id`
  column — a workspace member who can already see a shared document and
  its chunks cannot see that document's extraction metadata, chapter
  summaries, highlights, or flashcards at all. Confirmed by reading
  `0031`'s own file (lists exactly 14 objects; none of these six are
  among them). Does not block Document Exchange (import always writes
  fresh, owner-scoped rows) — a real, separate, independently-
  schedulable product gap, documented rather than fixed here.
- **The single biggest simplification**: `processDocument(documentId,
  userId)` already regenerates chunks, embeddings, and extraction
  metadata from nothing but the original file bytes — the exact same
  fire-and-forget call a native upload already makes
  (`useDocumentMutations.ts`). This means the AI-derived side of a
  document never needs to travel in a package at all; the package only
  ever needs the original file bytes plus genuinely user-authored
  content.
- **Package format decision — Option B (ZIP via the already-present
  `jszip` dependency)**, not a repeat of Assets' base64-in-JSON: at
  Documents' 200MB cap, base64 inflation risks ~700MB–1GB of peak
  browser memory for one file (vs. under 100MB for Assets' 25MB cap) —
  a real crash/OOM risk, not a theoretical one. `jszip` is already a
  direct dependency (used today to *parse* EPUB, itself a ZIP
  container), so writing one for export needs no new dependency, gets
  free per-entry CRC32 integrity checking, and avoids base64's
  ~1.33× size inflation entirely. Rejected a custom Option C binary
  format: no existing library backing it in this codebase, and a
  bespoke format is a portability regression (nothing but this app can
  open it, unlike `.zip`).

### 25.2 Object-by-object transfer/regenerate decisions

`documents` (transfer — the object itself), `document_tags` (transfer —
tag names, re-resolved by name like Notes), `highlights` (transfer —
the one genuinely user-authored side-artifact, no regeneration path
exists for a person's chosen passage; chapter-index-drift risk assessed
as bounded/cosmetic, not destructive, and explicitly accepted).
`document_chunks`, `embeddings`, `extraction_metadata`,
`chapter_summaries`, `flashcards` (all regenerate — mechanically
derived from the original bytes/chunks, cheap to reproduce, avoids ever
carrying a stale or chapter-index-drifted copy). `processing_jobs`,
`reading_progress` (neither — pure operational/positional state, not
content, never applicable to a package at all).

### 25.3 Processing strategy — immediately enter the pipeline

Recommended over "restore directly," and not just because nothing
needs restoring (§25.2): reusing `uploadDocument`+`processDocument`
unmodified costs zero new pipeline code, inherits every existing
failure mode/rate-limit handling unchanged, and gets progress reporting
for free via the existing `useProcessingJob`/`ProcessingStatusBadge`
polling UI, pointed at the freshly created document's id — no new
progress-reporting code needed.

### 25.4 Security review highlights

Reuses `uploadDocument` unmodified for the same structural guarantees
Assets' security review established (fresh IDs, fresh storage paths,
importer-owned, extension allow-list enforced, no path for a package to
assert ownership). Two considerations genuinely new to this phase: **zip
bombs** (mitigated by checking each ZIP entry's central-directory-
declared uncompressed size against `MAX_UPLOAD_BYTES` *before* calling
`.async()` to decompress it — a real, must-implement check the next
phase needs to build in from the start, since ZIP introduces this
attack surface where base64-in-JSON had none) and **duplicate
documents** (no canonical-identity resolver exists for documents, so
import always creates a fresh row, exactly like Notes'/Assets'
always-create precedent — not a new risk, matches uploading the same
file twice manually today).

### 25.5 Roadmap — split into three phases (not one, unlike prior types)

Document Exchange is larger than any prior phase (binary transfer *and*
a multi-stage regeneration pipeline *and* a new container format), so
