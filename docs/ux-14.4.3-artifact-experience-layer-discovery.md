# UX-14.4.3 — Artifact Intelligence Experience Layer: Discovery

**Status: design only.** No code, migrations, or UI changes were made to produce this document. Investigates the five areas requested before any implementation decision, grounded in the actual current codebase (post-UX-14.4.2), not assumption.

## Current flow (confirmed)

```
User request
  -> generateSpreadsheetCommand.ts (deterministic match)
  -> generateSpreadsheetArtifactAction.run
       -> generate-spreadsheet-artifact capability (runCapability/runWithFallback)
       -> parseSpreadsheetSpecificationResponse -> validateSpreadsheetSpecification
       -> compileSpreadsheetSpecification -> validateFormulaSafety (every formula)
       -> renderSpreadsheetArtifactMarkdown
  -> WorkspaceActionOutcome { responseText, references? }
  -> MessageBubble -> MarkdownRenderer -> TableBlock (generic markdown table rendering)
  -> [user says "save this" / clicks Save] -> saveMessageToNote
       -> detectArtifactKind(content) -> buildArtifactGenerationMetadata
       -> parseMarkdownTableToArtifact(content) -> generation_metadata.artifactData
       -> createNote -> linkNoteToConversation/linkNoteToMessage -> indexNote
       -> linkKnownConceptsToSource (scans for known-concept mentions, links into the knowledge graph)
```

This matches the user's stated flow exactly. Everything below investigates what's on either side of it.

## 1. Artifact response experience

**How a generated artifact renders in chat today:** `MessageBubble.tsx` renders every assistant message — a generated spreadsheet's response included — through the same generic `MarkdownRenderer` every other chat reply uses. `MarkdownRenderer` already has a real `TableBlock` (hand-written parser, no dependency), so the markdown table renders as an actual table, not a code block. But **nothing distinguishes it as an artifact.** A coincidental markdown table an assistant writes in ordinary prose renders identically to a deliberately generated spreadsheet. There is no kind badge, no confidence indicator, no "this hasn't been saved yet" visual cue beyond the trailing sentence `generateSpreadsheetArtifactAction.ts` appends to `responseText` — plain text, not a UI affordance.

**`WorkspaceActionOutcome` cannot carry more than text today.** `{ responseText: string, references?: Reference[] }` (`workspace-actions/types.ts`) is the entire contract. There is no field for "this response is/contains an artifact" — a future consumer (ChatPage, ReaderChatPanel) has no typed signal to render anything other than markdown.

**A dedicated preview object already exists — but only post-save.** `SpreadsheetArtifactPanel.tsx` (Phase 2), lazy-loaded from `NoteDetailPage.tsx`, is a real dedicated preview: a formatted table + XLSX/CSV download. It only ever renders for a saved `Note` with `generation_metadata.artifactData` — there is no equivalent for the unsaved chat-preview moment.

**Reusable primitives already exist for a chat-level preview.** `KnowledgeCard` (`shared/components/knowledge/KnowledgeCard.tsx`) — title (optionally linked), a `StatusBadge` type pill, an optional `ConfidenceBadge`, and a `children` slot — is already the platform's general-purpose "here is an AI-produced thing" card, reused across the Dashboard, Document Detail, and Knowledge Explorer. `ArtifactKindBadge` (Phase 1) already wraps `StatusBadge` for exactly the eight `ArtifactKind` values. Neither needs to change to serve this purpose.

**Smallest architecture improvement identified:** extend `WorkspaceActionOutcome` with one new optional field — e.g. `artifactPreview?: { kind: ArtifactKind; title: string; markdown: string }` — populated only by actions that generate a real artifact (today, just `generateSpreadsheetArtifactAction`). ChatPage/ReaderChatPanel render it via the existing `KnowledgeCard` + `ArtifactKindBadge` (a distinguishable card in the chat stream, not a plain bubble) instead of relying on the responseText's plain-prose "not saved yet" line. This is a type change to one file plus new (small) rendering in two chat surfaces — **not** a new component system, **not** a schema change, **not** a change to how anything is saved. It is the one piece of "the last mile" this milestone's own purpose statement ("turn chat outputs into recognizable NOVA intelligence objects") is actually missing today.

## 2. Artifact metadata model

`generation_metadata` is, and always has been (Phase 1 onward), an unstructured `Record<string, unknown> | null` JSONB column — every key added since (`artifactKind`, `artifactData`, `savedFrom`, `conversationId`, `messageId`, `messageCreatedAt`) has been additive with zero migrations. This matters directly: **every field this section asks about can be added the same way, with no schema change**, except where noted.

- **Artifact title.** Already a first-class column: `notes.title`. No metadata field needed or wanted — don't duplicate it into JSON.
- **Creation method.** Already exists in embryonic, inconsistent form: `saveMessageToNote.ts` writes `generationMetadata.savedFrom: 'chat-message'`; `generateBriefing.ts` only sets `artifactKind: 'briefing'` with no `savedFrom` equivalent. Recommendation: generalize the existing `savedFrom` key (rename/repurpose as `creationMethod: 'chat-save' | 'generate-briefing' | 'generate-spreadsheet-artifact' | 'manual' | 'merge' | ...`) and set it consistently from every note-creation call site — not a new field, a consistency fix to one already-live field.
- **Source context.** Already modeled — not as metadata, as graph edges: `linkNoteToConversation`/`linkNoteToMessage` (`knowledge_links`) already record exactly this for every note. Nothing to add; this is a "don't duplicate it" finding, not a gap.
- **Intelligence confidence.** No existing field for a Note's own confidence (distinct from `knowledge_links.confidence`, which scores a *relationship*, and `ai_memory.confidence`, which scores a *memory*). `ConfidenceBadge` already renders any `number | null` — reuse is trivial. The real work is deciding what the number *means* for a generated artifact (see Risks).
- **Related memories.** No linkage exists between `ai_memory` and `notes` today at all. `knowledge_links.target_type` is a plain string column, not an enum — recording `target_type: 'ai_memory'` needs zero migration, exactly the same polymorphic-edge pattern `linkNoteToConversation`/`linkNoteToAsset`/Collection membership already use.
- **Related knowledge.** **Already live, not a gap.** `linkKnownConceptsToSource` already runs on every saved note (wired into `saveMessageToNote.ts`), scanning content for known-concept mentions and recording `knowledge_node_sources` — a generated-and-saved spreadsheet artifact already participates in this exactly like any other note, today, with zero additional work.
- **Lifecycle state.** No existing field. See §3 — recommend `lifecycleState` as another additive `generation_metadata` key, but only for the states that are actually meaningful without further architecture (see below).

**Metadata-sprawl risk, flagged not solved:** every new ad hoc JSONB key adds implicit schema no migration documents. Recommend a single typed `ArtifactMetadata` TypeScript interface (application-level only, not a DB constraint) as the one place these keys are declared — mirroring how `ArtifactKind`/`ARTIFACT_KIND_DEFINITIONS` already govern the kind registry — rather than every call site inventing field names independently, as `savedFrom` already shows can drift.

## 3. Artifact lifecycle design

```
Generated -> Reviewed -> Saved -> Improved -> Shared -> Archived
```

**Critical finding: there is no persisted row during "Generated" or "Reviewed."** Today, a generated artifact exists only as chat message text until the user explicitly saves it. There is nothing to attach a `lifecycleState` field *to* before that point — "Generated"/"Reviewed" are, right now, chat-history states, not database states. Formalizing them as queryable fields would require persisting a draft-artifact row before save, which is itself a new schema/architecture decision (a "what should NOT be built yet" item below), not a metadata addition.

| State | Buildable with existing structures? |
|---|---|
| **Generated** | Yes — already exists (UX-14.4.2's unsaved preview). Not a persisted state; derivable from "is this a Workspace Action outcome shown in chat." |
| **Reviewed** | Not meaningfully, pre-save — no row exists yet to mark. Post-save, trivial (`generation_metadata.lifecycleState = 'reviewed'` the moment any interaction happens after saving). |
| **Saved** | Yes — already exists (`Note` row created). |
| **Improved** | No capability exists yet, but the *shape* is proven: a new Workspace Action + capability following UX-14.4.2's exact pattern, taking an existing Note's content as input instead of a bare request. Same risk profile as everything already shipped. |
| **Shared** | **Not buildable at all right now.** Blocked entirely on the authorization model — see §5. Recording the label without real enforcement would be actively misleading. |
| **Archived** | Two options, deliberately not chosen here: (a) `generation_metadata.lifecycleState = 'archived'`, zero schema change, but doesn't filter from `listNotes()` without added query logic and has no index; (b) a real `notes.archived_at` column, precedented exactly by `workspaces.archived_at` already in the schema — a small, low-risk migration, but a migration nonetheless. Deferred to whoever implements this, once there's an actual "hide old artifacts" user need to size it against. |

## 4. Pro user WOW opportunities

**Immediate, low-risk** (reuse the exact `Specification -> validate -> compile -> render` shape UX-14.4.2 already proved, or reuse existing grounding data with no new architecture):
- **"Improve this artifact"** — new Workspace Action + capability, current Note's content/spec as input, output validated through the identical pipeline. The riskiest-sounding item on this list is actually the cheapest to build, because UX-14.4.2 already built its entire shape.
- **"Explain assumptions"** — a read-only, grounded-in-the-artifact Q&A capability; architecturally indistinguishable from the existing `summarize`/`generate-briefing` capability pattern.
- **"Use my knowledge to refine this"** — `retrieveMemoryContext`/`retrieveGraphContext` are already computed on every chat turn (`AIService.sendMessage`) and already power `buildBriefingVariables`-style grounding for Generate Briefing. Feeding the same, already-available context into an "Improve" prompt is wiring, not new capability.

**Needs real design before building** (not immediate, not blocked on collaboration either):
- **"Compare with previous artifact"** — depends entirely on a "previous version" existing, and §3 already established zero versioning infrastructure exists anywhere in the schema. This needs an explicit data-model decision (a history table? a `generation_metadata.history` array snapshotted before each overwrite?) before any UI is meaningful — flagged, not solved here.

**Future collaboration features** (explicitly out of scope until UX-14.5's authorization work exists):
- `lifecycleState: 'shared'`, multi-user comments/annotations on an artifact, real-time co-editing — all require *someone else* to have access to a `user_id`-owned row, which nothing in the schema permits today.

## 5. Sharing preparation

Not collaboration — the boundaries UX-14.5 will need to cross, confirmed directly against the schema:

- **Ownership.** Every one of the 45 RLS policies checked follows the same `auth.uid() = user_id` single-owner pattern; zero exceptions found. There is no `workspace_members` table, no `shared_with` column, no role concept anywhere in `supabase/migrations/` or `src/`. This reconfirms, independently, the Phase 1 discovery doc's own finding: sharing is "the first multi-user capability this application would ever have," not an incremental Collections feature.
- **Permissions.** None exist to build on. A permissions model has to be designed from nothing, not extended from something partial.
- **Artifact identity.** Already solid, needs no change: an artifact's identity is `notes.id` — stable, addressable (`/notes/:id`), already carries provenance (`knowledge_links` to its conversation/message/document origins). A shared artifact would still be "a note, visible to more than one `user_id`" — this layer doesn't need to change for sharing to eventually work.
- **Versioning.** Does not exist (§3/§4). Real collaboration typically wants some version history before it's trustworthy, though a v1 (read-only, single current version, no diffing) could plausibly ship without it — a scoping call for UX-14.5, not this discovery.

**Recommendation:** UX-14.5's actual prerequisite is the authorization model, not more artifact metadata. Nothing in §2/§3's additive `generation_metadata` findings blocks or unblocks sharing either way — they're orthogonal. Do not let "artifact metadata" work masquerade as "sharing preparation" — it isn't.

## Recommended implementation sequence (if UX-14.4.3 is greenlit)

Three items, all additive, all zero-schema-change, all directly closing a gap this discovery actually found — not a redesign:

1. Extend `WorkspaceActionOutcome` with an optional structured `artifactPreview`; render it via the existing `KnowledgeCard`/`ArtifactKindBadge`/`ConfidenceBadge` in ChatPage and ReaderChatPanel (§1).
2. Generalize the existing ad hoc `savedFrom` metadata field into a consistently-set `creationMethod` across every note-creation call site (§2).
3. Wire "related memories" via `knowledge_links.target_type = 'ai_memory'` (§2) — same polymorphic-edge mechanism already used for everything else.

**Files likely affected:** `workspace-actions/types.ts`, `generateSpreadsheetArtifactAction.ts` (or a shared helper both it and future artifact-generating actions call), `ChatPage.tsx`, `ReaderChatPanel.tsx`, `saveMessageToNote.ts`, `SaveConversationDialog.tsx`, `generateBriefing.ts` (creationMethod consistency), a new small `linkArtifactToMemory`-style function alongside the existing `knowledge_links` helpers. No new files under `supabase/migrations/`.

## What should NOT be built yet

- Any new database table or migration for draft-artifact persistence or version history — no current demand signal; premature.
- Any `workspace_members`/permissions/RBAC scaffolding — UX-14.5's actual scope, too large and consequential to fold into an "experience layer" milestone.
- `lifecycleState: 'shared'` as a real option — a label with no enforcement behind it is worse than no label.
- "Compare with previous artifact" UI — blocked on a versioning decision not yet made.
- A new generic multi-kind "ArtifactPreview" component hierarchy — reuse `KnowledgeCard` as-is; don't build speculative infrastructure for chart/report/template kinds that have no generation capability yet.
- "Improve this artifact" itself — proven cheap to build (§4), but is a new AI capability, i.e. feature expansion, i.e. explicitly what this milestone was scoped to come *before*, not include.

## Risks

- **Scope creep.** "Experience Layer" is an evocative name that invites polish beyond what's proven needed. Mitigated by keeping the recommended sequence to the three items above, each traceable to a concrete gap this discovery found, not a vibe.
- **Metadata sprawl.** Flagged in §2 — recommend a typed `ArtifactMetadata` interface before more ad hoc keys accumulate the way `savedFrom` already has.
- **False confidence.** A `confidence` field on a generated artifact needs a real scoring basis (e.g., whether validation passed cleanly, `template` vs `data_model`, whether any formula was rejected) — not a placeholder number. Left as an implementation-time design detail, not decided here.
